13.11 — 10. Global Query Filters

Tóm tắt

Global query filter tự thêm điều kiện WHERE vào mọi truy vấn trên một entity — công cụ mạnh nhất cho soft delete và đa khách hàng, vì không ai quên được. Nhưng nó có ba cái bẫy nghiêm trọng. Một: mô hình EF Core được cache theo kiểu DbContext, nên filter tham chiếu tới giá trị thay đổi theo request (tenant id) chỉ được đánh giá đúng khi filter đọc từ một field của context — hiểu sai điểm này dẫn tới việc mọi request dùng tenant id của request đầu tiên. Hai: FindAsync bỏ qua filter hoàn toàn. Ba: IgnoreQueryFilters() bỏ qua tất cả filter, nên tắt soft delete cũng tắt luôn cách ly tenant — một lỗ hổng dữ liệu nghiêm trọng.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Cấu hình filter cho soft delete và đa khách hàng.
  • Hiểu mô hình được cache thế nào và tránh dùng sai tenant id.
  • Dùng IgnoreQueryFilters an toàn.
  • Xử lý filter với navigation property và khoá ngoại bắt buộc.
  • Đảm bảo hiệu năng với index phù hợp.

Nội dung bài học​

13.11.1 — Soft delete​

modelBuilder.Entity<Customer>().HasQueryFilter(c => c.DeletedAt == null);
modelBuilder.Entity<Lead>().HasQueryFilter(l => l.DeletedAt == null);

Mọi truy vấn tự động có thêm điều kiện:

SELECT * FROM Customers WHERE DeletedAt IS NULL;

Không ai quên được — đó là toàn bộ giá trị.

Áp cho mọi entity cài một interface chung:

public interface ISoftDeletable { DateTime? DeletedAt { get; set; } }

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    foreach (var entityType in modelBuilder.Model.GetEntityTypes()
                 .Where(e => typeof(ISoftDeletable).IsAssignableFrom(e.ClrType)))
    {
        var parameter = Expression.Parameter(entityType.ClrType, "e");
        var body = Expression.Equal(
            Expression.Property(parameter, nameof(ISoftDeletable.DeletedAt)),
            Expression.Constant(null, typeof(DateTime?)));

        modelBuilder.Entity(entityType.ClrType)
                    .HasQueryFilter(Expression.Lambda(body, parameter));
    }
}

Thêm entity mới cài ISoftDeletable là nó tự có filter — không cần nhớ khai.

Ghép với interceptor để Remove thành xoá mềm:

public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
    DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
{
    foreach (var entry in eventData.Context!.ChangeTracker.Entries<ISoftDeletable>()
                          .Where(e => e.State == EntityState.Deleted))
    {
        entry.State = EntityState.Modified;              // không xoá thật
        entry.Entity.DeletedAt = DateTime.UtcNow;
    }

    return base.SavingChangesAsync(eventData, result, ct);
}

Và nhớ filtered unique index (bài 12.2):

builder.HasIndex(c => c.Email).IsUnique().HasFilter("[DeletedAt] IS NULL");

13.11.2 — Đa khách hàng và cái bẫy cache mô hình​

public class CrmDbContext(DbContextOptions<CrmDbContext> options, ICurrentTenant tenant)
    : DbContext(options)
{
    private readonly int _tenantId = tenant.Id;          // doc MOT LAN vao field

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        modelBuilder.Entity<Customer>()
            .HasQueryFilter(c => c.DeletedAt == null && c.TenantId == _tenantId);
    }
}

Điểm mấu chốt là _tenantId phải là field của context, không phải lời gọi tới service:

// SAI — mọi request dùng tenant id của request ĐẦU TIÊN
.HasQueryFilter(c => c.TenantId == tenant.Id);

Vì sao: EF Core cache mô hình theo kiểu DbContext và chỉ chạy OnModelCreating một lần cho cả vòng đời ứng dụng. Cây biểu thức của filter được dựng lúc đó.

Khi filter tham chiếu tới field của instance context, EF Core nhận ra đó là giá trị thay đổi được và sinh ra một tham số — giá trị được đọc lại mỗi lần truy vấn chạy, từ instance context hiện tại.

Khi filter gọi tenant.Id trên một service được capture trong closure, biểu thức bắt giữ chính instance service của lần dựng mô hình đầu tiên. Mọi request sau đó dùng tenant id của request đầu tiên — một lỗ hổng rò rỉ dữ liệu nghiêm trọng, và nó chỉ xuất hiện khi có nhiều tenant thật.

Kiểm thử bắt buộc

Phải có integration test: đăng nhập tenant A, truy vấn, rồi đăng nhập tenant B trên cùng tiến trình và xác nhận không thấy dữ liệu của A. Không có test này, lỗi chỉ lộ ra trên production.

Với cấu trúc nhiều mô hình khác nhau theo tenant, dùng IModelCacheKeyFactory:

public sealed class TenantModelCacheKeyFactory : IModelCacheKeyFactory
{
    public object Create(DbContext context, bool designTime)
        => context is CrmDbContext crm
            ? (context.GetType(), crm.TenantId, designTime)
            : context.GetType();
}

builder.Services.AddDbContext<CrmDbContext>(o =>
    o.UseSqlServer(conn).ReplaceService<IModelCacheKeyFactory, TenantModelCacheKeyFactory>());

Cẩn thận: nó dựng một mô hình cho mỗi tenant, nên với hàng nghìn tenant đó là vấn đề bộ nhớ thật.

13.11.3 — IgnoreQueryFilters bỏ qua tất cả​

// Bỏ qua MỌI filter — cả soft delete LẪN tenant
var all = await db.Customers.IgnoreQueryFilters().ToListAsync(ct);

Đây là điểm nguy hiểm nhất của cơ chế này. Một lập trình viên muốn xem cả bản ghi đã xoá của tenant hiện tại sẽ viết dòng trên — và nhận dữ liệu của mọi tenant.

EF Core không cho bỏ qua một filter cụ thể. Phải tự áp lại phần còn lại:

var deleted = await db.Customers
    .IgnoreQueryFilters()
    .Where(c => c.TenantId == _tenantId)      // TỰ áp lại cách ly tenant
    .Where(c => c.DeletedAt != null)
    .ToListAsync(ct);

Cách an toàn hơn là gói lại thành một phương thức có tên, và cấm dùng IgnoreQueryFilters trực tiếp trong code nghiệp vụ:

public static IQueryable<T> IncludingDeleted<T>(this DbSet<T> set, int tenantId)
    where T : class, ISoftDeletable, ITenantOwned
    => set.IgnoreQueryFilters().Where(e => e.TenantId == tenantId);

Thêm một analyzer hoặc một bước grep trong CI để bắt IgnoreQueryFilters ngoài tầng hạ tầng. Đây là loại lỗi mà code review dễ bỏ qua vì dòng code trông vô hại.

Ba nơi khác bỏ qua filter:

Bỏ qua filter?
FindAsyncCó — tìm cả bản ghi đã xoá
FromSqlKhông — filter vẫn được áp
ExecuteUpdate / ExecuteDeleteKhông
Navigation property đã nạpCó thể — nếu entity đã trong tracker

Hàng đầu là nguồn của "tại sao FindAsync lấy được khách hàng đã xoá" (bài 13.6).

13.11.4 — Navigation property và khoá ngoại bắt buộc​

modelBuilder.Entity<Customer>().HasQueryFilter(c => c.DeletedAt == null);
// Contact KHÔNG có filter

var contacts = await db.Contacts.Include(c => c.Customer).ToListAsync(ct);
// Contact của customer ĐÃ XOÁ -> Customer là NULL

Filter được áp khi nạp navigation, nên contact.Customer thành null dù khoá ngoại là bắt buộc. Code giả định contact.Customer không bao giờ null sẽ ném NullReferenceException.

EF Core cảnh báo về điều này khi bạn có khoá ngoại bắt buộc trỏ tới entity có filter — và cảnh báo đó đáng nghe.

Quy tắc: nếu entity cha có filter thì entity con cũng phải có filter tương ứng.

modelBuilder.Entity<Contact>()
    .HasQueryFilter(c => c.DeletedAt == null && c.Customer.DeletedAt == null);

Cẩn thận: filter tham chiếu navigation sinh ra JOIN hoặc subquery trong mọi truy vấn trên Contacts — chi phí thật. Thường tốt hơn là sao chép cột TenantId và DeletedAt xuống bảng con, rồi lọc trực tiếp:

modelBuilder.Entity<Contact>()
    .HasQueryFilter(c => c.DeletedAt == null && c.TenantId == _tenantId);

Đây là phi chuẩn hoá có chủ đích, và nó đáng (bài 12.2).

13.11.5 — Hiệu năng​

Filter xuất hiện trong mọi truy vấn, nên index phải hỗ trợ nó:

// Cột filter đặt TRƯỚC trong composite index
builder.HasIndex(c => new { c.TenantId, c.DeletedAt, c.Status });

Thứ tự này đúng theo nguyên tắc ở bài 12.5: cột dùng với so sánh bằng đặt trước.

Với soft delete, filtered index còn tốt hơn:

CREATE INDEX IX_Customers_Tenant_Status
    ON Customers (TenantId, Status)
    WHERE DeletedAt IS NULL;

Nếu 70% bản ghi đã xoá mềm, index này chỉ bằng 30% kích thước và nằm gọn trong bộ nhớ.

Kiểm tra SQL sinh ra để chắc chắn filter được áp như mong đợi:

Console.WriteLine(db.Customers.Where(c => c.Status == CustomerStatus.Active).ToQueryString());

Tắt filter cho một entity khi không cần:

modelBuilder.Entity<AuditLog>().HasQueryFilter(null);

Bảng audit và bảng tham chiếu không nên có filter — chúng không thuộc về tenant nào và không bị xoá mềm.

13.11.6 — Rà lại code của bạn​

Danh sách rà soát global query filter

  • •Filter đa khách hàng đọc từ field của context, không gọi service trong biểu thức.
  • •Có integration test xác nhận hai tenant không thấy dữ liệu của nhau trong cùng tiến trình.
  • •Filter soft delete được áp tự động qua interface, không khai thủ công từng entity.
  • •Remove được chuyển thành xoá mềm bằng interceptor.
  • •Ràng buộc unique dùng filtered index loại bản ghi đã xoá.
  • •IgnoreQueryFilters không xuất hiện trong code nghiệp vụ.
  • •Mọi chỗ dùng IgnoreQueryFilters đều tự áp lại điều kiện tenant.
  • •Biết FindAsync bỏ qua filter.
  • •Entity con có filter tương ứng khi entity cha có filter.
  • •Filter không tham chiếu navigation nếu tránh được; sao chép cột xuống bảng con.
  • •Index có cột filter đặt trước, hoặc dùng filtered index.
  • •Bảng audit và bảng tham chiếu không có filter.

Bài tập áp dụng​

Bài 1 — Tenant id bị đóng băng trong mô hình​

Cài filter gọi tenant.Id trực tiếp trong biểu thức, gửi request với hai tenant khác nhau trên cùng tiến trình, và xác nhận request thứ hai thấy dữ liệu của tenant đầu. Sửa bằng field và kiểm chứng.

Tiêu chí hoàn thành: bạn giải thích được chính xác cái gì bị đóng băng, và vì sao lỗi không xuất hiện khi test một request đơn lẻ.

Gợi ý và lời giải — Bài 1

Gợi ý. OnModelCreating chạy bao nhiêu lần trong vòng đời một tiến trình?

Lời giải — bản có lỗi:

public class CrmDbContext : DbContext
{
    private readonly ITenantProvider _tenant;

    public CrmDbContext(DbContextOptions<CrmDbContext> options, ITenantProvider tenant)
        : base(options) => _tenant = tenant;

    protected override void OnModelCreating(ModelBuilder builder)
    {
        builder.Entity<Lead>().HasQueryFilter(l => l.TenantId == _tenant.Id);
        //                                                       ^^^^^^^^^^
        //                                                       giá trị bị đóng băng
    }
}
curl -H "X-Tenant: acme"  http://localhost:5000/leads    # 120 lead của acme  — ĐÚNG
curl -H "X-Tenant: globex" http://localhost:5000/leads   # 120 lead của acme  — SAI

Tenant globex thấy toàn bộ dữ liệu của acme. Đây là rò rỉ dữ liệu giữa khách hàng — loại sự cố nghiêm trọng nhất trong một hệ thống multi-tenant.

Chính xác cái gì bị đóng băng. Không phải _tenant (đối tượng), mà là giá trị _tenant.Id tại thời điểm mô hình được dựng lần đầu.

OnModelCreating chạy đúng một lần mỗi tiến trình, không phải mỗi request. EF Core dựng IModel rồi cache theo kiểu DbContext, vì dựng mô hình là việc rất tốn kém.

Request 1 (acme):    DbContext được tạo -> mô hình CHƯA có trong cache
                     -> OnModelCreating chạy
                     -> đọc _tenant.Id = "acme"
                     -> BIÊN DỊCH biểu thức lọc thành: l => l.TenantId == "acme"
                     -> cache mô hình đã biên dịch

Request 2 (globex):  DbContext được tạo -> mô hình ĐÃ có trong cache
                     -> OnModelCreating KHÔNG chạy
                     -> filter vẫn là: l => l.TenantId == "acme"

Điểm tinh tế: _tenant.Id trong biểu thức lambda được đánh giá khi cây biểu thức được dựng, không phải khi truy vấn chạy. Nó trở thành một hằng số nằm trong mô hình đã cache.

-- Mọi request, mọi tenant, mãi mãi
SELECT [l].[Id], [l].[Name] FROM [Leads] AS [l] WHERE [l].[TenantId] = N'acme'

Bản sửa — trỏ tới một field của DbContext thay vì đọc giá trị:

public class CrmDbContext : DbContext
{
    private readonly string _tenantId;      // field, không phải thuộc tính của dịch vụ khác

    public CrmDbContext(DbContextOptions<CrmDbContext> options, ITenantProvider tenant)
        : base(options) => _tenantId = tenant.Id;

    protected override void OnModelCreating(ModelBuilder builder)
    {
        builder.Entity<Lead>().HasQueryFilter(l => l.TenantId == _tenantId);
    }
}

Khác biệt trông nhỏ đến mức khó tin, nhưng nó quyết định. EF Core nhận ra _tenantId là field của chính DbContext instance, nên nó không nhúng giá trị vào mô hình mà sinh một tham số đọc từ instance tại thời điểm truy vấn:

SELECT [l].[Id], [l].[Name] FROM [Leads] AS [l] WHERE [l].[TenantId] = @__ef_filter__tenantId_0
curl -H "X-Tenant: acme"   http://localhost:5000/leads   # 120 lead của acme
curl -H "X-Tenant: globex" http://localhost:5000/leads   # 43 lead của globex  — ĐÚNG

Ba quy tắc rút ra:

ViếtKết quả
l.TenantId == _tenant.IdĐọc thuộc tính của dịch vụ khác → giá trị bị nhúng vào mô hình
l.TenantId == _tenantIdĐọc field của DbContext → thành tham số, đúng
l.TenantId == LayTenantId()Gọi phương thức → EF Core không dịch được hoặc gọi một lần rồi đóng băng

Vì sao lỗi không xuất hiện khi test một request đơn lẻ — đây là phần quan trọng nhất:

Vì với request đầu tiên trong tiến trình, giá trị đóng băng đúng là giá trị đúng. Mô hình vừa được dựng với tenant của chính request đó.

Test đơn lẻ:            1 request, 1 tenant -> đúng, test XANH
Integration test:       mỗi test một WebApplicationFactory mới
                        -> tiến trình mới -> mô hình mới -> đúng, test XANH
Chạy tay trên dev:      một người, một tenant -> đúng
Production:             nhiều tenant, cùng tiến trình -> SAI

Bốn lớp kiểm thử thông thường đều bỏ lọt, vì tất cả đều tình cờ thoả mãn điều kiện "chỉ một tenant trong vòng đời tiến trình". Lỗi chỉ lộ ra khi có tenant thứ hai gọi vào cùng một tiến trình — tức trên production, sau khi deploy, với khách hàng thật.

Test bắt được nó — hai request, hai tenant, cùng một factory:

[Fact]
public async Task Hai_tenant_tren_cung_tien_trinh_phai_thay_du_lieu_rieng()
{
    await using var factory = new WebApplicationFactory<Program>();
    var client = factory.CreateClient();          // cùng MỘT tiến trình cho cả hai request

    client.DefaultRequestHeaders.Remove("X-Tenant");
    client.DefaultRequestHeaders.Add("X-Tenant", "acme");
    var cuaAcme = await client.GetFromJsonAsync<List<LeadDto>>("/leads");

    client.DefaultRequestHeaders.Remove("X-Tenant");
    client.DefaultRequestHeaders.Add("X-Tenant", "globex");
    var cuaGlobex = await client.GetFromJsonAsync<List<LeadDto>>("/leads");

    cuaGlobex.Should().NotBeEquivalentTo(cuaAcme);
    cuaGlobex.Should().OnlyContain(l => l.TenantId == "globex");
}

Điểm mấu chốt là dùng chung một WebApplicationFactory cho cả hai request. Nếu bạn tạo factory mới cho request thứ hai, test sẽ xanh cả khi code sai.

Và một kiểm tra ở tầng mô hình, chạy một lần cho mọi entity:

[Fact]
public void Filter_theo_tenant_phai_sinh_tham_so_chu_khong_phai_hang_so()
{
    using var db = TaoContext(tenantId: "acme");

    var sql = db.Leads.ToQueryString();

    sql.Should().NotContain("'acme'", "tenant id bị nhúng thành hằng số trong mô hình");
    sql.Should().Contain("@__ef_filter__");
}

Test này không cần hai request và chạy trong vài mili giây — nên nó là thứ nên có trong CI.

Bài 2 — IgnoreQueryFilters rò rỉ​

Viết một endpoint admin dùng IgnoreQueryFilters() để xem bản ghi đã xoá, và xác nhận nó trả về dữ liệu của mọi tenant.

Tiêu chí hoàn thành: bạn giải thích được vì sao IgnoreQueryFilters không tắt được từng filter, và nêu được cách giữ lại filter tenant.

Gợi ý và lời giải — Bài 2

Gợi ý. Entity có hai filter. IgnoreQueryFilters() nhận tham số nào để chọn tắt cái nào?

Lời giải — endpoint có lỗi:

builder.Entity<Lead>().HasQueryFilter(l => !l.IsDeleted && l.TenantId == _tenantId);
app.MapGet("/admin/leads/da-xoa", async (CrmDbContext db, CancellationToken ct) =>
    await db.Leads
        .IgnoreQueryFilters()            // ý định: xem cả bản ghi đã xoá mềm
        .Where(l => l.IsDeleted)
        .ToListAsync(ct));
curl -H "X-Tenant: acme" http://localhost:5000/admin/leads/da-xoa
[
  { "id": 12, "name": "Lead của acme",   "tenantId": "acme"   },
  { "id": 98, "name": "Lead của globex", "tenantId": "globex" },
  { "id": 41, "name": "Lead của initech","tenantId": "initech"}
]

Admin của acme nhìn thấy dữ liệu của mọi khách hàng khác.

Vì sao IgnoreQueryFilters không tắt được từng filter. Vì nó không nhận tham số nào — chữ ký của nó là:

public static IQueryable<TEntity> IgnoreQueryFilters<TEntity>(this IQueryable<TEntity> source)

Không có cách nào nói "chỉ tắt phần soft delete". Nó tắt toàn bộ biểu thức lọc.

Lý do nằm ở cách EF Core lưu trữ filter: mỗi entity type có đúng một query filter, là một cây biểu thức duy nhất. Gọi HasQueryFilter lần thứ hai thay thế lần thứ nhất, không cộng thêm:

builder.Entity<Lead>().HasQueryFilter(l => !l.IsDeleted);
builder.Entity<Lead>().HasQueryFilter(l => l.TenantId == _tenantId);
// -> chỉ còn filter tenant; soft delete BIẾN MẤT

Đó là lý do người ta buộc phải nối bằng && vào một biểu thức. Và khi đã nối rồi, hai điều kiện không còn danh tính riêng để tắt riêng — chúng là hai nhánh của cùng một cây.

Mô hình lưu:   Lead -> QueryFilter: (l => !l.IsDeleted && l.TenantId == @tenant)
                                     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                     một biểu thức, không tách được

IgnoreQueryFilters()  ->  bỏ cả cây

Ba cách giữ lại filter tenant:

1. Thêm lại điều kiện tenant bằng tay — đơn giản nhất, nhưng dễ quên:

app.MapGet("/admin/leads/da-xoa", async (CrmDbContext db, ITenantProvider tenant, CancellationToken ct) =>
    await db.Leads
        .IgnoreQueryFilters()
        .Where(l => l.TenantId == tenant.Id)      // phải nhớ dòng này
        .Where(l => l.IsDeleted)
        .ToListAsync(ct));

2. Một extension method gói cả hai việc lại — nên dùng thay cho cách 1:

public static IQueryable<T> BoQuaSoftDelete<T>(this IQueryable<T> q, string tenantId)
    where T : class, ISoftDelete, IHasTenant
    => q.IgnoreQueryFilters().Where(e => e.TenantId == tenantId);
await db.Leads.BoQuaSoftDelete(tenant.Id).Where(l => l.IsDeleted).ToListAsync(ct);

Kèm một quy tắc analyzer cấm gọi IgnoreQueryFilters() trực tiếp ngoài file này. Đây là cách duy nhất khiến việc quên trở nên không thể, thay vì chỉ không nên.

3. Tách tenant ra khỏi query filter, đưa lên tầng kết nối. Cách triệt để nhất, và là cách mà hệ thống multi-tenant nghiêm túc thường chọn:

// Mỗi tenant một database hoặc một schema riêng
options.UseSqlServer(_tenantProvider.ChuoiKetNoi);
-- Hoặc row-level security của chính database
CREATE SECURITY POLICY TenantFilter
    ADD FILTER PREDICATE dbo.fn_TenantAccess(TenantId) ON dbo.Leads
    WITH (STATE = ON);

Với hai cách này, IgnoreQueryFilters() không thể vượt qua ranh giới tenant, vì ranh giới đó không nằm trong EF Core nữa. Không cần ai phải nhớ gì cả.

Ba nguyên tắc rút ra:

1. Đừng trộn hai mối quan tâm có mức độ nghiêm trọng khác nhau vào một filter. Bỏ lọt soft delete là hiển thị một bản ghi đã xoá — khó chịu. Bỏ lọt tenant là rò rỉ dữ liệu giữa khách hàng — có thể là vi phạm hợp đồng và nghĩa vụ pháp lý. Hai thứ đó không nên chung số phận.

2. IgnoreQueryFilters phải được coi như một thao tác đặc quyền. Mỗi lần dùng nên có lý do viết ngay tại chỗ:

// Màn hình khôi phục của admin nội bộ — cần thấy bản ghi đã xoá mềm.
// Đã lọc lại theo tenant ở dòng dưới; KHÔNG bỏ dòng đó.

3. Rà toàn bộ code base định kỳ:

grep -rn "IgnoreQueryFilters" --include="*.cs" src/ | wc -l

Mỗi kết quả là một chỗ phải đọc lại. Trong một hệ thống multi-tenant, con số này nên đếm được trên một bàn tay — và mọi chỗ nên nằm trong cùng một file.

Test chặn — chạy cho mọi endpoint admin:

[Fact]
public async Task Endpoint_admin_khong_duoc_tra_ve_du_lieu_cua_tenant_khac()
{
    await TaoLeadDaXoaAsync(tenantId: "acme");
    await TaoLeadDaXoaAsync(tenantId: "globex");

    var client = TaoClient(tenantId: "acme");
    var ketQua = await client.GetFromJsonAsync<List<LeadDto>>("/admin/leads/da-xoa");

    ketQua.Should().OnlyContain(l => l.TenantId == "acme");
    ketQua.Should().NotBeEmpty("nếu rỗng thì test không chứng minh được gì");
}

Khẳng định cuối quan trọng hơn vẻ ngoài của nó: OnlyContain trên một danh sách rỗng luôn đúng, nên nếu không có nó, một endpoint hỏng hoàn toàn cũng cho test xanh.

Bài 3 — Navigation property thành null​

Xoá mềm một Customer, rồi truy vấn Contacts với Include(c => c.Customer). Xác nhận Customer là null dù khoá ngoại bắt buộc.

Tiêu chí hoàn thành: bạn giải thích được vì sao filter được áp cho navigation, và nêu được hậu quả với LEFT JOIN trong SQL sinh ra.

Gợi ý và lời giải — Bài 3

Gợi ý. Include sinh ra một JOIN. Query filter của Customer xuất hiện ở đâu trong JOIN đó?

Lời giải:

builder.Entity<Customer>().HasQueryFilter(c => !c.IsDeleted);
// Contact có khoá ngoại BẮT BUỘC tới Customer
public class Contact
{
    public int Id { get; set; }
    public int CustomerId { get; set; }             // không nullable
    public Customer Customer { get; set; } = null!; // C# nói: không bao giờ null
}
await _db.Customers.Where(c => c.Id == 1)
    .ExecuteUpdateAsync(s => s.SetProperty(c => c.IsDeleted, true), ct);

var contacts = await _db.Contacts
    .Include(c => c.Customer)
    .Where(c => c.CustomerId == 1)
    .ToListAsync(ct);

Console.WriteLine(contacts.Count);              // 5 — contact vẫn còn
Console.WriteLine(contacts[0].Customer is null); // True
Console.WriteLine(contacts[0].Customer.Name);   // NullReferenceException

Contact vẫn trả về đầy đủ, nhưng Customer là null — dù CustomerId là int không nullable, dù ràng buộc khoá ngoại trong database vẫn nguyên, và dù C# khai báo = null!.

Vì sao filter được áp cho navigation. Query filter gắn với entity type, không gắn với DbSet. Mọi lần Customer xuất hiện trong một truy vấn — làm gốc, làm Include, làm đích của một JOIN — filter của nó đều được áp.

Đây là hành vi đúng và cần thiết. Nếu filter chỉ áp khi truy vấn trực tiếp _db.Customers, thì bất kỳ ai cũng đi vòng qua được:

// Nếu filter KHÔNG áp cho navigation, đây là một cửa hậu
var khachDaXoa = await _db.Contacts.Select(c => c.Customer).ToListAsync(ct);

Với multi-tenant, một cửa hậu như vậy là rò rỉ dữ liệu. Nên EF Core áp filter ở mọi nơi entity type xuất hiện — và cái giá là tình huống ở đầu bài.

Hậu quả với SQL — INNER JOIN trở thành LEFT JOIN:

-- Không có query filter trên Customer
SELECT [c].[Id], [c].[CustomerId], [t].[Id], [t].[Name]
FROM [Contacts] AS [c]
INNER JOIN [Customers] AS [t] ON [c].[CustomerId] = [t].[Id]
WHERE [c].[CustomerId] = 1
-- Có query filter trên Customer
SELECT [c].[Id], [c].[CustomerId], [t].[Id], [t].[Name]
FROM [Contacts] AS [c]
LEFT JOIN (
    SELECT [c0].[Id], [c0].[Name] FROM [Customers] AS [c0] WHERE [c0].[IsDeleted] = CAST(0 AS bit)
) AS [t] ON [c].[CustomerId] = [t].[Id]
WHERE [c].[CustomerId] = 1

Hai thay đổi:

  1. Bảng Customers trở thành một subquery đã lọc — chỉ chứa khách hàng chưa xoá.
  2. INNER JOIN thành LEFT JOIN.

Thay đổi thứ hai là thứ quyết định. Với INNER JOIN, một contact không khớp sẽ biến mất khỏi kết quả. EF Core không muốn Include làm mất dòng ở bảng gốc — Include phải là "nạp thêm", không phải "lọc bớt" — nên nó dùng LEFT JOIN. Contact được giữ lại, và cột của Customer là NULL.

INNER JOIN:  contact biến mất  -> Include vô tình trở thành bộ lọc -> tệ hơn
LEFT JOIN:   contact còn, Customer null -> đúng ngữ nghĩa của Include

Nói cách khác, null ở đây không phải lỗi — nó là câu trả lời trung thực cho câu hỏi "khách hàng của contact này, trong phạm vi bạn được phép thấy, là ai?". Câu trả lời là: không có ai.

Điều gây bối rối nhất: C# nói dối. Customer { get; set; } = null! tuyên bố với trình biên dịch rằng thuộc tính này không bao giờ null. Nullable reference types không cảnh báo gì, và code contact.Customer.Name trông hoàn toàn an toàn khi đọc. Nhưng = null! chỉ là một lời hứa của lập trình viên, và query filter vừa phá vỡ lời hứa đó.

Ba cách xử lý:

1. Lọc luôn cả phía Contact — thường là thứ bạn thật sự muốn:

builder.Entity<Contact>()
    .HasQueryFilter(c => !c.IsDeleted && !c.Customer.IsDeleted);

Khi khách hàng bị xoá mềm, contact của họ cũng biến mất khỏi mọi truy vấn. Nhất quán, và không còn null bất ngờ.

Lưu ý: filter tham chiếu tới navigation như vậy chỉ hoạt động cho quan hệ bắt buộc, và EF Core sẽ cảnh báo nếu Customer là optional.

2. IgnoreQueryFilters cho đúng truy vấn đó — khi màn hình cần thấy cả khách hàng đã xoá:

var contacts = await _db.Contacts
    .IgnoreQueryFilters()
    .Where(c => c.TenantId == tenantId)     // nhớ lọc lại tenant, như bài 2
    .Include(c => c.Customer)
    .ToListAsync(ct);

3. Khai báo trung thực trong C# — rẻ nhất, và nên làm bất kể chọn cách nào ở trên:

public Customer? Customer { get; set; }

Trình biên dịch lập tức cảnh báo ở mọi chỗ truy cập contact.Customer.Name, và bạn được nhắc xử lý trường hợp null ngay lúc viết code thay vì lúc chạy.

Và đây là lý do đáng nhớ nhất của cả bài: bất cứ khi nào bạn thêm một query filter, mọi navigation trỏ tới entity đó đều trở thành nullable trên thực tế — kể cả những navigation mà khoá ngoại là NOT NULL. Đó là một thay đổi lan rộng khắp mô hình, và nó không xuất hiện ở đâu trong migration.

# Rà mọi navigation trỏ tới entity có query filter
grep -rn "public Customer Customer" --include="*.cs" src/

Mỗi kết quả là một chỗ có thể ném NullReferenceException sau khi bạn bật soft delete cho Customer.

Tự kiểm tra​

Câu hỏi thường gặp

Global query filter giải quyết vấn đề gì?

Nó tự thêm điều kiện WHERE vào mọi truy vấn trên một entity, nên không ai quên lọc bản ghi đã xoá mềm hay lọc theo tenant. Đó là toàn bộ giá trị: biến một quy tắc mà con người phải nhớ thành một quy tắc mà hệ thống đảm bảo.

Vì sao filter tenant phải đọc từ field của context?

Vì EF Core cache mô hình theo kiểu DbContext và chỉ chạy OnModelCreating một lần cho cả vòng đời ứng dụng. Filter tham chiếu field của instance context được EF sinh thành tham số đọc lại mỗi truy vấn; còn filter gọi service sẽ bắt giữ instance của lần dựng mô hình đầu tiên, nên mọi request dùng tenant id của request đầu tiên.

Vì sao IgnoreQueryFilters nguy hiểm?

Vì nó bỏ qua tất cả filter chứ không chỉ một. Người muốn xem bản ghi đã xoá của tenant hiện tại sẽ nhận dữ liệu của mọi tenant. EF Core không cho bỏ qua một filter cụ thể, nên phải tự áp lại điều kiện tenant, và tốt nhất là cấm dùng nó trong code nghiệp vụ.

Những API nào bỏ qua global query filter?

FindAsync bỏ qua hoàn toàn, nên nó tìm thấy cả bản ghi đã xoá mềm. FromSql, ExecuteUpdate và ExecuteDelete thì vẫn áp filter. Ngoài ra navigation property có thể trả về entity đã bị lọc nếu entity đó đã nằm trong change tracker.

Vì sao navigation property có thể thành null dù khoá ngoại bắt buộc?

Vì filter được áp khi nạp navigation, nên entity cha đã xoá mềm sẽ bị loại và navigation thành null. Code giả định nó không bao giờ null sẽ ném NullReferenceException. Quy tắc là nếu entity cha có filter thì entity con cũng phải có filter tương ứng.

Filter ảnh hưởng hiệu năng thế nào?

Nó xuất hiện trong mọi truy vấn nên index phải hỗ trợ, với cột filter đặt trước trong composite index. Với soft delete thì filtered index còn tốt hơn vì nó chỉ chứa bản ghi chưa xoá. Và nên tránh filter tham chiếu navigation vì nó sinh JOIN trong mọi truy vấn.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Filter tenant phải đọc từ field của context — gọi service trong biểu thức làm mọi request dùng tenant đầu tiên.
  2. IgnoreQueryFilters bỏ qua tất cả, kể cả cách ly tenant.
  3. FindAsync bỏ qua filter — nó thấy cả bản ghi đã xoá mềm.
