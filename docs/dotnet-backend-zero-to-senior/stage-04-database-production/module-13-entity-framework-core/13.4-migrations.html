13.5 — 4. Migrations

Tóm tắt

EF Core sinh migration bằng cách so sánh mô hình hiện tại với ModelSnapshot — một file C# mô tả trạng thái schema sau migration cuối. Hai hệ quả trực tiếp. ModelSnapshot là nguồn xung đột merge phổ biến nhất: hai người cùng thêm migration trên hai nhánh sẽ sửa cùng một file, và giải quyết xung đột bằng tay gần như luôn sai — cách đúng là xoá migration của mình, merge, rồi sinh lại. Rollback không phải lúc nào cũng làm được: Down() sinh ra tự động biết cách khôi phục cấu trúc, nhưng dữ liệu trong cột đã bị DROP thì mất vĩnh viễn. Và với production, dùng script idempotent thay vì database update trực tiếp.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Giải thích ModelSnapshot và cách xử lý xung đột merge.
  • Sinh và áp dụng migration an toàn cho production.
  • Viết dữ liệu khởi tạo đúng chỗ.
  • Biết khi nào rollback được và khi nào không.
  • Xử lý nhiều DbContext trong một solution.

Nội dung bài học​

13.5.1 — Quy trình cơ bản​

dotnet tool install --global dotnet-ef

# Sinh migration — SO SÁNH model hiện tại với ModelSnapshot
dotnet ef migrations add AddCustomerTier \
    --project CRM.Infrastructure --startup-project CRM.Api

# Xem SQL sẽ chạy, KHÔNG thực thi
dotnet ef migrations script --idempotent --output migrate.sql

# Ap dung (Development)
dotnet ef database update

# Go migration CHUA ap dung
dotnet ef migrations remove

# Quay ve mot migration cu the
dotnet ef database update AddCustomerIndex

Mỗi migration sinh ba file:

Migrations/
├── 20260315103000_AddCustomerTier.cs              <- Up() va Down()
├── 20260315103000_AddCustomerTier.Designer.cs     <- snapshot tai thoi diem nay
└── CrmDbContext ModelSnapshot.cs                  <- trang thai HIEN TAI (ghi de)

File thứ ba bị ghi đè mỗi lần thêm migration — và đó là nguồn của mục tiếp theo.

13.5.2 — Xung đột merge​

Nhanh A: them migration 20260315_AddTier     -> sua ModelSnapshot
Nhanh B: them migration 20260315_AddSource   -> sua ModelSnapshot
Merge => XUNG DOT trong ModelSnapshot.cs

Đừng giải quyết xung đột này bằng tay. File snapshot phải phản ánh chính xác trạng thái sau cả hai migration, và ghép hai đoạn code bằng mắt rất dễ tạo ra một snapshot không khớp với schema thật — lỗi chỉ lộ ra ở migration sau nữa, khi EF so sánh với một snapshot sai và sinh ra migration vô nghĩa.

Quy trình đúng:

# 1. Go migration cua minh (chua merge)
dotnet ef migrations remove

# 2. Lấy code mới nhất từ nhánh chính
git pull origin main

# 3. Sinh lại — bây giờ nó so với snapshot ĐÃ CÓ migration của người kia
dotnet ef migrations add AddSource

Migration của bạn giờ nằm sau migration của người kia, và snapshot đúng.

Nếu migration đã được merge và bạn không gỡ được, cách cứu là xoá ModelSnapshot.cs, git checkout bản từ nhánh chính, rồi sinh một migration rỗng để EF tự dựng lại snapshot.

Phòng tránh: giữ migration nhỏ và merge sớm. Một nhánh sống ba tuần với bốn migration gần như chắc chắn sẽ xung đột.

13.5.3 — Script idempotent cho production​

dotnet ef migrations script --idempotent --output migrate.sql

Script idempotent bọc mỗi migration trong một kiểm tra:

IF NOT EXISTS (SELECT * FROM [__EFMigrationsHistory] WHERE [MigrationId] = N'20260315_AddTier')
BEGIN
    ALTER TABLE [Customers] ADD [Tier] nvarchar(50) NOT NULL DEFAULT N'Standard';

    INSERT INTO [__EFMigrationsHistory] ([MigrationId], [ProductVersion])
    VALUES (N'20260315_AddTier', N'9.0.0');
END;

Ba lợi ích so với dotnet ef database update:

  1. Chạy lại được — an toàn khi pipeline retry.
  2. Review được — DBA đọc SQL trước khi chạy.
  3. Không cần .NET SDK trên máy chạy migration.

Điểm 2 quan trọng trong môi trường có kiểm soát: không ai muốn một lệnh ALTER TABLE khoá bảng 20 phút xuất hiện bất ngờ (bài 12.9).

Sinh script cho một khoảng cụ thể:

dotnet ef migrations script AddCustomerIndex AddCustomerTier --idempotent

Và luôn đọc SQL trước khi chạy trên production. EF Core có thể sinh ra DROP COLUMN mà bạn không ngờ — đặc biệt khi đổi tên thuộc tính: EF thấy một cột biến mất và một cột mới xuất hiện, nên nó sinh DROP + ADD, mất toàn bộ dữ liệu.

// Sửa tay migration để giữ dữ liệu
migrationBuilder.RenameColumn(
    name: "Email", table: "Leads", newName: "ContactEmail");

13.5.4 — Dữ liệu trong migration​

// Cách 1: HasData — EF quản lý, sinh migration tự động
modelBuilder.Entity<Role>().HasData(
    new Role { Id = 1, Name = "Admin" },
    new Role { Id = 2, Name = "SalesRep" });

HasData hợp với dữ liệu tham chiếu cố định: vai trò, trạng thái, mã quốc gia. EF theo dõi chúng và sinh migration khi bạn sửa.

Ba ràng buộc: phải khai khoá chính tường minh (không dựa vào identity), không dùng được giá trị động như DateTime.Now, và không tạo được quan hệ phức tạp.

// Cách 2: SQL trong migration — cho chuyển đổi dữ liệu
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.AddColumn<string>("Tier", "Customers",
        nullable: false, defaultValue: "Standard");

    migrationBuilder.Sql("""
        UPDATE Customers
        SET    Tier = CASE
                 WHEN AnnualRevenue >= 1000000 THEN 'Enterprise'
                 WHEN AnnualRevenue >= 100000  THEN 'Business'
                 ELSE 'Standard' END
        WHERE  AnnualRevenue IS NOT NULL;
        """);
}

Với bảng lớn, chia lô thay vì một UPDATE (bài 12.9) — hoặc tách hẳn thành một job nền, vì migration nên nhanh.

// Cách 3: seeder riêng — cho dữ liệu khởi tạo có logic
public static class DatabaseSeeder
{
    public static async Task SeedAsync(CrmDbContext db, CancellationToken ct)
    {
        if (await db.Users.AnyAsync(ct)) return;     // idempotent

        db.Users.Add(new User { Email = "admin@crm.local", DisplayName = "Admin" });
        await db.SaveChangesAsync(ct);
    }
}

Cách 3 cho dữ liệu cần logic (băm mật khẩu, gọi service). Nó không thuộc về migration — migration lo schema, seeder lo dữ liệu ban đầu.

13.5.5 — Rollback: khi được và khi không​

dotnet ef database update AddCustomerIndex     # quay ve migration nay

EF chạy Down() của các migration sau đó. Nhưng:

Thao tácDown() khôi phục được?
AddColumnCó — DropColumn
CreateTableCó — DropTable
CreateIndexCó
DropColumnCấu trúc có, dữ liệu KHÔNG
DropTableCấu trúc có, dữ liệu KHÔNG
Sql(...) tuỳ biếnChỉ khi bạn tự viết Down

Hai hàng in đậm là lý do rollback không phải chiến lược khôi phục. Down() của DropColumn sẽ tạo lại cột — rỗng.

Ba nguyên tắc:

  1. Sao lưu trước mọi migration phá huỷ. Đây mới là chiến lược khôi phục thật.
  2. Ưu tiên tiến lên, không lùi lại. Sai thì viết migration mới sửa, thay vì rollback.
  3. Viết Down() cho mọi Sql() tuỳ biến — hoặc ghi rõ rằng nó không đảo ngược được.
protected override void Down(MigrationBuilder migrationBuilder)
{
    // Không khôi phục được dữ liệu gốc — chỉ đưa về trạng thái trước đó
    migrationBuilder.Sql("UPDATE Customers SET Tier = 'Standard';");
    migrationBuilder.DropColumn("Tier", "Customers");
}

Trên production, cách an toàn nhất là không rollback schema — expand-contract đảm bảo schema mới tương thích với code cũ, nên rollback code là đủ.

13.5.6 — Nhiều DbContext​

dotnet ef migrations add InitialIdentity \
    --context ApplicationIdentityDbContext \
    --output-dir Migrations/Identity

dotnet ef migrations add InitialCrm \
    --context CrmDbContext \
    --output-dir Migrations/Crm

--output-dir là bắt buộc: không có nó, hai context ghi migration vào cùng thư mục và bạn không phân biệt được cái nào thuộc về ai.

Mỗi context cũng nên có bảng lịch sử riêng:

options.UseSqlServer(conn, sql =>
    sql.MigrationsHistoryTable("__EFMigrationsHistory_Crm"));

Không có nó, hai context dùng chung __EFMigrationsHistory, và context này có thể tưởng migration của context kia là của mình.

dotnet ef cần biết cách tạo context ở design time. Nếu Program.cs phức tạp hoặc project hạ tầng không phải startup project:

public sealed class CrmDbContextFactory : IDesignTimeDbContextFactory<CrmDbContext>
{
    public CrmDbContext CreateDbContext(string[] args)
    {
        var options = new DbContextOptionsBuilder<CrmDbContext>()
            .UseSqlServer("Server=localhost;Database=CrmDesignTime;Trusted_Connection=True;TrustServerCertificate=True")
            .Options;

        return new CrmDbContext(options);
    }
}

Connection string ở đây chỉ dùng để sinh migration, không bao giờ kết nối thật — nên nó không phải secret, nhưng cũng đừng để trỏ vào production.

13.5.7 — Rà lại code của bạn​

Danh sách rà soát migration EF Core

  • •Xung đột ModelSnapshot được giải bằng cách sinh lại migration, không sửa tay.
  • •Migration nhỏ và được merge sớm.
  • •Production dùng script idempotent, không dùng database update trực tiếp.
  • •SQL sinh ra được đọc trước khi chạy trên production.
  • •Đổi tên thuộc tính được sửa thành RenameColumn, không để DROP + ADD.
  • •Dữ liệu tham chiếu cố định dùng HasData; dữ liệu có logic dùng seeder riêng.
  • •Backfill dữ liệu lớn chia lô hoặc tách thành job nền.
  • •Có sao lưu trước mọi migration phá huỷ.
  • •Mọi Sql() tuỳ biến đều có Down() tương ứng hoặc ghi rõ không đảo ngược được.
  • •Nhiều DbContext thì mỗi cái có output-dir và bảng lịch sử riêng.

Bài tập áp dụng​

Bài 1 — Xung đột model snapshot​

Tạo hai nhánh, mỗi nhánh thêm một migration, rồi merge. Thử giải xung đột bằng tay và xem migration tiếp theo sinh ra gì. Làm lại bằng quy trình gỡ và sinh lại.

Tiêu chí hoàn thành: bạn giải thích được vì sao giải xung đột bằng tay có vẻ đúng nhưng lại hỏng ở migration tiếp theo.

Gợi ý và lời giải — Bài 1

Gợi ý. EF Core so sánh mô hình hiện tại với cái gì để biết cần sinh migration nào?

Lời giải — tái hiện:

git checkout -b feature/them-source
# thêm thuộc tính Lead.Source
dotnet ef migrations add ThemLeadSource
git commit -am "thêm Lead.Source"

git checkout main && git checkout -b feature/them-priority
# thêm thuộc tính Lead.Priority
dotnet ef migrations add ThemLeadPriority
git commit -am "thêm Lead.Priority"

git checkout main
git merge feature/them-source      # sạch
git merge feature/them-priority    # XUNG ĐỘT
CONFLICT (content): Merge conflict in Migrations/CrmDbContextModelSnapshot.cs

Hai file migration không xung đột — chúng là file mới, tên khác nhau. Chỉ CrmDbContextModelSnapshot.cs xung đột, vì cả hai nhánh cùng sửa nó.

Giải bằng tay — và vì sao nó "có vẻ đúng":

b.Property<string>("Source").HasColumnType("nvarchar(max)");
b.Property<int>("Priority").HasColumnType("int");

Giữ cả hai dòng. Build xanh. dotnet ef database update chạy ngon lành, cả hai cột đều được tạo. Test đi qua. Nhìn từ mọi góc, mọi thứ đều ổn.

Vì sao nó hỏng ở migration tiếp theo. Vấn đề là snapshot không chỉ có hai dòng đó. Nó là bản chụp đầy đủ của toàn bộ mô hình — mọi entity, mọi thuộc tính, mọi index, mọi khoá ngoại, mọi annotation — và EF Core dùng nó làm điểm tham chiếu duy nhất để tính ra migration kế tiếp:

Migration tiếp theo = (mô hình hiện tại trong code) TRỪ (snapshot)

Merge bằng tay chỉ giải phần Git đánh dấu xung đột. Những phần Git tự merge được nhưng sai ngữ nghĩa vẫn lọt qua: thứ tự annotation, giá trị HasMaxLength bị chọn từ một phía, một index mà chỉ một nhánh biết. Hai nhánh còn có thể cùng chạm tới những dòng chung như giá trị ProductVersion hoặc khai báo HasAnnotation("Relational:MaxIdentifierLength", 128).

Kết quả là snapshot không còn khớp với mô hình thật. Và vì công thức trên lấy snapshot làm chuẩn, migration tiếp theo tính sai:

dotnet ef migrations add ThemLeadNotes
public partial class ThemLeadNotes : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        migrationBuilder.AddColumn<string>(name: "Notes", table: "Leads", nullable: true);

        // Không ai yêu cầu những dòng này
        migrationBuilder.AlterColumn<string>(
            name: "Source", table: "Leads", type: "nvarchar(100)", maxLength: 100,
            oldClrType: typeof(string), oldType: "nvarchar(max)");

        migrationBuilder.DropIndex(name: "IX_Leads_Priority", table: "Leads");
    }
}

Lỗi xuất hiện trễ một nhịp: nó không xảy ra ở lần merge, mà ở lần thay đổi schema tiếp theo — có thể nhiều ngày sau, do một người khác làm, trên một tính năng chẳng liên quan gì. Đó là lý do nó khó truy nguyên.

Quy trình đúng — gỡ và sinh lại:

git checkout main
git merge feature/them-source

git merge feature/them-priority
# Khi xung đột, lấy nguyên snapshot của nhánh ĐANG ĐƯỢC MERGE VÀO
git checkout --ours Migrations/CrmDbContextModelSnapshot.cs
git add Migrations/CrmDbContextModelSnapshot.cs
git commit

# Gỡ migration của nhánh đến (snapshot lúc này chưa biết về nó)
rm Migrations/*_ThemLeadPriority.cs

# Sinh lại — EF Core tự so mô hình với snapshot và sinh đúng phần còn thiếu
dotnet ef migrations add ThemLeadPriority

Điểm cốt lõi: đừng bao giờ sửa snapshot bằng tay. Nó là file sinh tự động. Cách duy nhất để nó đúng là để EF Core sinh ra nó.

Kiểm chứng sau mỗi lần merge có migration — một lệnh duy nhất:

dotnet ef migrations add KiemTra --dry-run

Hoặc trên bản EF Core không có --dry-run:

dotnet ef migrations add TamThoi && cat Migrations/*_TamThoi.cs
dotnet ef migrations remove

Nếu migration sinh ra rỗng, snapshot khớp với mô hình. Nếu nó chứa bất kỳ thao tác nào, snapshot đã sai và bạn vừa bắt được lỗi trước khi nó lên production.

Đưa kiểm tra đó vào CI — đây là thứ đáng làm nhất trong cả bài:

- name: Kiểm tra model snapshot khớp với mô hình
  run: |
    dotnet ef migrations add CiCheck --project src/Crm.Infrastructure
    if grep -q "migrationBuilder\." src/Crm.Infrastructure/Migrations/*_CiCheck.cs; then
      echo "Model snapshot không khớp với mô hình — hãy sinh lại migration"
      exit 1
    fi

Ba cách giảm tần suất xung đột:

  1. Một người phụ trách migration mỗi sprint — cách rẻ nhất, và hiệu quả bất ngờ với nhóm nhỏ.
  2. Merge main vào nhánh tính năng thường xuyên — xung đột được phát hiện sớm, khi chỉ có một migration để sinh lại.
  3. Gộp thay đổi schema thành một migration mỗi tính năng, đặt ở cuối nhánh thay vì rải rác — ít file hơn, ít lần chạm snapshot hơn.

Bài 2 — Đổi tên thuộc tính làm mất dữ liệu​

Đổi tên một thuộc tính trong entity, sinh migration, và đọc SQL. Xác nhận nó DROP rồi ADD. Sửa thành RenameColumn và kiểm chứng dữ liệu còn nguyên.

Tiêu chí hoàn thành: bạn giải thích được vì sao EF Core không thể tự nhận ra đây là đổi tên.

Gợi ý và lời giải — Bài 2

Gợi ý. EF Core so sánh hai bản chụp mô hình. Nó thấy gì khi một thuộc tính đổi tên?

Lời giải:

public class Lead
{
    public string Name { get; set; } = null!;     // đổi thành...
    public string FullName { get; set; } = null!;
}
dotnet ef migrations add DoiTenNameThanhFullName
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropColumn(name: "Name", table: "Leads");

    migrationBuilder.AddColumn<string>(
        name: "FullName", table: "Leads", type: "nvarchar(max)",
        nullable: false, defaultValue: "");
}
ALTER TABLE [Leads] DROP COLUMN [Name];
ALTER TABLE [Leads] ADD [FullName] nvarchar(max) NOT NULL DEFAULT N'';

Chạy migration này trên production: 50.000 tên khách hàng biến mất, thay bằng 50.000 chuỗi rỗng. Migration thành công, không lỗi, không cảnh báo nào ngoài một dòng An operation was scaffolded that may result in the loss of data trong log — dòng mà CI thường không đọc.

Bản sửa — sửa file migration bằng tay:

protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "Name", table: "Leads", newName: "FullName");
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "FullName", table: "Leads", newName: "Name");
}
EXEC sp_rename N'[Leads].[Name]', N'FullName', N'COLUMN';

Dữ liệu còn nguyên, và Down() khôi phục được hoàn toàn — khác hẳn bản DROP/ADD, nơi Down() chỉ tạo lại một cột rỗng.

Vì sao EF Core không thể tự nhận ra đây là đổi tên. Vì thông tin đó không tồn tại ở chỗ nó nhìn.

EF Core sinh migration bằng cách so sánh hai cấu trúc dữ liệu: snapshot cũ và mô hình mới. Mỗi thuộc tính trong đó được định danh bằng tên. Không có id ổn định, không có lịch sử, không có liên kết giữa thuộc tính cũ và mới:

Snapshot cũ:   { "Name": string }
Mô hình mới:   { "FullName": string }

Khác biệt:     - "Name" không còn    -> DropColumn
               - "FullName" mới có   -> AddColumn

Bài toán "hai tên khác nhau này thật ra là một thứ" là bài toán không giải được từ dữ liệu đó. Cân nhắc hai kịch bản tạo ra cùng một khác biệt:

Kịch bản A: đổi tên Name -> FullName
            Mong muốn: giữ dữ liệu

Kịch bản B: xoá cột Name, thêm cột FullName không liên quan
            Mong muốn: cột mới phải RỖNG

Snapshot không phân biệt được hai kịch bản này, vì cả hai để lại đúng cùng một dấu vết. EF Core buộc phải chọn một, và nó chọn DROP/ADD — diễn giải an toàn hơn về mặt ngữ nghĩa (không giả định dữ liệu cũ phù hợp với cột mới), dù nguy hiểm hơn về mặt dữ liệu.

Có công cụ đoán được — so sánh kiểu dữ liệu, độ tương đồng tên, vị trí cột — nhưng đó là suy đoán, và một công cụ migration đoán sai về dữ liệu production thì tệ hơn một công cụ không đoán.

Cách giữ ý định đổi tên cho EF Core biết — dùng HasColumnName thay vì đổi tên cột thật:

public string FullName { get; set; } = null!;   // đổi tên trong C#
builder.Property(l => l.FullName).HasColumnName("Name");   // cột database giữ nguyên

Không migration nào được sinh ra, vì database không đổi gì. Đây thường là lựa chọn đúng khi bạn chỉ muốn code đọc dễ hơn — và nó tách được hai việc vốn không liên quan: đặt tên trong C# và đặt tên trong schema.

Quy trình bắt buộc, không có ngoại lệ: đọc mọi migration trước khi commit.

dotnet ef migrations add TenMigration
cat src/Crm.Infrastructure/Migrations/*_TenMigration.cs

Và tốt hơn nữa, đọc SQL thật:

dotnet ef migrations script --idempotent --from <migration-trước> --to TenMigration

Chặn trong CI — bắt mọi thao tác phá dữ liệu, không chỉ đổi tên:

#!/usr/bin/env bash
# Cảnh báo khi migration mới chứa thao tác có thể mất dữ liệu
NGUY_HIEM="DropColumn|DropTable|AlterColumn.*nullable: false"
if git diff --name-only origin/main...HEAD -- '*/Migrations/*.cs' \
   | xargs --no-run-if-empty grep -lE "$NGUY_HIEM"; then
  echo "Migration chứa thao tác có thể mất dữ liệu — cần một người nữa duyệt"
  exit 1
fi

Đặt nó ở mức cảnh báo cần duyệt chứ không phải chặn cứng: DropColumn đôi khi đúng là thứ bạn muốn. Điều quan trọng là nó không bao giờ được đi qua mà không ai nhìn.

Bài 3 — Down() không khôi phục dữ liệu​

Chạy migration DropColumn trên bảng có dữ liệu, rồi rollback. Xác nhận cột trở lại nhưng rỗng.

Tiêu chí hoàn thành: bạn phân loại được thao tác migration nào rollback được thật và thao tác nào chỉ rollback được về mặt schema.

Gợi ý và lời giải — Bài 3

Gợi ý. Down() là code bạn viết. Nó chỉ làm được những gì bạn bảo nó làm — và nó không có bản sao dữ liệu nào để dùng.

Lời giải:

SELECT TOP 3 Id, Name, Notes FROM Leads;
Id   Name              Notes
1    Nguyễn Văn An     Khách quan tâm gói doanh nghiệp
2    Trần Thị Bình     Đã gọi 3 lần, hẹn gặp tuần sau
3    Lê Minh Cường     Yêu cầu báo giá chi tiết
dotnet ef migrations add BoCotNotes    # sau khi xoá thuộc tính Notes
dotnet ef database update
dotnet ef database update BanGhiTruocDo    # rollback
SELECT TOP 3 Id, Name, Notes FROM Leads;
Id   Name              Notes
1    Nguyễn Văn An     NULL
2    Trần Thị Bình     NULL
3    Lê Minh Cường     NULL

Cột trở lại. Dữ liệu thì không, và không có cách nào lấy lại từ database — ALTER TABLE DROP COLUMN giải phóng hẳn không gian đó.

Vì sao. Down() chỉ là một phương thức C# bạn viết, và nội dung EF Core sinh ra cho nó là phép đảo của thao tác schema, không phải của dữ liệu:

protected override void Up(MigrationBuilder migrationBuilder)
    => migrationBuilder.DropColumn(name: "Notes", table: "Leads");

protected override void Down(MigrationBuilder migrationBuilder)
    => migrationBuilder.AddColumn<string>(
           name: "Notes", table: "Leads", nullable: true);

AddColumn tạo một cột mới, rỗng. Nó không thể làm gì khác, vì không tồn tại bản sao nào của dữ liệu cũ để khôi phục. Migration không phải backup.

Phân loại thao tác — đây là phần chính của bài:

Nhóm 1 — rollback được thật, cả schema lẫn dữ liệu:

Thao tácDown()Vì sao an toàn
AddColumnDropColumnCột mới vốn chưa có dữ liệu nào đáng giữ
CreateIndexDropIndexIndex dẫn xuất hoàn toàn từ dữ liệu bảng
CreateTableDropTableBảng mới, dữ liệu sinh ra sau migration này
RenameColumnRenameColumnChỉ đổi metadata, dữ liệu không bị chạm
AddForeignKeyDropForeignKeyChỉ là ràng buộc
Nới lỏng kiểu (nvarchar(50) → nvarchar(200))Thu hẹp lạiGiá trị cũ vẫn vừa — trừ khi đã có giá trị dài hơn 50

Dòng cuối có điều kiện, và đó là điểm đáng nhớ: nó an toàn nếu rollback ngay, và không an toàn nếu ứng dụng đã chạy một thời gian với kiểu mới.

Nhóm 2 — chỉ rollback được schema, dữ liệu mất vĩnh viễn:

Thao tácMất gì
DropColumnToàn bộ giá trị của cột
DropTableToàn bộ bảng
Thu hẹp kiểu (nvarchar(200) → nvarchar(50))Phần bị cắt của mọi giá trị dài hơn 50
Đổi kiểu (nvarchar → int)Mọi giá trị không parse được
AlterColumn sang NOT NULL với defaultThông tin "giá trị này vốn chưa biết"
DELETE trong migrationCác dòng đã xoá

Dòng áp chót tinh tế hơn các dòng khác: không có byte nào mất đi, nhưng NULL và 0 mang hai ý nghĩa khác nhau — "chưa biết" và "bằng không" — và sau khi chuyển thì không phân biệt được nữa.

Nhóm 3 — không rollback được ngay cả về schema:

protected override void Down(MigrationBuilder migrationBuilder)
    => throw new NotSupportedException(
           "Migration này không thể rollback: dữ liệu đã được chuyển đổi không thuận nghịch.");

Tách một cột FullName thành FirstName và LastName là ví dụ điển hình: ghép lại được, nhưng "Nguyễn Văn An" tách rồi ghép có thể ra "Nguyễn Văn An" hoặc "An Nguyễn Văn" tuỳ quy tắc tách — không đảm bảo về đúng chuỗi ban đầu.

Trong trường hợp này, ném exception rõ ràng tốt hơn viết một Down() gần đúng: nó buộc người vận hành phải khôi phục từ backup thay vì tin vào một phép đảo không chính xác.

Hệ quả cho quy trình triển khai — điểm quan trọng nhất của bài.

Nếu Down() không khôi phục được dữ liệu, thì rollback không phải là kế hoạch dự phòng của bạn. Kế hoạch dự phòng thật là:

1. Expand–contract, và để khoảng cách giữa hai bước đủ dài. Chỉ Up() của bước expand mới được triển khai cùng code mới; bước contract chờ đến khi bạn chắc chắn không cần quay lại:

Tuần 1:  thêm cột mới, ghi cả hai cột       -> rollback được
Tuần 2:  chuyển đọc sang cột mới            -> rollback được
Tuần 3:  ngừng ghi cột cũ                   -> rollback được
Tuần 4:  DropColumn cột cũ                  -> điểm không quay lại

Ba tuần đầu, rollback chỉ là triển khai lại bản code cũ. Đến tuần 4 mới có thao tác phá huỷ, và lúc đó bạn đã có ba tuần để phát hiện vấn đề.

2. Backup ngay trước mọi migration có thao tác nhóm 2. Đưa vào pipeline, không để người vận hành nhớ:

sqlcmd -Q "BACKUP DATABASE Crm TO DISK='/backup/truoc-migration-$(date +%F-%H%M).bak'"
dotnet ef database update

3. Giữ dữ liệu thay vì xoá, khi có thể. Đổi tên cột sang Notes_DaBo và xoá thật ở một migration sau vài tuần:

migrationBuilder.RenameColumn(name: "Notes", table: "Leads", newName: "Notes_DaBo_20260925");

Cách này biến một thao tác nhóm 2 thành nhóm 1. Cái giá là một cột thừa trong vài tuần — rẻ hơn nhiều so với mất dữ liệu, và nó cho bạn đúng thứ mà Down() không cho được.

Tự kiểm tra​

Câu hỏi thường gặp

EF Core sinh migration dựa trên cái gì?

Nó so sánh mô hình hiện tại với ModelSnapshot, một file C# mô tả trạng thái schema sau migration cuối cùng. File này bị ghi đè mỗi lần thêm migration, nên nó là nguồn xung đột merge phổ biến nhất.

Giải quyết xung đột ModelSnapshot thế nào?

Không sửa bằng tay, vì ghép hai đoạn code bằng mắt dễ tạo ra snapshot không khớp schema thật, và lỗi chỉ lộ ra ở migration sau nữa. Cách đúng là gỡ migration của mình, lấy code mới nhất, rồi sinh lại để migration của bạn nằm sau migration của người kia.

Vì sao dùng script idempotent cho production?

Nó bọc mỗi migration trong kiểm tra bảng lịch sử nên chạy lại được an toàn khi pipeline retry, cho phép DBA review SQL trước khi chạy, và không cần cài .NET SDK trên máy chạy migration.

Đổi tên thuộc tính trong entity gây rủi ro gì?

EF Core thấy một cột biến mất và một cột mới xuất hiện nên sinh DROP COLUMN rồi ADD COLUMN, làm mất toàn bộ dữ liệu của cột đó. Phải sửa migration thành RenameColumn bằng tay, và đó là lý do luôn phải đọc SQL sinh ra trước khi chạy.

Rollback migration có khôi phục được dữ liệu không?

Không. Down của DropColumn sẽ tạo lại cột nhưng rỗng, vì dữ liệu đã mất khi cột bị xoá. Rollback không phải chiến lược khôi phục; sao lưu mới là. Trên production thì an toàn nhất là không rollback schema mà chỉ rollback code, nhờ migration tương thích ngược.

Nhiều DbContext trong một solution cần lưu ý gì?

Mỗi context phải có output-dir riêng cho migration, nếu không hai context ghi vào cùng thư mục và không phân biệt được. Và mỗi context nên có bảng lịch sử migration riêng, nếu không context này có thể tưởng migration của context kia là của mình.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Xung đột ModelSnapshot phải giải bằng sinh lại migration, không sửa tay.
  2. Đổi tên thuộc tính sinh ra DROP + ADD — sửa thành RenameColumn hoặc mất dữ liệu.
  3. Rollback không khôi phục dữ liệu. Sao lưu mới là chiến lược khôi phục.
