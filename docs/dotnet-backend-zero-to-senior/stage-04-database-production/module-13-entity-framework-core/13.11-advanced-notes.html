13.12 — Mở rộng và đào sâu

Tóm tắt

Những kỹ thuật EF Core nối tiếp Module 13, kèm điều kiện cụ thể. Kỹ thuật có tỷ lệ lợi ích cao nhất là interceptor: nó cho phép áp dụng hành vi chung — audit, soft delete, outbox, ghi log truy vấn chậm — cho mọi thao tác mà không sửa một dòng nào trong code nghiệp vụ. Kỹ thuật bị dùng sai nhiều nhất là thư viện bulk: chúng nhanh hơn thật, nhưng bỏ qua change tracker nên không kích hoạt interceptor, không sinh domain event, và không áp global query filter — dùng chúng cho dữ liệu có ý nghĩa nghiệp vụ là mất những thứ đó một cách im lặng.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Dùng interceptor cho hành vi áp dụng chung.
  • Biết compiled query giúp bao nhiêu và khi nào.
  • Chọn giữa owned entity và complex type.
  • Biết thư viện bulk bỏ qua những gì.

Nội dung bài học​

13.12.1 — Interceptor: ưu tiên cao​

Điều kiện kích hoạt: cần hành vi áp dụng cho mọi thao tác.

public sealed class AuditInterceptor(ICurrentUser currentUser, TimeProvider clock)
    : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var context = eventData.Context;
        if (context is null) return base.SavingChangesAsync(eventData, result, ct);

        var now = clock.GetUtcNow().UtcDateTime;

        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            switch (entry.State)
            {
                case EntityState.Added:
                    entry.Entity.CreatedUtc = now;
                    entry.Entity.CreatedBy = currentUser.Id;
                    break;

                case EntityState.Modified:
                    entry.Entity.ModifiedUtc = now;
                    entry.Entity.ModifiedBy = currentUser.Id;
                    break;

                case EntityState.Deleted:
                    // Soft delete — đổi thành Modified thay vì xoá thật
                    entry.State = EntityState.Modified;
                    entry.Entity.IsDeleted = true;
                    entry.Entity.DeletedUtc = now;
                    break;
            }
        }

        return base.SavingChangesAsync(eventData, result, ct);
    }
}

Một interceptor lo cả audit lẫn soft delete cho mọi entity, và không use case nào phải nhớ làm việc đó.

Loại interceptor thứ hai đáng có ngay: ghi log truy vấn chậm.

public sealed class SlowQueryInterceptor(ILogger<SlowQueryInterceptor> logger)
    : DbCommandInterceptor
{
    public override ValueTask<DbDataReader> ReaderExecutedAsync(
        DbCommand command, CommandExecutedEventData eventData,
        DbDataReader result, CancellationToken ct = default)
    {
        if (eventData.Duration.TotalMilliseconds > 500)
        {
            logger.LogWarning("Truy vấn chậm {Ms}ms: {Sql}",
                eventData.Duration.TotalMilliseconds, command.CommandText);
        }

        return base.ReaderExecutedAsync(command, eventData, result, ct);
    }
}

Nó bắt được truy vấn chậm trên production với dữ liệu thật — nơi vấn đề thực sự xuất hiện (bài 19.5).

Interceptor cũng là cách cài outbox pattern gọn nhất (bài 17.4).

13.12.2 — Compiled query​

Điều kiện kích hoạt: truy vấn giống hệt nhau chạy hàng nghìn lần.

private static readonly Func<AppDbContext, Guid, CancellationToken, Task<Lead?>> _layLead =
    EF.CompileAsyncQuery((AppDbContext db, Guid id, CancellationToken ct) =>
        db.Leads.FirstOrDefault(l => l.Id == id));

// Su dung
var lead = await _layLead(_db, id, ct);

EF Core cache kế hoạch truy vấn sẵn, nhưng vẫn phải phân tích cây biểu thức mỗi lần để tìm khoá cache. Compiled query bỏ qua bước đó.

Cải thiện thực tế: khoảng 10–30% thời gian chuẩn bị truy vấn — đáng kể chỉ khi truy vấn rất nhanh và chạy rất nhiều lần. Với truy vấn tốn 50ms ở database, tiết kiệm vài trăm micro giây không đổi gì.

Hạn chế: không dùng được cho truy vấn có cấu trúc thay đổi theo điều kiện (lọc động, sắp xếp động) — vì cây biểu thức phải cố định.

13.12.3 — Compiled model​

Điều kiện kích hoạt: model có hàng trăm entity và cold start quan trọng.

dotnet ef dbcontext optimize --output-dir Generated --namespace Crm.Infrastructure.Generated
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(cs).UseModel(AppDbContextModel.Instance));

EF Core dựng model từ cấu hình khi khởi tạo DbContext lần đầu. Với model lớn, việc đó tốn vài giây — đáng kể cho serverless hoặc khi pod khởi động lại thường xuyên.

Cái bẫy: model đã sinh không tự cập nhật khi bạn đổi cấu hình entity. Phải chạy lại lệnh trên, và nếu quên thì ứng dụng dùng model cũ — gây lỗi khó hiểu vì code và model không khớp. Đưa lệnh này vào build script.

13.12.4 — Owned entity và complex type​

Điều kiện kích hoạt: value object cần ánh xạ vào nhiều cột.

// Owned entity — có từ EF Core 2
b.OwnsOne(l => l.Address, a =>
{
    a.Property(x => x.HouseNumber).HasColumnName("Address_HouseNumber");
    a.Property(x => x.Street).HasColumnName("Address_Street");
});

// Complex type — EF Core 8+, tốt hơn
b.ComplexProperty(l => l.Address, a =>
{
    a.Property(x => x.HouseNumber).HasColumnName("Address_HouseNumber");
});
Owned entityComplex type
Có định danh ngầmCóKhông
Được theo dõi riêngCóKhông
Chia sẻ instance đượcKhôngCó
Dùng trong truy vấn SelectHạn chếTự do

Khác biệt thực tế quan trọng: với owned entity, EF Core coi nó như một entity có định danh, nên không dùng chung một instance cho hai bản ghi được — gán cùng một object DiaChi cho hai Lead sẽ ném exception. Complex type không có vấn đề đó, vì nó thật sự là một giá trị.

Với value object, complex type là lựa chọn đúng (bài 16.14).

13.12.5 — Thư viện bulk: biết nó bỏ qua gì​

Điều kiện kích hoạt: thao tác hàng chục nghìn bản ghi trở lên.

// EFCore.BulkExtensions
await _db.BulkInsertAsync(danhSachLead, ct);
await _db.BulkUpdateAsync(danhSachLead, ct);

Nhanh hơn SaveChanges hàng chục lần vì nó dùng SqlBulkCopy thay vì sinh câu INSERT riêng cho từng hàng.

Cái giá — nó bỏ qua toàn bộ tầng EF Core:

Bỏ quaHậu quả
Change trackerKhông biết entity nào đổi
InterceptorKhông có audit, không có soft delete
Domain eventKhông sinh event, outbox trống
Global query filterKhông lọc theo tenant
Validation của EF CoreDữ liệu sai vẫn ghi được

Ba hàng in đậm là lý do phải cẩn thận. Hàng cuối cùng đặc biệt nguy hiểm trong hệ multi-tenant: bulk update không áp global query filter, nên một điều kiện sai có thể sửa dữ liệu của mọi tenant (bài 13.11).

Quy tắc: dùng bulk cho nhập dữ liệu kỹ thuật — import ban đầu, đồng bộ từ hệ thống ngoài, dữ liệu tham chiếu. Dùng SaveChanges cho thao tác có ý nghĩa nghiệp vụ.

ExecuteUpdate và ExecuteDelete có sẵn trong EF Core cũng bỏ qua những thứ tương tự, nhưng chúng ít nguy hiểm hơn vì vẫn áp global query filter (bài 13.8).

13.12.8 — Rà lại code của bạn​

Danh sách rà soát EF Core nâng cao

  • •Audit và soft delete cài bằng interceptor, không lặp ở mỗi use case.
  • •Có interceptor ghi log truy vấn vượt ngưỡng thời gian.
  • •Value object dùng complex type thay vì owned entity.
  • •Thư viện bulk chỉ dùng cho nhập dữ liệu kỹ thuật.
  • •Biết bulk không áp global query filter và không sinh domain event.
  • •Global query filter tham chiếu service, không chụp giá trị.
  • •Nếu dùng compiled model, lệnh sinh lại nằm trong build script.
  • •Truy vấn nhiều collection dùng AsSplitQuery.

Bài tập áp dụng​

Bài 1 — Viết AuditInterceptor​

Cài AuditInterceptor cho một entity và xác nhận CreatedUtc được điền tự động.

Tiêu chí hoàn thành: interceptor của bạn xử lý đúng cả ba trường hợp mà bản viết vội hay bỏ sót.

Gợi ý và lời giải — Bài 1

Gợi ý. SaveChanges có hai bản. Entity có hơn hai trạng thái. Và UtcNow được gọi bao nhiêu lần?

Lời giải — bản viết vội:

public class AuditInterceptor : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData e, InterceptionResult<int> r, CancellationToken ct = default)
    {
        foreach (var entry in e.Context!.ChangeTracker.Entries<IAuditable>())
            if (entry.State == EntityState.Added)
                entry.Entity.CreatedUtc = DateTime.UtcNow;

        return base.SavingChangesAsync(e, r, ct);
    }
}

Chạy được với kịch bản cơ bản. Ba chỗ sót:

Sót 1 — không override bản đồng bộ. SaveChanges() không đi qua SavingChangesAsync:

db.Leads.Add(lead);
db.SaveChanges();              // đồng bộ -> CreatedUtc = default(DateTime)
CreatedUtc: 0001-01-01 00:00:00

Lỗi này đặc biệt khó chịu vì phần lớn code dùng async, nên nó chỉ xuất hiện ở vài chỗ lẻ — seeder, migration, một job cũ — và mỗi chỗ để lại vài dòng có CreatedUtc bằng năm 0001.

Sót 2 — không xử lý Modified, và không chặn sửa CreatedUtc:

lead.Status = "Won";
await db.SaveChangesAsync(ct);    // UpdatedUtc vẫn null

Tệ hơn: nếu ai đó vô tình gán lead.CreatedUtc = DateTime.UtcNow trong code nghiệp vụ, EF Core sẽ ghi giá trị đó xuống. Thời điểm tạo — vốn phải bất biến — bị sửa mà không ai biết.

Sót 3 — gọi DateTime.UtcNow nhiều lần. Mỗi entity nhận một mốc thời gian khác nhau vài chục micro giây:

Lead 1:  2026-09-25 08:14:22.1234567
Lead 2:  2026-09-25 08:14:22.1234612
Lead 3:  2026-09-25 08:14:22.1234698

Ba entity được tạo trong cùng một transaction, tức cùng một hành động nghiệp vụ, lại có ba thời điểm khác nhau. Hậu quả thực tế: sắp xếp theo CreatedUtc cho ra thứ tự tuỳ ý trong cùng một lô, và truy vấn WHERE CreatedUtc = @x không tìm được nhóm. Và DateTime.UtcNow trực tiếp thì không test được.

Bản đầy đủ:

public class AuditInterceptor : SaveChangesInterceptor
{
    private readonly ICurrentUser _currentUser;
    private readonly TimeProvider _clock;

    public AuditInterceptor(ICurrentUser currentUser, TimeProvider clock)
        => (_currentUser, _clock) = (currentUser, clock);

    public override InterceptionResult<int> SavingChanges(
        DbContextEventData e, InterceptionResult<int> r)
    {
        DienAudit(e.Context);
        return base.SavingChanges(e, r);
    }

    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData e, InterceptionResult<int> r, CancellationToken ct = default)
    {
        DienAudit(e.Context);
        return base.SavingChangesAsync(e, r, ct);
    }

    internal void DienAudit(DbContext? context)
    {
        if (context is null) return;

        // Gọi MỘT lần cho cả lô — mọi entity trong cùng SaveChanges cùng mốc thời gian
        var now    = _clock.GetUtcNow().UtcDateTime;
        var userId = _currentUser.Id;

        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            switch (entry.State)
            {
                case EntityState.Added:
                    entry.Entity.CreatedUtc = now;
                    entry.Entity.CreatedBy  = userId;
                    break;

                case EntityState.Modified:
                    entry.Entity.UpdatedUtc = now;
                    entry.Entity.UpdatedBy  = userId;
                    // Không cho sửa thông tin tạo, kể cả khi code nghiệp vụ gán nhầm
                    entry.Property(x => x.CreatedUtc).IsModified = false;
                    entry.Property(x => x.CreatedBy).IsModified  = false;
                    break;

                // Chuyển xoá cứng thành xoá mềm, nếu entity hỗ trợ
                case EntityState.Deleted when entry.Entity is ISoftDelete soft:
                    entry.State          = EntityState.Modified;
                    soft.IsDeleted       = true;
                    entry.Entity.UpdatedUtc = now;
                    entry.Entity.UpdatedBy  = userId;
                    break;
            }
        }
    }
}

Nhánh Deleted đáng chú ý: đổi entry.State từ Deleted sang Modified khiến EF Core sinh UPDATE thay vì DELETE. Nhờ vậy _db.Leads.Remove(lead) ở code nghiệp vụ tự động trở thành xoá mềm, và không ai phải nhớ gì.

Đăng ký:

builder.Services.AddSingleton(TimeProvider.System);
builder.Services.AddScoped<AuditInterceptor>();
builder.Services.AddDbContext<CrmDbContext>((sp, opt) =>
    opt.UseSqlServer(conn).AddInterceptors(sp.GetRequiredService<AuditInterceptor>()));

AddScoped là bắt buộc, không phải AddSingleton: interceptor phụ thuộc vào ICurrentUser, vốn khác nhau theo từng request.

Test — không cần database:

[Fact]
public void Moi_entity_trong_cung_mot_lo_phai_co_cung_moc_thoi_gian()
{
    var clock = new FakeTimeProvider(new DateTimeOffset(2026, 9, 25, 8, 0, 0, TimeSpan.Zero));
    var interceptor = new AuditInterceptor(new FakeCurrentUser("u1"), clock);
    using var db = TaoInMemoryContext();

    var a = new Lead { Name = "A" };
    var b = new Lead { Name = "B" };
    db.Leads.AddRange(a, b);

    interceptor.DienAudit(db);

    a.CreatedUtc.Should().Be(b.CreatedUtc);
}

[Fact]
public void Sua_entity_khong_duoc_thay_doi_CreatedUtc()
{
    // ... nạp entity, gán CreatedUtc sai, chạy DienAudit
    db.Entry(lead).Property(l => l.CreatedUtc).IsModified.Should().BeFalse();
}

Và nhớ giới hạn đã nêu ở bài 13.7: interceptor này không chạy cho ExecuteUpdateAsync và ExecuteDeleteAsync, vì chúng không đi qua SaveChanges.

Bài 2 — Bắt truy vấn chậm​

Thêm SlowQueryInterceptor với ngưỡng thấp và xem log sinh ra khi chạy ứng dụng.

Tiêu chí hoàn thành: interceptor log đủ thông tin để chẩn đoán chứ không chỉ để biết là có chậm, và bạn nêu được vì sao nó không thay thế được APM.

Gợi ý và lời giải — Bài 2

Gợi ý. Nhận được một dòng log "truy vấn chậm: 850 ms", bạn sẽ hỏi gì tiếp theo?

Lời giải:

public class SlowQueryInterceptor : DbCommandInterceptor
{
    private readonly ILogger<SlowQueryInterceptor> _logger;
    private readonly TimeSpan _nguong;

    public SlowQueryInterceptor(ILogger<SlowQueryInterceptor> logger, TimeSpan nguong)
        => (_logger, _nguong) = (logger, nguong);

    public override DbDataReader ReaderExecuted(
        DbCommand command, CommandExecutedEventData e, DbDataReader result)
    {
        Ghi(command, e);
        return base.ReaderExecuted(command, e, result);
    }

    public override ValueTask<DbDataReader> ReaderExecutedAsync(
        DbCommand command, CommandExecutedEventData e, DbDataReader result,
        CancellationToken ct = default)
    {
        Ghi(command, e);
        return base.ReaderExecutedAsync(command, e, result, ct);
    }

    public override int NonQueryExecuted(
        DbCommand command, CommandExecutedEventData e, int result)
    {
        Ghi(command, e);
        return base.NonQueryExecuted(command, e, result);
    }

    private void Ghi(DbCommand command, CommandExecutedEventData e)
    {
        if (e.Duration < _nguong) return;

        _logger.LogWarning(
            "Truy vấn chậm {Ms} ms (ngưỡng {Nguong} ms)\n" +
            "CommandId: {CommandId}\nConnectionId: {ConnectionId}\n" +
            "Tham số: {ThamSo}\nSQL:\n{Sql}",
            (int)e.Duration.TotalMilliseconds,
            (int)_nguong.TotalMilliseconds,
            e.CommandId,
            e.ConnectionId,
            string.Join(", ", command.Parameters.Cast<DbParameter>()
                                     .Select(p => $"{p.ParameterName}={p.Value}")),
            command.CommandText);
    }
}
builder.Services.AddScoped(sp => new SlowQueryInterceptor(
    sp.GetRequiredService<ILogger<SlowQueryInterceptor>>(),
    TimeSpan.FromMilliseconds(builder.Configuration.GetValue<int>("Database:SlowQueryMs", 500))));

Đặt ngưỡng qua cấu hình là chi tiết quan trọng: ở dev bạn muốn 50 ms để thấy nhiều, ở production 500 ms để không ngập log.

Thông tin cần có để chẩn đoán được, không chỉ để biết là chậm:

TrườngTrả lời câu hỏi
DurationChậm bao nhiêu?
CommandTextTruy vấn nào?
Tham sốChậm với giá trị nào?
ConnectionIdCó phải nhiều truy vấn cùng một kết nối không?
CommandIdGhép với các sự kiện khác của cùng lệnh
Trace idRequest nào của người dùng nào?

Tham số là trường hay bị bỏ sót nhất, và thường là trường quan trọng nhất. Cùng một câu SQL có thể nhanh với tham số này và chậm với tham số khác:

WHERE TenantId = 'startup-nho'   ->   12 ms   (300 dòng)
WHERE TenantId = 'tap-doan-lon'  ->  2.400 ms (4 triệu dòng)

Không có tham số, bạn nhìn vào câu SQL và không hiểu vì sao nó "lúc nhanh lúc chậm".

Cảnh báo về dữ liệu nhạy cảm: tham số có thể chứa email, số điện thoại, hay chuỗi tìm kiếm của người dùng. Ở production, hãy che hoặc chỉ log tên tham số và kiểu:

string.Join(", ", command.Parameters.Cast<DbParameter>()
    .Select(p => _moiTruong.IsDevelopment()
        ? $"{p.ParameterName}={p.Value}"
        : $"{p.ParameterName}:{p.DbType}"))

Gắn với trace id để nối ngược về request:

using var scope = _logger.BeginScope(new Dictionary<string, object>
{
    ["TraceId"] = Activity.Current?.TraceId.ToString() ?? "none",
});

Không có nó, bạn có một câu SQL chậm nhưng không biết endpoint nào gọi, ai gọi, và trong bối cảnh gì.

Vì sao nó không thay thế được APM — đây là phần chính của bài. Interceptor này thấy một truy vấn tại một thời điểm, và chỉ thấy phần bên trong DbCommand. Bốn thứ nó không thấy:

1. Tổng thể của một request. Một endpoint chạy 3 giây vì 200 truy vấn, mỗi cái 15 ms sẽ không sinh ra một dòng log nào, vì không truy vấn nào vượt ngưỡng. Đây chính là hình dạng của N+1 — vấn đề phổ biến nhất — và interceptor ngưỡng mù hoàn toàn với nó.

2. Thời gian chờ kết nối. e.Duration đo từ lúc lệnh bắt đầu thực thi. Nếu connection pool cạn và request chờ 5 giây để lấy kết nối, truy vấn vẫn được ghi nhận là 20 ms.

3. Xu hướng theo thời gian. Một truy vấn đi từ 80 ms lên 450 ms trong ba tháng là một vấn đề đang lớn dần, nhưng nó không bao giờ chạm ngưỡng 500 ms cho tới ngày nó chạm. APM lưu trữ chuỗi thời gian và cho bạn thấy độ dốc.

4. Phân bố, chứ không chỉ các ngoại lệ. Log ngưỡng chỉ ghi phần đuôi. Bạn không biết p50, p95, p99, và không biết một truy vấn 600 ms là bất thường hay là bình thường với truy vấn đó.

Phân vai đúng giữa ba công cụ:

Công cụTrả lời
Interceptor ngưỡngTruy vấn cụ thể nào chậm, với tham số nào — rẻ, có ngay, không cần hạ tầng
APM / OpenTelemetryRequest nào chậm, chậm ở đâu trong chuỗi, xu hướng và phân bố
DMV của databaseTruy vấn nào tốn tài nguyên nhất trên toàn hệ thống, kể cả từ ứng dụng khác

Ba công cụ này bổ sung nhau, không thay thế nhau. Interceptor là cái rẻ nhất và nên có ngay từ ngày đầu; nhưng nếu chỉ có nó, bạn sẽ bỏ lọt đúng loại vấn đề hay gặp nhất.

Xuất metric thay vì chỉ log — nâng cấp rẻ nhất cho interceptor này:

private static readonly Histogram<double> _thoiGianTruyVan =
    _meter.CreateHistogram<double>("db.query.duration", "ms");

_thoiGianTruyVan.Record(e.Duration.TotalMilliseconds,
    new KeyValuePair<string, object?>("db.operation", LayLoaiLenh(command.CommandText)));

Với histogram, bạn có phân bố đầy đủ thay vì chỉ phần đuôi — và nó ghép được vào cùng hệ thống quan sát với mọi metric khác.

Bài 3 — Bulk extension và query filter​

Chạy BulkInsert trên entity có global query filter theo tenant và xác nhận filter không được áp.

Tiêu chí hoàn thành: bạn giải thích được vì sao mọi thao tác bulk đều bỏ qua filter, và nêu được cách dùng an toàn.

Gợi ý và lời giải — Bài 3

Gợi ý. Query filter là một mệnh đề WHERE. Thư viện bulk sinh ra loại câu lệnh nào?

Lời giải:

builder.Entity<Lead>().HasQueryFilter(l => l.TenantId == _tenantId && !l.IsDeleted);
// Không đặt TenantId — người viết tin rằng filter sẽ lo
var leads = Enumerable.Range(1, 1000)
    .Select(i => new Lead { Name = $"Lead {i}", Status = "New" })
    .ToList();

await _db.BulkInsertAsync(leads, ct);
SELECT TenantId, COUNT(*) FROM Leads GROUP BY TenantId;
TenantId   COUNT
NULL       1000
acme       120
globex      43

Một nghìn dòng với TenantId = NULL, không thuộc về tenant nào và không tenant nào truy vấn được. Chúng trở thành dữ liệu mồ côi chiếm chỗ trong bảng.

BulkUpdate và BulkDelete còn nguy hiểm hơn:

await _db.Leads.Where(l => l.Status == "Stale").BulkDeleteAsync(ct);
// Xoá lead "Stale" của MỌI tenant, không chỉ tenant hiện tại

Vì sao mọi thao tác bulk đều bỏ qua filter. Vì global query filter là một mệnh đề WHERE mà EF Core thêm vào khi dịch IQueryable sang SQL. Thao tác bulk không đi qua đường dịch đó:

Truy vấn thường:  IQueryable -> pipeline dịch của EF Core -> thêm WHERE của filter -> SQL
Bulk:             List<T>    -> SqlBulkCopy / MERGE dựng thẳng -> gửi
                                ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
                                không qua pipeline, không có chỗ để chen WHERE vào

Đây chính là lý do tồn tại của thư viện bulk: bỏ qua pipeline là cách nó nhanh hơn một bậc độ lớn. Không thể có cả hai.

Danh sách đầy đủ những gì bulk bỏ qua — trùng với ExecuteUpdate ở bài 13.7, cộng thêm vài thứ:

Bỏ quaHậu quả
Global query filterGhi sai tenant, xoá dữ liệu tenant khác
Change trackerEntity đang theo dõi trở nên cũ
Interceptor và SaveChanges overrideKhông có audit, không có outbox
Concurrency tokenKhông phát hiện xung đột
Value converter (tuỳ thư viện)Dữ liệu ghi xuống sai định dạng
Domain eventKhông có sự kiện nào được phát
DbContext cascadeEntity con không được xử lý

Dòng value converter đáng lưu ý: một số thư viện bulk không áp converter, nên một List<string> được cấu hình lưu dạng chuỗi phân cách có thể ghi xuống sai hoàn toàn. Hãy kiểm chứng trên staging với đúng cấu hình của bạn trước khi dùng thật.

Cách dùng an toàn — bốn nguyên tắc:

1. Đặt TenantId tường minh, luôn luôn:

var leads = nguon.Select(x => new Lead
{
    Name     = x.Name,
    Status   = "New",
    TenantId = _tenantProvider.Id,                  // bắt buộc
    CreatedUtc = _clock.GetUtcNow().UtcDateTime,    // bắt buộc — không có interceptor
    CreatedBy  = _currentUser.Id,
}).ToList();

await _db.BulkInsertAsync(leads, ct);

2. Bọc lại, đừng gọi thẳng. Đây là biện pháp hiệu quả nhất vì nó khiến việc quên trở nên không thể:

public async Task ChenHangLoatAsync<T>(IEnumerable<T> items, CancellationToken ct)
    where T : class, IHasTenant, IAuditable
{
    var now    = _clock.GetUtcNow().UtcDateTime;
    var userId = _currentUser.Id;
    var tenant = _tenantProvider.Id;

    var danhSach = items.ToList();
    foreach (var item in danhSach)
    {
        item.TenantId   = tenant;
        item.CreatedUtc = now;
        item.CreatedBy  = userId;
    }

    await _db.BulkInsertAsync(danhSach, ct);
}

Kèm analyzer cấm gọi BulkInsertAsync ngoài lớp bọc này.

3. Với BulkUpdate và BulkDelete, đưa điều kiện tenant vào Where — và kiểm tra lại:

await _db.Leads
    .Where(l => l.TenantId == _tenantProvider.Id && l.Status == "Stale")
    .BulkDeleteAsync(ct);

4. Test khẳng định phạm vi, không chỉ khẳng định số lượng:

[Fact]
public async Task Chen_hang_loat_phai_dat_dung_tenant()
{
    await _service.ChenHangLoatAsync(TaoLeadThu(1000), ct);

    var theoTenant = await _db.Leads.IgnoreQueryFilters()
        .GroupBy(l => l.TenantId)
        .Select(g => new { g.Key, SoLuong = g.Count() })
        .ToListAsync(ct);

    theoTenant.Should().ContainSingle()
              .Which.Key.Should().Be("acme");
}

[Fact]
public async Task Xoa_hang_loat_khong_duoc_dung_toi_tenant_khac()
{
    await TaoLeadAsync(tenantId: "globex", status: "Stale");

    await _service.XoaLeadCuAsync(ct);     // chạy với tenant "acme"

    var conLai = await _db.Leads.IgnoreQueryFilters()
        .CountAsync(l => l.TenantId == "globex", ct);
    conLai.Should().Be(1, "dữ liệu của tenant khác không được đụng tới");
}

Cả hai test dùng IgnoreQueryFilters() — đây là một trong số ít chỗ nó đúng là công cụ phù hợp, vì test cần nhìn thấy toàn bộ bảng để chứng minh phạm vi.

Và câu hỏi nên hỏi trước tiên: bạn có thật sự cần bulk không?

< 1.000 dòng:          SaveChanges thường là đủ
1.000 – 50.000 dòng:   SaveChanges chia lô, hoặc ExecuteUpdate
> 50.000 dòng:         bulk extension hoặc SqlBulkCopy

Mỗi bậc đánh đổi thêm an toàn lấy tốc độ. Đừng trả giá đó khi chưa đo — và với phần lớn ứng dụng nghiệp vụ, số dòng mỗi lần ghi nằm ở bậc đầu tiên.

Tự kiểm tra​

Câu hỏi thường gặp

Interceptor giải quyết vấn đề gì?

Nó cho phép áp dụng hành vi chung như audit, soft delete, outbox hay ghi log truy vấn chậm cho mọi thao tác mà không sửa dòng nào trong code nghiệp vụ, và không use case nào phải nhớ làm việc đó.

Compiled query cải thiện được bao nhiêu?

Khoảng mười tới ba mươi phần trăm thời gian chuẩn bị truy vấn, vì nó bỏ bước phân tích cây biểu thức. Nó chỉ đáng kể khi truy vấn rất nhanh và chạy rất nhiều lần; với truy vấn tốn năm mươi mili giây ở database thì không đổi gì.

Cái bẫy của compiled model là gì?

Model đã sinh không tự cập nhật khi bạn đổi cấu hình entity. Quên chạy lại lệnh sinh thì ứng dụng dùng model cũ, gây lỗi khó hiểu vì code và model không khớp. Nên đưa lệnh đó vào build script.

Complex type hơn owned entity ở điểm nào?

Owned entity có định danh ngầm và được theo dõi riêng, nên không dùng chung một instance cho hai bản ghi được. Complex type thật sự là một giá trị nên không có hạn chế đó, và dùng tự do trong truy vấn Select.

Thư viện bulk bỏ qua những gì?

Change tracker, interceptor nên không có audit và soft delete, domain event nên outbox trống, và global query filter nên không lọc theo tenant. Ba cái sau là lý do phải cẩn thận với dữ liệu có ý nghĩa nghiệp vụ.

Vì sao ExecuteUpdate ít nguy hiểm hơn thư viện bulk?

Vì nó vẫn áp global query filter, nên không sửa nhầm dữ liệu của tenant khác. Nó vẫn bỏ qua interceptor và domain event, nhưng rủi ro rò rỉ dữ liệu giữa tenant thì không có.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Interceptor là kỹ thuật lợi ích cao nhất — audit, soft delete, outbox, log truy vấn chậm ở một chỗ.
  2. Thư viện bulk bỏ qua interceptor, domain event và global query filter — biết trước khi dùng.
  3. Complex type đúng hơn owned entity cho value object.
