4.10 — Những lỗi thường gặp

Tóm tắt

Tám lỗi dưới đây gặp trong gần như mọi codebase .NET đã chạy được vài năm. Điểm chung của chúng: không lỗi nào gây ra exception ngay lúc viết — chúng chỉ làm code khó đổi dần, cho tới lúc một yêu cầu nhỏ mất ba ngày. Đáng chú ý nhất là lỗi cuối: string.Equals mặc định so sánh theo thứ tự byte, nên "i".ToUpper() trong văn hoá Thổ Nhĩ Kỳ cho ra "İ" chứ không phải "I" — một lỗi từng làm hỏng phần đăng nhập của nhiều hệ thống thật, và chỉ xuất hiện trên máy của người dùng ở đúng khu vực đó.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Nhận ra tám lỗi thiết kế lớp phổ biến qua triệu chứng của chúng.
  • Giải thích hậu quả cụ thể của từng lỗi, không chỉ nói "không tốt".
  • Áp dụng cách sửa tương ứng.
  • Biết vì sao so sánh chuỗi phải nêu rõ StringComparison.

Nội dung bài học​

4.10.1 — Field công khai có thể thay đổi​

// SAI
public class Order { public decimal Total; }

// ĐÚNG
public class Order { public decimal Total { get; private set; } }

Triệu chứng: bất kỳ ai cũng đặt được giá trị bất kỳ, kể cả số âm.

Hậu quả: không có chỗ nào chèn kiểm tra, và đổi field thành property sau này là thay đổi phá vỡ tương thích nhị phân — mọi assembly tham chiếu tới phải build lại.

4.10.2 — God class​

// SAI — 1200 dòng, xử lý CRUD, email, báo cáo, chiết khấu, xuất Excel
public class CustomerManager { }

Triệu chứng: file dài hơn 500 dòng; constructor nhận bảy phụ thuộc trở lên; tên class chứa Manager, Helper, Util, Processor.

Hậu quả: không viết unit test nổi vì phải dựng cả bảy phụ thuộc; hai người sửa cùng file mỗi tuần nên xung đột liên tục; và đổi định dạng Excel lại làm vỡ test của phần chiết khấu.

Cách sửa — tách theo lý do thay đổi, không tách theo số dòng:

public class CustomerService     { }  // quy tắc nghiệp vụ
public class CustomerRepository  { }  // truy cập dữ liệu
public class CustomerExporter    { }  // xuất file
public class CustomerNotifier    { }  // gửi thông báo

Phép thử: "Ai là người yêu cầu thay đổi class này?" Nếu có nhiều hơn một nhóm người, hãy tách.

4.10.3 — Kế thừa để dùng lại code​

// SAI — PremiumCustomer kế thừa Customer chỉ để thêm một mức chiết khấu
public class PremiumCustomer : Customer
{
    public decimal DiscountRate => 0.15m;
}

Triệu chứng: lớp con chỉ thêm một hai thuộc tính; hoặc tên lớp con là một trạng thái chứ không phải một loại.

Hậu quả: khách hàng thường nâng hạng lên premium thì làm sao? Bạn không đổi được kiểu của một object đang tồn tại. Phải tạo object mới và cập nhật mọi tham chiếu.

Cách sửa — trạng thái là dữ liệu, không phải kiểu:

public class Customer
{
    public CustomerTier Tier { get; private set; }
    public void Upgrade(CustomerTier tier) => Tier = tier;
}

public class DiscountPolicy
{
    public decimal GetRate(Customer c) => c.Tier switch
    {
        CustomerTier.Premium => 0.15m,
        CustomerTier.Gold    => 0.10m,
        _                    => 0m
    };
}

Quy tắc: nếu một object có thể chuyển từ loại này sang loại kia trong đời nó, thì đó là trạng thái chứ không phải kiểu.

4.10.4 — Phụ thuộc thẳng vào lớp cài đặt​

// SAI
public class OrderService
{
    private readonly SqlCustomerRepository _repo = new();
}

Triệu chứng: new một lớp hạ tầng ngay trong class nghiệp vụ.

Hậu quả: không test được nếu không có database thật; đổi ORM phải sửa tầng nghiệp vụ; và class tự quyết vòng đời của phụ thuộc thay vì để DI container lo.

Cách sửa: nhận qua constructor, khai báo bằng interface — chi tiết ở bài 4.5 và Module 7.

4.10.5 — Anemic model​

// SAI — class chỉ là túi dữ liệu, quy tắc nằm rải rác ngoài kia
public class Order
{
    public decimal Total { get; set; }
    public OrderStatus Status { get; set; }
}

// Ở service A
if (order.Status == OrderStatus.Draft) order.Status = OrderStatus.Confirmed;
// Ở service B — quên kiểm tra
order.Status = OrderStatus.Confirmed;

Triệu chứng: entity nghiệp vụ không có phương thức nào ngoài property.

Hậu quả: cùng một quy tắc được cài đặt ở nhiều chỗ, và chỉ cần một chỗ quên là dữ liệu sai.

Cách sửa: đưa hành vi vào entity — xem bài 4.3. Lưu ý DTO thì nên anemic; vấn đề chỉ nằm ở entity nghiệp vụ.

4.10.6 — Trả về null thay vì nói rõ​

// Mơ hồ — null nghĩa là "không tìm thấy" hay "lỗi" hay "chưa có dữ liệu"?
public Customer? Find(int id) => _db.Customers.Find(id);

Triệu chứng: chuỗi if (x != null) lan khắp nơi; NullReferenceException lúc chạy.

Cách sửa, chọn theo ngữ nghĩa:

// 1. Không tìm thấy là BÌNH THƯỜNG -> mẫu TryXxx
public bool TryFind(int id, out Customer customer)

// 2. Không tìm thấy là BẤT THƯỜNG -> ném ngoại lệ
public Customer GetById(int id) =>
    _db.Customers.Find(id) ?? throw new NotFoundException($"Khách hàng {id}");

// 3. Danh sách rỗng -> trả collection rỗng, KHÔNG BAO GIỜ trả null
public IReadOnlyList<Order> GetOrders(int customerId) =>
    _db.Orders.Where(...).ToList();      // rỗng vẫn là một danh sách hợp lệ

Trường hợp 3 là quy tắc tuyệt đối: phương thức trả về collection không bao giờ trả null. Người gọi phải foreach được mà không cần kiểm tra trước.

4.10.7 — Ngoại lệ dùng cho luồng thông thường​

// SAI — người dùng gõ sai ngày là chuyện bình thường
try { date = DateTime.Parse(input); }
catch (FormatException) { date = DateTime.Today; }

Triệu chứng: try/catch bên trong vòng lặp; bắt FormatException hay KeyNotFoundException như một phần của logic.

Hậu quả: ném ngoại lệ tốn kém hơn trả về bool rất nhiều lần vì phải dựng stack trace. Trong vòng lặp hàng nghìn lần, đây là lỗi hiệu năng thật.

// ĐÚNG
if (!DateTime.TryParse(input, out var date))
    date = DateTime.Today;

Tiêu chí: thất bại này có bình thường không? Bình thường thì dùng TryXxx; bất thường thì mới ném.

4.10.8 — So sánh chuỗi không nêu rõ cách so sánh​

Đây là lỗi tinh vi nhất trong danh sách, và nó có lịch sử làm hỏng hệ thống thật.

// RỦI RO — phụ thuộc văn hoá của máy đang chạy
if (role.ToUpper() == "ADMIN") { }
if (string.Compare(a, b) == 0) { }

Trong văn hoá Thổ Nhĩ Kỳ, "i".ToUpper() cho ra "İ" (chữ I có dấu chấm) chứ không phải "I". Nên "admin".ToUpper() == "ADMIN" trả về false trên máy đặt tr-TR. Đây là lỗi kinh điển tới mức có tên riêng: Turkish I problem.

// ĐÚNG — nêu rõ ý định
if (string.Equals(role, "admin", StringComparison.OrdinalIgnoreCase)) { }

Chọn kiểu so sánh:

KiểuDùng cho
OrdinalMã, định danh, khoá, đường dẫn, tên file
OrdinalIgnoreCaseNhư trên, không phân biệt hoa thường
CurrentCultureChuỗi hiển thị cho người dùng, khi sắp xếp
InvariantCultureRất hiếm; hầu như luôn có lựa chọn tốt hơn

Quy tắc: mọi so sánh chuỗi mang tính kỹ thuật đều dùng Ordinal. Chỉ dùng so sánh theo văn hoá khi thật sự đang sắp xếp danh sách cho người đọc.

Chuyện tương tự xảy ra với định dạng số và ngày: decimal.Parse("1,5") cho kết quả khác nhau giữa vi-VN và en-US. Với dữ liệu máy đọc, luôn dùng CultureInfo.InvariantCulture.

4.10.9 — Rà lại code của bạn​

Danh sách rà soát lỗi thường gặp

  • •Không có field public nào; chỉ có property.
  • •Không có class nào tên Manager, Helper hay Util mà dài quá 300 dòng.
  • •Không có constructor nào nhận quá 5 phụ thuộc.
  • •Không kế thừa chỉ để dùng lại code; trạng thái được mô hình hoá bằng dữ liệu.
  • •Không new lớp hạ tầng bên trong class nghiệp vụ.
  • •Entity nghiệp vụ có phương thức mang nghĩa nghiệp vụ.
  • •Phương thức trả về collection không bao giờ trả null.
  • •Không dùng try/catch cho luồng chạy thông thường.
  • •Mọi so sánh chuỗi kỹ thuật đều nêu rõ StringComparison.Ordinal.
  • •Parse số và ngày từ dữ liệu máy đều dùng InvariantCulture.

Bài tập áp dụng​

  1. Tái hiện Turkish I. Viết một đoạn code so sánh "admin".ToUpper() == "ADMIN", đặt CultureInfo.CurrentCulture = new CultureInfo("tr-TR") trước đó. Ghi lại kết quả. Sửa bằng StringComparison.OrdinalIgnoreCase và chạy lại.

  2. Săn god class. Liệt kê năm file dài nhất trong dự án. Với mỗi file, trả lời câu hỏi "ai yêu cầu thay đổi class này". Nếu có nhiều hơn một nhóm người, phác thảo cách tách.

  3. Đo giá của ngoại lệ. Viết vòng lặp 100.000 lần parse chuỗi sai định dạng, một lần dùng try/catch với Parse, một lần dùng TryParse. Đo bằng Stopwatch và ghi lại tỉ lệ.

Tự kiểm tra​

Câu hỏi thường gặp

Vì sao đổi field public thành property lại là thay đổi phá vỡ?

Vì field và property được truy cập bằng chỉ thị IL khác nhau. Mọi assembly đã biên dịch dựa trên field sẽ không chạy được với phiên bản mới dùng property, mà phải build lại. Với mã nguồn trong cùng solution thì không thấy vấn đề, nhưng với thư viện phát hành ra ngoài thì đó là thay đổi phá vỡ tương thích nhị phân.

Nhận biết god class bằng cách nào?

Ba triệu chứng: file dài hơn khoảng năm trăm dòng, constructor nhận từ bảy phụ thuộc trở lên, và tên class chứa Manager, Helper, Util hay Processor. Phép thử dứt khoát là hỏi ai yêu cầu thay đổi class này — nếu có nhiều hơn một nhóm người thì nên tách.

Khi nào kế thừa là sai cách mô hình hoá?

Khi lớp con đại diện cho một trạng thái chứ không phải một loại. Nếu một object có thể chuyển từ loại này sang loại kia trong đời nó — khách thường nâng hạng lên premium — thì đó là trạng thái, vì bạn không đổi được kiểu của một object đang tồn tại. Hãy mô hình hoá bằng một thuộc tính dữ liệu.

Phương thức trả về collection có được trả null không?

Không bao giờ. Danh sách rỗng vẫn là một danh sách hợp lệ, và người gọi phải foreach được mà không cần kiểm tra trước. Trả null buộc mọi chỗ gọi thêm một nhánh kiểm tra, và chỉ cần quên một chỗ là NullReferenceException.

Vì sao không nên dùng ngoại lệ cho luồng thông thường?

Vì ném ngoại lệ tốn kém hơn trả về bool rất nhiều lần do phải dựng stack trace. Trong một vòng lặp chạy hàng nghìn lần, đó là lỗi hiệu năng thật. Tiêu chí quyết định là hỏi thất bại này có bình thường không: người dùng gõ sai định dạng là bình thường nên dùng TryParse.

Turkish I problem là gì?

Trong văn hoá Thổ Nhĩ Kỳ, chữ i viết hoa thành I có dấu chấm chứ không phải I thường. Nên so sánh kiểu role.ToUpper() bằng ADMIN trả về false trên máy đặt tr-TR, làm hỏng phần phân quyền. Cách tránh là luôn nêu rõ StringComparison.Ordinal hoặc OrdinalIgnoreCase cho mọi so sánh chuỗi mang tính kỹ thuật.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Không lỗi nào ở trên gây exception lúc viết. Chúng chỉ làm code khó đổi dần — đó là lý do chúng sống sót lâu.
  2. Trạng thái không phải kiểu. Nếu object đổi loại được trong đời nó, hãy dùng dữ liệu chứ đừng dùng kế thừa.
  3. Mọi so sánh chuỗi kỹ thuật đều nêu rõ Ordinal. Mặc định phụ thuộc văn hoá là một quả mìn theo khu vực người dùng.
