4.11 — Mở rộng và đào sâu

Tóm tắt

Những tính năng C# nối tiếp Module 4, xếp theo mức độ nên dùng. Ba thứ đáng áp dụng ngay: required (trình biên dịch buộc gán thuộc tính bắt buộc — loại bỏ cả một nhóm lỗi null khi tạo đối tượng), primary constructor (bỏ được đoạn gán tham số lặp đi lặp lại), và collection expression ([] thay cho new List<T>()). Một thứ cần cẩn thận: IDisposable — không phải vì nó khó, mà vì quên using là rò rỉ tài nguyên không có thông báo lỗi nào, và trong một ứng dụng web nó biểu hiện thành cạn connection pool sau vài giờ chạy.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Dùng required và primary constructor để viết gọn hơn.
  • Cài đặt IDisposable đúng cách và biết khi nào cần.
  • Biết static abstract member giải quyết vấn đề gì.
  • Chọn cú pháp hiện đại phù hợp với dự án.

Nội dung bài học​

4.11.1 — required members: dùng ngay​

// Trước — không có gì buộc phải gán Name
public class Lead
{
    public string Name { get; set; }        // cảnh báo: có thể null
    public string Email { get; set; }
}

var lead = new Lead();                       // biên dịch được, Name là null
// Sau — trình biên dịch BUỘC phải gán
public class Lead
{
    public required string Name { get; init; }
    public required string Email { get; init; }
    public string? Phone { get; init; }      // tuy chon, ro rang
}

var lead = new Lead();                       // LOI BIEN DICH
var lead = new Lead { Name = "An", Email = "an@x.com" };   // OK

Lợi ích cụ thể: nó loại bỏ cả một nhóm lỗi NullReferenceException ở tầng biên dịch, thay vì chờ tới lúc chạy. Và nó làm rõ ý định: đọc lớp là biết ngay trường nào bắt buộc.

Kết hợp với init cho đối tượng chỉ đọc sau khi tạo — đúng với hầu hết DTO và tham số cấu hình.

4.11.2 — Primary constructor: dùng ngay​

// Trước — ba lần lặp lại mỗi tên
public class LeadService
{
    private readonly ILeadRepository _repository;
    private readonly ILogger<LeadService> _logger;

    public LeadService(ILeadRepository repository, ILogger<LeadService> logger)
    {
        _repository = repository;
        _logger = logger;
    }
}

// Sau — mot dong
public class LeadService(ILeadRepository repository, ILogger<LeadService> logger)
{
    public async Task<Lead?> GetAsync(LeadId id, CancellationToken ct)
        => await repository.GetByIdAsync(id, ct);
}

Tham số dùng được trực tiếp trong mọi phương thức. Rất hợp với DI, nơi lớp nào cũng có vài dependency (Module 7).

Lưu ý: tham số primary constructor không tự động là readonly như trường được gán trong constructor thường. Nếu cần chắc chắn không đổi, vẫn gán vào trường readonly:

public class LeadService(ILeadRepository repository)
{
    private readonly ILeadRepository _repository = repository;
}

Với record, primary constructor sinh luôn thuộc tính public — khác với class, nơi tham số chỉ nằm trong phạm vi lớp.

4.11.3 — Collection expression: dùng ngay​

// Trước
List<string> names = new List<string> { "An", "Bình" };
int[] numbers = new int[] { 1, 2, 3 };
private readonly List<Activity> _activities = new();

// Sau — cú pháp thống nhất cho mọi kiểu collection
List<string> names = ["An", "Bình"];
int[] numbers = [1, 2, 3];
private readonly List<Activity> _activities = [];

// Ghép bằng spread
int[] all = [..numbers, 4, 5];

Ngắn hơn và — quan trọng hơn — thống nhất cho List, mảng, Span và ImmutableArray. Trước đây mỗi kiểu có cú pháp khởi tạo riêng.

4.11.4 — IDisposable: cẩn thận​

Cần khi lớp giữ tài nguyên mà garbage collector không tự dọn: file handle, kết nối mạng, kết nối database, HttpClient tạo thủ công.

public sealed class ExcelExporter : IDisposable
{
    private readonly FileStream _stream;
    private bool _disposed;

    public ExcelExporter(string path) => _stream = File.Create(path);

    public void Dispose()
    {
        if (_disposed) return;               // an toàn khi gọi nhiều lần
        _stream.Dispose();
        _disposed = true;
    }
}

// Sử dụng — using đảm bảo Dispose được gọi KỂ CẢ khi có exception
using var exporter = new ExcelExporter("revenue-report.xlsx");
exporter.Export(data);
// Dispose tự động gọi ở cuối phạm vi

Vì sao quên using nguy hiểm: không có lỗi nào được báo. Chương trình chạy bình thường, chỉ là tài nguyên không được trả lại. Trong ứng dụng web, biểu hiện là sau vài giờ chạy, mọi request bắt đầu timeout vì connection pool đã cạn — và nguyên nhân rất khó lần ra từ triệu chứng đó.

Bản bất đồng bộ cho tài nguyên có thao tác đóng tốn thời gian:

public sealed class Repository : IAsyncDisposable
{
    public async ValueTask DisposeAsync() => await _connection.DisposeAsync();
}

await using var repo = new Repository();

Khi nào KHÔNG cần: lớp chỉ chứa dữ liệu và object thường. Garbage collector lo được. Cài IDisposable cho lớp không giữ tài nguyên gì là thêm việc vô ích cho người dùng lớp đó.

Và trong ASP.NET Core, đừng tự new HttpClient — dùng IHttpClientFactory, nó quản lý vòng đời kết nối đúng cách (bài 7.6).

4.11.5 — Static abstract interface member​

Ưu tiên thấp — hữu ích cho thư viện, ít dùng trong code nghiệp vụ.

public interface IParsable<TSelf> where TSelf : IParsable<TSelf>
{
    static abstract TSelf Parse(string s);
}

public readonly record struct LeadId(Guid Value) : IParsable<LeadId>
{
    public static LeadId Parse(string s) => new(Guid.Parse(s));
}

// Giờ gọi được phương thức tĩnh qua generic
T ParseFrom<T>(string s) where T : IParsable<T> => T.Parse(s);

Trước .NET 7, không có cách nào ràng buộc "kiểu này phải có phương thức tĩnh tên Parse". Tính năng này làm được, và nó là nền tảng cho generic math trong .NET.

Trong code CRM thông thường bạn hiếm khi cần — nhưng biết nó tồn tại giúp đọc hiểu code thư viện hiện đại.

4.11.6 — Những tính năng khác​

Tính năngViệc làmƯu tiên

// Raw string — rất tiện cho SQL và JSON
var sql = """
    SELECT Id, Name, Email
    FROM Leads
    WHERE TenantId = @tenantId
      AND Status <> 'Lost'
    """;

// nameof — đổi tên thuộc tính thì chuỗi tự đổi theo
throw new ArgumentNullException(nameof(request));

nameof đáng dùng ở mọi nơi cần tên thành viên dưới dạng chuỗi: nếu ai đó đổi tên bằng refactor của IDE, chuỗi tự đổi theo — còn chuỗi viết tay thì lặng lẽ sai.

sealed nên là mặc định cho lớp không thiết kế để kế thừa: nó thể hiện ý định rõ ràng và cho JIT tối ưu lời gọi phương thức ảo.

4.11.8 — Rà lại code của bạn​

Danh sách rà soát C# hiện đại

  • •Thuộc tính bắt buộc dùng required thay vì để trình biên dịch cảnh báo.
  • •Lớp có dependency dùng primary constructor.
  • •Chuỗi tên thành viên dùng nameof, không viết tay.
  • •Lớp không thiết kế để kế thừa được đánh dấu sealed.
  • •Mọi đối tượng IDisposable đều được dùng trong using.
  • •Không tự new HttpClient, dùng IHttpClientFactory.
  • •Không cài IDisposable cho lớp không giữ tài nguyên.
  • •SQL và JSON nhiều dòng dùng raw string literal.

Bài tập áp dụng​

  1. Áp dụng required. Chọn một DTO trong dự án, thêm required cho trường bắt buộc và xem trình biên dịch bắt được bao nhiêu chỗ tạo thiếu.

  2. Rút gọn constructor. Chuyển ba lớp service sang primary constructor và đếm số dòng giảm được.

  3. Tìm IDisposable bị quên. Rà dự án tìm mọi chỗ tạo đối tượng IDisposable mà không có using.

Tự kiểm tra​

Câu hỏi thường gặp

required giải quyết vấn đề gì?

Nó buộc người tạo đối tượng phải gán thuộc tính bắt buộc, và lỗi được bắt ở tầng biên dịch thay vì chờ tới lúc chạy. Nó cũng làm rõ ý định: đọc lớp là biết ngay trường nào bắt buộc.

Tham số primary constructor có phải readonly không?

Không tự động. Khác với trường được gán trong constructor thường, nó có thể bị gán lại trong lớp. Nếu cần chắc chắn không đổi thì vẫn gán vào một trường readonly.

Vì sao quên using với IDisposable lại nguy hiểm?

Vì không có lỗi nào được báo. Chương trình chạy bình thường, chỉ là tài nguyên không được trả lại. Trong ứng dụng web, sau vài giờ mọi request bắt đầu timeout vì connection pool cạn, và rất khó lần ra nguyên nhân từ triệu chứng đó.

Khi nào không cần cài IDisposable?

Khi lớp chỉ chứa dữ liệu và object thường, vì garbage collector lo được. Cài nó cho lớp không giữ tài nguyên là thêm việc vô ích cho mọi người dùng lớp đó.

Vì sao nên dùng nameof thay vì chuỗi viết tay?

Vì khi ai đó đổi tên thành viên bằng refactor của IDE, nameof tự đổi theo, còn chuỗi viết tay thì lặng lẽ sai và không có gì cảnh báo.

Static abstract interface member giải quyết vấn đề gì?

Trước .NET 7 không có cách ràng buộc rằng một kiểu phải có phương thức tĩnh nhất định. Tính năng này cho phép gọi phương thức tĩnh qua generic, và là nền tảng cho generic math trong .NET.

Kết luận​

Ba điều đáng nhớ nhất:

  1. required và primary constructor rẻ và lợi ích rõ ngay — dùng từ hôm nay.
  2. Quên using là rò rỉ tài nguyên không có thông báo lỗi nào.
  3. nameof ở mọi nơi cần tên thành viên — chuỗi viết tay sẽ lặng lẽ sai khi refactor.
