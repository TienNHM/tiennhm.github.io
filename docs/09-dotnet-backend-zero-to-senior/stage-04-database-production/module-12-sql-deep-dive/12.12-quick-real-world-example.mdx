# 12.12 — Ví dụ thực tế nhanh

<SummaryBox>
Một tình huống gây bối rối: index **có tồn tại**, cột lọc **đúng là cột đã đánh index**, nhưng execution plan vẫn cho thấy **table scan**. Nguyên nhân nằm ở một nguyên tắc duy nhất mà nhiều người không biết: index chỉ dùng được khi cột được so sánh **trực tiếp**, ở dạng **nguyên bản** của nó. Bọc cột trong một hàm, ép kiểu ngầm, hay đặt wildcard ở đầu chuỗi — tất cả đều khiến database không còn cách nào dùng cấu trúc đã sắp xếp của index. Bài này liệt kê **năm cách** vô hiệu hoá index vô tình, kèm cách viết lại cho từng cái, và cách kiểm chứng bằng `logical reads`.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra năm cách vô hiệu hoá index vô tình.
- Viết lại truy vấn để index dùng được.
- Kiểm chứng bằng `logical reads` thay vì cảm giác.
- Hiểu vì sao ép kiểu ngầm nguy hiểm nhất.

## Nội dung bài học

### 12.12.1 — Nguyên tắc chung

```
Index la mot cau truc DA SAP XEP theo gia tri cot.
Database dung duoc no khi biet phai TIM O DAU.

Neu cot bi BOC trong mot ham, database KHONG biet ket qua ham
se roi vao vi tri nao trong index -> phai tinh ham cho MOI HANG
-> quet toan bang.
```

Nguyên tắc: **cột phải đứng một mình ở một vế của phép so sánh**, ở dạng nguyên bản.

### 12.12.2 — Cách 1: bọc cột trong hàm

```sql
-- KHONG dung index tren CreatedAt
SELECT * FROM Leads WHERE YEAR(CreatedAt) = 2026;
SELECT * FROM Leads WHERE CAST(CreatedAt AS DATE) = '2026-09-24';
SELECT * FROM Leads WHERE UPPER(Email) = 'AN@COMPANY.COM';

-- DUNG index
SELECT * FROM Leads WHERE CreatedAt >= '2026-01-01' AND CreatedAt < '2027-01-01';
SELECT * FROM Leads WHERE CreatedAt >= '2026-09-24' AND CreatedAt < '2026-09-25';
SELECT * FROM Leads WHERE Email = 'an@company.com';   -- collation thuong khong phan biet hoa thuong
```

Mẫu chung để viết lại: đổi từ "hàm của cột bằng giá trị" sang **khoảng giá trị** trên chính cột đó.

Với ngày tháng, dùng `>= đầu khoảng AND < đầu khoảng tiếp theo` — tránh `BETWEEN` với thời gian vì nó bao gồm cả mốc cuối, dễ sai khi cột có phần giờ phút.

### 12.12.3 — Cách 2: ép kiểu ngầm (nguy hiểm nhất)

```sql
-- Cot MaKhachHang la VARCHAR(20), tham so la NVARCHAR
SELECT * FROM Customers WHERE MaKhachHang = N'KH001';
```

Đây là cách **khó phát hiện nhất** vì truy vấn trông hoàn toàn bình thường. Nhưng execution plan cho thấy:

```
|--Index Scan(OBJECT:([IX_Customers_Ma]),
              WHERE:(CONVERT_IMPLICIT(nvarchar(20),[MaKhachHang])=[@1]))
```

`CONVERT_IMPLICIT` áp lên **cột**, không phải lên tham số — nên nó chính là "bọc cột trong hàm" ở dạng ẩn.

Lý do SQL Server chuyển cột thay vì chuyển tham số: `NVARCHAR` có **độ ưu tiên kiểu cao hơn** `VARCHAR`, nên theo quy tắc chuyển kiểu, vế còn lại phải được nâng lên.

Trong .NET, đây là nguyên nhân rất phổ biến vì `string` của C# ánh xạ mặc định sang `NVARCHAR`:

```csharp
// EF Core sinh tham so NVARCHAR — neu cot la VARCHAR thi ep kieu ngam
var kh = await _db.Customers.FirstOrDefaultAsync(c => c.MaKhachHang == ma, ct);
```

```csharp
// Sua: khai bao dung kieu cot
b.Property(c => c.MaKhachHang).HasColumnType("varchar(20)");
```

**Cách phát hiện:** tìm `CONVERT_IMPLICIT` trong execution plan. Mỗi lần thấy nó áp lên một cột là một index bị vô hiệu hoá.

### 12.12.4 — Cách 3: wildcard ở đầu chuỗi

```sql
-- KHONG dung index — khong biet bat dau tim tu dau
SELECT * FROM Leads WHERE Name LIKE '%nguyen%';

-- DUNG index — biet tien to
SELECT * FROM Leads WHERE Name LIKE 'nguyen%';
```

Index sắp xếp theo thứ tự chuỗi, nên biết tiền tố là biết bắt đầu tìm ở đâu. Không biết phần đầu thì không có cách nào thu hẹp.

Khi nghiệp vụ **bắt buộc** tìm giữa chuỗi, có ba lựa chọn: full-text index của database, một search engine riêng, hoặc chấp nhận quét nếu bảng nhỏ ([bài 19.10](../../stage-05-senior-engineering/module-19-performance-engineering/19.10-crm-context.mdx)).

### 12.12.5 — Cách 4: OR giữa các cột khác nhau

```sql
-- Kho dung index — moi nhanh can index khac nhau
SELECT * FROM Leads WHERE Email = 'a@b.com' OR Phone = '0901234567';

-- Viet lai bang UNION — moi nhanh dung index rieng
SELECT * FROM Leads WHERE Email = 'a@b.com'
UNION
SELECT * FROM Leads WHERE Phone = '0901234567';
```

Với `OR`, database thường phải quét vì không có index nào phủ cả hai điều kiện. `UNION` cho phép mỗi nhánh dùng index của riêng nó.

Dùng `UNION` (loại trùng) hay `UNION ALL` (giữ trùng) tuỳ nghiệp vụ — `UNION ALL` nhanh hơn nhưng có thể trả bản ghi hai lần nếu nó khớp cả hai điều kiện.

**Lưu ý:** `OR` trên **cùng một cột** thì không sao, database xử lý được:

```sql
-- On — cung mot cot
SELECT * FROM Leads WHERE Status = 'New' OR Status = 'Contacted';
SELECT * FROM Leads WHERE Status IN ('New', 'Contacted');      -- tuong duong
```

### 12.12.6 — Cách 5: thứ tự cột sai trong index ghép

```sql
CREATE INDEX IX_Leads_Tenant_Status ON Leads (TenantId, Status);
```

```sql
-- DUNG duoc index — co TenantId (cot dau)
SELECT * FROM Leads WHERE TenantId = 'acme';
SELECT * FROM Leads WHERE TenantId = 'acme' AND Status = 'New';

-- KHONG dung duoc — thieu cot dau
SELECT * FROM Leads WHERE Status = 'New';
```

Index ghép giống **danh bạ sắp theo họ rồi tên**: tìm được "mọi người họ Nguyễn" và "Nguyễn Văn An", nhưng không tìm nhanh được "mọi người tên An" vì danh bạ không sắp theo tên.

Nguyên tắc **leftmost prefix**: index `(A, B, C)` dùng được cho truy vấn lọc theo `A`, `(A, B)`, hoặc `(A, B, C)` — nhưng không dùng được cho truy vấn chỉ lọc theo `B` hay `C`.

Hệ quả thực tế: thứ tự cột trong index là **quyết định thiết kế**, không phải chuyện tuỳ ý. Đặt cột được lọc bằng `=` lên trước, cột dùng để sắp xếp sau ([bài 12.5](12.5-indexing.mdx)).

### 12.12.7 — Kiểm chứng bằng logical reads

Đừng đoán — đo.

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Leads WHERE YEAR(CreatedAt) = 2026;
-- Table 'Leads'. Scan count 1, logical reads 48291     <- QUET

SELECT * FROM Leads WHERE CreatedAt >= '2026-01-01' AND CreatedAt < '2027-01-01';
-- Table 'Leads'. Scan count 1, logical reads 412       <- SEEK
```

`logical reads` là số trang dữ liệu database phải đọc — chỉ số khách quan nhất, vì nó **không phụ thuộc** vào cache hay tải hiện tại của máy. Hai lần chạy cùng truy vấn luôn cho cùng con số, khác với thời gian thực thi.

Với EF Core, xem SQL sinh ra trước:

```csharp
var sql = _db.Leads.Where(l => l.CreatedAt.Year == 2026).ToQueryString();
// SELECT ... WHERE DATEPART(year, [l].[CreatedAt]) = 2026     <- ham tren cot!
```

```csharp
// Viet lai
var dau = new DateTime(2026, 1, 1);
var cuoi = new DateTime(2027, 1, 1);
var leads = await _db.Leads.Where(l => l.CreatedAt >= dau && l.CreatedAt < cuoi).ToListAsync(ct);
```

`ToQueryString()` là công cụ nhanh nhất để thấy EF Core đã dịch LINQ của bạn thành gì — nhiều biểu thức trông vô hại lại sinh ra hàm trên cột.

## Bài tập áp dụng

1. **Đo năm cách.** Với mỗi cách ở trên, chạy bản sai và bản đúng rồi so sánh `logical reads`.

2. **Tìm ép kiểu ngầm.** Tạo một cột `VARCHAR`, truy vấn bằng tham số `NVARCHAR`, và tìm `CONVERT_IMPLICIT` trong plan.

3. **Kiểm tra EF Core.** Chạy `ToQueryString()` trên 5 truy vấn phức tạp nhất trong dự án và tìm hàm áp lên cột.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Cột phải đứng một mình ở một vế của phép so sánh** để index dùng được.
2. **Ép kiểu ngầm là cách vô hiệu hoá index khó thấy nhất** — tìm `CONVERT_IMPLICIT`.
3. **Đo bằng `logical reads`**, và xem SQL sinh ra bằng `ToQueryString()`.
