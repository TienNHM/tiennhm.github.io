# 13.7 — 6. N+1 Problem

<SummaryBox>
N+1 là một truy vấn để lấy danh sách, rồi **một truy vấn nữa cho mỗi phần tử**. Với 200 khách hàng, đó là **201 lần đi về database** — và mỗi lần mất 2ms thì tổng là 400ms, gần như toàn bộ là độ trễ mạng chứ không phải công việc thật. Dạng rõ ràng (vòng lặp gọi `await`) dễ thấy, nhưng ba dạng **khó thấy** mới là thứ lọt vào production: **AutoMapper** truy cập navigation property khi map, **JSON serializer** truy cập chúng khi serialize entity, và **lazy loading** khiến mọi truy cập thuộc tính âm thầm sinh truy vấn. Cách phòng vệ tốt nhất không phải là cẩn thận — mà là **một bài test đếm số truy vấn**.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra N+1 trong log SQL.
- Tìm các dạng N+1 không nhìn thấy trong code.
- Sửa bằng `Include`, projection, hoặc nạp theo lô.
- Viết test tự động phát hiện N+1.
- Bật cảnh báo của EF Core cho truy vấn nguy hiểm.

## Nội dung bài học

### 13.7.1 — Dạng rõ ràng

```csharp
var customers = await db.Customers.ToListAsync(ct);          // 1 truy van

foreach (var c in customers)
{
    var count = await db.Contacts.CountAsync(x => x.CustomerId == c.Id, ct);   // N
    Console.WriteLine($"{c.Name}: {count}");
}
```

```sql
SELECT * FROM Customers;                                 -- 1
SELECT COUNT(*) FROM Contacts WHERE CustomerId = 1;      -- 2
SELECT COUNT(*) FROM Contacts WHERE CustomerId = 2;      -- 3
...                                                      -- 201
```

**Dấu hiệu trong log:** nhiều truy vấn **giống hệt nhau, chỉ khác tham số**.

Điều khiến nó nguy hiểm là **nó không chậm trên máy dev**: với 10 bản ghi thử nghiệm, 11 truy vấn mất 20ms và không ai để ý. Với 2.000 bản ghi production, đó là 4 giây.

### 13.7.2 — Ba dạng khó thấy

**1. AutoMapper**

```csharp
var customers = await db.Customers.ToListAsync(ct);      // KHÔNG Include

var dtos = mapper.Map<List<CustomerDto>>(customers);     // N+1 O DAY
```

Nếu `CustomerDto` có `ContactCount` hoặc `List<ContactDto>`, AutoMapper **truy cập `customer.Contacts`** — và với lazy loading bật, mỗi lần truy cập là một truy vấn. Không có lazy loading thì tệ hơn theo cách khác: collection rỗng và DTO **sai dữ liệu** mà không báo lỗi.

```csharp
// SUA — ProjectTo dich thang sang SQL
var dtos = await db.Customers
    .ProjectTo<CustomerDto>(mapper.ConfigurationProvider)
    .ToListAsync(ct);
```

`ProjectTo` sinh ra `Select` tương ứng với cấu hình map, nên nó thành **một** truy vấn lấy đúng cột cần. Đây là lý do chính để dùng AutoMapper với EF Core thay vì map thủ công sau khi nạp.

**2. JSON serializer**

```csharp
[HttpGet]
public async Task<IActionResult> GetAll(CancellationToken ct)
    => Ok(await db.Customers.ToListAsync(ct));     // tra ENTITY truc tiep
```

Khi ASP.NET Core serialize, nó đọc **mọi** thuộc tính công khai — kể cả navigation. Với lazy loading, đó là N truy vấn xảy ra **trong lúc ghi response**, sau khi action đã trả về. Lỗi lúc đó không bắt được bởi exception handler ([bài 8.9](../../stage-03-aspnet-core-backend/module-08-aspnet-core-fundamentals/8.8-global-exception-handling.mdx)).

Trả entity trực tiếp còn hai vấn đề khác: lộ cột nội bộ, và vòng lặp tham chiếu (`Customer` → `Contacts` → `Customer`). **Luôn trả DTO.**

**3. Lazy loading**

```csharp
options.UseLazyLoadingProxies();     // TRANH
```

Nó biến **mọi** truy cập navigation thành một truy vấn tiềm năng. Đoạn code gây N+1 trông hoàn toàn vô hại:

```csharp
foreach (var c in customers)
    total += c.Contacts.Count;       // mot truy van moi vong lap
```

Không có gì trong dòng đó gợi ý rằng nó chạm database.

### 13.7.3 — Bốn cách sửa

```csharp
// 1. Include — khi can ca entity con
var customers = await db.Customers
    .Include(c => c.Contacts)
    .AsNoTracking()
    .ToListAsync(ct);

// 2. Projection — TỐT NHẤT khi chỉ cần vài trường
var dtos = await db.Customers
    .Select(c => new CustomerDto(c.Id, c.Name, c.Contacts.Count()))
    .ToListAsync(ct);

// 3. Nạp theo lô — khi không ghép truy vấn được
var ids = customers.Select(c => c.Id).ToList();
var contactsByCustomer = await db.Contacts
    .Where(ct2 => ids.Contains(ct2.CustomerId))
    .GroupBy(ct2 => ct2.CustomerId)
    .ToDictionaryAsync(g => g.Key, g => g.ToList(), ct);

// 4. Mot truy van JOIN thu cong
var rows = await (from c in db.Customers
                  join ct2 in db.Contacts on c.Id equals ct2.CustomerId into g
                  select new { c.Id, c.Name, Contacts = g.ToList() })
                 .ToListAsync(ct);
```

Cách 3 đáng chú ý: nó biến N+1 thành **2 truy vấn** khi dữ liệu đến từ nhiều nguồn không ghép được — ví dụ danh sách khách hàng từ database và thông tin bổ sung từ một service khác.

Lưu ý với `Contains` trên danh sách lớn: SQL Server có giới hạn **2.100 tham số**, nên `ids` quá lớn sẽ ném lỗi. EF Core 8 dùng `OPENJSON` nên hết giới hạn này, nhưng vẫn nên chia lô với danh sách rất lớn.

### 13.7.4 — Phát hiện tự động

**Cảnh báo tích hợp của EF Core:**

```csharp
options.ConfigureWarnings(w =>
{
    w.Throw(CoreEventId.NavigationLazyLoading);          // nem khi lazy load
    w.Throw(RelationalEventId.MultipleCollectionIncludeWarning);
});
```

`NavigationLazyLoading` biến mọi lazy load thành **exception** — cách chắc chắn nhất để N+1 không lọt qua, nếu bạn lỡ bật lazy loading proxies.

**Test đếm truy vấn** là biện pháp mạnh nhất:

```csharp
public sealed class QueryCountingInterceptor : DbCommandInterceptor
{
    public int Count { get; private set; }
    public void Reset() => Count = 0;

    public override ValueTask<InterceptionResult<DbDataReader>> ReaderExecutingAsync(
        DbCommand command, CommandEventData eventData,
        InterceptionResult<DbDataReader> result, CancellationToken ct = default)
    {
        Count++;
        return base.ReaderExecutingAsync(command, eventData, result, ct);
    }
}
```

```csharp
[Fact]
public async Task GetCustomerList_ShouldNotCauseNPlusOne()
{
    await SeedCustomersAsync(count: 50, contactsEach: 5);
    _queryCounter.Reset();

    var result = await _service.GetCustomerListAsync(CancellationToken.None);

    Assert.Equal(50, result.Count);
    Assert.True(_queryCounter.Count <= 2,
        $"Expected at most 2 queries, got {_queryCounter.Count}");
}
```

Bài test này bắt được **mọi** dạng N+1, kể cả những dạng khó thấy ở mục trên — vì nó đo **hành vi**, không đọc code. Và nó chặn hồi quy: ai đó thêm một trường vào DTO khiến truy vấn nhân lên sẽ làm test đỏ.

Đặt một test như vậy cho mỗi endpoint danh sách quan trọng.

**Trong Development, log truy vấn kèm cảnh báo:**

```csharp
options.LogTo(
    message =>
    {
        if (message.Contains("Executed DbCommand")) _requestQueryCount++;
        Console.WriteLine(message);
    },
    [DbLoggerCategory.Database.Command.Name],
    LogLevel.Information);
```

Cộng một middleware ghi cảnh báo khi một request vượt ngưỡng truy vấn — ví dụ 10 — là cách rẻ tiền để thấy vấn đề sớm.

### 13.7.5 — N+1 ngược: nạp quá nhiều

Sửa N+1 quá tay dẫn tới vấn đề ngược:

```csharp
// Nap MOI thu de "tranh N+1"
var customers = await db.Customers
    .Include(c => c.Contacts).ThenInclude(ct2 => ct2.Notes)
    .Include(c => c.Leads).ThenInclude(l => l.Activities)
    .Include(c => c.Invoices).ThenInclude(i => i.Lines)
    .ToListAsync(ct);
```

Đây là cartesian explosion ở quy mô lớn ([bài 13.6](13.5-query-patterns.mdx)) — có thể hàng trăm nghìn dòng cho vài chục khách hàng.

Nguyên tắc cân bằng: **nạp đúng những gì màn hình cần, không hơn**. Và cách đạt được điều đó gần như luôn là **projection** — nó tự nhiên chỉ lấy những trường bạn khai trong DTO.

Với dữ liệu ít khi cần, **nạp theo yêu cầu**: danh sách trả về tóm tắt, và một endpoint riêng trả chi tiết khi người dùng mở một bản ghi.

## Bài tập áp dụng

1. **Đo N+1.** Tạo 500 khách hàng, mỗi người 5 contact. Chạy vòng lặp đếm contact và đo tổng thời gian cùng số truy vấn. Sửa bằng projection và đo lại.

2. **N+1 qua AutoMapper.** Map `List<Customer>` sang `List<CustomerDto>` có `ContactCount`, với lazy loading bật. Đếm số truy vấn. Chuyển sang `ProjectTo` và so sánh.

3. **Test đếm truy vấn.** Cài `QueryCountingInterceptor` và viết một test khẳng định endpoint danh sách không vượt 2 truy vấn. Sau đó thêm một trường vào DTO gây thêm truy vấn và xác nhận test đỏ.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Dấu hiệu N+1 là nhiều truy vấn giống hệt nhau, chỉ khác tham số.**
2. **AutoMapper và JSON serializer gây N+1 mà code không lộ ra gì.** Dùng `ProjectTo` và trả DTO.
3. **Test đếm truy vấn là biện pháp phòng vệ duy nhất đáng tin.**
