# 13.3 — 2. DbContext và Entity Configuration

<SummaryBox>
`DbContext` là **Unit of Work** — nó gom mọi thay đổi và ghi chúng trong **một transaction** khi bạn gọi `SaveChanges()`. Hai đặc tính quyết định cách dùng nó: **không thread-safe** (`Task.WhenAll` trên cùng một context là exception), và **vòng đời phải ngắn** (context sống lâu tích luỹ entity và trả dữ liệu cũ). Về cấu hình mô hình, **Fluent API mạnh hơn Data Annotations** ở mọi mặt và tách cấu hình hạ tầng khỏi entity — nhưng đừng nhồi hết vào `OnModelCreating`, hãy dùng `IEntityTypeConfiguration<T>` mỗi entity một file. Và **value converter** là công cụ bị đánh giá thấp nhất: nó cho phép domain dùng kiểu riêng mà database vẫn lưu kiểu nguyên thuỷ.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích `DbContext` là Unit of Work và hệ quả của nó.
- Tổ chức cấu hình mô hình bằng `IEntityTypeConfiguration<T>`.
- Dùng value converter cho kiểu domain.
- Dùng owned type cho value object.
- Viết interceptor cho audit thay vì override `SaveChanges`.

## Nội dung bài học

### 13.3.1 — `DbContext` là Unit of Work

```csharp
db.Customers.Add(customer);
db.Leads.Update(lead);
db.Contacts.Remove(contact);

await db.SaveChangesAsync(ct);      // MỘT transaction cho cả ba
```

EF Core tự bọc `SaveChanges` trong transaction. Cả ba thay đổi cùng thành công hoặc cùng thất bại — bạn **không cần** `BeginTransaction` cho trường hợp này.

Đây là lý do một interface `IUnitOfWork` chỉ gọi `SaveChanges` thường là lớp trung gian thừa — chi tiết ở [bài 13.10](13.9-unit-of-work-and-repository-pattern.mdx) và trong bài [Unit of Work trong .NET và ABP](/blog/unit-of-work-dotnet-abp).

Cần transaction tường minh khi bạn phải **nhiều lần** `SaveChanges` trong một đơn vị công việc:

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);

db.Customers.Add(customer);
await db.SaveChangesAsync(ct);             // can Id sinh ra

lead.ConvertedToCustomerId = customer.Id;
await db.SaveChangesAsync(ct);

await tx.CommitAsync(ct);
```

**`DbContext` không thread-safe:**

```csharp
// SAI — InvalidOperationException
var t1 = db.Customers.ToListAsync(ct);
var t2 = db.Leads.ToListAsync(ct);
await Task.WhenAll(t1, t2);
```

Đây là bẫy đã nói ở [bài 6.6](../../stage-02-csharp-professional/module-06-async-programming/6.5-task-parallel-library.mdx). Cần song song thật thì mỗi task một context từ `IDbContextFactory`.

**Vòng đời:** `Scoped` là mặc định của `AddDbContext` và gần như luôn đúng. Context sống lâu gây bốn vấn đề: bộ nhớ phình, dữ liệu cũ từ identity map, một lỗi làm hỏng toàn bộ context, và giữ connection lâu.

Ngoài request — background job, Blazor Server — dùng factory:

```csharp
builder.Services.AddDbContextFactory<CrmDbContext>(o => o.UseSqlServer(conn));

await using var db = await _factory.CreateDbContextAsync(ct);
```

### 13.3.2 — Fluent API và `IEntityTypeConfiguration`

```csharp
// SAI — mọi thứ trong một hàm
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Customer>().Property(c => c.Name).HasMaxLength(200);
    modelBuilder.Entity<Customer>().HasIndex(c => c.Email).IsUnique();
    // ... 400 dòng nữa
}
```

```csharp
// DUNG — moi entity mot file
public sealed class CustomerConfiguration : IEntityTypeConfiguration<Customer>
{
    public void Configure(EntityTypeBuilder<Customer> builder)
    {
        builder.ToTable("Customers");
        builder.HasKey(c => c.Id);

        builder.Property(c => c.Name).IsRequired().HasMaxLength(200);
        builder.Property(c => c.Email).IsRequired().HasMaxLength(256);
        builder.Property(c => c.Status).HasConversion<string>().HasMaxLength(50);
        builder.Property(c => c.RowVersion).IsRowVersion();

        builder.HasIndex(c => c.Email).IsUnique()
               .HasFilter("[IsDeleted] = 0");          // soft delete

        builder.HasIndex(c => new { c.TenantId, c.Status });

        builder.HasMany(c => c.Contacts)
               .WithOne(ct => ct.Customer)
               .HasForeignKey(ct => ct.CustomerId)
               .OnDelete(DeleteBehavior.Cascade);
    }
}
```

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
    => modelBuilder.ApplyConfigurationsFromAssembly(typeof(CrmDbContext).Assembly);
```

**Vì sao Fluent API thay vì Data Annotations:**

| | Data Annotations | Fluent API |
|---|---|---|
| Ở đâu | Trên entity | File cấu hình riêng |
| Entity phụ thuộc EF | **Có** | **Không** |
| Cấu hình quan hệ phức tạp | Hạn chế | **Đầy đủ** |
| Index có filter, khoá phức hợp | **Không** | **Có** |
| Đổi provider | Khó | Dễ |

Điểm quan trọng nhất là hàng thứ hai: với Fluent API, entity là **POCO thuần** không biết gì về EF Core — điều kiện cần cho kiến trúc mà domain không phụ thuộc hạ tầng ([Module 16](../../stage-05-senior-engineering/module-16-clean-architecture/)).

Chú ý `HasConversion<string>()` cho enum: mặc định EF lưu enum thành `int`. Lưu chuỗi khiến database **đọc được** và không vỡ khi ai đó chèn một giá trị vào giữa enum — cùng vấn đề với bitmask ở [bài 10.8](../../stage-03-aspnet-core-backend/module-10-authentication-authorization/10.7-permission-system.mdx). Đánh đổi là tốn chỗ hơn và so sánh chậm hơn chút.

### 13.3.3 — Value converter

Value converter cho phép **domain dùng kiểu riêng** trong khi database lưu kiểu nguyên thuỷ:

```csharp
// Strongly-typed ID — không thể truyền nhầm CustomerId vào chỗ LeadId
public readonly record struct CustomerId(int Value);

builder.Property(c => c.Id)
       .HasConversion(id => id.Value, value => new CustomerId(value));
```

```csharp
// Danh sach -> JSON
builder.Property(c => c.Tags)
       .HasConversion(
           v => JsonSerializer.Serialize(v, (JsonSerializerOptions?)null),
           v => JsonSerializer.Deserialize<List<string>>(v, (JsonSerializerOptions?)null)!,
           new ValueComparer<List<string>>(
               (a, b) => a!.SequenceEqual(b!),
               v => v.Aggregate(0, (h, s) => HashCode.Combine(h, s.GetHashCode())),
               v => v.ToList()));
```

**`ValueComparer` là bắt buộc với kiểu tham chiếu có thể thay đổi.** Không có nó, EF Core so sánh **tham chiếu** — và vì `customer.Tags.Add("vip")` không đổi tham chiếu, EF **không phát hiện thay đổi** và `SaveChanges` không làm gì. Một lỗi im lặng rất khó tìm.

```csharp
// DateTime luon UTC — chan loi mui gio tu goc
builder.Property(c => c.CreatedAt)
       .HasConversion(
           v => v.ToUniversalTime(),
           v => DateTime.SpecifyKind(v, DateTimeKind.Utc));
```

Bộ chuyển đổi này giải quyết một lớp bug cả nhóm: `DateTime` đọc từ SQL Server có `Kind = Unspecified`, nên `.ToLocalTime()` cho kết quả sai. Ép `Kind = Utc` khi đọc làm mọi phép tính múi giờ đúng.

Áp cho **mọi** `DateTime` trong mô hình:

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<DateTime>()
           .HaveConversion<UtcDateTimeConverter>();

    builder.Properties<decimal>()
           .HavePrecision(18, 2);        // tránh mặc định của provider
}
```

`ConfigureConventions` (EF Core 6+) là nơi đặt quy ước toàn cục — tốt hơn nhiều so với lặp cùng một cấu hình ở mọi entity.

### 13.3.4 — Owned type cho value object

```csharp
public sealed class Address                   // không có Id — là value object
{
    public required string Street { get; init; }
    public required string City { get; init; }
    public required string PostalCode { get; init; }
}

public class Customer
{
    public int Id { get; set; }
    public Address? BillingAddress { get; set; }
    public Address? ShippingAddress { get; set; }
}
```

```csharp
builder.OwnsOne(c => c.BillingAddress, a =>
{
    a.Property(p => p.Street).HasColumnName("BillingStreet").HasMaxLength(300);
    a.Property(p => p.City).HasColumnName("BillingCity").HasMaxLength(100);
    a.Property(p => p.PostalCode).HasColumnName("BillingPostalCode").HasMaxLength(20);
});
```

Owned type ánh xạ vào **cùng bảng** với entity chủ, nên không có JOIN nào. Domain có một kiểu `Address` rõ nghĩa; database chỉ có thêm ba cột.

Ba điều cần biết:

1. Owned type **không có identity riêng** — nó không tồn tại ngoài entity chủ.
2. Nó **luôn được nạp cùng** entity chủ; không cần `Include`.
3. Từ EF Core 8, có thể ánh xạ owned type thành **cột JSON** bằng `ToJson()` — hợp với dữ liệu lồng nhau ít khi truy vấn riêng.

### 13.3.5 — Interceptor thay vì override `SaveChanges`

```csharp
// Cách phổ biến nhưng hạn chế
public override Task<int> SaveChangesAsync(CancellationToken ct = default)
{
    foreach (var entry in ChangeTracker.Entries<Customer>()) { ... }   // CHI Customer
    return base.SaveChangesAsync(ct);
}
```

Cách này phải lặp cho **mỗi** loại entity, và logic nằm trong `DbContext` nên khó test và khó tái sử dụng.

```csharp
public interface IAuditable
{
    DateTime CreatedAt { get; set; }
    DateTime UpdatedAt { get; set; }
    string? CreatedBy { get; set; }
    string? UpdatedBy { get; set; }
}

public sealed class AuditInterceptor(ICurrentUser user, TimeProvider clock)
    : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var context = eventData.Context;
        if (context is null) return base.SavingChangesAsync(eventData, result, ct);

        var now = clock.GetUtcNow().UtcDateTime;

        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
            {
                entry.Entity.CreatedAt = now;
                entry.Entity.CreatedBy = user.Id;
            }

            if (entry.State is EntityState.Added or EntityState.Modified)
            {
                entry.Entity.UpdatedAt = now;
                entry.Entity.UpdatedBy = user.Id;
            }
        }

        return base.SavingChangesAsync(eventData, result, ct);
    }
}
```

```csharp
builder.Services.AddScoped<AuditInterceptor>();

builder.Services.AddDbContext<CrmDbContext>((sp, options) =>
    options.UseSqlServer(conn)
           .AddInterceptors(sp.GetRequiredService<AuditInterceptor>()));
```

Bốn lợi ích: áp cho **mọi** entity cài `IAuditable`; tiêm được dependency như `ICurrentUser`; test được riêng; và `DbContext` giữ nguyên trách nhiệm của nó.

Chú ý `AddDbContext` với overload nhận `IServiceProvider` — đó là cách lấy service scoped vào cấu hình context mà không gọi `BuildServiceProvider()` ([bài 7.7](../../stage-02-csharp-professional/module-07-dependency-injection/7.6-program-cs-and-webapplicationbuilder.mdx)).

EF Core còn có các interceptor khác đáng biết: `DbCommandInterceptor` để log hoặc sửa SQL, `DbConnectionInterceptor` để chuyển connection theo tenant.

## Bài tập áp dụng

#### Bài 1 — Value converter thiếu `ValueComparer`

Cấu hình value converter cho `List<string>` **không** có `ValueComparer`, thêm một phần tử vào danh sách, gọi `SaveChanges`, và xác nhận không có `UPDATE` nào. Thêm comparer và kiểm chứng.

**Tiêu chí hoàn thành:** bạn giải thích được vì sao EF Core **không phát hiện** thay đổi, và vì sao đây là lỗi im lặng chứ không phải exception.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Change tracker so sánh giá trị hiện tại với `OriginalValues`. Hãy nghĩ xem nó so sánh `List<string>` bằng cách nào.

**Lời giải — bản thiếu comparer:**

```csharp
builder.Property(l => l.Tags)
    .HasConversion(
        v => string.Join(',', v),
        v => v.Split(',', StringSplitOptions.RemoveEmptyEntries).ToList());
```

```csharp
var lead = await _db.Leads.FirstAsync(l => l.Id == 1, ct);
lead.Tags.Add("hot-lead");
await _db.SaveChangesAsync(ct);
```

```text
info: Microsoft.EntityFrameworkCore.Database.Command[20101]
      (không có câu lệnh nào được log)

SaveChangesAsync trả về 0
```

Không exception, không cảnh báo, không SQL. Thay đổi biến mất.

**Vì sao EF Core không phát hiện.** `DetectChanges` so sánh `CurrentValue` với `OriginalValue`. Với kiểu tham chiếu không có comparer riêng, phép so sánh mặc định là **so sánh tham chiếu** — `ReferenceEquals`.

Khi bạn gọi `lead.Tags.Add("hot-lead")`, bạn **không tạo list mới**. Bạn sửa nội dung của list cũ. Và vì `OriginalValue` giữ **cùng một tham chiếu** tới đúng list đó:

```text
Luc nap:      OriginalValue ──┐
                              ├──> [ "khach-moi", "b2b" ]     cùng MỘT object
              CurrentValue  ──┘

Sau .Add():   OriginalValue ──┐
                              ├──> [ "khach-moi", "b2b", "hot-lead" ]
              CurrentValue  ──┘

So sánh:      ReferenceEquals(OriginalValue, CurrentValue) == true
              -> "không có gì đổi"
```

`OriginalValue` bị sửa **cùng lúc** với `CurrentValue`, vì cả hai là một. Không có cách nào để thấy khác biệt.

**Bản đúng — thêm `ValueComparer`:**

```csharp
var comparer = new ValueComparer<List<string>>(
    // 1. So sánh: từng phần tử, không phải tham chiếu
    (a, b) => a!.SequenceEqual(b!),
    // 2. Băm: từ nội dung, để EF Core phát hiện thay đổi nhanh
    v => v.Aggregate(0, (h, s) => HashCode.Combine(h, s.GetHashCode())),
    // 3. Chụp lại: tạo BẢN SAO, đây là mảnh ghép quan trọng nhất
    v => v.ToList());

builder.Property(l => l.Tags)
    .HasConversion(
        v => string.Join(',', v),
        v => v.Split(',', StringSplitOptions.RemoveEmptyEntries).ToList())
    .Metadata.SetValueComparer(comparer);
```

```text
UPDATE [Leads] SET [Tags] = @p0 WHERE [Id] = @p1
SaveChangesAsync trả về 1
```

**Ba tham số của `ValueComparer` và vai trò của từng cái:**

| | Tham số | Làm gì |
|---|---|---|
| 1 | `equalsExpression` | So sánh hai giá trị — ở đây là `SequenceEqual` |
| 2 | `hashCodeExpression` | Băm theo nội dung, cho phép so nhanh trước khi so từng phần tử |
| 3 | `snapshotExpression` | **Tạo bản sao khi chụp `OriginalValue`** |

Tham số thứ ba là thứ thực sự sửa lỗi. Không có nó, dù có `SequenceEqual` thì hai bên vẫn trỏ cùng một list và vẫn luôn bằng nhau. `v => v.ToList()` tạo một list mới độc lập, nên khi bạn `Add` vào list hiện tại, bản snapshot vẫn giữ nội dung cũ và phép so sánh cho ra khác nhau.

**Vì sao đây là lỗi im lặng chứ không phải exception.** Vì từ góc nhìn của EF Core, **không có gì sai cả**. `SaveChanges` với 0 entity thay đổi là một tình huống hoàn toàn bình thường và hợp lệ — nó xảy ra hàng nghìn lần mỗi ngày trong mọi ứng dụng. EF Core không có cách nào phân biệt "thật sự không có gì đổi" với "có đổi nhưng tôi không thấy".

Đây là lý do loại lỗi này **luôn** được phát hiện ở production chứ không phải lúc code: nó không làm gì đổ vỡ, không ghi log gì bất thường, chỉ là dữ liệu không được lưu.

**Ba cách phòng:**

**1. Dùng `ComplexProperty` hoặc JSON column của EF Core 8+ thay cho converter tự viết** — chúng đã có comparer đúng sẵn:

```csharp
builder.OwnsMany(l => l.Tags, b => b.ToJson());
```

**2. Dùng kiểu bất biến.** Nếu `Tags` là `IReadOnlyList<string>` và mọi thay đổi đều tạo list mới, so sánh tham chiếu lại **đúng**:

```csharp
lead.Tags = lead.Tags.Append("hot-lead").ToList();   // object mới -> EF Core thấy ngay
```

Cách này rẻ nhất và an toàn nhất, vì nó loại bỏ hẳn nguyên nhân thay vì bù đắp cho nó.

**3. Test khẳng định — bắt được mọi converter, kể cả những cái viết sau này:**

```csharp
[Fact]
public void Moi_value_converter_deu_phai_co_comparer_tuy_chinh()
{
    using var db = TaoContext();

    var thieu = db.Model.GetEntityTypes()
        .SelectMany(e => e.GetProperties())
        .Where(p => p.GetValueConverter() is not null)
        .Where(p => !p.ClrType.IsValueType && p.ClrType != typeof(string))
        .Where(p => p.GetValueComparer() is null
                 || p.GetValueComparer()!.GetType().IsGenericType is false)
        .Select(p => $"{p.DeclaringType.ShortName()}.{p.Name}")
        .ToList();

    thieu.Should().BeEmpty("thuộc tính có converter mà kiểu là tham chiếu thì phải có ValueComparer");
}
```

Test này chạy trên **mô hình** chứ không cần database, nên nó nhanh và chạy được trong CI — và nó bảo vệ cả những converter mà người khác thêm vào sáu tháng sau.

</details>

#### Bài 2 — `DateTime.Kind` bị mất

Lưu một `DateTime` UTC vào SQL Server, đọc lại và in `Kind`. Xác nhận nó là `Unspecified`. Thêm converter và kiểm chứng.

**Tiêu chí hoàn thành:** bạn nêu được vì sao SQL Server không lưu `Kind`, và giải thích được hậu quả cụ thể của `Unspecified` khi gọi `ToLocalTime()`.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Kiểu `datetime2` của SQL Server lưu được gì? Hãy liệt kê các thành phần của nó.

**Lời giải:**

```csharp
var lead = new Lead { Name = "Test", CreatedAt = DateTime.UtcNow };
Console.WriteLine($"Trước khi lưu: {lead.CreatedAt:O}  Kind = {lead.CreatedAt.Kind}");
_db.Leads.Add(lead);
await _db.SaveChangesAsync(ct);

_db.ChangeTracker.Clear();   // bắt buộc — nếu không, identity map trả lại đúng object cũ

var docLai = await _db.Leads.FirstAsync(l => l.Id == lead.Id, ct);
Console.WriteLine($"Sau khi đọc:   {docLai.CreatedAt:O}  Kind = {docLai.CreatedAt.Kind}");
```

```text
Trước khi lưu: 2026-09-25T08:14:22.1234567Z   Kind = Utc
Sau khi đọc:   2026-09-25T08:14:22.1234567    Kind = Unspecified
```

Chú ý chữ `Z` biến mất. Giá trị số **hoàn toàn đúng**; chỉ có thông tin "đây là giờ UTC" bị mất.

`ChangeTracker.Clear()` là bước dễ quên nhất khi làm bài này: nếu không xoá, truy vấn thứ hai trả về đúng object đang nằm trong identity map — vẫn còn `Kind = Utc` — và bạn sẽ kết luận nhầm rằng không có vấn đề gì.

**Vì sao SQL Server không lưu `Kind`.** Vì `datetime2` không có chỗ cho nó. Kiểu này lưu đúng bảy thành phần:

```text
datetime2:  năm, tháng, ngày, giờ, phút, giây, phần giây
            (không có múi giờ, không có cờ UTC/local)
```

`DateTime.Kind` là khái niệm **của .NET**, không phải của SQL. Nó chỉ là hai bit đi kèm giá trị trong bộ nhớ CLR, và không có cột nào để ghi hai bit đó vào. Khi đọc lên, EF Core không có thông tin để khôi phục nên đặt `Unspecified` — lựa chọn trung thực nhất, vì nó nói "tôi không biết".

Kiểu **có** lưu múi giờ là `datetimeoffset`, ánh xạ sang `DateTimeOffset` của .NET:

```text
datetimeoffset:  các thành phần trên + độ lệch múi giờ (ví dụ +07:00)
```

**Hậu quả cụ thể của `Unspecified` khi gọi `ToLocalTime()`** — và đây là phần quan trọng nhất của bài:

```csharp
var utc  = DateTime.UtcNow;                                    // Kind = Utc
var unsp = DateTime.SpecifyKind(utc, DateTimeKind.Unspecified); // cùng giá trị số

Console.WriteLine(utc.ToLocalTime());    // 15:14  <- đúng (UTC+7)
Console.WriteLine(unsp.ToLocalTime());   // 15:14  <- TRÙNG HỢP đúng
```

Hai phương thức đối xứng nhau lại diễn giải `Unspecified` theo **hai chiều ngược nhau**: `ToLocalTime()` coi nó **như thể là UTC** và cộng offset, còn `ToUniversalTime()` coi nó **như thể là giờ địa phương** và trừ offset. Nên phép đầu tình cờ đúng, phép sau sai bảy tiếng:

```csharp
Console.WriteLine(utc.ToUniversalTime());    // 08:14  <- đúng, đã là UTC nên không đổi
Console.WriteLine(unsp.ToUniversalTime());   // 01:14  <- SAI, lệch 7 tiếng
```

Đo thật trên .NET 9 với `TZ=Asia/Ho_Chi_Minh` cho đúng bốn dòng trên. Kết quả là:

```text
Máy chủ ở UTC       -> offset = 0  -> mọi phép đổi đều "đúng"  -> dev không thấy lỗi
Máy dev ở UTC+7     -> lệch 7 tiếng ở một nửa số đường code
Sau khi đổi múi giờ -> lệch thành 8 tiếng
```

Lỗi chỉ xuất hiện trên một số máy, với một số phép đổi, và **luôn trả về một giá trị trông hợp lý** — không bao giờ ném exception. Đó là lý do nó thường sống sót qua nhiều đợt review.

**Bản sửa — converter toàn cục:**

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder builder)
{
    builder.Properties<DateTime>()
        .HaveConversion<UtcDateTimeConverter>();
    builder.Properties<DateTime?>()
        .HaveConversion<NullableUtcDateTimeConverter>();
}

public class UtcDateTimeConverter : ValueConverter<DateTime, DateTime>
{
    public UtcDateTimeConverter() : base(
        // Ghi xuống: chuẩn hoá về UTC dù đầu vào là Kind nào
        v => v.Kind == DateTimeKind.Utc ? v : v.ToUniversalTime(),
        // Đọc lên: gắn lại nhãn Utc
        v => DateTime.SpecifyKind(v, DateTimeKind.Utc))
    { }
}
```

```text
Sau khi đọc:   2026-09-25T08:14:22.1234567Z   Kind = Utc
```

Dùng `ConfigureConventions` thay vì cấu hình từng thuộc tính là điều quan trọng: nó áp cho **mọi** `DateTime` trong mô hình, kể cả những entity được thêm vào sau này. Cấu hình thủ công từng cột sẽ có ngày bị sót.

**Ba cách khác, theo thứ tự đáng cân nhắc:**

| Cách | Ưu | Nhược |
|---|---|---|
| **`DateTimeOffset` trong entity** | Múi giờ lưu cùng dữ liệu, không cần converter | Phải sửa entity và migration; tốn thêm 2 byte mỗi cột |
| Converter toàn cục (ở trên) | Không đổi entity, áp cho cả mô hình | Vẫn là `DateTime`, ai đó có thể `SpecifyKind` sai ở chỗ khác |
| PostgreSQL `timestamptz` | Npgsql tự xử lý `Kind` đúng | Chỉ có trên PostgreSQL |

**Với dự án mới, dùng `DateTimeOffset`.** Nó giải quyết vấn đề tận gốc thay vì bù đắp, và giá phải trả chỉ là hai byte mỗi cột.

**Và bất kể chọn cách nào, thêm một test:**

```csharp
[Fact]
public async Task DateTime_doc_len_phai_co_Kind_la_Utc()
{

    _db.Leads.Add(lead);
    await _db.SaveChangesAsync(ct);
    _db.ChangeTracker.Clear();

    var docLai = await _db.Leads.FirstAsync(l => l.Id == lead.Id, ct);
    docLai.CreatedAt.Kind.Should().Be(DateTimeKind.Utc);
}
```

#### Bài 3 — Chuyển audit sang interceptor

Chuyển logic audit từ override `SaveChangesAsync` sang `SaveChangesInterceptor`, và viết unit test cho interceptor đó mà không cần database.

**Tiêu chí hoàn thành:** bạn nêu được **hai lý do** interceptor tốt hơn override, và chỉ ra được một thao tác mà **cả hai** đều bỏ sót.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Hỏi hai câu: logic audit phụ thuộc vào gì, và nó được test thế nào?

**Lời giải — bản override (điểm xuất phát):**

```csharp
public class CrmDbContext : DbContext
{
    private readonly ICurrentUser _currentUser;      // DbContext phải biết về người dùng
    private readonly TimeProvider _clock;

    public override async Task<int> SaveChangesAsync(CancellationToken ct = default)
    {
        foreach (var entry in ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
            {
                entry.Entity.CreatedUtc = _clock.GetUtcNow().UtcDateTime;
                entry.Entity.CreatedBy  = _currentUser.Id;
            }
            else if (entry.State == EntityState.Modified)
            {
                entry.Entity.UpdatedUtc = _clock.GetUtcNow().UtcDateTime;
                entry.Entity.UpdatedBy  = _currentUser.Id;
            }
        }
        return await base.SaveChangesAsync(ct);
    }
}
```

**Bản interceptor:**

```csharp
public class AuditInterceptor : SaveChangesInterceptor
{
    private readonly ICurrentUser _currentUser;
    private readonly TimeProvider _clock;

    public AuditInterceptor(ICurrentUser currentUser, TimeProvider clock)
        => (_currentUser, _clock) = (currentUser, clock);

    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        DienThongTinAudit(eventData.Context);
        return base.SavingChangesAsync(eventData, result, ct);
    }

    // Bản đồng bộ — bắt buộc phải có, nếu không thì SaveChanges() không qua audit
    public override InterceptionResult<int> SavingChanges(
        DbContextEventData eventData, InterceptionResult<int> result)
    {
        DienThongTinAudit(eventData.Context);
        return base.SavingChanges(eventData, result);
    }

    // internal để test gọi được trực tiếp, không cần dựng interceptor pipeline
    internal void DienThongTinAudit(DbContext? context)
    {
        if (context is null) return;
        var now = _clock.GetUtcNow().UtcDateTime;

        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            if (entry.State == EntityState.Added)
            {
                entry.Entity.CreatedUtc = now;
                entry.Entity.CreatedBy  = _currentUser.Id;
            }
            else if (entry.State == EntityState.Modified)
            {
                entry.Entity.UpdatedUtc = now;
                entry.Entity.UpdatedBy  = _currentUser.Id;
            }
        }
    }
}
```

```csharp
builder.Services.AddScoped<AuditInterceptor>();
builder.Services.AddDbContext<CrmDbContext>((sp, opt) =>
    opt.UseSqlServer(conn)
       .AddInterceptors(sp.GetRequiredService<AuditInterceptor>()));
```

**Unit test không cần database:**

```csharp
[Fact]
public void Entity_moi_duoc_dien_CreatedUtc_va_CreatedBy()
{
    var clock = new FakeTimeProvider(new DateTimeOffset(2026, 9, 25, 8, 0, 0, TimeSpan.Zero));
    var user  = new FakeCurrentUser("user-42");
    var interceptor = new AuditInterceptor(user, clock);

    // Không có provider thật — chỉ cần mô hình để ChangeTracker hoạt động
    var options = new DbContextOptionsBuilder<CrmDbContext>()
        .UseInMemoryDatabase(Guid.NewGuid().ToString())
        .Options;
    using var db = new CrmDbContext(options);

    var lead = new Lead { Name = "Test" };
    db.Leads.Add(lead);

    interceptor.DienThongTinAudit(db);

    lead.CreatedUtc.Should().Be(new DateTime(2026, 9, 25, 8, 0, 0));
    lead.CreatedBy.Should().Be("user-42");
    lead.UpdatedUtc.Should().BeNull();
}
```

Test chạy trong vài mili giây, không cần SQL Server, không cần migration, không cần dọn dữ liệu giữa các lần chạy.

**Hai lý do interceptor tốt hơn override:**

**1. `DbContext` không còn phụ thuộc vào `ICurrentUser`.** Với override, `DbContext` phải nhận người dùng hiện tại qua constructor. Hệ quả dây chuyền:

- Mọi chỗ tạo `DbContext` bằng tay — migration tool, seeder, background job, integration test — phải cung cấp một `ICurrentUser`, dù chẳng có người dùng nào.
- `dotnet ef migrations add` cần `IDesignTimeDbContextFactory` chỉ để dựng một `ICurrentUser` giả.
- `DbContext` — vốn là hạ tầng truy cập dữ liệu — nay biết về khái niệm xác thực, một tầng hoàn toàn khác.

Với interceptor, quan hệ đảo lại: interceptor phụ thuộc vào `ICurrentUser`, còn `DbContext` không biết gì. Ai không cần audit thì đơn giản là không đăng ký interceptor.

**2. Interceptor test được độc lập, và tổ hợp được.** Logic audit nằm trong một class riêng có thể khởi tạo trực tiếp với dependency giả. Và vì nhiều interceptor đăng ký được cùng lúc, mỗi mối quan tâm là một class:

```csharp
.AddInterceptors(
    sp.GetRequiredService<AuditInterceptor>(),
    sp.GetRequiredService<SoftDeleteInterceptor>(),
    sp.GetRequiredService<OutboxInterceptor>(),
    sp.GetRequiredService<SlowQueryInterceptor>())
```

Với override, cả bốn mối quan tâm chen vào cùng một phương thức `SaveChangesAsync`, và nó lớn dần theo thời gian.

**Thao tác mà cả hai đều bỏ sót** — `ExecuteUpdateAsync` và `ExecuteDeleteAsync`:

```csharp
await _db.Leads
    .Where(l => l.Status == "Stale")
    .ExecuteUpdateAsync(s => s.SetProperty(l => l.Status, "Archived"), ct);

// UpdatedUtc:  KHÔNG được đặt
// UpdatedBy:   KHÔNG được đặt
```

Lý do: hai phương thức này gửi thẳng một câu lệnh `UPDATE`/`DELETE` xuống database, **không nạp entity, không qua change tracker, không gọi `SaveChanges`**. Mà cả override lẫn interceptor đều móc vào `SaveChanges` và đều đọc `ChangeTracker.Entries()`. Không có entity nào trong tracker thì không có gì để điền.

Đây chính là thứ khiến `ExecuteUpdate` nhanh ([bài 13.7](13.7-performance.mdx) đo được nhanh hơn 14 lần), nên không phải lỗi — nhưng bạn phải biết.

**Ba cách xử lý:**

**1. Đặt tay trong chính lệnh đó** — rõ ràng nhất, và là cách nên dùng mặc định:

```csharp
await _db.Leads.Where(l => l.Status == "Stale")
    .ExecuteUpdateAsync(s => s
        .SetProperty(l => l.Status,     "Archived")
        .SetProperty(l => l.UpdatedUtc, _clock.GetUtcNow().UtcDateTime)
        .SetProperty(l => l.UpdatedBy,  _currentUser.Id), ct);
```

**2. Trigger trong database** — bắt được **mọi** đường ghi, kể cả script chạy tay trong SSMS. Nhưng logic nằm ngoài code, không nhìn thấy khi đọc C#, và khó test.

**3. Bọc `ExecuteUpdateAsync` bằng extension method bắt buộc truyền audit:**

```csharp
public static Task<int> ExecuteUpdateWithAuditAsync<T>(
    this IQueryable<T> query,
    Expression<Func<SetPropertyCalls<T>, SetPropertyCalls<T>>> setters,
    IAuditContext audit, CancellationToken ct) where T : class, IAuditable
    => query.ExecuteUpdateAsync(
           s => setters.Compile()(s)
                 .SetProperty(e => e.UpdatedUtc, audit.Now)
                 .SetProperty(e => e.UpdatedBy,  audit.UserId), ct);
```

Kèm một quy tắc analyzer cấm gọi `ExecuteUpdateAsync` trần trên entity `IAuditable`. Cách này đắt nhất để dựng nhưng là cách duy nhất **không thể quên** — và nếu bạn có nhiều chỗ gọi `ExecuteUpdate`, nó trả lại chi phí khá nhanh.

## Kết luận

Ba điều đáng nhớ nhất:

1. **`DbContext` là Unit of Work, không thread-safe, và phải sống ngắn.**
2. **Value converter cho kiểu tham chiếu phải có `ValueComparer`**, nếu không thay đổi bị bỏ qua im lặng.
3. **Audit thuộc về interceptor**, không thuộc về `SaveChanges` được override.
