# 13.10 — 9. Unit of Work và Repository Pattern

<SummaryBox>
`DbContext` **đã là** một Unit of Work, và `DbSet<T>` **đã là** một Repository. Một `IUnitOfWork` chỉ gọi `SaveChanges` và một `IRepository<T>` chỉ gọi lại `DbSet<T>` là **lớp trung gian không thêm gì** — bạn viết thêm code, mất tính năng của EF Core, và không được lợi ích nào. Nhưng có **ba trường hợp** lớp bọc thật sự đáng: cần **cô lập domain khỏi EF Core** vì lý do kiến trúc, cần **đóng gói truy vấn phức tạp** để không lặp lại khắp nơi, hoặc cần **chặn quyền truy cập** để không ai viết truy vấn tuỳ ý. Điểm quyết định là repository trả về **`IQueryable` hay `IEnumerable`** — trả `IQueryable` giữ được sức mạnh EF Core nhưng cũng làm rò rỉ trừu tượng.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích vì sao `DbContext` đã là Unit of Work.
- Nhận ra repository chỉ là lớp trung gian.
- Thiết kế repository có giá trị thật khi cần.
- Chọn giữa trả `IQueryable` và `IEnumerable`.
- Biết các phương án thay thế.

## Nội dung bài học

### 13.10.1 — `DbContext` đã là Unit of Work

Unit of Work theo định nghĩa của Martin Fowler: *"theo dõi mọi thứ bạn làm trong một giao dịch nghiệp vụ và điều phối việc ghi thay đổi"*.

Đó **chính xác** là những gì `DbContext` làm:

```csharp
db.Customers.Add(customer);
db.Leads.Update(lead);
db.Contacts.Remove(contact);

await db.SaveChangesAsync(ct);      // MỘT transaction cho cả ba
```

Change tracker theo dõi; `SaveChanges` điều phối và bọc trong transaction ([bài 13.3](13.2-dbcontext-and-entity-configuration.mdx)).

Tương tự, `DbSet<T>` là Repository: *"trung gian giữa domain và tầng ánh xạ dữ liệu, hoạt động như một tập đối tượng trong bộ nhớ"*.

```csharp
public interface IUnitOfWork
{
    Task<int> SaveChangesAsync(CancellationToken ct = default);
}

public sealed class UnitOfWork(CrmDbContext db) : IUnitOfWork
{
    public Task<int> SaveChangesAsync(CancellationToken ct = default)
        => db.SaveChangesAsync(ct);        // chi goi lai
}
```

Lớp này **không thêm gì**. Nó tồn tại để "trừu tượng hoá EF Core" nhưng thực tế chỉ chuyển tiếp một lời gọi.

Chi tiết trong bài [Unit of Work trong .NET và ABP: `SaveChangesAsync` không phải commit](/blog/unit-of-work-dotnet-abp).

### 13.10.2 — Repository generic: cái giá

```csharp
public interface IRepository<T> where T : class
{
    Task<T?> GetByIdAsync(int id, CancellationToken ct = default);
    Task<List<T>> GetAllAsync(CancellationToken ct = default);
    void Add(T entity);
    void Update(T entity);
    void Remove(T entity);
}
```

Nó **mất** những gì EF Core cho:

| Mất | Hệ quả |
|---|---|
| `Include` / `ThenInclude` | Không nạp được dữ liệu liên quan |
| Projection | **Luôn** nạp entity đầy đủ |
| `AsNoTracking` | Luôn tracking, chậm hơn |
| `AsSplitQuery` | Không tránh được cartesian explosion |
| Phân trang | `GetAllAsync` nạp **cả bảng** |
| `ExecuteUpdate` | Cập nhật hàng loạt phải nạp entity |

Nghĩa là gần như **toàn bộ** nội dung [bài 13.6](13.5-query-patterns.mdx), [13.7](13.6-n-plus-1-problem.mdx) và [13.8](13.7-performance.mdx) trở thành không dùng được.

Người ta thường "giải quyết" bằng cách nhồi thêm tham số:

```csharp
Task<List<T>> GetAsync(
    Expression<Func<T, bool>>? filter = null,
    Func<IQueryable<T>, IOrderedQueryable<T>>? orderBy = null,
    string includeProperties = "",
    int? skip = null, int? take = null,
    bool asNoTracking = true,
    CancellationToken ct = default);
```

Đây là **`IQueryable` viết lại bằng tay** — xấu hơn, ít khả năng hơn, và không kiểm tra được lúc biên dịch (`includeProperties` là chuỗi!). Đến bước này, lớp trừu tượng đã thất bại hoàn toàn.

### 13.10.3 — Ba trường hợp repository có giá trị

**1. Cô lập domain khỏi EF Core**

```csharp
// Trong tầng Domain — KHÔNG tham chiếu EF Core
public interface ICustomerRepository
{
    Task<Customer?> GetByIdAsync(CustomerId id, CancellationToken ct);
    Task<Customer?> GetWithContactsAsync(CustomerId id, CancellationToken ct);
    Task<bool> EmailExistsAsync(string email, CancellationToken ct);
    void Add(Customer customer);
}
```

Đây là lý do chính đáng nhất, và nó đến từ kiến trúc chứ không từ EF Core: tầng domain không được phụ thuộc hạ tầng ([Module 16](../../stage-05-senior-engineering/module-16-clean-architecture/)).

Chú ý interface này **cụ thể**, không generic — mỗi phương thức có tên nói rõ nó làm gì.

**2. Đóng gói truy vấn phức tạp**

```csharp
public interface ILeadRepository
{
    Task<PagedResult<LeadSummaryDto>> SearchAsync(LeadSearchCriteria criteria, CancellationToken ct);
    Task<IReadOnlyList<Lead>> GetStaleLeadsAsync(TimeSpan olderThan, CancellationToken ct);
    Task<decimal> GetPipelineValueAsync(int userId, CancellationToken ct);
}
```

Mỗi phương thức là một **truy vấn nghiệp vụ có tên**. Logic "lead cũ nghĩa là gì" nằm ở **một chỗ** thay vì lặp lại ở năm service.

Đây là giá trị thật: không phải trừu tượng hoá EF Core, mà **đặt tên cho truy vấn**.

**3. Chặn quyền truy cập**

Khi bạn **không muốn** ai đó viết truy vấn tuỳ ý — vì lý do bảo mật đa khách hàng, hoặc vì đã có truy vấn làm sập production. Repository với tập phương thức đóng là hàng rào.

### 13.10.4 — `IQueryable` hay `IEnumerable`

```csharp
// Tra IQueryable — giu suc manh EF Core
public interface ICustomerRepository
{
    IQueryable<Customer> Query();
}

// Người gọi
var dtos = await repo.Query()
    .Where(c => c.Status == CustomerStatus.Active)
    .Select(c => new CustomerDto(c.Id, c.Name))
    .ToListAsync(ct);
```

| | Trả `IQueryable` | Trả `IEnumerable` / DTO |
|---|---|---|
| Hiệu năng | **Tốt** — ghép vào SQL | Rủi ro nạp thừa |
| Tính trừu tượng | **Rò rỉ** — người gọi biết đây là ORM | Kín |
| Kiểm soát truy vấn | Không | **Có** |
| Test bằng mock | Khó | **Dễ** |

Trả `IQueryable` khiến lớp trừu tượng **rò rỉ**: người gọi có thể viết một biểu thức không dịch được, và nó nổ lúc chạy ([bài 13.2](13.1-ef-core-overview.mdx)). Về lý thuyết bạn "có thể đổi ORM", nhưng thực tế mọi nơi gọi đều phụ thuộc vào hành vi của EF Core.

Vậy nên: **nếu trả `IQueryable`, thì lớp bọc gần như không có ý nghĩa** — cứ dùng `DbContext` trực tiếp.

**Nếu cần trừu tượng thật, trả DTO hoặc entity đã hoàn chỉnh**, và chấp nhận rằng mọi truy vấn mới cần một phương thức mới.

Mẫu **Specification** là điểm giữa:

```csharp
public sealed class ActiveCustomersInTerritorySpec : Specification<Customer>
{
    public ActiveCustomersInTerritorySpec(string territory)
    {
        Query.Where(c => c.Status == CustomerStatus.Active && c.Territory == territory)
             .Include(c => c.Contacts)
             .OrderBy(c => c.Name)
             .AsNoTracking();
    }
}

var customers = await repo.ListAsync(new ActiveCustomersInTerritorySpec("HN"), ct);
```

Nó giữ được `Include`, projection và phân trang, đồng thời đóng gói truy vấn thành một lớp có tên và test được riêng. Cái giá là thêm một khái niệm mà cả team phải học.

### 13.10.5 — Phương án thay thế

**1. Dùng `DbContext` trực tiếp**

```csharp
public sealed class CustomerService(CrmDbContext db)
{
    public async Task<PagedResult<CustomerDto>> SearchAsync(
        CustomerSearchCriteria criteria, CancellationToken ct)
    {
        var query = db.Customers.AsNoTracking().ApplyFilters(criteria);
        ...
    }
}
```

Với ứng dụng nhỏ và vừa, đây là lựa chọn **đúng nhất**: ít code, đầy đủ sức mạnh EF Core, và ai đọc cũng hiểu ngay. Integration test với Testcontainers ([bài 9.9](../../stage-03-aspnet-core-backend/module-09-web-api-professional/9.8-api-testing.mdx)) thay thế hoàn toàn nhu cầu mock repository.

**2. Extension method cho truy vấn dùng lại**

```csharp
public static class CustomerQueries
{
    public static IQueryable<Customer> ActiveOnly(this IQueryable<Customer> q)
        => q.Where(c => c.Status == CustomerStatus.Active && c.DeletedAt == null);

    public static IQueryable<Customer> InTerritory(this IQueryable<Customer> q, string t)
        => q.Where(c => c.Territory == t);
}

var customers = await db.Customers.ActiveOnly().InTerritory("HN").ToListAsync(ct);
```

Không có lớp nào, không có interface nào — nhưng logic được đặt tên và dùng lại. **Đây là 80% giá trị của repository với gần như không có chi phí.**

**3. CQRS: tách đọc và ghi**

```csharp
// Ghi — dùng repository để bảo vệ bất biến của domain
public interface ICustomerRepository
{
    Task<Customer?> GetByIdAsync(CustomerId id, CancellationToken ct);
    void Add(Customer customer);
}

// Doc — dung DbContext truc tiep, toi uu tu do
public sealed class CustomerQueryService(CrmDbContext db)
{
    public Task<PagedResult<CustomerDto>> SearchAsync(...) => ...;
}
```

Đây là mẫu cân bằng nhất cho hệ thống lớn: **đường ghi cần trừu tượng** vì nó chứa quy tắc nghiệp vụ; **đường đọc cần tự do** vì nó chỉ cần nhanh.

### 13.10.6 — Câu hỏi quyết định

Trước khi thêm repository, trả lời ba câu:

1. **Nó giải quyết vấn đề gì?** Nếu câu trả lời là "trừu tượng hoá database" mà không có yêu cầu kiến trúc cụ thể, đó chưa phải lý do.
2. **Bạn có thật sự sẽ đổi ORM?** Gần như không ai đổi. Và nếu đổi, repository cũng không cứu được bạn — hành vi của change tracker đã ngấm vào code.
3. **Nó có làm bạn mất tính năng không?** Nếu có, cái giá đó có đáng với lợi ích không?

Lời khuyên thực dụng:

| Quy mô | Nên |
|---|---|
| CRUD nhỏ, một team | **`DbContext` trực tiếp** + extension method |
| Domain phức tạp, nhiều quy tắc | Repository **cụ thể** cho đường ghi, `DbContext` cho đường đọc |
| Kiến trúc yêu cầu domain độc lập | Repository trong domain, cài đặt ở hạ tầng |
| "Vì best practice bảo thế" | **Không** |

## Bài tập áp dụng

#### Bài 1 — Đếm chi phí của `IRepository<T>`

Lấy một `IRepository<T>` generic trong dự án và liệt kê mọi tính năng EF Core mà nó chặn. Với mỗi cái, tìm một chỗ trong code lẽ ra sẽ dùng nó.

**Tiêu chí hoàn thành:** bạn nêu được vì sao chi phí này **tăng dần theo thời gian** thay vì cố định.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Nhìn kiểu trả về của mỗi phương thức. Nó là `IQueryable` hay là thứ gì đã vật chất hoá?

**Lời giải — một `IRepository<T>` điển hình:**

```csharp
public interface IRepository<T> where T : class
{
    Task<T?>        GetByIdAsync(int id, CancellationToken ct);
    Task<List<T>>   GetAllAsync(CancellationToken ct);
    Task<List<T>>   FindAsync(Expression<Func<T, bool>> predicate, CancellationToken ct);
    Task            AddAsync(T entity, CancellationToken ct);
    void            Update(T entity);
    void            Remove(T entity);
    Task<int>       SaveChangesAsync(CancellationToken ct);
}
```

Trông vô hại. Nhưng hãy liệt kê những gì nó **không cho phép**:

| Tính năng EF Core bị chặn | Chỗ lẽ ra sẽ dùng |
|---|---|
| Projection `Select` | Endpoint danh sách — chỉ cần 3 cột, nhưng nhận về entity đầy đủ |
| `AsNoTracking` | Mọi truy vấn chỉ đọc — mất 2× hiệu năng đo được ở [bài 13.1](13.1-ef-core-overview.mdx) |
| `Include` / `ThenInclude` | Màn hình chi tiết khách hàng cần contact và lead |
| `AsSplitQuery` | Khách hàng có nhiều collection — cartesian explosion |
| `ExecuteUpdate` / `ExecuteDelete` | Job lưu trữ hàng loạt — chậm 14× |
| `GroupBy` dịch sang SQL | Báo cáo doanh số theo tháng |
| `IgnoreQueryFilters` | Màn hình admin xem bản ghi đã xoá mềm |
| Phân trang `Skip` / `Take` ở SQL | Mọi danh sách có phân trang |
| `FromSql` | Truy vấn phức tạp cần SQL viết tay |
| `TemporalAsOf` | Màn hình lịch sử thay đổi |

**Hệ quả cụ thể của hai dòng đầu:**

```csharp
// Qua repository — nạp mọi cột, có tracking
var customers = await _repo.GetAllAsync(ct);
var dtos = customers.Select(c => new CustomerDto(c.Id, c.Name)).ToList();
// SELECT * FROM Customers      50.000 entity đầy đủ + change tracker

// Không qua repository
var dtos = await _db.Customers.AsNoTracking()
    .Select(c => new CustomerDto(c.Id, c.Name)).ToListAsync(ct);
// SELECT Id, Name FROM Customers
```

Với 50.000 dòng, chênh lệch đo được ở [bài 13.1](13.1-ef-core-overview.mdx) là **9 lần về thời gian và 3 lần về bộ nhớ**.

Và dòng `FindAsync(predicate)` còn tệ hơn vẻ ngoài của nó: nó nhận `Expression` nên **trông như** vẫn dịch được sang SQL, nhưng kiểu trả về `Task<List<T>>` nghĩa là truy vấn **đã thực thi xong**. Không ghép thêm `Skip`, `Take`, `OrderBy` vào được — chúng sẽ chạy trong bộ nhớ.

**Vì sao chi phí tăng dần theo thời gian** — đây là phần chính của bài.

Ngày đầu, repository phủ đủ nhu cầu: đọc theo id, đọc danh sách, thêm, sửa, xoá. Rồi từng yêu cầu mới đến, và mỗi yêu cầu để lại một vết:

```text
Tháng 1:  GetByIdAsync, GetAllAsync, AddAsync, Update, Remove     — đủ dùng
Tháng 2:  cần phân trang       -> GetPagedAsync(int trang, int kichThuoc)
Tháng 3:  cần sắp xếp          -> GetPagedAsync(..., string sapXep, bool giamDan)
Tháng 4:  cần nạp quan hệ      -> GetByIdWithIncludesAsync(int id, params Expression[])
Tháng 6:  cần chỉ vài cột      -> GetProjectedAsync<TDto>(Expression<Func<T,TDto>>)
Tháng 8:  cần lọc động         -> GetFilteredAsync(ISpecification<T>)
Tháng 11: cần GroupBy          -> chịu, viết DbContext trực tiếp ở một chỗ
Tháng 14: cần ExecuteUpdate    -> chịu, viết DbContext trực tiếp ở chỗ nữa
```

Ba hiện tượng xảy ra cùng lúc, và mỗi cái đều làm tình hình xấu đi:

**1. Interface phình ra.** Từ 7 phương thức lên 20, mỗi cái nhiều tham số hơn. `GetPagedAsync` với sáu tham số optional khó dùng và khó nhớ hơn `IQueryable`.

**2. Nó hội tụ về chính `IQueryable`, nhưng tệ hơn.** `ISpecification<T>` với `Criteria`, `Includes`, `OrderBy`, `Skip`, `Take` là một bản dựng lại `IQueryable` — kém đầy đủ hơn, kém quen thuộc hơn, không có ai viết tài liệu, và phải tự bảo trì. Bạn đã trả tiền để có `IQueryable` rồi.

**3. Lớp trừu tượng bị rò rỉ ở những chỗ khó nhất.** Đúng những truy vấn phức tạp — báo cáo, dashboard, xuất dữ liệu, tức những chỗ hiệu năng quan trọng nhất — lại là những chỗ buộc phải bỏ qua repository. Kết quả là dự án có **hai** cách truy cập dữ liệu, và quy tắc "khi nào dùng cái nào" chỉ nằm trong đầu vài người.

**Và cái giá cuối cùng, khó thấy nhất:** một lập trình viên mới đọc code sẽ thấy `_repo.GetAllAsync()` rồi lọc trong bộ nhớ, và **học theo** — vì đó là mẫu có sẵn trong codebase. Lớp trừu tượng không chỉ chặn tính năng, nó còn dạy sai.

**Câu hỏi để tự đánh giá repository trong dự án bạn:**

1. Có bao nhiêu chỗ trong code **bỏ qua** repository và dùng `DbContext` trực tiếp? Con số càng lớn, lớp trừu tượng càng ít giá trị.
2. Interface đã có bao nhiêu phương thức, so với lúc mới viết?
3. Có phương thức nào nhận `Expression` hay `ISpecification` không? Nếu có, bạn đang dựng lại `IQueryable`.
4. Nếu bỏ repository đi, code gọi sẽ **ngắn hơn hay dài hơn**?

Câu 4 là câu quyết định. Nếu bỏ đi mà code ngắn hơn và rõ hơn, lớp trừu tượng đang không trả lại gì cho chi phí của nó.

</details>

#### Bài 2 — Extension method thay cho repository

Chuyển ba truy vấn lặp lại thành extension method trên `IQueryable<T>`. So sánh số dòng code với một repository làm cùng việc.

**Tiêu chí hoàn thành:** bạn nêu được vì sao extension method **tổ hợp được** trong khi phương thức repository thì không.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Nhìn kiểu trả về. Bạn làm gì được với nó sau khi gọi?

**Lời giải — extension method:**

```csharp
public static class LeadQueryExtensions
{
    public static IQueryable<Lead> CuaTenant(this IQueryable<Lead> q, string tenantId)
        => q.Where(l => l.TenantId == tenantId);

    public static IQueryable<Lead> DangHoatDong(this IQueryable<Lead> q)
        => q.Where(l => !l.IsDeleted && l.Status != "Closed");

    public static IQueryable<Lead> GiaTriCaoHon(this IQueryable<Lead> q, decimal nguong)
        => q.Where(l => l.Value > nguong);
}
```

```csharp
// 24 dòng cho ba extension method, kể cả dấu ngoặc
```

**Repository làm cùng việc:**

```csharp
public interface ILeadRepository
{
    Task<List<Lead>> LayTheoTenantAsync(string tenantId, CancellationToken ct);
    Task<List<Lead>> LayDangHoatDongAsync(CancellationToken ct);
    Task<List<Lead>> LayGiaTriCaoHonAsync(decimal nguong, CancellationToken ct);

    // Rồi mọi tổ hợp...
    Task<List<Lead>> LayDangHoatDongTheoTenantAsync(string tenantId, CancellationToken ct);
    Task<List<Lead>> LayGiaTriCaoTheoTenantAsync(string tenantId, decimal nguong, CancellationToken ct);
    Task<List<Lead>> LayDangHoatDongGiaTriCaoAsync(decimal nguong, CancellationToken ct);
    Task<List<Lead>> LayDangHoatDongGiaTriCaoTheoTenantAsync(
        string tenantId, decimal nguong, CancellationToken ct);
}
```

```csharp
// 7 phương thức trong interface + 7 phần cài đặt ≈ 70 dòng
// và mỗi cái phải có test riêng
```

**Vì sao extension method tổ hợp được.** Vì nó **nhận** `IQueryable<T>` và **trả về** `IQueryable<T>` — cùng một kiểu ở cả hai đầu. Bất cứ thứ gì có hình dạng đó đều nối được với bất cứ thứ gì khác có cùng hình dạng:

```csharp
var leads = await _db.Leads
    .CuaTenant("acme")
    .DangHoatDong()
    .GiaTriCaoHon(5_000_000)
    .OrderByDescending(l => l.Value)
    .Skip(0).Take(20)
    .Select(l => new LeadDto(l.Id, l.Name, l.Value))
    .AsNoTracking()
    .ToListAsync(ct);
```

Một câu SQL duy nhất, có đủ mọi điều kiện, chỉ đọc ba cột.

Phương thức repository trả về `Task<List<Lead>>` — một kiểu **khác** với đầu vào. Chuỗi bị cắt ngay tại đó:

```text
IQueryable<Lead> -> IQueryable<Lead>      nối tiếp được, vô hạn
Task<List<Lead>> -> ???                   hết, dữ liệu đã ở trong bộ nhớ
```

Hệ quả là số phương thức cần có tăng theo **tổ hợp** của các điều kiện, không phải theo số điều kiện:

```text
3 điều kiện  -> 2³ - 1 = 7 phương thức
4 điều kiện  -> 2⁴ - 1 = 15 phương thức
5 điều kiện  -> 2⁵ - 1 = 31 phương thức
```

Với extension method, **n điều kiện cần đúng n hàm**, và mọi tổ hợp có sẵn miễn phí. Đây là khác biệt giữa tăng trưởng tuyến tính và tăng trưởng hàm mũ — và nó là lý do kỹ thuật, không phải sở thích.

**Bốn lợi ích khác của extension method:**

**1. Đặt tên theo ngôn ngữ nghiệp vụ mà không mất khả năng tổ hợp:**

```csharp
public static IQueryable<Lead> DangChoXuLy(this IQueryable<Lead> q)
    => q.Where(l => l.Status == "New" || l.Status == "Contacted");
```

Đây là giá trị thật mà repository hứa hẹn — gói một quy tắc nghiệp vụ vào một cái tên — nhưng đạt được mà không chặn gì.

**2. Test được như hàm thuần, không cần database:**

```csharp
[Fact]
public void DangHoatDong_loai_lead_da_xoa_va_da_dong()
{
    var data = new List<Lead>
    {
        new() { Id = 1, IsDeleted = false, Status = "New" },
        new() { Id = 2, IsDeleted = true,  Status = "New" },
        new() { Id = 3, IsDeleted = false, Status = "Closed" },
    }.AsQueryable();

    data.DangHoatDong().Select(l => l.Id).Should().Equal(1);
}
```

**3. Dùng lại cho mọi hình dạng kết quả.** Cùng một `DangHoatDong()` phục vụ danh sách, đếm, báo cáo và xuất file:

```csharp
var soLuong = await _db.Leads.CuaTenant(id).DangHoatDong().CountAsync(ct);
var tong    = await _db.Leads.CuaTenant(id).DangHoatDong().SumAsync(l => l.Value, ct);
var coNao   = await _db.Leads.CuaTenant(id).DangHoatDong().AnyAsync(ct);
```

Repository cần ba phương thức nữa cho ba dòng này.

**4. Nơi gọi đọc được ngay.** `CuaTenant("acme").DangHoatDong()` nói rõ điều gì đang xảy ra. `LayDangHoatDongTheoTenantAsync("acme")` thì phải mở phần cài đặt ra xem "đang hoạt động" nghĩa là gì.

**Nhược điểm cần nói cho đủ:**

**1. Không mock được trong unit test.** Nhưng đây phần nào là câu hỏi sai: những gì đáng test ở đây là **SQL sinh ra** và **kết quả trả về**, và cả hai đều cần một database thật (SQLite in-memory là đủ) chứ không cần mock.

**2. Không ngăn được ai đó viết truy vấn tệ.** Đúng — nhưng repository cũng không, nó chỉ khiến truy vấn tệ **khó sửa hơn**. Công cụ đúng cho việc này là test đếm truy vấn ở [bài 13.6](13.6-n-plus-1-problem.mdx).

**3. `DbContext` lộ ra khắp tầng ứng dụng.** Là vấn đề thật nếu bạn muốn tầng application không phụ thuộc vào EF Core. Giải quyết bằng cách đặt truy vấn trong query handler chứ không rải khắp nơi — xem [bài 16.4](../../stage-05-senior-engineering/module-16-clean-architecture/16.4-vertical-slice-architecture.mdx).

#### Bài 3 — Kiểm chứng lập luận "để đổi ORM"

Thử thay EF Core bằng Dapper phía sau một `IRepository<T>` hiện có, và đếm số chỗ trong code gọi phải sửa.

**Tiêu chí hoàn thành:** bạn đưa ra được con số thật, và nêu được lớp trừu tượng nào **thật sự** cho phép đổi hạ tầng.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Repository trả về cái gì? Những thứ đó có phụ thuộc vào EF Core không?

**Lời giải — thử thật.** Thay phần cài đặt `IRepository<Lead>` bằng Dapper, giữ nguyên interface:

```csharp
public class LeadRepositoryDapper : IRepository<Lead>
{
    private readonly IDbConnection _conn;

    public async Task<Lead?> GetByIdAsync(int id, CancellationToken ct)
        => await _conn.QuerySingleOrDefaultAsync<Lead>(
               "SELECT * FROM Leads WHERE Id = @id", new { id });

    public async Task<List<Lead>> GetAllAsync(CancellationToken ct)
        => (await _conn.QueryAsync<Lead>("SELECT * FROM Leads")).ToList();
}
```

Hai phương thức đầu chuyển được. Rồi bạn gặp phần còn lại:

**1. `FindAsync(Expression<Func<T, bool>>)` — không chuyển được.**

```csharp
public async Task<List<Lead>> FindAsync(Expression<Func<Lead, bool>> predicate, CancellationToken ct)
{
    // Dapper không dịch Expression sang SQL. Hoặc bạn tự viết bộ dịch
    // Expression -> SQL (tức là viết lại một phần của EF Core), hoặc:
    var tatCa = await _conn.QueryAsync<Lead>("SELECT * FROM Leads");
    return tatCa.Where(predicate.Compile()).ToList();    // lọc toàn bộ bảng trong bộ nhớ
}
```

Cách duy nhất giữ được chữ ký là **kéo cả bảng về và lọc trong C#**. Nghĩa là repository vẫn biên dịch được, test vẫn xanh, và ứng dụng chậm đi hàng chục lần ở mọi chỗ gọi `FindAsync`.

**2. Change tracking — không có.**

```csharp
// Code gọi hiện tại dựa vào tracking
var lead = await _repo.GetByIdAsync(1, ct);
lead.Status = "Won";
await _repo.SaveChangesAsync(ct);      // với Dapper: KHÔNG LÀM GÌ CẢ
```

Dapper không theo dõi thay đổi. `Update(entity)` phải sinh `UPDATE` cho **mọi** cột, và `SaveChangesAsync` không còn ý nghĩa gì. **Mọi** chỗ gọi theo mẫu đọc-sửa-lưu phải viết lại.

**3. Navigation property — `null` hết.**

```csharp
var lead = await _repo.GetByIdAsync(1, ct);
Console.WriteLine(lead.Customer.Name);      // NullReferenceException
```

Dapper không tự nạp quan hệ. Mọi chỗ chạm tới navigation phải đổi sang `JOIN` viết tay hoặc truy vấn riêng.

**4. Unit of Work — không có.** Nhiều `Update` rồi một `SaveChanges` phải thành một transaction viết tay:

```csharp
using var tx = _conn.BeginTransaction();
// ... từng lệnh một, tự quản lý
tx.Commit();
```

**Con số thật, trên một dự án CRM cỡ vừa:**

| | Số chỗ |
|---|---:|
| Chỗ gọi `_repo.*` | ~180 |
| Phải sửa vì đọc-sửa-lưu | ~60 |
| Phải sửa vì navigation property | ~45 |
| Phải sửa vì `FindAsync` với expression | ~30 |
| Phải sửa vì `SaveChanges` gộp nhiều thay đổi | ~25 |
| **Tổng phải sửa** | **~160 / 180 (89%)** |

Repository — thứ được dựng lên chính là để tránh việc này — giảm công việc từ 180 chỗ xuống 160 chỗ. Khoảng **11%**.

**Vì sao ít vậy.** Vì repository chỉ giấu được **cách gọi**, không giấu được **mô hình lập trình**. Và mô hình lập trình mới là thứ code phụ thuộc vào:

```text
Repository giấu được:    _db.Leads.Where(...)  ->  _repo.FindAsync(...)
Repository KHÔNG giấu:   - entity tự theo dõi thay đổi
                         - navigation property nạp được
                         - SaveChanges gộp nhiều thay đổi thành một transaction
                         - Expression dịch được sang SQL
```

Bốn giả định đó nằm trong **kiểu trả về** và trong **cách code gọi được viết**, không nằm trong chữ ký phương thức. EF Core và Dapper khác nhau ở đúng bốn điểm này, nên bất kỳ code nào dựa vào chúng đều phải viết lại.

**Và câu hỏi nên hỏi trước tiên: bạn có bao giờ đổi không?**

Trong thực tế, ORM gần như không bao giờ bị thay. Cái thường xảy ra là **bổ sung**: giữ EF Core cho ghi và cho phần lớn phần đọc, thêm Dapper cho vài truy vấn báo cáo nặng. Và việc đó **không cần lớp trừu tượng nào** — hai thứ dùng chung một kết nối, sống cạnh nhau:

```csharp
// EF Core cho ghi và cho đa số phần đọc
var lead = await _db.Leads.FirstAsync(l => l.Id == id, ct);

// Dapper cho một truy vấn báo cáo cụ thể
var thongKe = await _db.Database.GetDbConnection()
    .QueryAsync<ThongKeDto>(SqlBaoCao, new { tenantId });
```

**Lớp trừu tượng thật sự cho phép đổi hạ tầng** là loại được định nghĩa bằng **ngôn ngữ nghiệp vụ**, không phải bằng thao tác dữ liệu:

```csharp
// Không cho đổi được gì — mô tả thao tác dữ liệu
public interface IRepository<T>
{
    Task<List<T>> FindAsync(Expression<Func<T, bool>> predicate, CancellationToken ct);
}

// Cho đổi được — mô tả một câu hỏi nghiệp vụ
public interface ILeadQueries
{
    Task<PagedResult<LeadDto>> TimLeadDangHoatDongAsync(
        string tenantId, int trang, int kichThuoc, CancellationToken ct);
}
```

Khác biệt ở chỗ: interface thứ hai **không nhận `Expression`, không trả về entity, không giả định có change tracking**. Nó nhận tham số nguyên thuỷ và trả về DTO. Cài bằng EF Core, bằng Dapper, bằng stored procedure, hay bằng một lời gọi HTTP tới dịch vụ khác — nơi gọi không biết và không cần biết.

**Đó mới là lớp trừu tượng đáng viết** — và nó được viết cho **từng nghiệp vụ cụ thể**, không phải generic theo `T`. Một `IRepository<T>` generic, theo định nghĩa, không thể mô tả nghiệp vụ nào cả, vì nó phải đúng cho mọi `T`.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **`DbContext` đã là Unit of Work, `DbSet` đã là Repository.** Bọc lại phải có lý do cụ thể.
2. **Repository generic chặn mọi công cụ tối ưu của EF Core.**
3. **Repository cụ thể cho đường ghi, `DbContext` trực tiếp cho đường đọc** là cân bằng tốt nhất.
