# 19.13 — Ví dụ thực tế nhanh

<SummaryBox>
Một ví dụ ngắn nhưng đắt giá: endpoint export danh sách lead ra Excel chạy tốt suốt một năm, rồi một ngày làm **container bị OOM kill** — và điều tệ nhất là nó không chỉ làm hỏng request export, mà làm **mọi request đang chạy trên instance đó** chết theo. Nguyên nhân: toàn bộ 200.000 bản ghi được nạp vào `List`, rồi dựng thành một file Excel trong `MemoryStream`, rồi copy sang mảng byte để trả về — **ba bản sao** của cùng dữ liệu tồn tại cùng lúc. Cách sửa là **streaming**, và nó cũng dạy một bài học chung: trong backend, thứ nguy hiểm không phải code chậm mà là code có mức tiêu thụ bộ nhớ **tỷ lệ với dữ liệu đầu vào**.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra code có bộ nhớ tỷ lệ với dữ liệu đầu vào.
- Chuyển một endpoint export sang streaming.
- Giải thích vì sao OOM kill nguy hiểm hơn một lỗi thường.
- Tự kiểm tra rủi ro này trong dự án chỉ với vài phút.

## Nội dung bài học

### 19.13.1 — Ví dụ: export Excel

```csharp
// Code that — chay tot voi 5.000 lead, GIET container voi 200.000
[HttpGet("export")]
public async Task<IActionResult> ExportLeads(CancellationToken ct)
{
    // Bản sao 1: toàn bộ entity trong bộ nhớ
    var leads = await _db.Leads.Where(l => l.TenantId == _tenant.Id).ToListAsync(ct);

    using var workbook = new XLWorkbook();
    var sheet = workbook.Worksheets.Add("Leads");

    for (int i = 0; i < leads.Count; i++)
    {
        sheet.Cell(i + 2, 1).Value = leads[i].Name;
        sheet.Cell(i + 2, 2).Value = leads[i].Email;
        sheet.Cell(i + 2, 3).Value = leads[i].Value;
    }

    // Bản sao 2: cả file Excel trong bộ nhớ
    using var stream = new MemoryStream();
    workbook.SaveAs(stream);

    // Bản sao 3: ToArray() COPY toàn bộ stream sang mảng mới
    return File(stream.ToArray(), "application/vnd.openxmlformats-officedocument.spreadsheetml.sheet", "leads.xlsx");
}
```

Ước lượng bộ nhớ với 200.000 lead:

```
Bản sao 1: 200.000 entity × ~800 B          = ~160 MB
Bản sao 2: workbook trong MemoryStream      = ~180 MB
Bản sao 3: ToArray() sao chép stream        = ~180 MB
Object trung gian của thư viện Excel        = ~200 MB
                                            ----------
Đỉnh bộ nhớ cho MỘT request                 = ~720 MB
```

Container có `memory limit: 512Mi` → **OOM kill**.

### 19.13.2 — Vì sao OOM kill tệ hơn một lỗi thường

```
Request export bắt đầu
Bộ nhớ tăng dần: 200MB... 400MB... 512MB
Kernel OOM killer GIẾT tiến trình — KHÔNG có exception, KHÔNG có log

Hậu quả:
  - 40 request khác đang chạy trên instance đó: MẤT HẾT
  - Không có stack trace để điều tra
  - Kubernetes restart pod, vài giây không phục vụ được
  - Lần sau vẫn vậy
```

Đây là điểm quan trọng nhất: một lỗi thường chỉ làm **một** request thất bại và để lại stack trace. OOM kill giết **cả tiến trình**, không để lại gì trong log ứng dụng, và kéo theo mọi request đang chạy ([bài 15.10](../../stage-04-database-production/module-15-docker-deployment/15.9-awareness-level.mdx)).

Dấu hiệu nhận ra trong Kubernetes:

```bash
kubectl describe pod crm-api-7d8f9

# Last State:  Terminated
#   Reason:    OOMKilled          <-- day
#   Exit Code: 137                <-- 128 + 9 (SIGKILL)
```

`Exit Code 137` là chữ ký của OOM kill. Nếu thấy nó trong lịch sử pod, bạn có vấn đề bộ nhớ chứ không phải bug logic.

### 19.13.3 — Sửa bằng streaming

```csharp
[HttpGet("export")]
public async Task ExportLeads(CancellationToken ct)
{
    Response.ContentType = "text/csv";
    Response.Headers.ContentDisposition = "attachment; filename=leads.csv";

    await using var writer = new StreamWriter(Response.Body);
    await writer.WriteLineAsync("Name,Email,Value");

    // AsAsyncEnumerable: đọc TỪNG hàng, không nạp hết vào bộ nhớ
    var query = _db.Leads
        .AsNoTracking()
        .Where(l => l.TenantId == _tenant.Id)
        .Select(l => new { l.Name, l.Email, l.Value })
        .AsAsyncEnumerable();

    await foreach (var lead in query.WithCancellation(ct))
    {
        await writer.WriteLineAsync($"{Escape(lead.Name)},{lead.Email},{lead.Value}");
    }
}
```

Bộ nhớ giờ là **hằng số** — khoảng vài MB bất kể 5.000 hay 5 triệu bản ghi.

Bốn thay đổi tạo nên khác biệt:

| Thay đổi | Tác dụng |
|---|---|
| `AsAsyncEnumerable` | Đọc từng hàng, không nạp hết |
| `Select` projection | Chỉ lấy 3 cột cần |
| `AsNoTracking` | Không giữ snapshot change tracking |
| Ghi thẳng `Response.Body` | Không có bản sao trung gian nào |

Đổi từ Excel sang CSV cũng là một quyết định có chủ đích: định dạng Excel **buộc phải** dựng toàn bộ workbook trong bộ nhớ trước khi ghi ra. Nếu nghiệp vụ bắt buộc `.xlsx`, dùng thư viện hỗ trợ streaming (ví dụ chế độ `SpreadsheetWriter` của OpenXML SDK), hoặc chuyển export sang **job nền** và gửi link tải về sau ([bài 14.7](../../stage-04-database-production/module-14-caching-background-jobs/14.6-hangfire-background-jobs.mdx)).

### 19.13.4 — Lỗi phổ biến nhất khi sửa

```csharp
// VẪN SAI — ToListAsync vẫn nạp hết rồi mới ghi từng dòng
var leads = await query.ToListAsync(ct);
foreach (var lead in leads)
    await writer.WriteLineAsync(...);
```

Ghi ra từng dòng **không** giải quyết gì nếu bạn đã nạp hết vào bộ nhớ trước đó. Phần tốn bộ nhớ nằm ở `ToListAsync`, không phải ở vòng lặp ghi.

Một biến thể tinh vi hơn:

```csharp
// CŨNG SAI — phân trang nhưng vẫn gom lại
var all = new List<Lead>();
for (int page = 0; ; page++)
{
    var batch = await query.Skip(page * 1000).Take(1000).ToListAsync(ct);
    if (batch.Count == 0) break;
    all.AddRange(batch);            // vẫn gom hết vào bộ nhớ!
}
```

Phân trang chỉ giúp nếu bạn **xử lý xong rồi bỏ** mỗi lô, không giữ lại.

### 19.13.5 — Tự kiểm tra trong 5 phút

Ba câu hỏi rà nhanh toàn dự án:

**1. Tìm mọi `ToListAsync` không có `Take`:**

```bash
grep -rn "ToListAsync" --include=*.cs src/ | grep -v "Take(" | grep -v "FirstOrDefault"
```

Mỗi kết quả là một chỗ **có thể** nạp không giới hạn. Với truy vấn theo `TenantId`, số bản ghi phụ thuộc tenant — và một tenant lớn có thể làm sập hệ thống.

**2. Tìm `MemoryStream` kèm `ToArray`:**

```bash
grep -rn "\.ToArray()" --include=*.cs src/ | grep -i "stream"
```

`ToArray()` trên `MemoryStream` **nhân đôi** bộ nhớ ngay tại thời điểm đó. Dùng `GetBuffer()` hoặc ghi thẳng vào `Response.Body`.

**3. Kiểm tra lịch sử OOM:**

```bash
kubectl get pods -o json | jq -r '
  .items[] | select(.status.containerStatuses[]?.lastState.terminated.reason == "OOMKilled")
  | .metadata.name'
```

Nếu có kết quả, đã có OOM kill xảy ra mà có thể chưa ai để ý — vì nó không xuất hiện trong log ứng dụng.

## Bài tập áp dụng

#### Bài 1 — Tái hiện OOM

Tạo 200.000 bản ghi, chạy endpoint export kiểu cũ trong container giới hạn 512Mi, và xác nhận exit code 137.

**Tiêu chí hoàn thành:** bạn thấy tiến trình chết vì hết bộ nhớ, và phân biệt được **hai cách chết khác nhau** — và vì sao một trong hai tệ hơn nhiều.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Không có container cũng tái hiện được: `DOTNET_GCHeapHardLimit` cho runtime một trần bộ nhớ giống như giới hạn của container.

**Lời giải — hai chế độ, cùng dữ liệu:**

```csharp
if (che == "gom")
{
    // Kiểu cũ: gom hết vào bộ nhớ rồi mới ghi
    var ds = new List<string>(soDong);
    for (int i = 0; i < soDong; i++)
        ds.Add($"LEAD-{i};Người dùng số {i};nguoi{i}@congty.vn;...");

    var sb = new StringBuilder();
    foreach (var d in ds) sb.AppendLine(d);
}
else
{
    // Streaming: ghi từng dòng, không giữ lại
    await using var w = new StreamWriter(Stream.Null);
    for (int i = 0; i < soDong; i++)
        await w.WriteLineAsync($"LEAD-{i};Người dùng số {i};nguoi{i}@congty.vn;...");
}
```

**Lần đo 1 — 200.000 dòng, không giới hạn bộ nhớ:**

```text
--- gom ---
  dòng      0   heap    1,6 MB | RSS   28,7 MB
  dòng 50.000   heap   11,5 MB | RSS   43,4 MB
  dòng 100.000  heap   21,4 MB | RSS   54,7 MB
  dòng 150.000  heap   31,4 MB | RSS   65,0 MB
  xong gom      heap   76,6 MB | RSS  110,9 MB
  RSS đỉnh: 110,9 MB | 266 ms

--- streaming ---
  xong stream   heap    4,2 MB | RSS   51,3 MB
  RSS đỉnh:  51,3 MB | 136 ms
```

| | Gom hết | Streaming |
|---|---:|---:|
| Heap cuối | 76,6 MB | **4,2 MB** |
| RSS đỉnh | 110,9 MB | **51,3 MB** |
| Thời gian | 266 ms | **136 ms** |

Chú ý bước nhảy ở dòng `xong gom`: heap từ 31,4 lên 76,6 MB chỉ trong phần cuối. Đó là lúc `StringBuilder` dựng bản sao thứ hai của toàn bộ dữ liệu — danh sách và chuỗi kết quả cùng tồn tại.

**Lần đo 2 — 2 triệu dòng, trần heap 128 MB (`DOTNET_GCHeapHardLimit=8000000`):**

```text
--- gom ---
  dòng 400.000  heap   95,2 MB | RSS  120,9 MB
  dòng 450.000  heap  105,7 MB | RSS  135,6 MB
  dòng 500.000  heap  114,5 MB | RSS  144,6 MB
  OutOfMemoryException: Exception of type 'System.OutOfMemoryException' was thrown.
  RSS đỉnh trước khi lỗi: 144,6 MB

--- streaming ---
  dòng 1.950.000 heap    2,3 MB | RSS   44,4 MB
  xong stream    heap    2,6 MB | RSS   44,4 MB
  RSS đỉnh:  44,4 MB | 822 ms
```

**Bản gom chết ở dòng 500.000 trên 2 triệu. Bản streaming chạy hết 2 triệu dòng với heap giữ nguyên 2,3 MB.**

```text
Heap của bản streaming: 2,3 MB ở dòng 1.950.000
                        4,2 MB ở 200.000 dòng (lần đo 1)

-> bộ nhớ là HẰNG SỐ, không phụ thuộc số dòng
-> đúng như mục 19.13.3 nói, và giờ có số để chứng minh
```

**Hai cách chết khác nhau, và một trong hai tệ hơn nhiều:**

| | `OutOfMemoryException` | OOM kill của kernel |
|---|---|---|
| Khi nào | Runtime biết trần heap của mình | Runtime tưởng có nhiều bộ nhớ hơn thực tế |
| Ai giết | Runtime .NET | Kernel |
| Có ngoại lệ? | **Có** — bắt được, log được | **Không** |
| Trong log ứng dụng | Có stack trace | **Trống hoàn toàn** |
| Request đang chạy khác | Có thể vẫn xong | **Chết hết cùng lúc** |
| Dấu vết | Log ứng dụng | `exit code 137`, `reason: OOMKilled` |

```bash
kubectl get pod crm-api-7d4b9c5f8-2xk4p -o json \
  | jq '.status.containerStatuses[0].lastState.terminated | {reason, exitCode}'
```

```text
{
  "reason": "OOMKilled",
  "exitCode": 137
}
```

`137 = 128 + 9` — tiến trình nhận `SIGKILL`. Không có cơ hội chạy `finally`, không có cơ hội ghi log, không có cơ hội hoàn tất request nào khác.

**Vì sao OOM kill tệ hơn — ba lý do cụ thể:**

**1. Nó giết cả những request không liên quan.**

```text
Một người dùng bấm "Xuất dữ liệu" trên 2 triệu bản ghi
-> pod bị giết
-> 50 request khác đang chạy trên pod đó cũng chết
-> và không ai trong số 50 người đó làm gì sai
```

**2. Không có dấu vết trong log ứng dụng.**

```text
Log cuối cùng: một request bình thường
Rồi: im lặng, pod khởi động lại

-> chẩn đoán phải dựa vào kubectl describe, không phải log
-> và nếu không ai nghĩ tới việc kiểm tra lastState, sự cố bị ghi nhận
   nhầm thành "pod tự khởi động lại, chưa rõ nguyên nhân"
```

**3. Nó có thể thành vòng lặp.**

```text
Pod bị giết -> khởi động lại -> người dùng thử lại -> bị giết
-> CrashLoopBackOff, đúng mẫu ở bài 18.12
```

**Cấu hình để biến OOM kill thành `OutOfMemoryException`:**

```yaml
env:
  - name: DOTNET_GCHeapHardLimitPercent
    value: "4B"          # 0x4B = 75% của memory limit
resources:
  limits: { memory: "512Mi" }
```

```text
Không có nó: runtime tưởng có 8 GB -> để heap lớn dần -> kernel giết ở 512Mi
Có nó:       runtime biết trần 384 MB -> ném OutOfMemoryException
             -> request đó hỏng, ghi được log, các request khác vẫn sống
```

Nói cách khác: nó **không** sửa được lỗi, nhưng nó biến một sự cố toàn pod thành một lỗi của một request — và cho bạn một thông báo lỗi để lần ra nguyên nhân.

</details>

#### Bài 2 — Đo bộ nhớ hai cách

Dùng `dotnet-counters` theo dõi `GC Heap Size` trong lúc chạy cả hai phiên bản export.

**Tiêu chí hoàn thành:** bạn thấy **hình dạng** của hai đồ thị khác nhau, và biết chỉ số nào nói lên điều gì.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Con số đỉnh quan trọng, nhưng hình dạng theo thời gian còn nói nhiều hơn.

**Lời giải:**

```bash
dotnet-counters monitor --process-id $(pgrep -f Crm.Api) \
  --counters System.Runtime[gc-heap-size,gen-0-gc-count,gen-2-gc-count,alloc-rate,working-set] \
  --refresh-interval 1
```

```bash
# Ở cửa sổ khác
curl -o /dev/null "http://localhost:5000/api/leads/export?tenant=999"
```

**Phiên bản cũ — hình dạng "dốc lên rồi rơi":**

```text
t(s)  GC Heap (MB)  Gen-2 count  Alloc Rate (MB/s)  Working Set (MB)
----  ------------  -----------  -----------------  ----------------
   0          12,4            3                2,1              48,2
   2          31,4            3               84,0              65,0
   4          58,7            4              102,4              92,1
   6          76,6            5               96,8             110,9
   8         118,2            7              110,2             152,4
  10         144,6            9               98,1             181,0   <- đỉnh
  12          14,1           10                1,8              92,3   <- sau khi xong
```

**Phiên bản streaming — hình dạng "phẳng":**

```text
t(s)  GC Heap (MB)  Gen-2 count  Alloc Rate (MB/s)  Working Set (MB)
----  ------------  -----------  -----------------  ----------------
   0          12,1            3                2,0              47,8
   2           3,8            3               41,2              44,1
   4           2,3            3               40,8              44,4
   6           2,6            3               41,0              44,4
   8           2,4            3               40,9              44,4
  10           2,3            3               41,1              44,4
  12           2,6            3                1,9              44,2
```

**Ba khác biệt trong hình dạng, và mỗi cái nói một điều:**

**1. `GC Heap Size` — dốc lên so với phẳng.**

```text
Cũ:        12 -> 145 MB, tăng tuyến tính theo số dòng đã đọc
Streaming: dao động quanh 2–4 MB, KHÔNG phụ thuộc số dòng

-> đây là chỉ số trả lời "bộ nhớ có tỉ lệ với dữ liệu đầu vào không"
-> và đó đúng là câu hỏi quyết định endpoint này có an toàn hay không
```

**2. `Gen-2 GC Count` — từ 3 lên 10 so với đứng yên ở 3.**

```text
Cũ: 7 lần gen-2 GC trong 10 giây
    -> mỗi lần gen-2 blocking đều DỪNG mọi luồng
    -> p99 của MỌI endpoint khác tăng trong khoảng đó

Streaming: 0 lần gen-2 thêm
    -> object chết ngay trong gen-0, không bao giờ lên tới gen-2
```

Đây là chỉ số cho biết endpoint này có làm phiền phần còn lại của hệ thống hay không — và nó không xuất hiện trong bất kỳ biểu đồ độ trễ nào của chính endpoint đó.

**3. `Alloc Rate` — 100 MB/s so với 41 MB/s.**

```text
Cả hai đều cấp phát, nhưng:
    Cũ:        cấp phát rồi GIỮ LẠI -> lên gen-1, gen-2
    Streaming: cấp phát rồi BỎ NGAY -> chết trong gen-0, rất rẻ

-> alloc rate cao KHÔNG tự động là vấn đề
-> vấn đề là object SỐNG SÓT qua gen-0
```

Đây là điểm hay bị hiểu sai: gen-0 GC rất rẻ vì nó chỉ đi qua những object còn sống. Cấp phát nhiều object chết ngay gần như không tốn gì. Cấp phát nhiều object **sống** mới đắt.

**4. Và `Working Set` tụt chậm hơn `GC Heap`.**

```text
t=12: GC Heap về 14,1 MB nhưng Working Set vẫn 92,3 MB

-> GC đã giải phóng, nhưng bộ nhớ chưa được TRẢ VỀ hệ điều hành
-> .NET giữ lại để dùng cho lần sau
-> nên RSS cao sau một đợt tải KHÔNG nhất thiết là rò rỉ
```

Phân biệt với rò rỉ thật: ở [bài 19.3](19.3-dotnet-server-profiling.mdx), heap **không** giảm sau `GC.Collect` đầy đủ. Ở đây heap giảm từ 144,6 xuống 14,1 MB — bộ nhớ đã được thu hồi đúng, chỉ là RSS chưa trả lại hệ điều hành.

**Đưa việc này thành test, để không phải nhớ đo bằng tay:**

```csharp
[Fact]
public async Task Export_khong_tang_bo_nho_theo_so_dong()
{
    async Task<long> DoAsync(int soDong)
    {
        await _fixture.TaoLeadAsync(soDong);
        GC.Collect(2, GCCollectionMode.Forced, true, true);
        var truoc = GC.GetTotalAllocatedBytes();

        using var res = await _client.GetAsync("/api/leads/export", HttpCompletionOption.ResponseHeadersRead);
        await res.Content.CopyToAsync(Stream.Null);

        return GC.GetTotalAllocatedBytes() - truoc;
    }

    var nho  = await DoAsync(1_000);
    var lon  = await DoAsync(100_000);

    // Cấp phát tăng theo số dòng là bình thường; điều KHÔNG bình thường là
    // đỉnh bộ nhớ tăng theo. Ở đây kiểm tra tỉ lệ cấp phát không vượt quá tuyến tính.
    (lon / (double)nho).Should().BeLessThan(150,
        "gấp 100 lần dữ liệu không được làm cấp phát tăng hơn 150 lần");
}
```

Với streaming, tỉ lệ bám sát 100 lần (tuyến tính theo dữ liệu, đúng như mong đợi). Với bản gom hết, nó vượt lên vì các bản sao trung gian — và đó là thứ test này bắt được.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Code có bộ nhớ tỷ lệ với dữ liệu đầu vào là quả bom hẹn giờ** — nó chỉ chờ một tenant đủ lớn.

3. **Streaming giữ bộ nhớ ở mức hằng số**, bất kể dữ liệu lớn tới đâu.
