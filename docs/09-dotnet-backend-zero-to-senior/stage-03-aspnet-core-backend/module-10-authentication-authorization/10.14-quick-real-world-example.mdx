# 10.14 — Ví dụ thực tế nhanh

<SummaryBox>
Lỗ hổng phổ biến nhất trong ứng dụng nghiệp vụ, và cũng dễ bỏ sót nhất: endpoint có `[Authorize(Roles = "Sales")]` nên trông đã được bảo vệ, nhưng bất kỳ nhân viên sales nào cũng **sửa được lead của đồng nghiệp** chỉ bằng cách đổi id trên URL. Nguyên nhân là nhầm lẫn giữa hai câu hỏi khác nhau: *"người này có phải nhân viên sales không"* (vai trò) và *"người này có được sửa **bản ghi cụ thể này** không"* (tài nguyên). `[Authorize]` chỉ trả lời câu đầu. Đây là lớp lỗ hổng mà **OWASP xếp hạng cao nhất** — và nó không xuất hiện trong test vì test thường chỉ dùng dữ liệu của chính người dùng đang đăng nhập.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Phân biệt phân quyền theo vai trò và theo tài nguyên.
- Cài `IAuthorizationHandler` cho tài nguyên cụ thể.
- Tránh lộ thông tin qua sự khác biệt giữa 403 và 404.
- Viết test bắt được lỗ hổng này.

## Nội dung bài học

### 10.14.1 — Lỗ hổng

```csharp
[Authorize(Roles = "Sales")]
[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(Guid id, UpdateLeadRequest request, CancellationToken ct)
{
    var lead = await _db.Leads.FindAsync([new LeadId(id)], ct);
    if (lead is null) return NotFound();

    lead.Update(request.Name, request.Value);       // KHONG kiem tra chu so huu
    await _db.SaveChangesAsync(ct);

    return NoContent();
}
```

```
Nhan vien A (sales) dang nhap, xem lead cua minh:
  PUT /api/leads/8f3a1b2c-...     -> OK, dung

Nhan vien A doi id tren URL:
  PUT /api/leads/7c1d9e4f-...     -> OK, VA DAY LA LEAD CUA NHAN VIEN B
```

`[Authorize(Roles = "Sales")]` trả lời đúng câu hỏi nó được hỏi: A **có** vai trò Sales. Nhưng câu hỏi cần trả lời là: A có được sửa **lead này** không?

Lớp lỗ hổng này gọi là **Broken Object Level Authorization**, và nó đứng đầu danh sách rủi ro API của OWASP. Lý do nó phổ biến: endpoint trông đã được bảo vệ, và test thường chỉ dùng dữ liệu của chính người dùng đang đăng nhập nên không phát hiện ra.

### 10.14.2 — Sửa nhanh và sửa đúng

**Sửa nhanh — kiểm tra ngay trong controller:**

```csharp
var lead = await _db.Leads.FindAsync([new LeadId(id)], ct);
if (lead is null) return NotFound();

if (lead.OwnerId != _currentUser.Id && !User.IsInRole("SalesManager"))
    return Forbid();
```

Nó hoạt động, nhưng logic này sẽ phải **lặp lại ở mọi endpoint** động tới lead — và chỗ nào quên là một lỗ hổng.

**Sửa đúng — tách thành policy dùng chung:**

```csharp
public sealed class LeadOwnerRequirement : IAuthorizationRequirement;

public sealed class LeadOwnerHandler(ICurrentUser currentUser)
    : AuthorizationHandler<LeadOwnerRequirement, Lead>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        LeadOwnerRequirement requirement,
        Lead lead)
    {
        if (lead.OwnerId == currentUser.Id)
            context.Succeed(requirement);

        else if (context.User.IsInRole("SalesManager") &&
                 lead.TenantId == currentUser.TenantId)
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
```

```csharp
builder.Services.AddScoped<IAuthorizationHandler, LeadOwnerHandler>();
builder.Services.AddAuthorization(options =>
    options.AddPolicy("LeadOwner", p => p.Requirements.Add(new LeadOwnerRequirement())));
```

```csharp
[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(
    Guid id, UpdateLeadRequest request, CancellationToken ct)
{
    var lead = await _db.Leads.FindAsync([new LeadId(id)], ct);
    if (lead is null) return NotFound();

    var authorized = await _authorizationService.AuthorizeAsync(User, lead, "LeadOwner");
    if (!authorized.Succeeded) return Forbid();

    lead.Update(request.Name, request.Value);
    await _db.SaveChangesAsync(ct);
    return NoContent();
}
```

Ba lợi ích so với cách sửa nhanh: quy tắc nằm **một chỗ**, test được độc lập, và khi quy tắc đổi (thêm vai trò được xem chéo chẳng hạn) bạn sửa một file thay vì rà cả codebase ([bài 10.7](10.7-resource-based-authorization.mdx)).

Lưu ý thứ tự: **phải nạp tài nguyên trước** rồi mới phân quyền được — đó là lý do không dùng được attribute `[Authorize(Policy = "LeadOwner")]` đặt trên action.

### 10.14.3 — Cái bẫy: 403 làm lộ thông tin

```csharp
if (lead is null) return NotFound();        // 404
if (!authorized.Succeeded) return Forbid(); // 403
```

Hai mã khác nhau **tiết lộ** thông tin:

```
GET /api/leads/{id-khong-ton-tai}      -> 404
GET /api/leads/{id-cua-nguoi-khac}     -> 403   <- xac nhan ID NAY TON TAI
```

Kẻ tấn công dò id và phân biệt được id nào tồn tại — đủ để suy ra quy mô dữ liệu, và trong một số trường hợp id mang ý nghĩa (số hoá đơn tăng dần chẳng hạn) thì đó là rò rỉ thật.

**Với dữ liệu nhạy cảm, trả `404` cho cả hai:**

```csharp
var lead = await _db.Leads.FindAsync([new LeadId(id)], ct);

var authorized = lead is not null &&
    (await _authorizationService.AuthorizeAsync(User, lead, "LeadOwner")).Succeeded;

if (!authorized) return NotFound();      // khong phan biet duoc
```

**Đánh đổi:** người dùng hợp lệ gặp lỗi phân quyền sẽ thấy "không tìm thấy" thay vì "không có quyền" — khó hiểu hơn, và có thể làm tăng số cuộc gọi hỗ trợ.

Cân bằng thực dụng: dùng `403` cho ứng dụng nội bộ (nơi mọi người dùng đã được tin tưởng ở mức cơ bản) và `404` cho API công khai hoặc dữ liệu nhạy cảm.

### 10.14.4 — Lọc theo tenant: phòng thủ hai lớp

Trong hệ multi-tenant, kiểm tra ở tầng ứng dụng **không đủ** — một chỗ quên là rò rỉ dữ liệu giữa các công ty khác nhau.

```csharp
// Global query filter — ap dung TU DONG cho MOI truy van
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Lead>()
        .HasQueryFilter(l => l.TenantId == _tenantContext.TenantId);
}
```

Giờ `_db.Leads.FindAsync(id)` **không bao giờ** trả về lead của tenant khác, kể cả khi lập trình viên quên kiểm tra. Đây là lớp phòng thủ ở tầng dữ liệu, dưới cả tầng phân quyền ([bài 13.11](../../stage-04-database-production/module-13-entity-framework-core/13.11-global-query-filters.mdx)).

**Hai cái bẫy của global query filter:**

```csharp
// 1. IgnoreQueryFilters bo qua HET — chi dung trong job he thong
var tatCa = await _db.Leads.IgnoreQueryFilters().ToListAsync(ct);

// 2. Filter dung gia tri tu scoped service nhung DbContext bi cache model
// -> neu TenantId duoc doc luc DUNG MODEL, moi tenant se dung chung filter cua
//    tenant dau tien. Phai dung IModelCacheKeyFactory theo tenant.
```

Cái bẫy thứ hai tinh vi và nguy hiểm: EF Core cache model đã dựng, nên nếu biểu thức filter chụp giá trị `TenantId` tại thời điểm dựng model, mọi tenant sau đó dùng chung giá trị của tenant đầu tiên. Cách tránh là tham chiếu tới **service** trong biểu thức (như ví dụ trên) chứ không tới **giá trị**.

### 10.14.5 — Test bắt được lỗ hổng

Test thông thường không phát hiện được vì nó dùng dữ liệu của chính người dùng đang đăng nhập:

```csharp
[Fact]
public async Task Update_TraVe403_KhiSuaLeadCuaNguoiKhac()
{
    var leadCuaB = await SeedLeadAsync(ownerId: _userB.Id);

    var client = _factory.CreateClientAs(_userA);      // dang nhap la A
    var response = await client.PutAsJsonAsync(
        $"/api/leads/{leadCuaB.Id}", new { Name = "Đã sửa" });

    Assert.Equal(HttpStatusCode.Forbidden, response.StatusCode);
}

[Fact]
public async Task Get_TraVe404_KhiDocLeadCuaTenantKhac()
{
    var leadTenantB = await SeedLeadAsync(tenantId: _tenantB.Id);

    var client = _factory.CreateClientAs(_userTenantA);
    var response = await client.GetAsync($"/api/leads/{leadTenantB.Id}");

    Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
}
```

**Quy tắc:** mỗi endpoint nhận id từ client cần **ít nhất một** test dùng id của người khác. Đây là loại test dễ viết và bắt được đúng lớp lỗ hổng nghiêm trọng nhất ([bài 16.10](../../stage-05-senior-engineering/module-16-clean-architecture/16.10-testing-strategy-overview.mdx)).

## Bài tập áp dụng

1. **Tìm lỗ hổng.** Rà mọi endpoint nhận id từ route và đếm số endpoint không kiểm tra quyền trên bản ghi.

2. **Viết policy.** Cài một `AuthorizationHandler` cho một loại tài nguyên và thay các kiểm tra rải rác bằng nó.

3. **Test cách ly tenant.** Viết test gọi API bằng token của tenant A với id của tenant B và xác nhận không rò rỉ.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Vai trò và tài nguyên là hai câu hỏi khác nhau.** `[Authorize]` chỉ trả lời câu đầu.
2. **Global query filter là lớp phòng thủ ở tầng dữ liệu** — nó đúng cả khi lập trình viên quên.
3. **Mỗi endpoint nhận id cần một test dùng id của người khác.**
