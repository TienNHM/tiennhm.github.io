# 9.5 — 4. Pagination, Filtering, Sorting

<SummaryBox>
Phân trang có hai kiểu và chúng **không thay thế được cho nhau**. **Offset** (`?page=3&pageSize=20`) quen thuộc và cho nhảy tới trang bất kỳ, nhưng có hai khuyết điểm nghiêm trọng: `OFFSET 100000` buộc database **đọc và bỏ** 100.000 dòng, và nếu dữ liệu thay đổi giữa hai lần gọi thì người dùng **bỏ sót hoặc thấy trùng** bản ghi. **Cursor** giải quyết cả hai bằng cách hỏi "cho tôi 20 bản ghi **sau** bản ghi này", nhưng đánh đổi: không có tổng số trang và không nhảy được. Ngoài ra bài này có hai thứ bắt buộc về an toàn: **whitelist cho `sortBy`** và **trần cứng cho `pageSize`**.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích vì sao `OFFSET` lớn chậm và vì sao nó bỏ sót bản ghi.
- Cài cursor pagination với khoá ổn định.
- Chặn sorting tuỳ ý bằng whitelist.
- Đặt trần cho `pageSize` và xác thực tham số phân trang.
- Tránh đếm tổng khi không cần.

## Nội dung bài học

### 9.5.1 — Tham số và vỏ phản hồi

```csharp
public record PaginationRequest
{
    private const int MaxPageSize = 100;
    private int _pageSize = 20;

    [Range(1, int.MaxValue)]
    public int Page { get; init; } = 1;

    [Range(1, MaxPageSize)]
    public int PageSize
    {
        get => _pageSize;
        init => _pageSize = value is > 0 and <= MaxPageSize ? value : MaxPageSize;
    }

    public int Skip => (Page - 1) * PageSize;
}
```

Trần cứng trong setter là **tầng phòng thủ thứ hai** sau `[Range]`. Nếu ai đó gọi endpoint từ code nội bộ mà bỏ qua validation, `pageSize=1000000` vẫn bị chặn.

Đây không phải chuyện lý thuyết: một `pageSize` không giới hạn là cách đơn giản nhất để làm sập API của bạn — một request kéo toàn bộ bảng.

```csharp
public record PagedResponse<T>
{
    public required IReadOnlyList<T> Data { get; init; }
    public required PaginationMeta Pagination { get; init; }
}

public record PaginationMeta
{
    public required int Page { get; init; }
    public required int PageSize { get; init; }
    public required int Total { get; init; }
    public int TotalPages => (int)Math.Ceiling((double)Total / PageSize);
    public bool HasNext => Page < TotalPages;
    public bool HasPrev => Page > 1;
}
```

### 9.5.2 — Hai vấn đề của offset

**Vấn đề 1: chậm dần theo số trang.**

```sql
SELECT * FROM Customers ORDER BY CreatedAt DESC
OFFSET 100000 ROWS FETCH NEXT 20 ROWS ONLY;
```

Database phải **đọc 100.020 dòng** rồi vứt đi 100.000 dòng đầu. Trang 1 mất vài mili giây; trang 5000 mất vài giây. Và chi phí này tăng **tuyến tính** theo số trang.

**Vấn đề 2: bỏ sót và trùng lặp.**

```
t=0   Người dùng xem trang 1 (bản ghi 1-20, mới nhất trước)
t=1   Có 5 bản ghi MỚI được tạo
t=2   Người dùng bấm trang 2 -> OFFSET 20
      => 5 ban ghi cuoi cua trang 1 cu bi day xuong va hien LAI o trang 2
      => 5 ban ghi khac bi BO SOT hoan toan
```

Với danh sách người dùng lướt thì đây là phiền toái. Với **job đồng bộ dữ liệu** duyệt hết mọi trang thì đây là **mất dữ liệu im lặng** — và rất khó phát hiện.

### 9.5.3 — Cursor pagination

Thay vì "bỏ qua N dòng", hỏi "cho tôi N dòng **sau** dòng này":

```sql
SELECT TOP 20 * FROM Customers
WHERE (CreatedAt, Id) < (@lastCreatedAt, @lastId)
ORDER BY CreatedAt DESC, Id DESC;
```

```csharp
public async Task<CursorResponse<CustomerDto>> GetPageAsync(
    string? cursor, int pageSize, CancellationToken ct)
{
    var query = _db.Customers.AsNoTracking();

    if (cursor is not null)
    {
        var (lastCreatedAt, lastId) = DecodeCursor(cursor);
        query = query.Where(c =>
            c.CreatedAt < lastCreatedAt ||
            (c.CreatedAt == lastCreatedAt && c.Id < lastId));   // tie-breaker
    }

    var items = await query
        .OrderByDescending(c => c.CreatedAt).ThenByDescending(c => c.Id)
        .Take(pageSize + 1)                                    // lấy dư 1 để biết còn nữa không
        .Select(c => new CustomerDto(c.Id, c.Name, c.Email, c.CreatedAt))
        .ToListAsync(ct);

    var hasMore = items.Count > pageSize;
    if (hasMore) items.RemoveAt(pageSize);

    return new CursorResponse<CustomerDto>
    {
        Data = items,
        NextCursor = hasMore ? EncodeCursor(items[^1].CreatedAt, items[^1].Id) : null
    };
}
```

Ba chi tiết quyết định nó đúng hay sai:

1. **Tie-breaker bắt buộc.** `CreatedAt` không duy nhất — hai bản ghi tạo cùng mili giây sẽ bị bỏ sót hoặc lặp. Luôn thêm `Id` làm khoá phụ, và `ORDER BY` phải khớp chính xác điều kiện `WHERE`.
2. **`Take(pageSize + 1)`** để biết còn trang sau mà không phải `COUNT` thêm một lần.
3. **Mã hoá cursor** thành chuỗi mờ (Base64 của JSON) để client coi nó là con trỏ chứ không phải dữ liệu để chỉnh sửa.

| | Offset | Cursor |
|---|---|---|
| Nhảy tới trang bất kỳ | **Có** | Không |
| Tổng số trang | **Có** | Không |
| Hiệu năng ở trang sâu | Kém dần | **Ổn định** |
| Nhất quán khi dữ liệu đổi | Không | **Có** |
| Độ phức tạp | Thấp | Trung bình |

**Chọn thế nào:** giao diện quản trị có thanh số trang → offset. API công khai, cuộn vô hạn, feed, job đồng bộ dữ liệu → cursor.

### 9.5.4 — Filtering trên `IQueryable`

```csharp
public static IQueryable<Customer> ApplyFilters(
    this IQueryable<Customer> query, CustomerFilterRequest request)
{
    if (!string.IsNullOrWhiteSpace(request.Search))
        query = query.Where(c => c.Name.Contains(request.Search)
                              || c.Email.Contains(request.Search));

    if (request.Status is not null)
        query = query.Where(c => c.Status == request.Status);

    if (request.CreatedFrom is { } from)
        query = query.Where(c => c.CreatedAt >= from);

    if (request.CreatedTo is { } to)
        query = query.Where(c => c.CreatedAt < to.AddDays(1));   // bao gom ca ngay do

    return query;
}
```

`IQueryable` nghĩa là mọi `Where` được **dịch sang SQL** và gộp vào một câu lệnh. Một `.ToList()` đặt sớm sẽ kéo cả bảng về bộ nhớ rồi lọc trong ứng dụng — xem [Module 5 — Advanced C#](../../stage-02-csharp-professional/module-05-advanced-csharp/).

Hai điểm dễ sai:

- **`Contains` sinh ra `LIKE '%...%'`**, không dùng được index. Với bảng lớn, đó là quét toàn bảng ở mỗi lần gõ phím trong ô tìm kiếm. Giải pháp là full-text search, hoặc tối thiểu yêu cầu độ dài tối thiểu cho từ khoá.
- **So sánh ngày.** `<= to` với `to` là `2026-09-24 00:00:00` sẽ **loại** mọi bản ghi trong ngày 24. Dùng `< to.AddDays(1)`.

### 9.5.5 — Sorting phải có whitelist

```csharp
// SAI — cho phép sắp xếp theo bất kỳ cột nào
query = query.OrderBy(request.SortBy);      // Dynamic LINQ

// DUNG — whitelist
private static readonly Dictionary<string, Expression<Func<Customer, object>>> Sortable =
    new(StringComparer.OrdinalIgnoreCase)
    {
        ["name"]      = c => c.Name,
        ["email"]     = c => c.Email,
        ["createdAt"] = c => c.CreatedAt,
        ["status"]    = c => c.Status,
    };

public static IQueryable<Customer> ApplySort(
    this IQueryable<Customer> query, string? sortBy, string? sortDir)
{
    var key = Sortable.TryGetValue(sortBy ?? "createdAt", out var expr) ? expr : Sortable["createdAt"];
    var desc = !string.Equals(sortDir, "asc", StringComparison.OrdinalIgnoreCase);

    query = desc ? query.OrderByDescending(key) : query.OrderBy(key);

    return query.ThenBy(c => c.Id);       // thứ tự ổn định
}
```

Whitelist giải quyết ba vấn đề cùng lúc:

1. **Không sắp xếp được theo cột không có index** → không ai vô tình gây quét toàn bảng.
2. **Không lộ cột nội bộ** — client không sắp xếp được theo `PasswordHash` để suy ra thông tin.
3. **Không nhận chuỗi tuỳ ý** vào biểu thức truy vấn.

`ThenBy(c => c.Id)` là chi tiết nhỏ nhưng quan trọng: không có nó, hai bản ghi cùng giá trị sắp xếp có thứ tự **không xác định**, và chúng có thể đổi chỗ giữa hai lần gọi — gây ra đúng vấn đề bỏ sót như ở mục 9.5.2.

### 9.5.6 — Đừng đếm khi không cần

```csharp
var total = await query.CountAsync(ct);     // MOT truy van
var items = await query.Skip(...).Take(...).ToListAsync(ct);   // truy van THU HAI
```

Mỗi trang là **hai** truy vấn, và `COUNT` với điều kiện lọc phức tạp thường **đắt hơn** truy vấn lấy dữ liệu.

Ba cách giảm:

```csharp
// 1. Không trả tổng — chỉ cho biết còn trang sau không
var items = await query.Skip(skip).Take(pageSize + 1).ToListAsync(ct);
var hasNext = items.Count > pageSize;

// 2. Cache tổng trong thời gian ngắn khi bộ lọc không đổi
// 3. Trả tổng gần đúng khi vượt ngưỡng: "hơn 10.000 kết quả"
```

Google, GitHub và phần lớn API lớn đều làm cách 1 hoặc 3. Người dùng hiếm khi cần biết chính xác có 48.213 kết quả; họ cần biết **có còn trang sau không**.

### 9.5.7 — Endpoint hoàn chỉnh

```csharp
[HttpGet]
[ProducesResponseType<PagedResponse<CustomerDto>>(StatusCodes.Status200OK)]
public async Task<ActionResult<PagedResponse<CustomerDto>>> GetAll(
    [FromQuery] CustomerFilterRequest request, CancellationToken ct)
{
    var query = _db.Customers
        .AsNoTracking()                     // chi doc -> tat change tracker
        .ApplyFilters(request)
        .ApplySort(request.SortBy, request.SortDir);

    var total = await query.CountAsync(ct);

    var items = await query
        .Skip(request.Skip)
        .Take(request.PageSize)
        .Select(c => new CustomerDto(c.Id, c.Name, c.Email, c.Status, c.CreatedAt))
        .ToListAsync(ct);

    return Ok(new PagedResponse<CustomerDto>
    {
        Data = items,
        Pagination = new PaginationMeta
        {
            Page = request.Page, PageSize = request.PageSize, Total = total
        }
    });
}
```

Hai chi tiết hiệu năng: `AsNoTracking()` bỏ change tracker cho truy vấn chỉ đọc, và `.Select(...)` **trước** `ToListAsync` khiến SQL chỉ lấy đúng những cột cần — không kéo về `Notes` dài 10KB mà DTO không dùng.

Và nhớ [bài về N+1](/blog/ef-core-n-plus-1-query): nếu `CustomerDto` có danh sách con, `Select` lồng nhau là đúng còn truy cập navigation property trong vòng lặp là sai.

## Bài tập áp dụng

#### Bài 1 — Đo chi phí của `OFFSET`

Tạo bảng 1 triệu bản ghi, đo thời gian lấy trang 1, trang 100, trang 10.000. So sánh với phân trang theo con trỏ trên cùng dữ liệu.

**Tiêu chí hoàn thành:** bạn giải thích được vì sao thời gian tăng theo **số trang**, dù mỗi trang vẫn trả về đúng 20 dòng.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** `OFFSET 200000` không nói với database "nhảy tới dòng 200.000". Nó nói "đọc và **bỏ đi** 200.000 dòng đầu". Hãy nghĩ xem việc bỏ đi đó tốn gì.

**Lời giải — đo bằng SQL:**

```sql
-- Trang 1
EXPLAIN ANALYZE
SELECT * FROM "Orders" ORDER BY "CreatedAt" DESC LIMIT 20 OFFSET 0;

-- Trang 100
EXPLAIN ANALYZE
SELECT * FROM "Orders" ORDER BY "CreatedAt" DESC LIMIT 20 OFFSET 2000;

-- Trang 10.000
EXPLAIN ANALYZE
SELECT * FROM "Orders" ORDER BY "CreatedAt" DESC LIMIT 20 OFFSET 200000;
```

**Kết quả điển hình trên bảng 1 triệu dòng có chỉ mục trên `CreatedAt`:**

| Trang | `OFFSET` | Thời gian | Số dòng database phải đọc |
|---|---|---|---|
| 1 | 0 | ~0,5 ms | 20 |
| 100 | 2.000 | ~3 ms | 2.020 |
| 10.000 | 200.000 | **~250 ms** | **200.020** |

**Vì sao tăng theo số trang.** Database phải **đọc và sắp xếp** toàn bộ 200.000 dòng đầu tiên rồi mới vứt chúng đi. Công việc đó tỉ lệ thuận với `OFFSET`, chứ không phải với số dòng trả về.

Đây là O(n) với n là **vị trí trang**, không phải O(1) như trực giác gợi ý.

**Phân trang theo con trỏ:**

```sql
-- Trang bất kỳ — dùng giá trị của dòng cuối trang trước làm mốc
SELECT * FROM "Orders"
WHERE ("CreatedAt", "Id") < (@lastCreatedAt, @lastId)
ORDER BY "CreatedAt" DESC, "Id" DESC
LIMIT 20;
```

| Trang | Thời gian |
|---|---|
| 1 | ~0,5 ms |
| 100 | ~0,5 ms |
| 10.000 | **~0,5 ms** |

**Không đổi**, vì chỉ mục cho phép nhảy thẳng tới vị trí bắt đầu. Đây là O(log n) của B-tree, đúng như [bài 1.8](../../stage-01-foundation/module-01-programming-logic/1.7-data-structures-and-big-o.mdx) mô tả.

**Cài đặt trong EF Core:**

```csharp
public record Cursor(DateTime CreatedAt, int Id);

var q = db.Orders.AsNoTracking();

if (cursor is not null)
    q = q.Where(o => o.CreatedAt < cursor.CreatedAt
                  || (o.CreatedAt == cursor.CreatedAt && o.Id < cursor.Id));

var items = await q.OrderByDescending(o => o.CreatedAt)
                   .ThenByDescending(o => o.Id)
                   .Take(size + 1)                    // lấy dư 1 để biết còn trang sau
                   .ToListAsync(ct);

var coTrangSau = items.Count > size;
if (coTrangSau) items.RemoveAt(size);
```

**Ba lưu ý khi cài đặt:**

1. **Phải có tie-breaker.** Cột `Id` trong điều kiện là bắt buộc — không có nó, các bản ghi trùng `CreatedAt` sẽ bị lặp hoặc bị sót. Bài 3 chứng minh điều này.
2. **Lấy dư một dòng** để biết có trang sau không, thay vì chạy thêm một truy vấn `COUNT`.
3. **Mã hoá con trỏ** trước khi trả cho client, để họ không phụ thuộc vào cấu trúc bên trong:

   ```csharp
   var token = Convert.ToBase64String(JsonSerializer.SerializeToUtf8Bytes(cursor));
   ```

**Chọn cách nào:**

| | Offset | Cursor |
|---|---|---|
| Nhảy tới trang bất kỳ | **Có** | Không |
| Hiển thị tổng số trang | **Có** | Không |
| Hiệu năng ở trang xa | **Kém** | Không đổi |
| Ổn định khi dữ liệu thay đổi | **Không** | Có |

Dùng offset cho giao diện quản trị có phân trang số trang và dữ liệu vừa phải. Dùng cursor cho danh sách cuộn vô hạn, cho API công khai, và cho mọi thứ vượt vài nghìn bản ghi.

</details>

#### Bài 2 — Mất bản ghi khi phân trang bằng offset

Viết script duyệt hết mọi trang bằng offset trong khi một script khác chèn bản ghi mới liên tục. Đếm số bản ghi thu được so với thực tế. Lặp lại với cursor.

**Tiêu chí hoàn thành:** bạn giải thích được **cả hai** hiện tượng — bỏ sót và lặp lại — và điều kiện gây ra từng cái.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** `OFFSET` đếm theo **vị trí** trong kết quả sắp xếp. Khi dữ liệu thay đổi giữa hai lần gọi, vị trí của mọi bản ghi dịch chuyển.

**Lời giải — minh hoạ bằng số:**

```text
Trạng thái ban đầu, sắp xếp CreatedAt giảm dần:
  [A, B, C, D, E, F]        (A mới nhất)

Client lấy trang 1: LIMIT 2 OFFSET 0  ->  [A, B]

Trong lúc đó, bản ghi mới Z được chèn vào (mới nhất):
  [Z, A, B, C, D, E, F]

Client lấy trang 2: LIMIT 2 OFFSET 2  ->  [B, C]
                                            ^ B ĐÃ LẤY RỒI — LẶP LẠI
```

**Chiều ngược lại — bản ghi bị xoá:**

```text
Ban đầu: [A, B, C, D, E, F]
Trang 1: OFFSET 0 -> [A, B]

A bị xoá:  [B, C, D, E, F]

Trang 2: OFFSET 2 -> [D, E]
                      ^ C BỊ BỎ SÓT
```

**Hai hiện tượng, hai điều kiện:**

| Hiện tượng | Xảy ra khi | Hậu quả |
|---|---|---|
| **Lặp lại** | Bản ghi mới được chèn vào **trước** vị trí hiện tại | Xử lý trùng — gửi email hai lần, tính tiền hai lần |
| **Bỏ sót** | Bản ghi bị xoá **trước** vị trí hiện tại | Mất dữ liệu — không xuất hiện trong báo cáo |

Với danh sách sắp xếp mới nhất lên đầu, **lặp lại phổ biến hơn nhiều**, vì bản ghi mới luôn được chèn vào đầu.

**Đo thật:**

```bash
# Script A — duyệt hết mọi trang
page=1; total=0
while true; do
  n=$(curl -s "localhost:5000/api/v1/orders?page=$page&size=100" | jq '.items | length')
  [ "$n" -eq 0 ] && break
  total=$((total + n)); page=$((page + 1))
done
echo "thu được $total bản ghi"

# Script B — chạy song song, chèn liên tục
while true; do curl -s -X POST localhost:5000/api/v1/orders -d '{...}' > /dev/null; sleep 0.1; done
```

Kết quả điển hình: số bản ghi thu được **nhiều hơn** tổng thật, và trong đó có bản ghi trùng.

**Với cursor thì không xảy ra:**

```sql
WHERE ("CreatedAt", "Id") < (@last, @lastId)
```

Điều kiện dựa trên **giá trị**, không dựa trên vị trí. Chèn thêm bản ghi mới ở đầu danh sách không ảnh hưởng gì tới việc "lấy những bản ghi cũ hơn mốc này".

**Bản ghi mới chèn vào vẫn không xuất hiện** trong lượt duyệt đang chạy — nhưng đó là hành vi **đúng và mong muốn**: bạn đang duyệt một ảnh chụp logic của dữ liệu tại thời điểm bắt đầu.

**Hệ quả thực tế.** Với các tác vụ duyệt toàn bộ dữ liệu — đồng bộ sang hệ thống khác, xuất báo cáo, gửi email hàng loạt — dùng offset nghĩa là **chấp nhận sai số**. Ba lựa chọn đúng:

1. **Dùng cursor**, như trên.
2. **Chốt một mốc thời gian** và chỉ lấy dữ liệu trước mốc đó:

   ```csharp
   var moc = DateTime.UtcNow;
   var q = db.Orders.Where(o => o.CreatedAt <= moc);   // dữ liệu mới không lọt vào
   ```
3. **Dùng giao dịch có mức cô lập ảnh chụp**, nếu database hỗ trợ và tập dữ liệu không quá lớn.

Cách 2 đơn giản nhất và giải quyết được phần lớn trường hợp.

</details>

#### Bài 3 — Sắp xếp không ổn định

Sắp xếp theo một cột có nhiều giá trị trùng, **không** có tie-breaker, gọi cùng một trang 10 lần và so sánh kết quả.

**Tiêu chí hoàn thành:** bạn quan sát được kết quả **khác nhau giữa các lần gọi** và nêu được vì sao database được phép làm vậy.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** SQL **không bảo đảm** thứ tự của các dòng có cùng giá trị sắp xếp. Database tự do trả về chúng theo bất kỳ thứ tự nào thuận tiện cho kế hoạch thực thi.

**Lời giải.**

```sql
-- Bảng có 10.000 đơn hàng, tất cả cùng Status = 'Pending'
SELECT "Id" FROM "Orders" WHERE "Status" = 'Pending'
ORDER BY "Status"
LIMIT 5 OFFSET 100;
```

Chạy 10 lần:

```text
lần 1: 4821, 4822, 4823, 4824, 4825
lần 2: 4821, 4822, 4823, 4824, 4825
lần 3: 7412, 7413, 7414, 7415, 7416      <- KHÁC
lần 4: 4821, 4822, 4823, 4824, 4825
...
```

Kết quả thay đổi, thường sau khi database đổi kế hoạch thực thi — do thống kê được cập nhật, do dữ liệu thay đổi, hoặc do có truy vấn song song.

**Vì sao database được phép.** Chuẩn SQL chỉ bảo đảm thứ tự theo **các cột được nêu trong `ORDER BY`**. Với các dòng có cùng giá trị ở mọi cột đó, thứ tự là **không xác định** — và database tận dụng quyền tự do này để chọn kế hoạch nhanh nhất, ví dụ đọc song song nhiều phân vùng.

**Hậu quả khi phân trang:**

```text
Trang 1 (OFFSET 0):  lấy 20 dòng theo thứ tự X
Trang 2 (OFFSET 20): database đổi kế hoạch, thứ tự thành Y
                     -> một số dòng xuất hiện hai lần
                     -> một số dòng không bao giờ xuất hiện
```

Điều này xảy ra **ngay cả khi dữ liệu hoàn toàn không thay đổi** — khác với bài 2, nơi nguyên nhân là dữ liệu bị sửa.

**Sửa bằng tie-breaker — một cột duy nhất ở cuối:**

```sql
ORDER BY "Status", "Id"
```

```csharp
q.OrderBy(o => o.Status).ThenBy(o => o.Id);
```

`Id` là khoá chính nên duy nhất, và thứ tự trở thành **hoàn toàn xác định**.

**Quy tắc: mọi `ORDER BY` dùng cho phân trang đều phải kết thúc bằng một cột duy nhất.**

```csharp
// SAI — không ổn định
q.OrderByDescending(o => o.CreatedAt);              // CreatedAt có thể trùng

// ĐÚNG
q.OrderByDescending(o => o.CreatedAt).ThenByDescending(o => o.Id);
```

Ngay cả `CreatedAt` với độ chính xác mili-giây cũng trùng được — khi nhiều bản ghi được tạo trong cùng một giao dịch, chúng thường có **cùng một giá trị thời gian**.

**Cách kiểm tra trong dự án:**

```bash
grep -rn "OrderBy\|OrderByDescending" --include=*.cs src/ | grep -v "ThenBy"
```

Mỗi kết quả là một chỗ cần rà: nếu truy vấn đó được phân trang, nó cần tie-breaker.

**Áp dụng chung cho cả sắp xếp do người dùng chọn:**

```csharp
private static readonly Dictionary<string, Expression<Func<Order, object>>> AllowedSorts = new()
{
    ["createdAt"] = o => o.CreatedAt,
    ["total"]     = o => o.Total,
    ["status"]    = o => o.Status
};

var sort = AllowedSorts.TryGetValue(sortBy ?? "createdAt", out var e) ? e : AllowedSorts["createdAt"];

var q = desc ? db.Orders.OrderByDescending(sort) : db.Orders.OrderBy(sort);
q = desc ? ((IOrderedQueryable<Order>)q).ThenByDescending(o => o.Id)
         : ((IOrderedQueryable<Order>)q).ThenBy(o => o.Id);      // LUÔN có tie-breaker
```

Chú ý cả **danh sách cho phép** cho tên cột — không có nó, người dùng sắp xếp được theo bất kỳ cột nào kể cả cột nhạy cảm, và theo cột không có chỉ mục để gây quá tải. Đây là cùng vấn đề với bộ lọc động ở [bài 5.8](../../stage-02-csharp-professional/module-05-advanced-csharp/5.7-overview.mdx).

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **`OFFSET` lớn vừa chậm vừa bỏ sót bản ghi.** Job đồng bộ dữ liệu phải dùng cursor.
2. **Whitelist cho `sortBy` và trần cứng cho `pageSize`** — cả hai đều là vấn đề an toàn.
3. **Mọi sắp xếp cần tie-breaker theo khoá chính.**
