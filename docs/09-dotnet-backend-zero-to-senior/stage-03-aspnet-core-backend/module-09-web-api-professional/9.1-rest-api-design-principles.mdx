# 9.2 — 1. REST API Design Principles

<SummaryBox>
REST không phải "dùng JSON qua HTTP" mà là **sáu ràng buộc kiến trúc**, trong đó **stateless** là cái đắt giá nhất: không có trạng thái trên server nghĩa là bất kỳ instance nào cũng xử lý được bất kỳ request nào — đó chính là thứ cho phép scale ngang. Khái niệm thực dụng nhất trong bài là **idempotency**: gửi lại cùng một request phải cho cùng một kết quả. Nó quan trọng vì mạng **sẽ** hỏng, client **sẽ** retry, và một `POST /orders` bị gửi hai lần vì timeout sẽ tạo hai đơn hàng nếu bạn không thiết kế cho điều đó.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Liệt kê sáu ràng buộc REST và nêu hệ quả thực tế của từng cái.
- Phân biệt safe và idempotent, và biết method nào thuộc loại nào.
- Chọn đúng giữa PUT và PATCH.
- Thiết kế URL tài nguyên không chứa động từ.
- Làm cho `POST` idempotent bằng idempotency key.

## Nội dung bài học

### 9.2.1 — Sáu ràng buộc

| Ràng buộc | Hệ quả thực tế |
|---|---|
| **Client–Server** | Hai bên tiến hoá độc lập; đổi UI không cần đổi API |
| **Stateless** | Mỗi request tự chứa đủ thông tin → **scale ngang được** |
| **Cacheable** | Response nói rõ nó cache được bao lâu → giảm tải |
| **Uniform interface** | Cùng một cách dùng cho mọi tài nguyên → không phải học lại |
| **Layered system** | Client không biết có proxy, cache hay gateway ở giữa |
| **Code on demand** (tuỳ chọn) | Server gửi được code thực thi; hiếm dùng |

**Stateless là ràng buộc quan trọng nhất** và cũng hay bị vi phạm nhất. Nó có nghĩa: server **không nhớ gì** giữa hai request. Không session trong bộ nhớ, không "bước hiện tại của wizard", không giỏ hàng lưu ở tiến trình.

Vi phạm nó thì scale ngang gãy ngay: request đầu vào pod A, request sau vào pod B, và pod B không biết gì. Người ta hay vá bằng sticky session — nhưng như vậy pod chết là mất trạng thái, và tải phân bổ không đều.

Trạng thái phải nằm ở **client** (token JWT) hoặc ở **kho dùng chung** (Redis, database).

### 9.2.2 — URL định danh tài nguyên

```
# DUNG — danh tu so nhieu, dong tu nam o HTTP method
GET    /api/v1/customers
GET    /api/v1/customers/{id}
POST   /api/v1/customers
PUT    /api/v1/customers/{id}
PATCH  /api/v1/customers/{id}
DELETE /api/v1/customers/{id}
GET    /api/v1/customers/{id}/contacts

# SAI — dong tu trong URL
POST   /api/v1/getCustomers
POST   /api/v1/deleteCustomer
POST   /api/v1/customers/create
```

Quy ước: **danh từ số nhiều**, chữ thường, phân tách bằng dấu gạch ngang. `/purchase-orders` chứ không phải `/purchaseOrders` hay `/purchase_orders`.

**Còn những hành động không phải CRUD?** Ví dụ "duyệt đơn hàng", "gửi lại email xác nhận". Có hai cách chấp nhận được:

```
# 1. Coi hanh dong nhu mot tai nguyen con
POST /api/v1/orders/{id}/approval
POST /api/v1/orders/{id}/cancellation

# 2. Doi trang thai bang PATCH
PATCH /api/v1/orders/{id}   {"status": "approved"}
```

Cách 1 rõ hơn khi hành động có tác dụng phụ (gửi email, trừ kho) hoặc cần tham số riêng. Đừng cố ép mọi thứ vào CRUD — một `POST /orders/{id}/approval` dễ hiểu hơn nhiều so với một `PATCH` mà server phải đoán ý.

### 9.2.3 — Safe và idempotent

| Method | Safe | Idempotent | Nghĩa |
|---|---|---|---|
| `GET` | Có | Có | Không đổi gì |
| `HEAD` | Có | Có | Như GET nhưng không có body |
| `OPTIONS` | Có | Có | Hỏi khả năng |
| `PUT` | Không | **Có** | Thay thế toàn bộ |
| `DELETE` | Không | **Có** | Xoá |
| `POST` | Không | **Không** | Tạo mới |
| `PATCH` | Không | **Không bắt buộc** | Sửa một phần |

- **Safe** = không thay đổi trạng thái. Crawler và prefetch của trình duyệt tự do gọi.
- **Idempotent** = gọi một lần hay mười lần thì trạng thái cuối giống nhau.

Đây **không phải** lý thuyết suông. Mạng hỏng, client timeout rồi retry, và bạn không biết request trước đã tới server hay chưa:

```
Client --POST /orders--> [timeout]
                          ^ request DA toi server, don hang DA tao,
                            chi co response bi mat
Client --POST /orders--> tao them mot don hang nua
```

Hệ quả thiết kế:

- **`DELETE` phải idempotent**: xoá một thứ đã xoá vẫn trả **204**, không phải 404. Client retry không nhận lỗi giả.
- **`PUT` idempotent tự nhiên** vì nó thay toàn bộ: gửi cùng body mười lần cho cùng kết quả.
- **`PATCH` thường không idempotent**: `{"credit": "+100"}` gửi hai lần là cộng 200. Thiết kế PATCH theo kiểu **đặt giá trị** (`{"credit": 500}`) thay vì **thay đổi tương đối** thì nó trở thành idempotent.

### 9.2.4 — Làm `POST` idempotent

`POST` không idempotent theo bản chất, nhưng bạn **làm cho nó** idempotent được:

```http
POST /api/v1/orders
Idempotency-Key: 7f3a9c2e-1b4d-4a8f-9e12-5c6d7e8f9a0b

{ "customerId": "...", "items": [...] }
```

Server lưu khoá đó cùng kết quả:

```csharp
public async Task<Result<OrderDto>> CreateAsync(
    CreateOrderRequest request, string idempotencyKey, CancellationToken ct)
{
    var existing = await _store.GetAsync(idempotencyKey, ct);
    if (existing is not null)
        return Result.Success(existing.Response);    // tra lai ket qua cu

    var order = await _orders.CreateAsync(request, ct);
    await _store.SaveAsync(idempotencyKey, order, TimeSpan.FromHours(24), ct);
    return Result.Success(order);
}
```

Client sinh khoá **một lần** rồi dùng lại cho mọi lần retry của **cùng** thao tác. Kết quả: retry an toàn, không tạo đơn trùng.

Đây là mẫu bắt buộc cho mọi API có liên quan tới tiền — Stripe và các cổng thanh toán đều làm vậy.

### 9.2.5 — PUT hay PATCH

```http
# PUT — thay the TOAN BO. Truong khong gui se bi XOA.
PUT /api/v1/customers/{id}
{ "name": "Nguyen Van A", "email": "a@example.com", "phone": null }

# PATCH — chi sua truong duoc gui
PATCH /api/v1/customers/{id}
{ "phone": "0901234567" }
```

Lỗi hay gặp: cài `PUT` nhưng xử lý như `PATCH` — chỉ cập nhật trường có trong body. Client gửi `PUT` thiếu một trường sẽ **tưởng** trường đó bị xoá; nó không bị xoá, và dữ liệu lệch nhau mà không ai biết.

Hoặc cài đúng `PUT` mà client dùng sai: gửi `PUT` chỉ với `phone` và **mất** tên cùng email.

Lời khuyên thực dụng: **cài `PATCH` cho cập nhật một phần và đừng hỗ trợ `PUT`** trừ khi bạn thật sự cần ngữ nghĩa thay thế toàn bộ. Hai endpoint trông giống nhau nhưng khác ngữ nghĩa là nguồn lỗi bền vững.

Với `PATCH`, có hai chuẩn: **JSON Merge Patch** (RFC 7386, đơn giản — gửi object với các trường cần đổi) và **JSON Patch** (RFC 6902, mạnh hơn — danh sách thao tác `add`/`remove`/`replace`). Merge Patch đủ cho 95% trường hợp.

### 9.2.6 — Mô hình trưởng thành Richardson

| Mức | Đặc điểm | Thực tế |
|---|---|---|
| 0 | Một endpoint, mọi thứ qua POST | SOAP trá hình |
| 1 | Nhiều tài nguyên, vẫn chỉ POST | Nửa vời |
| 2 | Tài nguyên + HTTP method + status code đúng | **Phần lớn API ở đây** |
| 3 | Thêm HATEOAS — response chứa link | Hiếm |

Mức 2 là mục tiêu thực tế. Mức 3 (HATEOAS) nghe hay nhưng hiếm khi đáng: client vẫn hardcode URL, và chi phí duy trì link không được bù lại.

Ngoại lệ đáng làm là **link phân trang**, vì client thật sự dùng chúng:

```json
{
  "items": [...],
  "page": 2,
  "pageSize": 20,
  "totalCount": 342,
  "_links": {
    "self": "/api/v1/customers?page=2&pageSize=20",
    "next": "/api/v1/customers?page=3&pageSize=20",
    "prev": "/api/v1/customers?page=1&pageSize=20"
  }
}
```

Chi tiết ở [bài 9.5](9.4-pagination-filtering-sorting.mdx).

## Bài tập áp dụng

#### Bài 1 — Tạo đơn trùng do thử lại

Viết endpoint `POST /orders` **không** có khoá idempotency, mô phỏng client hết giờ chờ rồi thử lại, và xác nhận có hai đơn hàng. Thêm `Idempotency-Key` và kiểm chứng lại.

**Tiêu chí hoàn thành:** bạn nêu được vì sao client **không thể** tự tránh việc này.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Khi client hết giờ chờ, nó biết gì về kết quả? Câu trả lời: **không biết gì cả**. Request có thể đã tới server và được xử lý xong, hoặc chưa bao giờ tới.

**Lời giải — tái hiện:**

```csharp
app.MapPost("/orders", async (CreateOrderRequest req, CrmDbContext db, CancellationToken ct) =>
{
    await Task.Delay(3000, ct);                  // mô phỏng xử lý chậm
    var order = new Order { CustomerId = req.CustomerId, Total = req.Total };
    db.Orders.Add(order);
    await db.SaveChangesAsync(ct);
    return Results.Created($"/orders/{order.Id}", order);
});
```

```bash
# Client hết giờ after 2 giây rồi thử lại
curl -m 2 -X POST localhost:5000/orders -d '{"customerId":1,"total":500000}' -H "Content-Type: application/json"
# curl: (28) Operation timed out
curl -m 10 -X POST localhost:5000/orders -d '{"customerId":1,"total":500000}' -H "Content-Type: application/json"
# {"id":2,...}

psql -c 'SELECT COUNT(*) FROM "Orders" WHERE "CustomerId" = 1;'
# 2     <- HAI đơn hàng cho một lần đặt
```

**Vì sao client không thể tự tránh.** Khi hết giờ chờ, client ở trong tình trạng **hoàn toàn mù**:

| Khả năng | Client phân biệt được? |
|---|---|
| Request chưa tới server | Không |
| Request tới, server đang xử lý | Không |
| Server xử lý xong, phản hồi mất trên đường về | **Không** |

Cả ba trường hợp trông giống hệt nhau từ phía client. Nếu client **không** thử lại, nó có thể mất một đơn hàng hợp lệ. Nếu **có** thử lại, nó có thể tạo đơn trùng. Không có lựa chọn an toàn nào — **vấn đề phải được giải quyết ở phía server**.

**Bản có khoá idempotency:**

```csharp
app.MapPost("/orders", async (
    CreateOrderRequest req,
    [FromHeader(Name = "Idempotency-Key")] string? key,
    CrmDbContext db, CancellationToken ct) =>
{
    if (string.IsNullOrWhiteSpace(key))
        return Results.BadRequest("Thiếu header Idempotency-Key");

    // Ghi khoá TRƯỚC, dựa vào ràng buộc duy nhất của database
    var ban = new IdempotencyRecord { Key = key, CreatedAt = DateTime.UtcNow };
    db.IdempotencyRecords.Add(ban);
    try
    {
        await db.SaveChangesAsync(ct);
    }
    catch (DbUpdateException) when (LaLoiTrungKhoa())
    {
        // Đã xử lý rồi — trả lại kết quả cũ
        var cu = await db.IdempotencyRecords.AsNoTracking()
                         .FirstAsync(x => x.Key == key, ct);
        return Results.Ok(JsonSerializer.Deserialize<Order>(cu.Response!));
    }

    var order = new Order { CustomerId = req.CustomerId, Total = req.Total };
    db.Orders.Add(order);
    ban.Response = JsonSerializer.Serialize(order);
    await db.SaveChangesAsync(ct);

    return Results.Created($"/orders/{order.Id}", order);
});
```

Thử lại với **cùng** khoá cho ra cùng một đơn hàng, và bảng `Orders` chỉ có một dòng.

**Ba điểm quan trọng trong cách cài đặt trên:**

1. **Dựa vào ràng buộc duy nhất của database, không dựa vào việc kiểm tra trước.** Kiểm tra rồi mới ghi có khoảng trống đua, đúng như [bài 2.6](../../stage-01-foundation/module-02-computer-science-basics/2.6-what-is-a-database.mdx) đã chứng minh. Ràng buộc duy nhất là lớp bảo đảm thật.
2. **Lưu lại phản hồi**, để lần thử lại nhận được **cùng một kết quả** chứ không phải một lỗi.
3. **Dọn bản ghi cũ** theo lịch — thường giữ 24 tới 48 giờ là đủ.

**Client sinh khoá thế nào.** Một `Guid` cho **mỗi ý định thao tác**, không phải mỗi lần gọi:

```ts
const key = crypto.randomUUID();
for (let i = 0; i < 3; i++) {
  try { return await post('/orders', body, { 'Idempotency-Key': key }); }   // CÙNG key
  catch (e) { if (i === 2) throw e; await sleep(2 ** i * 1000); }
}
```

Sinh khoá mới ở mỗi lần thử lại là quay lại đúng vấn đề ban đầu.

**Endpoint nào cần.** Mọi endpoint **thay đổi dữ liệu và không idempotent tự nhiên**: tạo bản ghi, thanh toán, gửi thông báo. `PUT` và `DELETE` idempotent theo bản chất nên không cần. [Module 17](../../stage-05-senior-engineering/module-17-distributed-systems/) mở rộng ý này cho xử lý thông điệp.

</details>

#### Bài 2 — `PUT` đúng ngữ nghĩa thay thế toàn bộ

Cài `PUT` đúng nghĩa thay thế toàn bộ, gọi với thân request **thiếu** trường `email`, và ghi lại điều xảy ra. Thảo luận xem client của bạn có biết điều đó không.

**Tiêu chí hoàn thành:** bạn nêu được vì sao `PUT` đúng chuẩn lại **nguy hiểm** với client viết cẩu thả.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Ngữ nghĩa của `PUT` là *"thay thế tài nguyên bằng cái tôi gửi"*. Vậy trường không được gửi nghĩa là gì?

**Lời giải.**

```csharp
app.MapPut("/customers/{id:int}", async (int id, CustomerDto dto, CrmDbContext db, CancellationToken ct) =>
{
    var customer = await db.Customers.FindAsync([id], ct);
    if (customer is null) return Results.NotFound();

    // PUT = THAY THẾ TOÀN BỘ
    customer.Name  = dto.Name;
    customer.Email = dto.Email;        // dto.Email là null vì client không gửi
    customer.Phone = dto.Phone;
    customer.Note  = dto.Note;

    await db.SaveChangesAsync(ct);
    return Results.NoContent();
});
```

```bash
curl -X PUT localhost:5000/customers/42 \
     -H "Content-Type: application/json" \
     -d '{"name":"Nguyễn Văn An"}'
```

Kết quả: `Email`, `Phone`, `Note` đều **bị xoá thành null**. Theo chuẩn HTTP, đây là hành vi **đúng** — client đã nói "tài nguyên này giờ chỉ có tên".

**Vì sao nguy hiểm.** Client thường không nghĩ như vậy. Mẫu sai rất phổ biến ở phía giao diện:

```ts
// Form chỉ cho sửa tên
await fetch(`/customers/${id}`, {
  method: 'PUT',
  body: JSON.stringify({ name: tenMoi })      // chỉ gửi trường vừa sửa
});
```

Lập trình viên frontend nghĩ "tôi chỉ sửa tên nên chỉ gửi tên". Server làm đúng chuẩn và xoá sạch phần còn lại. **Không bên nào sai về mặt kỹ thuật**, nhưng dữ liệu đã mất.

Tệ hơn: lỗi này **không báo gì cả**. Phản hồi là `204 No Content` — thành công. Người dùng chỉ phát hiện khi mở lại hồ sơ và thấy email biến mất.

**Ba cách xử lý:**

```csharp
// Cách 1 — dùng PATCH cho cập nhật một phần (khuyến nghị)
app.MapPatch("/customers/{id:int}", async (int id, JsonElement body, ...) =>
{
    if (body.TryGetProperty("name", out var n))  customer.Name = n.GetString();
    if (body.TryGetProperty("email", out var e)) customer.Email = e.GetString();
    // trường không gửi -> không đụng tới
});

// Cách 2 — PUT nhưng bắt buộc gửi đủ, từ chối nếu thiếu
public record CustomerDto
{
    public required string Name { get; init; }
    public required string Email { get; init; }
    public required string Phone { get; init; }
}
// thiếu trường -> 400 với thông báo rõ ràng

// Cách 3 — JSON Patch theo RFC 6902
[{ "op": "replace", "path": "/name", "value": "Nguyễn Văn An" }]
```

**Cách 2 đáng chú ý.** Nó giữ đúng ngữ nghĩa `PUT` mà vẫn an toàn: client quên gửi trường nào sẽ nhận `400` kèm danh sách trường thiếu, thay vì âm thầm mất dữ liệu. Từ .NET 8, `required` kết hợp với `System.Text.Json` làm việc này tự động — xem [bài 5.6](../../stage-02-csharp-professional/module-05-advanced-csharp/5.6-nullable-reference-types.mdx).

**Bảng so sánh:**

| | `PUT` | `PATCH` |
|---|---|---|
| Ngữ nghĩa | Thay thế toàn bộ | Cập nhật một phần |
| Trường không gửi | **Bị xoá** | Giữ nguyên |
| Idempotent | **Có** | Tuỳ cài đặt |
| Phân biệt "xoá" và "không đổi" | Không cần | **Cần** — xem [bài 2.5](../../stage-01-foundation/module-02-computer-science-basics/2.5-api-and-json.mdx) |

**Khuyến nghị thực dụng.** Với API phục vụ form có nhiều trường, **dùng `PATCH`**. Chỉ dùng `PUT` khi client thật sự gửi toàn bộ trạng thái — ví dụ đồng bộ dữ liệu giữa hai hệ thống, hoặc cấu hình được quản lý bằng file.

Và dù chọn cách nào, **ghi rõ trong tài liệu API**. Đây là một trong những chỗ mà giả định ngầm giữa hai đội gây mất dữ liệu nhiều nhất.

</details>

#### Bài 3 — Phá tính phi trạng thái

Lưu bước hiện tại của một biểu mẫu nhiều bước vào bộ nhớ tiến trình, chạy hai thể hiện sau bộ cân bằng tải luân phiên, và ghi lại tỉ lệ request thất bại.

**Tiêu chí hoàn thành:** bạn tính được tỉ lệ thất bại theo công thức, và nêu được ba nơi đúng để lưu trạng thái đó.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Bài này lặp lại thí nghiệm ở [bài 2.8](../../stage-01-foundation/module-02-computer-science-basics/2.8-hosting-and-cloud-co-ban.mdx) nhưng với hệ quả nghiệp vụ rõ hơn. Công thức tỉ lệ thất bại: với `n` thể hiện và phân phối đều, xác suất một request rơi đúng thể hiện giữ trạng thái là `1/n`.

**Lời giải.**

```csharp
public static class WizardStore
{
    private static readonly ConcurrentDictionary<string, WizardState> _store = new();
    public static void Luu(string id, WizardState s) => _store[id] = s;
    public static WizardState? Get(string id) => _store.GetValueOrDefault(id);
}

app.MapPost("/wizard/{id}/buoc/{n:int}", (string id, int n, StepData data) =>
{
    var s = WizardStore.Get(id) ?? new WizardState();
    s.Buoc = n;
    s.DuLieu[n] = data;
    WizardStore.Luu(id, s);
    return Results.Ok(new { buocTiepTheo = n + 1 });
});

app.MapGet("/wizard/{id}", (string id) =>
    WizardStore.Get(id) is { } s ? Results.Ok(s) : Results.NotFound("Phiên đã hết hạn"));
```

Chạy hai thể hiện sau Nginx luân phiên, đi qua 5 bước:

```text
Bước 1 -> thể hiện A   (lưu trạng thái ở A)
Bước 2 -> thể hiện B   -> KHÔNG thấy trạng thái -> tạo mới, MẤT dữ liệu bước 1
Bước 3 -> thể hiện A   -> thấy trạng thái cũ của A, thiếu bước 2
Bước 4 -> thể hiện B
Bước 5 -> thể hiện A   -> dữ liệu chắp vá, không hoàn tất được
```

**Tỉ lệ thất bại theo công thức.** Với `n` thể hiện, xác suất một request rơi đúng thể hiện giữ trạng thái là `1/n`, nên tỉ lệ thất bại là `(n−1)/n`:

| Số thể hiện | Tỉ lệ request đọc sai |
|---|---|
| 2 | **50%** |
| 3 | 67% |
| 5 | 80% |

Với biểu mẫu 5 bước trên 2 thể hiện, xác suất **hoàn tất trọn vẹn** chỉ là `(1/2)⁴ ≈ 6%`.

**Vì sao lỗi này thoát khỏi mọi khâu kiểm tra.** Trên máy phát triển có **một** thể hiện, tỉ lệ thất bại là **0%**. Nó chạy hoàn hảo. Lỗi chỉ xuất hiện sau khi mở rộng lên hai thể hiện — thường là lúc hệ thống đã có người dùng thật.

**Ba nơi đúng để lưu trạng thái này:**

| Nơi | Hợp khi | Lưu ý |
|---|---|---|
| **Client** — trong biểu mẫu hoặc `sessionStorage` | Dữ liệu không nhạy cảm, không cần xác thực giữa các bước | Server **phải** xác thực lại toàn bộ ở bước cuối |
| **Redis** với thời hạn | Cần giữ giữa các thiết bị, hoặc dữ liệu lớn | Đặt thời hạn, đừng để tích tụ |
| **Database** dưới dạng bản nháp | Người dùng cần quay lại sau nhiều ngày | Có bản ghi thật, truy vấn được, báo cáo được |

**Lựa chọn tốt nhất cho phần lớn trường hợp là cách thứ nhất.** Nếu client giữ trạng thái và gửi toàn bộ ở bước cuối, server hoàn toàn phi trạng thái — và bạn không cần thêm hạ tầng nào.

Điều bắt buộc: **server không được tin dữ liệu client gửi**. Mọi quy tắc nghiệp vụ phải được kiểm tra lại ở bước cuối, đúng nguyên tắc ở [bài 2.3](../../stage-01-foundation/module-02-computer-science-basics/2.3-client.mdx).

**Vì sao "dính phiên" không phải giải pháp.** Cấu hình bộ cân bằng tải luôn gửi một người dùng về cùng một thể hiện sẽ làm biểu mẫu chạy được. Nhưng nó giữ nguyên bệnh:

- Thể hiện đó khởi động lại là mất trạng thái — và triển khai nào cũng khởi động lại.
- Tải phân bố không đều.
- Không thu nhỏ số thể hiện được khi vắng khách.

**Danh sách trạng thái cục bộ cần rà trong dự án:**

```bash
grep -rn "static.*Dictionary\|static.*List\|static.*ConcurrentDictionary" --include=*.cs src/ \
  | grep -v "readonly.*=.*new.*{.*}"      # bỏ bảng tra hằng số
```

Mỗi kết quả là một ứng viên: nó có bị **ghi vào** sau khi khởi tạo không? Có thì nó là trạng thái cục bộ.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **Stateless là thứ cho phép scale ngang.** Trạng thái nằm ở client hoặc kho dùng chung.
2. **Idempotency không phải lý thuyết** — nó là cách API sống sót qua mạng không ổn định.
3. **Mức 2 Richardson là đủ.** Đừng đuổi theo HATEOAS, trừ link phân trang.
