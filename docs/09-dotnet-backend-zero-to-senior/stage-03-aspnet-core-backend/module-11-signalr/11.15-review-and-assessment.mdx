## Nội dung bài học

### 11.15.1 — Thực hành

### Bài 1 — Setup CrmNotificationHub và test cơ bản

**Yêu cầu:**
1. Tạo `CrmNotificationHub` với interface `ICrmNotificationClient`
2. Đăng ký `AddSignalR()` và `MapHub<CrmNotificationHub>("/hubs/notifications")`
3. Bật CORS cho SignalR (thêm `AllowCredentials()` và whitelist origin)
4. Tạo HTML test page đơn giản:

```html
<!DOCTYPE html>
<html>
<head>
    <script src="https://cdn.jsdelivr.net/npm/@microsoft/signalr/dist/browser/signalr.min.js"></script>
</head>
<body>
    <div id="messages"></div>
    <script>
        const connection = new signalR.HubConnectionBuilder()
            .withUrl("https://localhost:7001/hubs/notifications")
            .build();

        connection.on("ReceiveNotification", (notification) => {
            document.getElementById("messages").innerHTML +=
                `<p>[${notification.type}] ${notification.message}</p>`;
        });

        connection.start()
            .then(() => console.log("Connected:", connection.connectionId))
            .catch(err => console.error(err));
    </script>
</body>
</html>
```

5. Tạo endpoint `POST /api/test/notify?userId=xxx&message=yyy` dùng `IHubContext` để push notification
6. Dùng Postman gọi endpoint và xem message xuất hiện trên HTML page

**Kiểm tra**: Gửi 5 notification liên tiếp từ Postman, tất cả xuất hiện ngay lập tức trên browser.

### Bài 2 — Notification khi Lead status thay đổi

**Yêu cầu:**
1. Tạo entity `Lead` với field `AssigneeId`, `Status`
2. Tạo `LeadService.AssignLeadAsync(leadId, assigneeId)`:
   - Cập nhật DB
   - Tạo `Notification` record
   - Push real-time qua `IHubContext.Clients.User(assigneeId)`
3. Bảo vệ Hub bằng `[Authorize]`, cấu hình JWT đọc từ query string
4. Client TypeScript: connect với token, hiển thị notification dạng toast

**Luồng kiểm tra:**
- User A (assignee) mở browser, connect Hub với JWT token của mình
- Gọi API `PUT /api/leads/{id}/assign` với body `{ assigneeId: "userId-A" }`
- User A nhận notification ngay lập tức mà không refresh trang

### Bài 3 — Notification Center đầy đủ

**Yêu cầu:**
1. Tạo bảng `Notifications` trong DB với các field: `Id, UserId, Message, Type, EntityType, EntityId, IsRead, ReadAt, CreatedAt`
2. Implement `NotificationService` với `SendAsync`, `MarkAsReadAsync`, `GetUnreadAsync`
3. API endpoints:
   - `GET /api/notifications?unreadOnly=true&limit=20` — lấy danh sách
   - `PUT /api/notifications/{id}/read` — đánh dấu đã đọc
   - `PUT /api/notifications/read-all` — đánh dấu tất cả đã đọc
4. Real-time: khi có notification mới → push ngay qua Hub
5. Frontend (React hoặc HTML): hiển thị badge số unread, dropdown list, click → đánh dấu đã đọc

**Bonus**: Implement `LeadAssignedEventHandler` dùng MediatR notification để tách logic domain event khỏi service.

### 11.15.2 — Tóm tắt

| Khái niệm | Ghi nhớ |
|---|---|
| Transport negotiation | WebSocket > SSE > Long Polling, SignalR tự chọn |
| Strongly-typed Hub | Dùng `Hub<TClient>` + interface để compile-time safety |
| JWT trong WebSocket | Truyền qua query string, đọc trong `OnMessageReceived` |
| `Groups` | Organize connections; join khi connect, leave khi disconnect |
| `IHubContext` | Push từ service/job ngoài Hub; inject `IHubContext<THub, TClient>` |
| Presence | Track `OnConnectedAsync`/`OnDisconnectedAsync`; dùng Redis khi scale |
| Scale-out | Redis backplane hoặc Azure SignalR Service; cần sticky session |

SignalR giải quyết hoàn toàn bài toán real-time cho CRM: notification center, live dashboard, và presence tracking — với developer experience tốt hơn nhiều so với WebSocket thuần nhờ transport fallback, auto-reconnect và strongly-typed API.

### 11.15.7 — Phần A — Quiz trắc nghiệm (20 điểm)

> **Gợi ý làm bài:** mỗi câu **4 điểm**. Ưu tiên suy nghĩ *hệ quả trên CRM* (tiền, dữ liệu, đa tenant, hiệu năng, bảo mật) — không chỉ nhớ định nghĩa.

Mỗi câu **4 điểm**.

1. SignalR transport fallback thứ tự ưu tiên điển hình (hiện đại)?  
   A. WebSocket → SSE → long polling B. Chỉ UDP C. FTP D. SMTP  
   > **Đáp án:** A (tinh thần; chi tiết phụ thuộc client/server).

2. Redis backplane dùng khi?  
   A. Một instance duy nhất B. Scale-out nhiều server cần broadcast chung C. Thay thế SQL D. Chỉ dev local  
   > **Đáp án:** B.

3. Hub method nên tránh pattern nào?  
   A. `async Task` B. Gọi DB đồng bộ chặn lâu trong hub mà không scale C. Strongly typed client D. Groups  
   > **Đáp án:** B (cần thiết kế + async).

4. Auth SignalR thường truyền JWT qua?  
   A. Header HTTP khi negotiate/access token theo tài liệu client B. Telnet C. DNS D. ICMP  
   > **Đáp án:** A (accessTokenFactory trên web client).

5. Sticky session khi **không** dùng backplane?  
   A. Luôn cần B. Có thể cần nếu connection không shared giữa node C. Không bao giờ D. Chỉ với gRPC  
   > **Đáp án:** B.
