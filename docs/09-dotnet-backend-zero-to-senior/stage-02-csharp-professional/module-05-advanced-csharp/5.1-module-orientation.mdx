# 5.1 — Định hướng Module 5: C# nâng cao

<SummaryBox>
Module 4 dạy cách mô hình hoá **một** khái niệm nghiệp vụ. Module này dạy cách viết code **không lặp lại chính nó** khi số khái niệm tăng lên hai mươi. Bốn công cụ chính: **SOLID** để biết khi nào nên tách, **Generics** để viết một lần dùng cho mọi kiểu, **LINQ** để diễn đạt phép biến đổi dữ liệu bằng ý định thay vì vòng lặp, và **Nullable Reference Types** để trình biên dịch chỉ ra chỗ có thể `null` trước khi người dùng chỉ ra hộ bạn. Cảnh báo quan trọng: mọi công cụ ở đây đều **dễ dùng quá tay**, nên mỗi bài đều có phần "khi nào thì đừng".
</SummaryBox>

## Module này giải quyết vấn đề gì

Sau module 4, bạn có `Customer`, `Lead`, `Contact`. Bây giờ mỗi lớp cần lưu trữ, phân trang, lọc, và trả về kết quả kèm thông tin lỗi. Viết thủ công thì thành ra thế này:

```csharp
public class CustomerRepository
{
    public List<Customer> GetPage(int page, int size) { /* 15 dòng */ }
    public int Count() { /* 5 dòng */ }
}

public class LeadRepository
{
    public List<Lead> GetPage(int page, int size) { /* 15 dòng GIỐNG HỆT */ }
    public int Count() { /* 5 dòng GIỐNG HỆT */ }
}

public class ContactRepository
{
    public List<Contact> GetPage(int page, int size) { /* 15 dòng GIỐNG HỆT */ }
    public int Count() { /* 5 dòng GIỐNG HỆT */ }
}
```

Trùng lặp không chỉ tốn công gõ. Cái giá thật là khi phát hiện lỗi off-by-one trong logic phân trang: phải sửa ở ba chỗ, và gần như chắc chắn sẽ quên một chỗ. Sáu tháng sau có thêm `Deal` và `Task`, thành năm chỗ.

Generics gộp cả ba thành một:

```csharp
public class Repository<T> where T : class, IEntity
{
    public List<T> GetPage(int page, int size) { /* 15 dòng, viết một lần */ }
    public int Count() { /* 5 dòng, viết một lần */ }
}
```

Nhưng — và đây là lý do module này cần một bài riêng cho mỗi công cụ — **gộp quá đà cũng tai hại không kém**. Một `Repository<T>` gánh cả phân trang, xuất Excel, gửi email thông báo và ghi nhật ký kiểm toán sẽ trở thành thứ không ai dám sửa. Ranh giới giữa "trừu tượng hoá đúng chỗ" và "trừu tượng hoá quá sớm" chính là nội dung thật sự của SOLID.

## Sản phẩm bàn giao của module

Một thư viện **`Crm.Shared`** chứa các khối dùng lại, cộng với `Crm.Domain` đã bật NRT:

```text
Crm.Shared/
├── Result.cs            Result<T>: thành công kèm giá trị, thất bại kèm lỗi
├── PagedResult.cs       PagedResult<T>: items, tổng số, trang hiện tại
├── IRepository.cs       hợp đồng chung cho mọi kho dữ liệu
├── Extensions/
│   ├── QueryableExtensions.cs   .Paginate(page, size)
│   └── StringExtensions.cs      .ToSlug(), .Truncate(n)
└── Events/
    └── DomainEvent.cs   lớp cơ sở cho sự kiện nghiệp vụ
```

Tiêu chí nghiệm thu:

1. `Crm.Domain` bật `<Nullable>enable</Nullable>` và biên dịch **không còn cảnh báo**.
2. `Result<T>` được dùng thay cho việc ném ngoại lệ ở ít nhất ba chỗ xử lý lỗi nghiệp vụ dự đoán được.
3. Có một truy vấn LINQ nhóm dữ liệu và một truy vấn tổng hợp, cùng viết được bằng hai cú pháp.
4. `Lead` phát một sự kiện khi chuyển trạng thái, và có ít nhất hai bên đăng ký nhận.

`Result<T>` sẽ quay lại ở [Module 9](../../stage-03-aspnet-core-backend/module-09-web-api-professional/) khi ánh xạ lỗi nghiệp vụ sang mã HTTP, và ở [Module 16](../../stage-05-senior-engineering/module-16-clean-architecture/) khi bàn về ranh giới use case.

## Ba sai lầm thường gặp khi học module này

**Một — áp dụng SOLID như luật thay vì như công cụ chẩn đoán.** Một codebase áp dụng SOLID máy móc sẽ có bốn mươi interface mỗi cái một phương thức, và đọc một luồng nghiệp vụ phải mở mười hai file. Đó không phải mục tiêu của SOLID. Cách dùng đúng là chẩn đoán: *khi sửa một yêu cầu, tôi phải đụng vào mấy file?* Nếu đụng nhiều file cho một thay đổi, hoặc một file cho nhiều thay đổi khác nhau, thì mới cần tách. Không có triệu chứng thì không cần thuốc.

**Hai — không phân biệt thực thi hoãn của LINQ.** `IEnumerable` và `IQueryable` trông giống nhau nhưng khác nhau ở chỗ quyết định: khi nào truy vấn **thật sự chạy**. Gọi `.Where()` không chạy gì cả; nó chỉ dựng mô tả. Truy vấn chạy khi bạn duyệt kết quả, gọi `.ToList()` hay `.Count()`. Hệ quả thực tế là một vòng lặp duyệt `IQueryable` bên trong một vòng lặp khác có thể sinh ra hàng nghìn câu lệnh gửi xuống database — đúng lỗi mà [Module 13](../../stage-04-database-production/module-13-entity-framework-core/) gọi là N+1.

**Ba — tắt cảnh báo Nullable Reference Types cho nhanh.** Khi bật NRT trên dự án có sẵn, trình biên dịch thường phun ra hàng trăm cảnh báo, và cám dỗ lớn nhất là rắc toán tử `!` cho im tiếng. Làm vậy là vứt bỏ toàn bộ giá trị của tính năng: mỗi `!` là một lời hứa "chỗ này chắc chắn không null" mà không ai kiểm chứng. Cách đúng là bật theo từng file bằng `#nullable enable`, xử lý dứt điểm rồi chuyển sang file kế tiếp.

## Bài tập khởi động

Làm trước khi vào 5.2. Bài này đo khả năng nhìn ra trách nhiệm chồng chéo.

> **Đề bài.** Lớp dưới đây có mặt trong rất nhiều dự án thật. Hãy liệt kê **các lý do khác nhau** khiến lớp này phải bị sửa trong tương lai. Với mỗi lý do, ghi rõ ai là người yêu cầu thay đổi đó.
>
> ```csharp
> public class LeadService
> {
>     public void CreateLead(string name, string email, decimal value)
>     {
>         if (!email.Contains("@")) throw new Exception("Email sai");
>
>         var sql = $"INSERT INTO Leads (Name, Email, Value) VALUES ('{name}', '{email}', {value})";
>         using var conn = new SqlConnection("Server=prod;Database=Crm;...");
>         conn.Execute(sql);
>
>         var body = $"<h1>Lead mới</h1><p>{name} - {value:N0} đ</p>";
>         _smtp.Send("sales@company.com", "Lead mới", body);
>
>         File.AppendAllText("C:\\logs\\leads.txt", $"{DateTime.Now}: {name}\n");
>     }
> }
> ```

<details>
<summary><strong>Gợi ý — cách đếm trách nhiệm</strong></summary>

Đừng đếm số dòng hay số thao tác. Hãy hỏi: **ai trong tổ chức có thể yêu cầu đổi đoạn này?**

Đi qua từng khối và gán cho một phòng ban hoặc một vai trò. Nếu hai khối thuộc về hai người khác nhau, đó là hai trách nhiệm — và cũng là hai lý do độc lập khiến file này phải mở ra sửa.

Ngoài ra, có một lỗi **bảo mật nghiêm trọng** trong đoạn code này, không liên quan tới SOLID. Tìm ra nó luôn.

</details>

<details>
<summary><strong>Hướng dẫn giải — đọc sau khi đã tự làm</strong></summary>

**Năm lý do thay đổi, tương ứng năm người yêu cầu khác nhau:**

| Trách nhiệm | Ai yêu cầu đổi | Ví dụ yêu cầu |
|---|---|---|
| Xác thực dữ liệu | Phân tích nghiệp vụ | "Email phải thuộc tên miền công ty" |
| Truy cập dữ liệu | Quản trị database | "Chuyển sang PostgreSQL" |
| Soạn nội dung email | Marketing | "Đổi mẫu email, thêm logo" |
| Quyết định gửi cho ai | Trưởng phòng kinh doanh | "Gửi cho quản lý khu vực thay vì địa chỉ chung" |
| Ghi nhật ký | Vận hành | "Đẩy log về hệ thống tập trung thay vì file" |

Năm lý do độc lập để sửa một lớp chính là định nghĩa vi phạm **Single Responsibility Principle**. Hệ quả cụ thể chứ không trừu tượng: marketing đổi mẫu email và vô tình làm hỏng logic lưu dữ liệu, vì cả hai nằm trong một hàm và cùng đi qua một lần triển khai.

**Ba vấn đề nữa, quan trọng không kém:**

1. **SQL injection.** Chuỗi SQL được nối trực tiếp từ đầu vào người dùng. Đặt tên khách hàng là `'); DROP TABLE Leads; --` là xoá sạch bảng. Đây là lỗ hổng thuộc nhóm Injection trong [OWASP Top 10](https://owasp.org/Top10/). [Module 12](../../stage-04-database-production/module-12-sql-deep-dive/) và [Module 13](../../stage-04-database-production/module-13-entity-framework-core/) xử lý bằng tham số hoá truy vấn.

2. **Không thể kiểm thử.** Muốn viết một bài kiểm thử cho logic xác thực email, bạn buộc phải có database thật, máy chủ SMTP thật và ổ đĩa `C:\`. Vì vậy trên thực tế sẽ không ai viết kiểm thử cho lớp này. Không kiểm thử được là **triệu chứng**, còn bệnh là phụ thuộc bị gắn cứng — và [Module 7](../module-07-dependency-injection/) chữa đúng bệnh đó.

3. **Chuỗi kết nối nằm trong code.** Mật khẩu production nằm trong mã nguồn, tức là nằm trong Git, tức là ai đọc được kho code đều đọc được nó. [Module 8](../../stage-03-aspnet-core-backend/module-08-aspnet-core-fundamentals/) trình bày cách đưa nó ra cấu hình, và [Module 5 bài 5.2](5.2-solid-principles.mdx) giải thích vì sao lớp này không nên tự biết mình nối tới đâu.

**Hướng tách.** Năm trách nhiệm thành bốn thành phần, `LeadService` chỉ còn điều phối:

```csharp
public class LeadService
{
    private readonly ILeadRepository _repository;
    private readonly INotificationSender _notifier;
    private readonly ILogger<LeadService> _logger;

    public async Task<Result<Lead>> CreateLeadAsync(CreateLeadRequest request, CancellationToken ct)
    {
        var lead = Lead.Create(request.Name, request.Email, request.Value);
        if (lead.IsFailure) return lead;

        await _repository.AddAsync(lead.Value, ct);
        await _notifier.NotifyNewLeadAsync(lead.Value, ct);
        _logger.LogInformation("Đã tạo lead {LeadId}", lead.Value.Id);
        return lead;
    }
}
```

Bản này kiểm thử được mà không cần database, marketing đổi mẫu email không đụng tới logic lưu trữ, và không còn chỗ nào nối chuỗi SQL. Đó là toàn bộ điều SOLID hướng tới — không phải để đúng nguyên tắc, mà để giảm chi phí thay đổi.

**Điểm tự chấm.** Tìm ra từ ba trách nhiệm trở lên **và** phát hiện SQL injection là mức tốt để vào module.
