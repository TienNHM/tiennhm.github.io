# 4.12 — Mini case study

<SummaryBox>
Bài toán thiết kế cổ điển và đầy cạm bẫy: mô hình hoá **sản phẩm** trong một CRM bán cả **hàng vật lý**, **dịch vụ** và **gói đăng ký**. Phản xạ đầu tiên của hầu hết mọi người là dùng **kế thừa** — và nó hoạt động hoàn hảo trong hai tháng, rồi sụp đổ khi có yêu cầu "một sản phẩm vừa là hàng vật lý vừa bán theo gói". Lúc đó cây kế thừa không mở rộng được nữa mà không viết lại từ đầu. Bài này đi qua **cả hai thiết kế**, cho thấy chính xác chỗ kế thừa gãy, và trình bày cách dùng **composition** để cùng một yêu cầu chỉ mất vài dòng. Nguyên tắc rút ra: **kế thừa mô hình quan hệ "là một" cố định; composition mô hình khả năng có thể thêm bớt**.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra khi nào kế thừa là lựa chọn sai.
- Thiết kế bằng composition thay cho cây kế thừa.
- Dùng `record` cho value object đúng chỗ.
- Đánh giá một thiết kế bằng câu hỏi "yêu cầu tiếp theo sẽ thế nào".

### 4.12.2 — Thiết kế 1: kế thừa

```csharp
public abstract class Product
{
    public ProductId Id { get; protected set; }
    public string Name { get; protected set; }
    public Money Price { get; protected set; }
    public decimal TaxRate { get; protected set; }
    public bool IsActive { get; protected set; }

    public abstract Money CalculateTotal(int quantity);
}

public class PhysicalProduct : Product
{
    public decimal WeightKg { get; private set; }
    public Dimensions Size { get; private set; }
    public int StockQuantity { get; private set; }

    public override Money CalculateTotal(int quantity)
        => Price * quantity + CalculateShipping(quantity);
}

public class ServiceProduct : Product
{
    public TimeSpan Duration { get; private set; }
    public UserId AssignedTo { get; private set; }

    public override Money CalculateTotal(int quantity) => Price * quantity;
}

public class SubscriptionProduct : Product
{
    public BillingCycle Cycle { get; private set; }
    public bool AutoRenew { get; private set; }

    public override Money CalculateTotal(int quantity) => Price * quantity;
}
```

Thiết kế này **tốt** — trong hai tháng.

### 4.12.3 — Chỗ nó gãy

**Yêu cầu tháng thứ ba:** *"Bán máy in kèm gói mực hàng tháng. Nó là hàng vật lý (giao hàng, tồn kho) và cũng là gói đăng ký (thu tiền hàng tháng)."*

```csharp
// Khong hop le trong C# — khong the ke thua HAI lop
public class PhysicalSubscriptionProduct : PhysicalProduct, SubscriptionProduct
```

Ba cách chữa, cả ba đều tệ:

| Cách chữa | Vấn đề |
|---|---|
| Chép thuộc tính đăng ký vào `PhysicalProduct` | Dịch vụ cũng cần? Lại chép lần nữa |
| Đưa mọi thuộc tính lên lớp `Product` | Lớp cơ sở phình to, hàng vật lý có `AutoRenew` vô nghĩa |
| Thêm `PhysicalSubscriptionProduct` chép code cả hai | Sửa một chỗ phải nhớ sửa hai |

**Và yêu cầu tháng thứ tư:** *"Dịch vụ tư vấn cũng bán theo gói."* Giờ cần `ServiceSubscriptionProduct`. Tháng thứ năm: *"Gói bảo trì gồm cả linh kiện."*

Số lớp tăng theo **tổ hợp**, không phải theo số loại. Đây chính là điểm gãy của kế thừa cho bài toán này.

### 4.12.4 — Thiết kế 2: composition

Câu hỏi cần hỏi lại từ đầu: **"hàng vật lý" là bản chất của sản phẩm, hay là một khả năng nó có?**

Nhìn lại yêu cầu: một sản phẩm **có thể** cần giao hàng, **có thể** thu tiền định kỳ, **có thể** cần người thực hiện. Đó là **khả năng**, không phải bản chất — nên nó thuộc về composition.

```csharp
public sealed class Product
{
    public ProductId Id { get; private set; }
    public string Name { get; private set; }
    public Money Price { get; private set; }
    public decimal TaxRate { get; private set; }
    public bool IsActive { get; private set; }

    // Kha nang — co the co, co the khong
    public ShippingInfo? Shipping { get; private set; }
    public SubscriptionInfo? Subscription { get; private set; }
    public ServiceInfo? Service { get; private set; }

    public Money CalculateTotal(int quantity)
    {
        var total = Price * quantity;

        if (Shipping is not null)
            total += Shipping.CalculateCost(quantity);

        return total;
    }

    public void EnableShipping(decimal weightKg, Dimensions size)
        => Shipping = new ShippingInfo(weightKg, size);

    public void EnableSubscription(BillingCycle cycle, bool autoRenew)
        => Subscription = new SubscriptionInfo(cycle, autoRenew);
}

// Value object — bat bien, so sanh theo gia tri
public sealed record ShippingInfo(decimal WeightKg, Dimensions Size)
{
    public Money CalculateCost(int quantity)
        => Money.Vnd(WeightKg * quantity * 15_000m);
}

public sealed record SubscriptionInfo(BillingCycle Cycle, bool AutoRenew);
public sealed record ServiceInfo(TimeSpan Duration, UserId AssignedTo);
```

Máy in kèm gói mực giờ là:

```csharp
var mayIn = Product.Create("Máy in HP", Money.Vnd(5_000_000m));
mayIn.EnableShipping(weightKg: 8.5m, size: new Dimensions(45, 35, 30));
mayIn.EnableSubscription(BillingCycle.Monthly, autoRenew: true);
```

**Không lớp mới nào cả.** Và dịch vụ bán theo gói cũng vậy:

```csharp
var tuVan = Product.Create("Tư vấn CRM", Money.Vnd(2_000_000m));
tuVan.EnableService(TimeSpan.FromHours(2), consultantId);
tuVan.EnableSubscription(BillingCycle.Monthly, autoRenew: false);
```

Tám tổ hợp khả năng chỉ cần **một** lớp.

### 4.12.5 — Vì sao dùng record cho khả năng

```csharp
public sealed record ShippingInfo(decimal WeightKg, Dimensions Size);
```

Ba lý do cụ thể:

**Bất biến.** Sau khi tạo, không ai đổi được `WeightKg` từ bên ngoài. Muốn đổi thì tạo bản mới qua `EnableShipping` — nên `Product` luôn kiểm soát được trạng thái của mình.

**So sánh theo giá trị.** Hai `ShippingInfo` cùng số liệu là bằng nhau, điều này đúng về mặt nghĩa: chúng mô tả cùng một cấu hình vận chuyển, không phải hai thực thể khác nhau.

**Ngắn gọn.** Một dòng thay cho constructor, property, `Equals`, `GetHashCode` và `ToString` viết tay ([bài 4.8](4.8-records-and-value-objects.mdx)).

### 4.12.6 — Khi nào kế thừa vẫn đúng

Composition không phải lúc nào cũng thắng. Kế thừa phù hợp khi quan hệ "là một" **cố định và không chồng chéo**:

```csharp
// DUNG — mot exception KHONG THE vua la NotFound vua la Validation
public abstract class DomainException : Exception { }
public sealed class NotFoundException : DomainException { }
public sealed class ValidationException : DomainException { }
```

Hoặc khi lớp cơ sở cung cấp hành vi mặc định mà lớp con chỉ tinh chỉnh:

```csharp
// DUNG — Controller cung cap ha tang, ban chi them action
public class LeadsController : ControllerBase { }
```

**Câu hỏi phân biệt:** *"một đối tượng có thể thuộc hai loại con cùng lúc không?"*

- Không bao giờ → kế thừa được.
- Có thể → **composition**.

Trong ca này, một sản phẩm **có thể** vừa cần giao hàng vừa thu định kỳ, nên câu trả lời là composition ([bài 4.4](4.4-inheritance-and-polymorphism.mdx)).

### 4.12.7 — Đánh giá thiết kế bằng yêu cầu tiếp theo

Cách kiểm tra rẻ nhất trước khi cam kết một thiết kế: **nghĩ ra ba yêu cầu có thể tới trong sáu tháng** và xem thiết kế phản ứng thế nào.

| Yêu cầu | Kế thừa | Composition |
|---|---|---|
| Sản phẩm vừa vật lý vừa đăng ký | **Không làm được** | Gọi thêm một phương thức |
| Thêm khả năng "cho thuê" | Thêm 4 lớp tổ hợp | Thêm 1 record |
| Báo cáo mọi sản phẩm cần giao hàng | Kiểm tra kiểu ở nhiều nơi | Lọc `Shipping is not null` |
| Bỏ khả năng đăng ký của một sản phẩm | Đổi kiểu đối tượng — rất khó | Gán `null` |

Hàng cuối đáng chú ý: với kế thừa, "sản phẩm này không bán theo gói nữa" nghĩa là **đổi kiểu của đối tượng** — điều gần như không làm được khi nó đã có id và đang được tham chiếu ở nơi khác.

## Bài tập áp dụng

1. **Thêm khả năng mới.** Thêm "cho thuê" (có thời hạn thuê và tiền cọc) vào cả hai thiết kế. Đếm số file phải sửa.

2. **Tìm lớp tổ hợp.** Rà dự án của bạn tìm lớp có tên ghép từ hai khái niệm và xem nó có phải triệu chứng của vấn đề này không.

3. **Viết truy vấn.** Với thiết kế composition, viết truy vấn lấy mọi sản phẩm cần giao hàng và so sánh với cách làm ở thiết kế kế thừa.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Kế thừa mô hình bản chất cố định; composition mô hình khả năng thêm bớt được.**
2. **Số lớp tăng theo tổ hợp** là dấu hiệu kế thừa sai chỗ.
3. **Thử thiết kế bằng ba yêu cầu giả định** trước khi cam kết — rẻ hơn viết lại rất nhiều.
