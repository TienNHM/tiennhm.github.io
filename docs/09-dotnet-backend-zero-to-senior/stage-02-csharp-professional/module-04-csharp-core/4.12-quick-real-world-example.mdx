# 4.13 — Ví dụ thực tế nhanh

<SummaryBox>
Một bug rất hay gặp và rất khó tin khi mới gặp: hai đối tượng có **dữ liệu giống hệt nhau** nhưng `==` trả về `false`, và `list.Contains(x)` không tìm thấy dù `x` rõ ràng nằm trong danh sách. Nguyên nhân: với `class`, C# so sánh **địa chỉ trong bộ nhớ**, không so sánh nội dung. Hai đối tượng khác nhau thì luôn khác nhau, dù mọi thuộc tính đều bằng. Cách sửa đơn giản nhất là dùng **`record`** — một từ khoá thay cho hàng chục dòng code. Nhưng có một cái bẫy ít người biết: nếu tự ghi đè `Equals` mà **quên `GetHashCode`**, `Dictionary` và `HashSet` sẽ hoạt động **sai một cách im lặng** — không lỗi, chỉ là không tìm thấy thứ rõ ràng có ở đó.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích vì sao hai đối tượng cùng dữ liệu lại không bằng nhau.
- Chọn giữa `class`, `record` và `struct` theo tình huống.
- Ghi đè `Equals` và `GetHashCode` đúng cách khi cần.
- Nhận ra bug do quên `GetHashCode`.

## Nội dung bài học

### 4.13.1 — Bug

```csharp
public class Address
{
    public string HouseNumber { get; set; }
    public string Street { get; set; }
    public string District { get; set; }
}

var a1 = new Address { HouseNumber = "12", Street = "Nguyễn Huệ", District = "1" };
var a2 = new Address { HouseNumber = "12", Street = "Nguyễn Huệ", District = "1" };

Console.WriteLine(a1 == a2);          // False  (!!)
Console.WriteLine(a1.Equals(a2));     // False  (!!)

var list = new List<Address> { a1 };
Console.WriteLine(list.Contains(a2));        // False — dù dữ liệu giống hệt
```

Trong code thật, bug này biểu hiện như sau:

```csharp
// Kiểm tra địa chỉ giao hàng đã tồn tại chưa
if (!customer.Addresses.Contains(newAddress))
    customer.Addresses.Add(newAddress);

// Kết quả: danh sách đầy địa chỉ TRÙNG NHAU
```

### 4.13.2 — Vì sao

Với `class`, C# so sánh **tham chiếu** — tức hai biến có trỏ vào **cùng một ô nhớ** hay không.

```csharp
var a1 = new Address { ... };    // tạo đối tượng ở ô nhớ A
var a2 = new Address { ... };    // tạo đối tượng ở ô nhớ B  (KHÁC)

a1 == a2      // so sánh A với B -> False

var a3 = a1;  // a3 trỏ vào CÙNG ô nhớ A
a1 == a3      // True
```

Mặc định này **đúng** cho phần lớn trường hợp: hai khách hàng cùng tên không phải cùng một người. Nhưng với những thứ chỉ **mang giá trị** — địa chỉ, số tiền, khoảng thời gian — thì so sánh theo nội dung mới đúng.

### 4.13.3 — Sửa bằng record

```csharp
public record Address(string HouseNumber, string Street, string District);

var a1 = new Address("12", "Nguyễn Huệ", "1");
var a2 = new Address("12", "Nguyễn Huệ", "1");

Console.WriteLine(a1 == a2);               // True
Console.WriteLine(danhSach.Contains(a2));   // True
```

Một từ khoá. Trình biên dịch tự sinh `Equals`, `GetHashCode`, `ToString`, toán tử `==` và `!=`, cùng phương thức `with` để tạo bản sao có sửa đổi ([bài 4.8](4.7-records-and-value-objects.mdx)).

```csharp
var dcMoi = a1 with { District = "3" };    // ban sao, chi doi District
```

`record` cũng **bất biến** mặc định — sau khi tạo không đổi được thuộc tính. Đây là điều bạn muốn với value object: nếu địa chỉ thay đổi thì đó là một địa chỉ **khác**, không phải cùng địa chỉ đã bị sửa.

### 4.13.4 — Cái bẫy: quên GetHashCode

Nếu vì lý do nào đó bạn không dùng được `record` và phải tự ghi đè:

```csharp
// SAI — ghi đè Equals nhưng QUÊN GetHashCode
public class Address
{
    public string HouseNumber { get; set; }
    public string Street { get; set; }

    public override bool Equals(object? obj)
        => obj is Address other && HouseNumber == other.HouseNumber && Street == other.Street;

    // GetHashCode: KHÔNG ghi đè -> vẫn dùng mặc định theo tham chiếu
}
```

Hậu quả, và nó **rất khó chẩn đoán**:

```csharp
var set = new HashSet<Address>();
set.Add(a1);

Console.WriteLine(a1.Equals(a2));   // True
Console.WriteLine(set.Contains(a2)); // False  (!!)
```

`HashSet` và `Dictionary` tìm phần tử theo **hai bước**: trước hết dùng `GetHashCode` để xác định "ngăn" chứa nó, sau đó mới dùng `Equals` trong ngăn đó. Nếu `GetHashCode` khác nhau, chúng rơi vào hai ngăn khác nhau và `Equals` **không bao giờ được gọi**.

**Quy tắc bắt buộc:** ghi đè `Equals` thì **phải** ghi đè `GetHashCode`, và hai cái phải dùng **cùng bộ thuộc tính**.

```csharp
public override int GetHashCode() => HashCode.Combine(HouseNumber, Street);
```

`HashCode.Combine` xử lý đúng cả trường hợp `null` và phân bố giá trị tốt — không tự viết bằng cách nhân số nguyên tố nữa.

Trình biên dịch **có** cảnh báo về việc này (CS0659), nên đừng bỏ qua cảnh báo.

### 4.13.5 — Cái bẫy thứ hai: thuộc tính thay đổi được

```csharp
// NGUY HIỂM — thuộc tính dùng để băm lại đổi được
public class Address
{
    public string Street { get; set; }      // set được!
    public override int GetHashCode() => HashCode.Combine(Street);
}

var set = new HashSet<Address> { a };
a.Street = "Lê Lợi";                         // đổi SAU khi đã thêm vào tập

set.Contains(a);         // False — dù a ĐANG nằm trong tập!
```

Đối tượng vẫn ở trong `HashSet`, nhưng nó nằm ở ngăn tương ứng với mã băm **cũ**. Tìm theo mã băm mới không tới đúng ngăn đó.

Đây là lý do value object **phải bất biến**, và cũng là lý do `record` mặc định bất biến. Nếu dùng `class` với `Equals` tự viết, hãy đặt mọi thuộc tính là `init` hoặc `private set`.

### 4.13.6 — Chọn class, record hay struct

| | `class` | `record` | `struct` |
|---|---|---|---|
| So sánh | Tham chiếu | **Giá trị** | Giá trị |
| Lưu ở đâu | Heap | Heap | **Stack** (thường) |
| Bất biến mặc định | Không | **Có** | Không |
| Dùng cho | Thực thể có định danh | **Value object** | Giá trị nhỏ, dùng rất nhiều |

**Quy tắc chọn:**

- Có **định danh** riêng, hai đối tượng cùng dữ liệu vẫn là hai thứ khác nhau → **`class`**. Ví dụ: `Customer`, `Order`, `Lead`.
- Chỉ **mang giá trị**, cùng dữ liệu nghĩa là cùng một thứ → **`record`**. Ví dụ: `Address`, `Money`, `DateRange`.
- Rất nhỏ (dưới 16 byte) và tạo rất nhiều lần → **`struct`** hoặc `readonly record struct`.

```csharp
// Thực thể — có định danh
public class Customer { public CustomerId Id { get; init; } /* ... */ }

// Value object — chỉ mang giá trị
public record Money(decimal Amount, string Currency);

// Value object nhỏ, dùng nhiều
public readonly record struct LeadId(Guid Value);
```

Dòng cuối là mẫu **strongly-typed ID**: nó vừa cho so sánh theo giá trị, vừa không cấp phát trên heap, vừa khiến trình biên dịch bắt lỗi truyền nhầm id ([bài 16.14](../../stage-05-senior-engineering/module-16-clean-architecture/16.13-advanced-notes.mdx)).

## Bài tập áp dụng

#### Bài 1 — Tái hiện bug

Tạo một `class` và kiểm tra `Contains` với hai đối tượng cùng dữ liệu. Đổi sang `record` và thử lại.

**Tiêu chí hoàn thành:** bạn thấy **bốn phép kiểm tra cùng đổi kết quả** khi chuyển sang `record`, và giải thích được `record` sinh ra những gì.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Đừng chỉ thử `Equals`. Thử cả `List.Contains`, `HashSet.Contains` và `Distinct` — chúng cho thấy phạm vi ảnh hưởng.

**Lời giải:**

```csharp
class DiaChiClass(string tinh, string quan)
{
    public string Tinh { get; } = tinh;
    public string Quan { get; } = quan;
}

record DiaChiRecord(string Tinh, string Quan);
```

```csharp
var c1 = new DiaChiClass("Hà Nội", "Cầu Giấy");
var c2 = new DiaChiClass("Hà Nội", "Cầu Giấy");

Console.WriteLine($"class  : c1.Equals(c2)     -> {c1.Equals(c2)}");
Console.WriteLine($"class  : List.Contains     -> {new List<DiaChiClass> { c1 }.Contains(c2)}");
Console.WriteLine($"class  : HashSet.Contains  -> {new HashSet<DiaChiClass> { c1 }.Contains(c2)}");
Console.WriteLine($"class  : Distinct đếm      -> {new[] { c1, c2 }.Distinct().Count()}");
```

Kết quả chạy trên .NET 9.0.203:

```text
class  : c1.Equals(c2)     -> False
class  : List.Contains     -> False
class  : HashSet.Contains  -> False
class  : Distinct đếm      -> 2

record : r1 == r2          -> True
record : List.Contains     -> True
record : HashSet.Contains  -> True
record : Distinct đếm      -> 1
```

**Bốn phép kiểm tra, bốn kết quả ngược nhau — chỉ vì một từ khoá.**

**`record` sinh ra những gì:**

| Thành viên | Tác dụng |
|---|---|
| `Equals(T?)` và `Equals(object?)` | So sánh **từng thuộc tính**, không so sánh tham chiếu |
| `GetHashCode()` | Băm từ **tất cả** thuộc tính |
| `operator ==` và `operator !=` | Gọi `Equals` thay vì so sánh tham chiếu |
| `IEquatable<T>` | Cho phép so sánh không cần đóng hộp |
| `ToString()` | In ra dạng `DiaChiRecord { Tinh = Hà Nội, Quan = Cầu Giấy }` |
| `Deconstruct` | Cho phép `var (tinh, quan) = diaChi;` |
| `<Clone>$` | Hỗ trợ cú pháp `with` |

```text
Với class, MỌI thứ trong bảng trên phải tự viết.
Và tự viết đúng cả Equals lẫn GetHashCode là chỗ hay sai — xem bài 2.
```

**Vì sao `List.Contains` và `HashSet.Contains` đều đổi:**

```text
List.Contains    -> gọi EqualityComparer<T>.Default.Equals(a, b)
                 -> Equals -> record có, class thì dùng mặc định (so tham chiếu)

HashSet.Contains -> tính GetHashCode trước, rồi mới Equals
                 -> cần CẢ HAI đúng
```

Đây là lý do phải thử cả hai: chúng đi qua hai cơ chế khác nhau, và một cài đặt sai có thể làm đúng cái này mà hỏng cái kia — chính xác là tình huống ở bài 2.

**`record` cũng cho cú pháp `with`, tiện cho dữ liệu bất biến:**

```csharp
var cu = new DiaChiRecord("Hà Nội", "Cầu Giấy");
var moi = cu with { Quan = "Đống Đa" };

Console.WriteLine(cu);    // DiaChiRecord { Tinh = Hà Nội, Quan = Cầu Giấy }
Console.WriteLine(moi);   // DiaChiRecord { Tinh = Hà Nội, Quan = Đống Đa }
```

```text
cu KHÔNG đổi — with tạo một đối tượng MỚI.
Đây là cách làm việc với dữ liệu bất biến mà không phải viết constructor sao chép.
```

**Và một giới hạn quan trọng: `record` so sánh theo thuộc tính, nhưng chỉ ở mức NÔNG.**

```csharp
record DonHang(int Id, List<string> MatHang);

var d1 = new DonHang(1, ["A", "B"]);
var d2 = new DonHang(1, ["A", "B"]);

Console.WriteLine(d1 == d2);      // False!
```

```text
Hai List khác nhau -> List không so sánh theo nội dung
-> record gọi Equals của List -> so tham chiếu -> False
```

```csharp
// Sửa: dùng kiểu collection có so sánh theo giá trị
record DonHang(int Id, ImmutableArray<string> MatHang);   // vẫn so tham chiếu

// Hoặc tự ghi đè phần đó
record DonHang(int Id, List<string> MatHang)
{
    public virtual bool Equals(DonHang? o) =>
        o is not null && o.Id == Id && o.MatHang.SequenceEqual(MatHang);
    public override int GetHashCode() =>
        HashCode.Combine(Id, MatHang.Count);
}
```

```text
Lưu ý `virtual` ở Equals(DonHang?) — record yêu cầu đúng chữ ký đó.
Viết `override` hay bỏ `virtual` đều không biên dịch được.
```

**Quy tắc đơn giản:** dùng `record` cho **giá trị** (địa chỉ, tiền, khoảng thời gian, DTO), dùng `class` cho **thực thể có định danh** (một Lead là chính nó, dù đổi tên thì vẫn là Lead đó).

</details>

#### Bài 2 — Tái hiện bẫy GetHashCode

Ghi đè `Equals` mà không ghi đè `GetHashCode`, rồi thử `HashSet.Contains`.

**Tiêu chí hoàn thành:** bạn thấy `Equals` trả `True` nhưng `HashSet.Contains` trả `False`, và giải thích được vì sao **hai cấu trúc dữ liệu cho hai kết quả khác nhau**.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Trình biên dịch có cảnh báo cho đúng trường hợp này. Xem output khi build.

**Lời giải:**

```csharp
class DiaChiChiEquals(string tinh, string quan)
{
    public string Tinh { get; } = tinh;
    public string Quan { get; } = quan;

    public override bool Equals(object? o) =>
        o is DiaChiChiEquals k && k.Tinh == Tinh && k.Quan == Quan;

    // CỐ Ý không ghi đè GetHashCode
}
```

Trình biên dịch cảnh báo ngay:

```text
warning CS0659: 'DiaChiChiEquals' overrides Object.Equals(object o)
                but does not override Object.GetHashCode()
```

Kết quả chạy trên .NET 9.0.203:

```text
Equals                 -> True
List.Contains          -> True
HashSet.Contains       -> False
Dictionary tra cứu     -> False
HashCode e1 / e2       -> 33736294 / 35191196
HashSet thêm cả hai    -> số phần tử = 2
```

**`Equals` nói hai đối tượng bằng nhau. `HashSet` nói không. Cả hai đều "đúng" theo cách chúng làm việc.**

**Vì sao `List` đúng mà `HashSet` sai:**

```text
List.Contains: duyệt tuần tự, gọi Equals cho từng phần tử
               -> chỉ cần Equals -> ĐÚNG

HashSet.Contains: bước 1 — tính GetHashCode để tìm ĐÚNG NGĂN
                  bước 2 — trong ngăn đó, gọi Equals

GetHashCode mặc định dựa trên tham chiếu
-> hai đối tượng cho hai mã băm khác nhau (33736294 và 35191196)
-> tìm ở hai NGĂN khác nhau
-> bước 2 không bao giờ chạy -> trả False
```

```text
Nói cách khác: HashSet không bao giờ SO SÁNH hai đối tượng đó,
vì nó tin rằng chúng nằm ở hai chỗ khác nhau.
```

**Hợp đồng giữa hai phương thức, phát biểu chính xác:**

```text
a.Equals(b) == true   =>   a.GetHashCode() == b.GetHashCode()      BẮT BUỘC

Chiều ngược lại KHÔNG bắt buộc:
    hai mã băm bằng nhau mà đối tượng khác nhau là bình thường (va chạm)
    -> HashSet xử lý được, vì nó còn gọi Equals ở bước 2
```

```text
Vi phạm hợp đồng -> HashSet, Dictionary, Distinct, GroupBy, ToLookup,
                    Join và mọi thứ dựa trên băm đều sai.
Và chúng sai ÂM THẦM: không ngoại lệ, chỉ là kết quả không đúng.
```

**Cách viết đúng:**

```csharp
public override int GetHashCode() => HashCode.Combine(Tinh, Quan);
```

```text
HashCode.Combine nhận tới 8 tham số và xử lý null an toàn.
Không cần tự nghĩ công thức kiểu "hash * 31 + ..." nữa.
```

**Và quan trọng hơn: dùng đúng những thuộc tính đã dùng trong `Equals`.**

```csharp
// SAI — Equals dùng hai thuộc tính, GetHashCode chỉ dùng một
public override bool Equals(object? o) =>
    o is DiaChi k && k.Tinh == Tinh && k.Quan == Quan;
public override int GetHashCode() => Tinh.GetHashCode();
```

```text
Cách này KHÔNG vi phạm hợp đồng — bằng nhau vẫn cho cùng mã băm.
Nhưng mọi địa chỉ cùng tỉnh rơi vào MỘT ngăn
-> HashSet suy biến thành danh sách -> tra cứu O(n) thay vì O(1)
-> đúng nhưng chậm
```

**Ba dòng cuối của kết quả đo đáng dừng lại:**

```text
HashSet thêm cả hai -> số phần tử = 2
```

```text
Một HashSet lẽ ra phải loại trùng, giờ chứa hai phần tử "bằng nhau".
-> mọi giả định về tính duy nhất dựa trên nó đều sai
-> ví dụ: một HashSet dùng để khử trùng lặp message sẽ cho qua cả hai
```

**Cách phòng, theo thứ tự nên làm:**

**1. Dùng `record` thay vì tự viết — nó sinh cả hai, luôn khớp nhau.**

**2. Nếu phải dùng `class`, bật cảnh báo thành lỗi:**

```xml
<PropertyGroup>
  <WarningsAsErrors>$(WarningsAsErrors);CS0659;CS0661</WarningsAsErrors>
</PropertyGroup>
```

```text
CS0659: ghi đè Equals mà không ghi đè GetHashCode
CS0661: định nghĩa operator == mà không ghi đè Equals
```

**3. Viết một test chung cho mọi kiểu có so sánh theo giá trị:**

```csharp
[Theory]
[MemberData(nameof(CacKieuSoSanhTheoGiaTri))]
public void Hai_doi_tuong_bang_nhau_phai_cung_ma_bam(object a, object b)
{
    a.Equals(b).Should().BeTrue();
    a.GetHashCode().Should().Be(b.GetHashCode(),
        "hai đối tượng bằng nhau phải cho cùng mã băm, nếu không HashSet và Dictionary sẽ sai");

    new HashSet<object> { a }.Contains(b).Should().BeTrue();
    new Dictionary<object, int> { [a] = 1 }.ContainsKey(b).Should().BeTrue();
}
```

Bốn dòng kiểm tra này bắt được cả hai lỗi ở bài này và bài 3, và chúng chạy trong vài mili giây.

</details>

#### Bài 3 — Tái hiện bẫy thuộc tính đổi được

Thêm đối tượng vào `HashSet`, đổi một thuộc tính dùng để băm, rồi tìm lại nó.

**Tiêu chí hoàn thành:** bạn thấy `HashSet` **không tìm được chính đối tượng nó đang chứa**, và nhận ra `Remove` cũng thất bại — nghĩa là phần tử đó không bao giờ xoá được.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Thử cả `Contains`, `Count`, duyệt bằng `foreach`, và `Remove`. Bốn phép này cho một bức tranh đầy đủ hơn một phép.

**Lời giải:**

```csharp
class DiaChiDoiDuoc
{
    public string Tinh { get; set; } = "";      // set — đổi được
    public string Quan { get; set; } = "";

    public override bool Equals(object? o) =>
        o is DiaChiDoiDuoc k && k.Tinh == Tinh && k.Quan == Quan;

    public override int GetHashCode() => HashCode.Combine(Tinh, Quan);
}
```

```csharp
var m = new DiaChiDoiDuoc { Tinh = "Hà Nội", Quan = "Cầu Giấy" };
var set = new HashSet<DiaChiDoiDuoc> { m };

Console.WriteLine($"trước khi đổi: Contains  -> {set.Contains(m)}");

m.Quan = "Đống Đa";                            // đổi thuộc tính dùng để băm

Console.WriteLine($"sau khi đổi  : Contains  -> {set.Contains(m)}");
Console.WriteLine($"sau khi đổi  : Count     -> {set.Count}");
Console.WriteLine($"duyệt thấy nó không      -> {set.Any(x => ReferenceEquals(x, m))}");
Console.WriteLine($"Remove có thành công     -> {set.Remove(m)}");
Console.WriteLine($"Count sau Remove         -> {set.Count}");
```

Kết quả chạy trên .NET 9.0.203:

```text
trước khi đổi: Contains  -> True
sau khi đổi  : Contains  -> False   (chính đối tượng đó!)
sau khi đổi  : Count     -> 1
duyệt thấy nó không      -> True
Remove có thành công     -> False
Count sau Remove         -> 1
```

**Đọc bốn dòng cuối cùng nhau, bức tranh mới đầy đủ:**

```text
Count = 1          -> phần tử VẪN nằm trong tập
foreach thấy nó    -> duyệt tuần tự không dùng mã băm -> thấy
Contains = False   -> tra cứu theo mã băm -> tìm sai ngăn -> không thấy
Remove = False     -> cũng tra cứu theo mã băm -> không xoá được
```

**Phần tử đó bị kẹt: không tìm được, không xoá được, nhưng vẫn chiếm chỗ.**

```text
Cách duy nhất để lấy nó ra: dựng lại toàn bộ tập.
    set = new HashSet<DiaChiDoiDuoc>(set.Where(x => !ReferenceEquals(x, m)));
```

**Vì sao xảy ra:**

```text
Lúc thêm vào: GetHashCode() = H1 -> lưu ở ngăn tương ứng H1
Đổi Quan     : GetHashCode() = H2
Lúc tìm      : tính H2 -> đi tới ngăn của H2 -> ngăn đó RỖNG

HashSet KHÔNG được thông báo khi thuộc tính đối tượng thay đổi.
Nó không có cách nào biết để xếp lại.
```

**Đây là lý do khoá của `Dictionary` và phần tử của `HashSet` nên BẤT BIẾN:**

```csharp
// ĐÚNG — không đổi được sau khi tạo
record DiaChi(string Tinh, string Quan);

// ĐÚNG — class với init, không có setter công khai
class DiaChi
{
    public required string Tinh { get; init; }
    public required string Quan { get; init; }
}
```

```text
init cho phép gán lúc khởi tạo đối tượng, cấm gán sau đó
-> đối tượng không thể đổi mã băm giữa chừng
-> lỗi này biến mất về mặt cấu trúc, không cần ai phải nhớ
```

**Cùng một lỗi ở ba chỗ khác, khó thấy hơn:**

**1. Khoá `Dictionary` là một đối tượng đổi được.**

```csharp
var theoDiaChi = new Dictionary<DiaChiDoiDuoc, List<Lead>>();
theoDiaChi[diaChi] = danhSach;
diaChi.Quan = "Đống Đa";           // ai đó sửa ở nơi khác
theoDiaChi[diaChi];                // KeyNotFoundException
```

**2. `GroupBy` trên một thuộc tính bị đổi giữa chừng.**

```csharp
var nhom = leads.GroupBy(l => l.DiaChi).ToList();   // hoãn lại, chưa chạy
leads[0].DiaChi.Quan = "Đống Đa";                    // sửa
foreach (var g in nhom) { }                          // giờ mới chạy -> nhóm sai
```

Đây là deferred execution gặp dữ liệu đổi được — hai vấn đề riêng lẻ cộng lại thành một lỗi rất khó lần.

**3. Entity của EF Core làm khoá `Dictionary`.**

```csharp
var lead = await _db.Leads.FindAsync(id);
var bang = new Dictionary<Lead, decimal> { [lead] = 0 };

lead.HoTen = "Tên mới";            // EF cho phép, và đây là việc bình thường
bang[lead];                         // hỏng, nếu Lead có Equals/GetHashCode theo giá trị
```

```text
Với entity, cách đúng là dùng ID làm khoá:
    var bang = new Dictionary<int, decimal> { [lead.Id] = 0 };

Id không đổi trong vòng đời của entity -> an toàn.
```

**Quy tắc gói gọn, đáng thuộc:**

```text
Bất cứ thứ gì làm khoá của một cấu trúc dựa trên băm thì phải BẤT BIẾN
suốt thời gian nó nằm trong cấu trúc đó.

Cách chắc chắn nhất để đảm bảo điều đó: làm cho nó không thể đổi được.
```

Nối lại ba bài: bài 1 cho thấy `record` sinh sẵn so sánh theo giá trị, bài 2 cho thấy tự viết dễ sai chỗ nào, bài 3 cho thấy ngay cả khi viết đúng, dữ liệu đổi được vẫn phá vỡ mọi thứ. Cả ba đều dẫn về cùng một kết luận của mục 4.13.6: với kiểu mang **giá trị**, `record` với thuộc tính `init` là mặc định đúng.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **`class` so sánh tham chiếu, `record` so sánh giá trị.** Chọn theo ý nghĩa của kiểu.
2. **Ghi đè `Equals` thì phải ghi đè `GetHashCode`** — quên là bug im lặng.
3. **Value object phải bất biến**, nếu không `HashSet` và `Dictionary` sẽ mất dấu nó.
