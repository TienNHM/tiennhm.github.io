# 4.12 — Mini case study

<SummaryBox>
Bài toán thiết kế cổ điển và đầy cạm bẫy: mô hình hoá **sản phẩm** trong một CRM bán cả **hàng vật lý**, **dịch vụ** và **gói đăng ký**. Phản xạ đầu tiên của hầu hết mọi người là dùng **kế thừa** — và nó hoạt động hoàn hảo trong hai tháng, rồi sụp đổ khi có yêu cầu "một sản phẩm vừa là hàng vật lý vừa bán theo gói". Lúc đó cây kế thừa không mở rộng được nữa mà không viết lại từ đầu. Bài này đi qua **cả hai thiết kế**, cho thấy chính xác chỗ kế thừa gãy, và trình bày cách dùng **composition** để cùng một yêu cầu chỉ mất vài dòng. Nguyên tắc rút ra: **kế thừa mô hình quan hệ "là một" cố định; composition mô hình khả năng có thể thêm bớt**.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra khi nào kế thừa là lựa chọn sai.
- Thiết kế bằng composition thay cho cây kế thừa.
- Dùng `record` cho value object đúng chỗ.
- Đánh giá một thiết kế bằng câu hỏi "yêu cầu tiếp theo sẽ thế nào".

## Nội dung bài học

### 4.12.1 — Đề bài

```
CRM bán ba loại sản phẩm:
  - Hàng vật lý:  có cân nặng, kích thước, tồn kho, phí vận chuyển
  - Dịch vụ:      có thời lượng, người thực hiện, không có tồn kho
  - Gói đăng ký:  có chu kỳ thanh toán, ngày bắt đầu, tự gia hạn

Yêu cầu chung: mã sản phẩm, tên, giá, thuế suất, trạng thái kinh doanh
```

### 4.12.2 — Thiết kế 1: kế thừa

```csharp
public abstract class Product
{
    public ProductId Id { get; protected set; }
    public string Name { get; protected set; }
    public Money Price { get; protected set; }
    public decimal TaxRate { get; protected set; }
    public bool IsActive { get; protected set; }

    public abstract Money CalculateTotal(int quantity);
}

public class PhysicalProduct : Product
{
    public decimal WeightKg { get; private set; }
    public Dimensions Size { get; private set; }
    public int StockQuantity { get; private set; }

    public override Money CalculateTotal(int quantity)
        => Price * quantity + CalculateShipping(quantity);
}

public class ServiceProduct : Product
{
    public TimeSpan Duration { get; private set; }
    public UserId AssignedTo { get; private set; }

    public override Money CalculateTotal(int quantity) => Price * quantity;
}

public class SubscriptionProduct : Product
{
    public BillingCycle Cycle { get; private set; }
    public bool AutoRenew { get; private set; }

    public override Money CalculateTotal(int quantity) => Price * quantity;
}
```

Thiết kế này **tốt** — trong hai tháng.

### 4.12.3 — Chỗ nó gãy

**Yêu cầu tháng thứ ba:** *"Bán máy in kèm gói mực hàng tháng. Nó là hàng vật lý (giao hàng, tồn kho) và cũng là gói đăng ký (thu tiền hàng tháng)."*

```csharp
// Không hợp lệ trong C# — không thể kế thừa HAI lớp
public class PhysicalSubscriptionProduct : PhysicalProduct, SubscriptionProduct
```

Ba cách chữa, cả ba đều tệ:

| Cách chữa | Vấn đề |
|---|---|
| Chép thuộc tính đăng ký vào `PhysicalProduct` | Dịch vụ cũng cần? Lại chép lần nữa |
| Đưa mọi thuộc tính lên lớp `Product` | Lớp cơ sở phình to, hàng vật lý có `AutoRenew` vô nghĩa |
| Thêm `PhysicalSubscriptionProduct` chép code cả hai | Sửa một chỗ phải nhớ sửa hai |

**Và yêu cầu tháng thứ tư:** *"Dịch vụ tư vấn cũng bán theo gói."* Giờ cần `ServiceSubscriptionProduct`. Tháng thứ năm: *"Gói bảo trì gồm cả linh kiện."*

Số lớp tăng theo **tổ hợp**, không phải theo số loại. Đây chính là điểm gãy của kế thừa cho bài toán này.

### 4.12.4 — Thiết kế 2: composition

Câu hỏi cần hỏi lại từ đầu: **"hàng vật lý" là bản chất của sản phẩm, hay là một khả năng nó có?**

Nhìn lại yêu cầu: một sản phẩm **có thể** cần giao hàng, **có thể** thu tiền định kỳ, **có thể** cần người thực hiện. Đó là **khả năng**, không phải bản chất — nên nó thuộc về composition.

```csharp
public sealed class Product
{
    public ProductId Id { get; private set; }
    public string Name { get; private set; }
    public Money Price { get; private set; }
    public decimal TaxRate { get; private set; }
    public bool IsActive { get; private set; }

    // Khả năng — có thể có, có thể không
    public ShippingInfo? Shipping { get; private set; }
    public SubscriptionInfo? Subscription { get; private set; }
    public ServiceInfo? Service { get; private set; }

    public Money CalculateTotal(int quantity)
    {
        var total = Price * quantity;

        if (Shipping is not null)
            total += Shipping.CalculateCost(quantity);

        return total;
    }

    public void EnableShipping(decimal weightKg, Dimensions size)
        => Shipping = new ShippingInfo(weightKg, size);

    public void EnableSubscription(BillingCycle cycle, bool autoRenew)
        => Subscription = new SubscriptionInfo(cycle, autoRenew);
}

// Value object — bất biến, so sánh theo giá trị
public sealed record ShippingInfo(decimal WeightKg, Dimensions Size)
{
    public Money CalculateCost(int quantity)
        => Money.Vnd(WeightKg * quantity * 15_000m);
}

public sealed record SubscriptionInfo(BillingCycle Cycle, bool AutoRenew);
public sealed record ServiceInfo(TimeSpan Duration, UserId AssignedTo);
```

Máy in kèm gói mực giờ là:

```csharp
var mayIn = Product.Create("Máy in HP", Money.Vnd(5_000_000m));
mayIn.EnableShipping(weightKg: 8.5m, size: new Dimensions(45, 35, 30));
mayIn.EnableSubscription(BillingCycle.Monthly, autoRenew: true);
```

**Không lớp mới nào cả.** Và dịch vụ bán theo gói cũng vậy:

```csharp
var tuVan = Product.Create("Tư vấn CRM", Money.Vnd(2_000_000m));
tuVan.EnableService(TimeSpan.FromHours(2), consultantId);
tuVan.EnableSubscription(BillingCycle.Monthly, autoRenew: false);
```

Tám tổ hợp khả năng chỉ cần **một** lớp.

### 4.12.5 — Vì sao dùng record cho khả năng

```csharp
public sealed record ShippingInfo(decimal WeightKg, Dimensions Size);
```

Ba lý do cụ thể:

**Bất biến.** Sau khi tạo, không ai đổi được `WeightKg` từ bên ngoài. Muốn đổi thì tạo bản mới qua `EnableShipping` — nên `Product` luôn kiểm soát được trạng thái của mình.

**So sánh theo giá trị.** Hai `ShippingInfo` cùng số liệu là bằng nhau, điều này đúng về mặt nghĩa: chúng mô tả cùng một cấu hình vận chuyển, không phải hai thực thể khác nhau.

**Ngắn gọn.** Một dòng thay cho constructor, property, `Equals`, `GetHashCode` và `ToString` viết tay ([bài 4.8](4.7-records-and-value-objects.mdx)).

### 4.12.6 — Khi nào kế thừa vẫn đúng

Composition không phải lúc nào cũng thắng. Kế thừa phù hợp khi quan hệ "là một" **cố định và không chồng chéo**:

```csharp
// ĐÚNG — một exception KHÔNG THỂ vừa là NotFound vừa là Validation
public abstract class DomainException : Exception { }
public sealed class NotFoundException : DomainException { }
public sealed class ValidationException : DomainException { }
```

Hoặc khi lớp cơ sở cung cấp hành vi mặc định mà lớp con chỉ tinh chỉnh:

```csharp
// ĐÚNG — Controller cung cấp hạ tầng, bạn chỉ thêm action
public class LeadsController : ControllerBase { }
```

**Câu hỏi phân biệt:** *"một đối tượng có thể thuộc hai loại con cùng lúc không?"*

- Không bao giờ → kế thừa được.
- Có thể → **composition**.

Trong ca này, một sản phẩm **có thể** vừa cần giao hàng vừa thu định kỳ, nên câu trả lời là composition ([bài 4.4](4.3-inheritance-and-polymorphism.mdx)).

### 4.12.7 — Đánh giá thiết kế bằng yêu cầu tiếp theo

Cách kiểm tra rẻ nhất trước khi cam kết một thiết kế: **nghĩ ra ba yêu cầu có thể tới trong sáu tháng** và xem thiết kế phản ứng thế nào.

| Yêu cầu | Kế thừa | Composition |
|---|---|---|
| Sản phẩm vừa vật lý vừa đăng ký | **Không làm được** | Gọi thêm một phương thức |
| Thêm khả năng "cho thuê" | Thêm 4 lớp tổ hợp | Thêm 1 record |
| Báo cáo mọi sản phẩm cần giao hàng | Kiểm tra kiểu ở nhiều nơi | Lọc `Shipping is not null` |
| Bỏ khả năng đăng ký của một sản phẩm | Đổi kiểu đối tượng — rất khó | Gán `null` |

Hàng cuối đáng chú ý: với kế thừa, "sản phẩm này không bán theo gói nữa" nghĩa là **đổi kiểu của đối tượng** — điều gần như không làm được khi nó đã có id và đang được tham chiếu ở nơi khác.

## Bài tập áp dụng

#### Bài 1 — Thêm khả năng mới

Thêm "cho thuê" (có thời hạn thuê và tiền cọc) vào cả hai thiết kế. Đếm số file phải sửa.

**Tiêu chí hoàn thành:** bạn có **con số cụ thể cho cả hai thiết kế**, và nhận ra chênh lệch không nằm ở lần thêm này mà ở lần thêm **tiếp theo**.

<details>
<summary><strong>Gợi ý và lời giải — Bài 1</strong></summary>

**Gợi ý.** Với thiết kế kế thừa, đừng chỉ đếm lớp mới. Đếm cả những lớp tổ hợp mà nó tạo ra.

**Lời giải — thiết kế composition:**

```csharp
// 1. Thêm một record
public sealed record RentalInfo(TimeSpan ThoiHan, Money TienCoc);

// 2. Thêm một thuộc tính và một phương thức vào Product
public RentalInfo? Rental { get; private set; }

public void EnableRental(TimeSpan thoiHan, Money tienCoc)
    => Rental = new RentalInfo(thoiHan, tienCoc);
```

```text

Dòng thêm: khoảng 6
```

Và mọi tổ hợp đều dùng được ngay:

```csharp
var mayChieu = Product.Create("Máy chiếu", Money.Vnd(12_000_000m));
mayChieu.EnableShipping(weightKg: 3.2m, size: new Dimensions(40, 30, 15));
```


Đây chính là điều mục 4.12.7 nói — đánh giá một thiết kế bằng yêu cầu **tiếp theo**, không bằng yêu cầu hiện tại. Ở lần thêm đầu tiên, hai thiết kế chênh nhau vài chục dòng. Ở lần thứ năm, một bên vẫn là vài dòng còn bên kia không còn khả thi.

**Và một chi phí của kế thừa mà việc đếm file không thấy:**


#### Bài 2 — Tìm lớp tổ hợp

Rà dự án của bạn tìm lớp có tên ghép từ hai khái niệm và xem nó có phải triệu chứng của vấn đề này không.

**Tiêu chí hoàn thành:** bạn có danh sách kèm đánh giá từng lớp, và phân biệt được tên ghép **hợp lý** với tên ghép là **triệu chứng**.

<details>
<summary><strong>Gợi ý và lời giải — Bài 2</strong></summary>

**Gợi ý.** Không phải mọi tên ghép đều xấu. `AsyncLocal` và `ReadOnlyDictionary` là tên ghép hoàn toàn hợp lý.

**Lời giải — tìm bằng một lệnh:**

```bash
  | grep -v "/Tests/" | grep -v "Handler\|Controller\|Repository\|Service\b"
```

**Phân loại — dùng ba câu hỏi:**

```text

   Không loại trừ -> nhiều khả năng là triệu chứng

2. Có bao nhiêu lớp anh em cùng kiểu ghép?
   Nhiều -> chắc chắn là triệu chứng

3. Một đối tượng có bao giờ cần CHUYỂN từ dạng này sang dạng khác không?
```

| Lớp | Đánh giá | Lý do |
|---|---|---|

| `LeadWithCustomerAndOrdersDto` | Hợp lý | DTO mô tả đúng hình dạng dữ liệu trả về |

**Hai trường hợp "hợp lý" đáng giải thích:**

**1. `ReadOnlyCachedRepository` — decorator chồng nhau là mẫu đúng.**

```csharp
IRepository goc = new SqlRepository(db);
IRepository coCache = new CachedRepository(goc, cache);
IRepository chiDoc = new ReadOnlyRepository(coCache);
```

```text
Mỗi lớp thêm MỘT hành vi và uỷ quyền phần còn lại.
Tổ hợp xảy ra lúc CHẠY, không phải lúc biên dịch
-> 3 decorator cho 8 tổ hợp mà không cần 8 lớp
```

Đây là composition, chỉ là tên lớp nghe giống tổ hợp.

**2. `LeadWithCustomerAndOrdersDto` — DTO mô tả hình dạng.**

```text
Đây không phải mô hình nghiệp vụ, nó là hình dạng của MỘT phản hồi API.
Tên dài nhưng nói đúng nó chứa gì -> hữu ích.

Nếu có 15 DTO kiểu này cho cùng một entity, lúc đó mới là vấn đề khác:
     nên cân nhắc cho client chọn trường, hoặc gom lại.
```

```csharp
class User
{
    public HashSet<VaiTro> CacVaiTro { get; } = [];

```

#### Bài 3 — Viết truy vấn

Với thiết kế composition, viết truy vấn lấy mọi sản phẩm cần giao hàng và so sánh với cách làm ở thiết kế kế thừa.

**Tiêu chí hoàn thành:** bạn viết được truy vấn cho cả hai thiết kế, và chỉ ra được cái nào **dịch được sang SQL** còn cái nào không.

<details>
<summary><strong>Gợi ý và lời giải — Bài 3</strong></summary>

**Gợi ý.** Câu hỏi quyết định không phải "code nào ngắn hơn" mà "EF Core dịch được câu nào thành SQL".

**Lời giải — với composition:**

```csharp
var canGiao = await _db.Products
    .Where(p => p.Shipping != null)
    .Select(p => new SanPhamGiaoDto(p.Id, p.Name, p.Shipping!.WeightKg))
    .ToListAsync(ct);
```

```sql
SELECT [p].[Id], [p].[Name], [p].[Shipping_WeightKg]
FROM [Products] AS [p]
WHERE [p].[Shipping_WeightKg] IS NOT NULL
```

```text
Một truy vấn, lọc ở DATABASE, chỉ lấy ba cột.
```

Cấu hình EF Core cho khả năng dạng này:

```csharp
builder.OwnsOne(p => p.Shipping, s =>
{
    s.Property(x => x.WeightKg).HasColumnName("Shipping_WeightKg");
    s.OwnsOne(x => x.Size);
});
```

**Với kế thừa — phụ thuộc vào chiến lược ánh xạ, và cả ba đều có vấn đề riêng:**

**1. Table-per-hierarchy (mặc định):**

```csharp
var canGiao = await _db.Products
    .Where(p => p is ShippableProduct
             || p is ShippableSubscriptionProduct
             || p is ShippableServiceProduct
             || p is ShippableSubscriptionServiceProduct)
    .ToListAsync(ct);
```

```sql
SELECT ...
FROM [Products] AS [p]
WHERE [p].[Discriminator] IN (
    N'ShippableProduct', N'ShippableSubscriptionProduct',
    N'ShippableServiceProduct', N'ShippableSubscriptionServiceProduct')
```

```text
Dịch được, nhưng: THÊM một lớp có khả năng giao hàng
                  -> phải sửa MỌI truy vấn kiểu này
                  -> và quên một chỗ thì không có lỗi, chỉ thiếu dữ liệu
```

**2. Table-per-type:**

```sql
SELECT ... FROM [Products] AS [p]
LEFT JOIN [ShippableProducts] AS [s] ON [p].[Id] = [s].[Id]
LEFT JOIN [ShippableSubscriptionProducts] AS [ss] ON [p].[Id] = [ss].[Id]
LEFT JOIN [ShippableServiceProducts] AS [sv] ON [p].[Id] = [sv].[Id]
...
```

```text
Mỗi lớp con là một bảng -> mỗi truy vấn là một chuỗi JOIN
8 lớp -> 8 LEFT JOIN cho một câu hỏi đơn giản
```

**3. Và cách nhiều người chọn khi hai cách trên khó: lọc trong bộ nhớ.**

```csharp
// SAI — nạp TOÀN BỘ sản phẩm rồi mới lọc
var tatCa = await _db.Products.ToListAsync(ct);
var canGiao = tatCa.Where(p => p is IShippable).ToList();
```

```text
200.000 sản phẩm nạp hết vào bộ nhớ để lấy ra 12.000
-> đây đúng là lỗi ở bài 1.10, chỉ xuất hiện dưới một hình thức khác
```

**Bảng so sánh:**

| | Composition | Kế thừa (TPH) | Kế thừa (TPT) |
|---|---|---|---|
| Dịch sang SQL | **Có** | Có | Có |
| Sửa khi thêm khả năng | **Không phải sửa** | Sửa mọi truy vấn | Sửa mọi truy vấn |
| Số JOIN | **0** | 0 | Nhiều |
| Đánh index được không | **Có** — trên cột Shipping_WeightKg | Có — trên Discriminator | Khó |
| Rủi ro lọc trong bộ nhớ | Thấp | Trung bình | **Cao** |

**Và một câu hỏi phức tạp hơn cho thấy rõ hơn — "sản phẩm cần giao HOẶC có gói dịch vụ":**

```csharp
// Composition
.Where(p => p.Shipping != null || p.Subscription != null)
```

```csharp
// Kế thừa: phải liệt kê 6 trong 8 lớp
.Where(p => p is ShippableProduct || p is SubscriptionProduct
         || p is ShippableSubscriptionProduct || p is ShippableServiceProduct
         || p is SubscriptionServiceProduct
         || p is ShippableSubscriptionServiceProduct)
```

```text
Composition: điều kiện phản ánh đúng câu hỏi nghiệp vụ
Kế thừa:     phải tự tính ra tập con của phân cấp -> dễ sót, khó đọc lại
```

**Thêm index cho truy vấn composition:**

```csharp
builder.HasIndex(p => p.Shipping!.WeightKg)
       .HasFilter("[Shipping_WeightKg] IS NOT NULL");
```

```text
Index có lọc chỉ chứa những dòng CÓ khả năng giao hàng
-> nhỏ hơn nhiều so với index trên toàn bảng
-> và truy vấn "cần giao hàng" dùng đúng index đó
```

Nối lại ba bài: bài 1 đo chi phí thêm khả năng, bài 2 tìm triệu chứng trong dự án thật, bài 3 cho thấy hệ quả ở tầng dữ liệu. Điểm chung của cả ba: **kế thừa cố định tổ hợp lúc biên dịch, còn composition để nó là dữ liệu lúc chạy** — và mọi khác biệt còn lại đều bắt nguồn từ đó.

</details>

## Kết luận

Ba điều đáng nhớ nhất:

1. **Kế thừa mô hình bản chất cố định; composition mô hình khả năng thêm bớt được.**
2. **Số lớp tăng theo tổ hợp** là dấu hiệu kế thừa sai chỗ.
3. **Thử thiết kế bằng ba yêu cầu giả định** trước khi cam kết — rẻ hơn viết lại rất nhiều.
