# 1.11 — Ví dụ thực tế nhanh

<SummaryBox>
Một đoạn code **6 dòng, hoàn toàn đúng về logic**, làm màn hình báo cáo treo **40 giây**. Nó chạy tốt suốt một năm với 500 khách hàng, rồi hệ thống lên 5.000 khách và thời gian chạy tăng **100 lần** chứ không phải 10 lần. Nguyên nhân là **vòng lặp lồng nhau** — mỗi khách hàng lại duyệt toàn bộ danh sách đơn hàng. Cách sửa chỉ là đổi cách tra cứu sang `Dictionary`, và thời gian xuống **0,4 giây**. Điều đáng nhớ nhất: bug này **không bao giờ lộ ra ở môi trường phát triển**, vì với vài chục bản ghi thì cả hai cách đều chạy tức thì.
</SummaryBox>

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra vòng lặp lồng nhau trên hai tập dữ liệu lớn.
- Chuyển tra cứu tuyến tính sang `Dictionary`.
- Giải thích vì sao O(n²) không lộ ra khi dữ liệu nhỏ.
- Tự rà dự án tìm lỗi tương tự.

## Nội dung bài học

### 1.11.1 — Code gây ra sự cố

```csharp
// Tinh tong gia tri don hang cho moi khach — LOGIC DUNG, hieu nang tham hoa
var ketQua = new List<BaoCaoKhachHang>();

foreach (var khach in danhSachKhach)              // 5.000 khach
{
    decimal tong = 0;
    foreach (var don in danhSachDon)              // 200.000 don
    {
        if (don.MaKhach == khach.Ma)
            tong += don.GiaTri;
    }
    ketQua.Add(new BaoCaoKhachHang(khach.Ten, tong));
}
```

Đếm số phép so sánh:

```
5.000 khach x 200.000 don = 1.000.000.000 phep so sanh
```

Một tỷ phép so sánh — đó là 40 giây.

Điều nguy hiểm: ở môi trường phát triển với 50 khách và 200 đơn, con số là **10.000** phép so sánh, chạy trong vài mili giây. Không ai thấy vấn đề gì.

### 1.11.2 — Vì sao tăng 10 lần dữ liệu lại chậm 100 lần

```
500 khach   x  20.000 don  =      10.000.000  ->  0,4 giay
5.000 khach x 200.000 don  =   1.000.000.000  -> 40 giay
```

Dữ liệu tăng **10 lần** ở cả hai chiều, nhưng số phép so sánh tăng **100 lần** — vì 10 × 10 = 100. Đây là đặc trưng của độ phức tạp **O(n²)** ([bài 1.8](1.7-data-structures-and-big-o.mdx)).

Hệ quả thực tế: hệ thống trông ổn cho tới một ngưỡng nào đó rồi **đổ sập rất nhanh**. Không có giai đoạn "hơi chậm" để bạn kịp nhận ra và xử lý.

### 1.11.3 — Sửa bằng Dictionary

```csharp
// Buoc 1: gom don hang theo ma khach — duyet danh sach don DUNG MOT LAN
var tongTheoKhach = new Dictionary<int, decimal>();

foreach (var don in danhSachDon)                  // 200.000 lan
{
    if (tongTheoKhach.ContainsKey(don.MaKhach))
        tongTheoKhach[don.MaKhach] += don.GiaTri;
    else
        tongTheoKhach[don.MaKhach] = don.GiaTri;
}

// Buoc 2: duyet khach, tra cuu TUC THI
var ketQua = new List<BaoCaoKhachHang>();

foreach (var khach in danhSachKhach)              // 5.000 lan
{
    decimal tong = tongTheoKhach.GetValueOrDefault(khach.Ma, 0m);
    ketQua.Add(new BaoCaoKhachHang(khach.Ten, tong));
}
```

```
200.000 + 5.000 = 205.000 thao tac    ->  0,4 giay
(truoc: 1.000.000.000                 -> 40 giay)
```

Nhanh hơn **gần 5.000 lần**, và code cũng không dài hơn bao nhiêu.

Lý do `Dictionary` nhanh: nó dùng bảng băm, nên tra cứu theo khoá mất thời gian **không đổi** bất kể có 10 hay 10 triệu phần tử. Duyệt `List` để tìm thì phải xem từng phần tử ([bài 1.8](1.7-data-structures-and-big-o.mdx)).

**Viết gọn hơn với LINQ:**

```csharp
var tongTheoKhach = danhSachDon
    .GroupBy(d => d.MaKhach)
    .ToDictionary(g => g.Key, g => g.Sum(d => d.GiaTri));

var ketQua = danhSachKhach
    .Select(k => new BaoCaoKhachHang(k.Ten, tongTheoKhach.GetValueOrDefault(k.Ma, 0m)))
    .ToList();
```

Hai cách cho hiệu năng tương đương. Chọn cách nào là tuỳ đội — nhưng cả hai đều **nhanh hơn hẳn** vòng lặp lồng nhau, và đó mới là điều quan trọng.

### 1.11.4 — Cái bẫy tinh vi hơn

```csharp
// Nhin KHONG thay vong lap long — nhung van la O(n^2)
foreach (var khach in danhSachKhach)
{
    var donCuaKhach = danhSachDon.Where(d => d.MaKhach == khach.Ma);   // duyet HET
    ketQua.Add(new BaoCaoKhachHang(khach.Ten, donCuaKhach.Sum(d => d.GiaTri)));
}
```

`Where` **là** một vòng lặp, chỉ là nó không được viết ra. Mỗi lần gọi nó duyệt toàn bộ `danhSachDon`.

**Dấu hiệu nhận biết:** một lời gọi `Where`, `First`, `Any`, `Contains` hoặc `Sum` trên một tập lớn nằm **bên trong** vòng lặp chạy trên một tập lớn khác. Nhìn thì ngắn gọn, nhưng chi phí giống hệt vòng lặp lồng nhau.

Cùng một lỗi xuất hiện với `List.Contains`:

```csharp
// Cham — Contains tren List duyet tuyen tinh
var maDaXuLy = new List<int>();
foreach (var don in danhSachDon)
{
    if (maDaXuLy.Contains(don.Ma)) continue;      // O(n) moi lan goi
    maDaXuLy.Add(don.Ma);
}

// Nhanh — HashSet tra cuu tuc thi
var maDaXuLy = new HashSet<int>();
foreach (var don in danhSachDon)
{
    if (!maDaXuLy.Add(don.Ma)) continue;          // Add tra ve false neu da co
}
```

`HashSet.Add` vừa thêm vừa cho biết phần tử đã tồn tại chưa — gọn hơn và nhanh hơn cặp `Contains` + `Add`.

### 1.11.5 — Tự rà dự án

**1. Tìm vòng lặp lồng nhau:**

```bash
grep -rn -A 5 "foreach" --include=*.cs src/ | grep -B 2 "foreach"
```

Với mỗi kết quả, hỏi: **hai tập này có thể lớn tới mức nào?** Vòng lặp lồng trên 10 phần tử không sao; trên 10.000 thì có.

**2. Tìm truy vấn LINQ trong vòng lặp:**

```bash
grep -rn -A 3 "foreach" --include=*.cs src/ | grep -E "\.Where\(|\.First|\.Any\(|\.Contains\("
```

**3. Tìm `Contains` trên `List`:**

```bash
grep -rn "List<.*>.*\.Contains(" --include=*.cs src/
```

Mỗi kết quả là một ứng viên chuyển sang `HashSet`.

**Cách kiểm chứng nhanh nhất:** đo với dữ liệu gấp 10 lần. Nếu thời gian tăng khoảng 10 lần thì code là O(n) — bình thường. Nếu tăng khoảng 100 lần thì là O(n²) — cần sửa.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Code đúng logic vẫn có thể không dùng được** khi dữ liệu đủ lớn.
2. **`Where` bên trong `foreach` là vòng lặp lồng nhau**, chỉ là không nhìn thấy.
3. **Đo với dữ liệu gấp 10 lần** là cách rẻ nhất để phát hiện O(n²).
