## 1. Git là gì và tại sao cần

### Version control là gì?

Hãy tưởng tượng bạn đang xây hệ thống CRM cho một công ty với 5 developer. Tuần trước bạn vừa hoàn thành tính năng tìm kiếm khách hàng. Hôm nay một đồng nghiệp vô tình xóa mất file `CustomerService.cs`. Không có Git, bạn phải viết lại từ đầu.

Git là một **hệ thống quản lý phiên bản phân tán (Distributed Version Control System)**. Nó lưu lại toàn bộ lịch sử thay đổi của codebase, cho phép nhiều người làm việc song song mà không ghi đè lên nhau.

### Câu chuyện thực tế: Trước và sau khi dùng Git

**Không dùng Git — thực trạng phổ biến ở team nhỏ:**

```
project_v1/
project_v1_backup/
project_v2_final/
project_v2_final_FINAL/
project_v2_final_FINAL_ok/       ← ai tạo cái này?
project_v2_final_FINAL_ok_2/     ← thảm họa
```

Hệ quả: không ai biết phiên bản nào đang chạy trên production, không rollback được khi lỗi, merge code thủ công bằng copy-paste gây mất tính năng.

**Với Git:**

- Mỗi thay đổi được ghi lại với tác giả, thời gian, lý do
- Rollback về bất kỳ thời điểm nào trong vài giây
- Nhiều người làm song song trên cùng codebase
- Review code trước khi merge vào nhánh chính

### Git vs SVN vs không dùng gì

| Tiêu chí | Không có VCS | SVN | Git |
|---|---|---|---|
| Làm việc offline | Khó | Không | Có |
| Branching | Thủ công | Chậm, nặng | Nhanh, nhẹ |
| Distributed | Không | Không | Có |
| Phổ biến trong .NET | — | Có (legacy) | Chuẩn hiện tại |

## 2. Cài đặt và cấu hình Git

### Cài đặt

Tải Git tại [https://git-scm.com](https://git-scm.com) và cài đặt theo hướng dẫn. Kiểm tra sau khi cài:

```bash
git --version
# git version 2.44.0.windows.1
```

### Cấu hình cơ bản

Trước tiên phải khai báo danh tính — Git dùng thông tin này để gắn tên tác giả vào mỗi commit:

```bash
git config --global user.name "Nguyen Van A"
git config --global user.email "nguyenvana@company.com"
git config --global core.editor "code --wait"   # dùng VS Code làm editor mặc định
git config --global init.defaultBranch main      # đặt nhánh mặc định là main
```

Kiểm tra cấu hình:

```bash
git config --list
```

### Kết nối GitHub qua SSH

HTTPS yêu cầu nhập mật khẩu mỗi lần push. SSH key giúp xác thực tự động — bắt buộc trong môi trường team.

```bash
# Bước 1: Tạo SSH key
ssh-keygen -t ed25519 -C "nguyenvana@company.com"
# Nhấn Enter để dùng đường dẫn mặc định (~/.ssh/id_ed25519)

# Bước 2: Lấy nội dung public key
cat ~/.ssh/id_ed25519.pub

# Bước 3: Vào GitHub → Settings → SSH and GPG keys → New SSH key
# Dán nội dung public key vào

# Bước 4: Kiểm tra kết nối
ssh -T git@github.com
# Hi nguyenvana! You've successfully authenticated...
```

## 3. Workflow cơ bản

### Khởi tạo và clone repo

```bash
# Tạo repo mới từ thư mục trống
git init crm-backend
cd crm-backend

# Hoặc clone repo đã có trên GitHub (dùng SSH)
git clone git@github.com:company/crm-backend.git
cd crm-backend
```

### Vòng lặp làm việc hàng ngày

Mỗi ngày làm việc, một developer .NET thường lặp lại chu trình:

```bash
# 1. Cập nhật code mới nhất từ remote
git pull origin main

# 2. Tạo branch cho tính năng mới (xem mục 4)
git checkout -b feature/customer-search

# 3. Viết code... sau đó xem những gì đã thay đổi
git status
git diff

# 4. Thêm file vào staging area
git add src/Services/CustomerService.cs
git add src/Controllers/CustomerController.cs
# Hoặc thêm tất cả file đã thay đổi (dùng cẩn thận)
git add .

# 5. Commit với message rõ ràng
git commit -m "feat(crm): add customer search by name and phone"

# 6. Đẩy lên remote
git push origin feature/customer-search
```

### Xem lịch sử commit

```bash
git log --oneline --graph --all
# * a3f1c2e (HEAD -> feature/customer-search) feat(crm): add customer search by name and phone
# * 8b2d4e1 (main) feat(crm): initialize project structure

git log --author="Nguyen Van A" --since="1 week ago"
```

## 4. Branching và Merging

### Tại sao cần branch?

Branch cho phép bạn làm việc trên một tính năng mới mà không ảnh hưởng đến code đang chạy trên production. Ví dụ: trong khi bạn đang phát triển tính năng "báo cáo doanh thu CRM" (mất 2 tuần), đồng nghiệp vẫn có thể fix bug trên nhánh `main` và deploy ngay lập tức.

### Chiến lược đặt tên branch

| Prefix | Mục đích | Ví dụ |
|---|---|---|
| `feature/` | Tính năng mới | `feature/customer-import` |
| `fix/` | Sửa bug thông thường | `fix/customer-duplicate-email` |
| `hotfix/` | Sửa lỗi khẩn cấp trên production | `hotfix/login-crash-null-ref` |
| `refactor/` | Cải thiện code, không đổi behavior | `refactor/customer-service-clean` |
| `docs/` | Cập nhật tài liệu | `docs/api-swagger-customer` |

### Các lệnh branch thường dùng

```bash
# Xem tất cả branch
git branch -a

# Tạo branch mới và chuyển sang
git checkout -b feature/crm-lead-pipeline

# Chuyển sang branch đã có
git checkout main

# Xóa branch sau khi merge xong
git branch -d feature/crm-lead-pipeline

# Đổi tên branch hiện tại
git branch -m feature/crm-lead-pipeline feature/crm-sales-pipeline
```

### Merge vs Rebase

**Merge** — tạo một "merge commit" ghép lịch sử hai nhánh lại. Lịch sử trung thực, phù hợp khi merge vào `main`.

```bash
git checkout main
git merge feature/customer-search
```

**Rebase** — viết lại lịch sử, đặt commit của bạn lên "trên" nhánh đích. Lịch sử gọn hơn, dùng khi cần sync branch với `main` trước khi mở PR.

```bash
git checkout feature/customer-search
git rebase main
# Sau đó push (cần --force-with-lease vì lịch sử đã thay đổi)
git push --force-with-lease origin feature/customer-search
```

> **Quy tắc vàng:** Không bao giờ rebase nhánh `main` hoặc nhánh đang có người khác làm việc cùng.

## 5. GitHub và Pull Request

### Tại sao cần Pull Request?

PR không chỉ là "yêu cầu merge code". Đây là cơ chế **code review bắt buộc** trong team chuyên nghiệp — giúp phát hiện lỗi sớm, chia sẻ kiến thức và đảm bảo code đạt tiêu chuẩn trước khi vào nhánh chính.

### Quy trình tạo PR

```bash
# 1. Push branch lên GitHub
git push origin feature/crm-customer-notes

# 2. Vào GitHub → repo → "Compare & pull request"
# 3. Điền thông tin PR:
#    - Title: feat(crm): add customer notes with attachment support
#    - Description: mô tả changes, link ticket Jira, screenshot nếu có UI
#    - Reviewers: chọn ít nhất 1 đồng nghiệp
#    - Labels: feature / bug / hotfix
```

### Checklist PR chất lượng

Trước khi mở PR, hãy tự hỏi:

- [ ] Code có compile và pass tất cả unit test không?
- [ ] Có self-review (đọc lại diff của mình) chưa?
- [ ] Commit message có theo chuẩn Conventional Commits không?
- [ ] File `.gitignore` đã loại trừ `appsettings.Development.json`, `*.user`, `bin/`, `obj/` chưa?
- [ ] Không có hardcode connection string, API key trong code?

### Squash merge — lựa chọn phổ biến cho CRM team

Squash merge gộp tất cả commit của một branch thành một commit duy nhất khi merge vào `main`. Giúp lịch sử `main` gọn, dễ đọc:

```
main: feat(crm): add customer notes with attachment support (#42)
```

Thay vì hàng chục commit lộn xộn như `wip`, `fix typo`, `add test`, `fix again`.

## 6. Git Conflicts

### Nguyên nhân conflict

Conflict xảy ra khi hai người cùng sửa **cùng một dòng** trong cùng một file và Git không thể tự quyết định dùng phiên bản nào.

Ví dụ: bạn và đồng nghiệp cùng sửa `CustomerService.cs` dòng 45:

```
<<<<<<< HEAD (nhánh của bạn)
public async Task<Customer> GetByEmailAsync(string email)
=======
public async Task<Customer?> GetByEmailAsync(string email)
>>>>>>> feature/nullable-refactor (nhánh của đồng nghiệp)
```

### Cách resolve conflict

```bash
# Bước 1: Xem file nào đang conflict
git status
# both modified: src/Services/CustomerService.cs

# Bước 2: Mở file, tìm các marker <<<<<<< và chọn phiên bản đúng
# Trong VS Code: dùng "Accept Current Change" / "Accept Incoming Change" / "Accept Both"

# Bước 3: Sau khi sửa xong, đánh dấu đã resolve
git add src/Services/CustomerService.cs

# Bước 4: Hoàn tất merge
git commit -m "fix(crm): resolve conflict in CustomerService nullable refactor"
```

### Best practices tránh conflict

- Pull `main` vào branch của mình thường xuyên (ít nhất mỗi ngày)
- Chia nhỏ PR — PR nhỏ ít conflict hơn PR lớn
- Giao tiếp trong team: "Mình đang sửa CustomerService.cs, đừng đụng vào nhé"
- Dùng `git fetch` + `git log origin/main..HEAD` để xem mình đang cách main bao nhiêu commit

## 7. Developer Workflow thực tế

### Vòng đời một tính năng CRM

```
[Nhận ticket Jira]
       ↓
git pull origin main
       ↓
git checkout -b feature/crm-customer-import
       ↓
[Viết code + unit test]
       ↓
git add . && git commit -m "feat(crm): add CSV customer import endpoint"
       ↓
git push origin feature/crm-customer-import
       ↓
[Mở Pull Request trên GitHub]
       ↓
[Code review — sửa theo feedback]
       ↓
[CI/CD pass — Squash merge vào main]
       ↓
[Auto deploy lên staging]
       ↓
[QA test → deploy production]
```

### `.gitignore` chuẩn cho dự án .NET

Tạo file `.gitignore` ở root project với nội dung:

```bash
# .NET build output
bin/
obj/
*.user
*.suo
.vs/

# Cấu hình môi trường cục bộ — KHÔNG được commit
appsettings.Development.json
appsettings.Local.json
*.env
.env

# Packages (NuGet sẽ restore)
packages/

# Test results
TestResults/
coverage/

# OS
.DS_Store
Thumbs.db
```

> **Quan trọng:** `appsettings.Development.json` thường chứa connection string, API key. Nếu vô tình commit file này lên GitHub public, thông tin bí mật sẽ bị lộ. Luôn kiểm tra `.gitignore` trước `git add .`.

## 8. Debugging Workflow

### Tư duy debug đúng đắn

Debug không phải là "thêm `Console.WriteLine` rồi xóa đi". Đó là quá trình có hệ thống:

1. **Tái hiện lỗi** — xác định bước chính xác gây ra lỗi
2. **Đặt giả thuyết** — tại sao đoạn code này sai?
3. **Kiểm chứng** — dùng debugger để xác nhận hoặc bác bỏ giả thuyết
4. **Sửa và verify** — sửa xong, chạy lại để chắc chắn không có regression

### Visual Studio Debugger — các tính năng thiết yếu

**Breakpoint** — dừng chương trình tại một dòng cụ thể:

- Nhấn `F9` trên dòng muốn dừng, hoặc click vào margin trái
- **Conditional breakpoint**: chuột phải vào breakpoint → Conditions → ví dụ `customer.Email == "test@example.com"` (chỉ dừng khi điều kiện đúng — rất hữu ích khi debug vòng lặp 1000 phần tử)

**Các phím điều hướng khi đang debug:**

| Phím | Hành động |
|---|---|
| `F5` | Tiếp tục chạy đến breakpoint tiếp theo |
| `F10` | Step Over — chạy dòng hiện tại, không đi vào trong hàm |
| `F11` | Step Into — đi vào trong hàm đang gọi |
| `Shift+F11` | Step Out — thoát ra khỏi hàm hiện tại |
| `F9` | Toggle breakpoint |

**Watch Window** — theo dõi giá trị biến theo thời gian thực. Mở qua Debug → Windows → Watch.

**Call Stack** — xem chuỗi các hàm đã gọi dẫn đến điểm hiện tại. Rất hữu ích khi debug exception ở tầng sâu:

```
CustomerController.SearchAsync()
  → CustomerService.SearchByNameAsync()
    → CustomerRepository.FindAsync()    ← lỗi xảy ra ở đây
```

**Exception Settings** — cấu hình để debugger dừng ngay khi exception xảy ra (kể cả exception đã được catch):

Debug → Windows → Exception Settings → tích `Common Language Runtime Exceptions`

### Debug trong môi trường API (.NET)

Khi debug ASP.NET Core Web API cho CRM:

```bash
# Chạy với hot reload để không cần restart liên tục
dotnet watch run

# Hoặc chạy ở chế độ Development để xem đầy đủ stack trace
ASPNETCORE_ENVIRONMENT=Development dotnet run
```

Dùng file `launch.json` trong VS Code để cấu hình debug profile, hoặc nhấn `F5` trong Visual Studio sau khi chọn project API làm Startup Project.

## 9. Conventional Commits

### Tại sao cần chuẩn hóa commit message?

Một lịch sử commit như thế này hoàn toàn vô nghĩa:

```
fix
aaa
test123
cuoi cung xong roi
update
```

Trong khi đây là lịch sử commit của team chuyên nghiệp:

```
feat(crm): add customer search by name and phone number
fix(crm): resolve null reference when customer has no address
refactor(auth): extract token validation to middleware
test(crm): add unit tests for CustomerService.SearchAsync
docs(api): update Swagger description for customer endpoints
```

Commit message tốt giúp: đồng đội hiểu thay đổi không cần đọc code, tự động tạo CHANGELOG, dễ `git bisect` khi tìm commit gây ra bug.

### Format chuẩn Conventional Commits

```
<type>(<scope>): <mô tả ngắn gọn>

[body tùy chọn — giải thích tại sao, không phải cái gì]

[footer tùy chọn — BREAKING CHANGE, Refs #123]
```

**Các type phổ biến:**

| Type | Ý nghĩa | Ví dụ cho CRM |
|---|---|---|
| `feat` | Tính năng mới | `feat(crm): add customer import from CSV` |
| `fix` | Sửa bug | `fix(crm): customer search returns 500 on empty query` |
| `refactor` | Cải thiện code | `refactor(crm): extract search logic to specification pattern` |
| `test` | Thêm/sửa test | `test(crm): add integration tests for CustomerController` |
| `docs` | Tài liệu | `docs(crm): add API usage examples in Swagger` |
| `chore` | Công việc bảo trì | `chore: update NuGet packages to latest stable` |
| `perf` | Cải thiện hiệu năng | `perf(crm): add index on customer email column` |

**Breaking change** — khi thay đổi phá vỡ API hiện tại:

```bash
git commit -m "feat(crm)!: rename GetCustomer to GetCustomerById

BREAKING CHANGE: API endpoint /api/customers/{id} now requires authentication header"
```

### Cấu hình commitlint để enforce chuẩn (tuỳ chọn)

Trong dự án có thể dùng `commitlint` + `husky` để tự động reject commit không đúng format:

```bash
npm install --save-dev @commitlint/cli @commitlint/config-conventional husky
```

## Thực hành

### Bài 1 — Khởi tạo repo CRM (Cơ bản)

```bash
# Tạo thư mục và init git
mkdir crm-backend && cd crm-backend
git init

# Tạo .NET Web API project
dotnet new webapi -n CrmBackend
cd CrmBackend

# Tạo .gitignore cho .NET
dotnet new gitignore

# Commit đầu tiên
git add .
git commit -m "chore: initialize CRM backend project with ASP.NET Core Web API"

# Tạo repo trên GitHub và push lên
git remote add origin git@github.com:<username>/crm-backend.git
git push -u origin main
```

**Mục tiêu:** Có repo trên GitHub với ít nhất 1 commit.

### Bài 2 — Feature branch workflow (Trung bình)

```bash
# Tạo branch cho tính năng customer search
git checkout -b feature/crm-customer-search

# Tạo file CustomerController.cs đơn giản
# ... viết code ...

git add .
git commit -m "feat(crm): add GET /api/customers/search endpoint"

# Thêm unit test
git add .
git commit -m "test(crm): add unit tests for customer search by name"

# Push và tạo PR
git push origin feature/crm-customer-search
# Vào GitHub → mở Pull Request → tự review → merge
```

**Mục tiêu:** Hoàn thành vòng lặp branch → commit → PR → merge.

### Bài 3 — Resolve conflict (Khó)

Mô phỏng conflict để luyện tập:

```bash
# Terminal 1: Tạo branch thứ nhất
git checkout -b feature/crm-update-customer-v1
# Sửa dòng 10 trong CustomerService.cs
git commit -m "feat(crm): add email validation in UpdateCustomer"

# Terminal 2: Tạo branch thứ hai từ cùng commit gốc
git checkout main
git checkout -b feature/crm-update-customer-v2
# Sửa cùng dòng 10 trong CustomerService.cs theo cách khác
git commit -m "feat(crm): add phone validation in UpdateCustomer"

# Merge branch 1 vào main
git checkout main
git merge feature/crm-update-customer-v1

# Merge branch 2 → conflict!
git merge feature/crm-update-customer-v2
# Resolve conflict, sau đó:
git add src/Services/CustomerService.cs
git commit -m "fix(crm): resolve merge conflict in UpdateCustomer validation"
```

**Mục tiêu:** Resolve conflict thành công và giữ nguyên cả hai tính năng validation.

### Bài 4 — Submit PR vào CRM repo mẫu (Nâng cao)

1. Fork repo mẫu: `github.com/course/crm-backend-starter`
2. Clone về máy
3. Tạo branch `feature/crm-<tên-bạn>-customer-notes`
4. Implement endpoint `POST /api/customers/{id}/notes`
5. Viết ít nhất 2 unit test
6. Commit đúng chuẩn Conventional Commits
7. Push và mở PR vào repo mẫu với mô tả đầy đủ

### Phần A — Quiz (20 điểm)

Mỗi câu **4 điểm**.

1. Lệnh nào tạo nhánh mới và chuyển sang nhánh đó?  
   A. `git branch` B. `git checkout -b feature/x` hoặc `git switch -c feature/x` C. `git clone` D. `git push`  
   > **Đáp án:** B.

2. Conventional Commits: tiền tố nào cho sửa lỗi?  
   A. `feat:` B. `fix:` C. `chore:` D. `docs:`  
   > **Đáp án:** B.

3. Sau khi resolve conflict, bước bắt buộc trước `git commit`?  
   A. `git pull` B. `git add` file đã sửa C. `git reset --hard` D. `git stash pop`  
   > **Đáp án:** B.

4. `.gitignore` dùng để?  
   A. Xóa commit B. Bỏ qua file khỏi staging mặc định C. Mã hóa repo D. Gộp branch  
   > **Đáp án:** B.

5. Pull Request chủ yếu phục vụ?  
   A. Xóa remote B. Review + CI trước merge C. Tăng tốc clone D. Backup DB  
   > **Đáp án:** B.

### Phần B — Lab chấm điểm (80 điểm)

| Tiêu chí | Điểm | Ghi chú |
