# 10.6 — 6. Resource-based Authorization

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-03-aspnet-core-backend/module-10-authentication-authorization/10.6-resource-based-authorization
> Khi quyền phụ thuộc vào dữ liệu: IAuthorizationService, vì sao phải nạp bản ghi trước khi kiểm tra, IDOR, và lọc ở tầng truy vấn cho danh sách.

> Attribute không trả lời được câu hỏi *"người này có sở hữu **bản ghi số 42** không?"* — vì lúc attribute chạy, bản ghi **chưa được nạp**. Phân quyền theo tài nguyên đảo thứ tự: nạp dữ liệu trước, rồi mới kiểm tra quyền bằng `IAuthorizationService`. Lỗ hổng mà nó ngăn chặn có tên riêng — **IDOR** (Insecure Direct Object Reference) — và nó nằm trong OWASP Top 10 vì cực kỳ phổ biến: đổi `/customers/42` thành `/customers/43` và bạn đọc được dữ liệu của người khác. Với **danh sách**, kiểm tra từng bản ghi là sai cách; quyền phải nằm **trong truy vấn**.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Giải thích vì sao attribute không đủ cho quyền theo dữ liệu.
- Dùng `IAuthorizationService` trong action.
- Nhận ra và ngăn lỗ hổng IDOR.
- Lọc quyền ở tầng truy vấn cho danh sách.
- Chọn đúng giữa 403 và 404 khi từ chối.

## Nội dung bài học

### 10.7.1 — Vì sao attribute không đủ

```csharp
[Authorize(Roles = "SalesRep")]     // chạy TRƯỚC khi action bắt đầu
[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(Guid id, UpdateRequest req, CancellationToken ct)
{
    var customer = await _db.Customers.FindAsync([id], ct);   // ban ghi nap O DAY
    ...
}
```

Attribute chạy ở tầng phân quyền, **trước** action — lúc đó chưa ai truy vấn database. Nó biết bạn là `SalesRep`, nhưng không biết khách hàng 42 thuộc về ai.

Thứ tự bắt buộc phải là: **nạp bản ghi → kiểm tra quyền trên bản ghi đó → thực hiện thao tác.**

### 10.7.2 — Lỗ hổng IDOR

```csharp
// SAI — chỉ kiểm tra "đã đăng nhập chưa"
[Authorize]
[HttpGet("{id:guid}")]
public async Task<ActionResult<CustomerDto>> GetById(Guid id, CancellationToken ct)
{
    var customer = await _db.Customers.FindAsync([id], ct);
    return customer is null ? NotFound() : Ok(customer.ToDto());
}
```

Bất kỳ ai đăng nhập cũng đọc được **mọi** khách hàng. Kẻ tấn công chỉ cần đổi id trong URL — không cần công cụ, không cần kỹ năng.

Đây là **Broken Access Control**, hạng mục **số 1** trong OWASP Top 10. Nó phổ biến vì code trông hoàn toàn bình thường: có `[Authorize]`, có kiểm tra `null`, có trả DTO. Không có gì trông sai cả.

Dùng GUID thay số tự tăng làm việc dò id khó hơn, nhưng **không phải** giải pháp: id vẫn xuất hiện trong URL, trong log, trong response của các endpoint khác. Đó là che giấu, không phải kiểm soát.

### 10.7.3 — `IAuthorizationService`

```csharp
public sealed class SameOwnerRequirement : IAuthorizationRequirement;

public sealed class CustomerOwnerHandler
    : AuthorizationHandler<SameOwnerRequirement, Customer>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        SameOwnerRequirement requirement,
        Customer resource)
    {
        var userId = context.User.FindFirstValue(ClaimTypes.NameIdentifier);

        if (userId is not null && resource.OwnerId == userId)
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}

// Con đường thứ hai: quản lý cùng khu vực
public sealed class CustomerTerritoryHandler
    : AuthorizationHandler<SameOwnerRequirement, Customer>
{
    protected override Task HandleRequirementAsync(
        AuthorizationHandlerContext context,
        SameOwnerRequirement requirement,
        Customer resource)
    {
        if (context.User.IsInRole(CrmRoles.Manager)
            && context.User.FindFirstValue("territory") == resource.Territory)
            context.Succeed(requirement);

        return Task.CompletedTask;
    }
}
```

Hai handler độc lập cho cùng một requirement, và vì nhiều handler là **OR** ([bài 10.6](10.5-policy-based-authorization.mdx)), chỉ cần một cái `Succeed` là qua. Thêm một con đường mới — ví dụ "người được uỷ quyền tạm thời" — là thêm một handler, không sửa hai handler cũ.

```csharp
[Authorize]
[HttpPut("{id:guid}")]
public async Task<IActionResult> Update(
    Guid id, UpdateCustomerRequest request,
    [FromServices] IAuthorizationService authorization,
    CancellationToken ct)
{
    var customer = await _db.Customers.FindAsync([id], ct);
    if (customer is null) return NotFound();

    var result = await authorization.AuthorizeAsync(
        User, customer, new SameOwnerRequirement());

    if (!result.Succeeded) return Forbid();

    customer.Apply(request);
    await _db.SaveChangesAsync(ct);
    return NoContent();
}
```

`AuthorizeAsync` nhận **ba** tham số: người dùng, **tài nguyên**, và requirement. Tham số giữa là điểm khác biệt với mọi thứ ở các bài trước.

### 10.7.4 — 403 hay 404

```csharp
if (!result.Succeeded) return Forbid();       // 403: "có tồn tại, bạn không được xem"
if (!result.Succeeded) return NotFound();     // 404: "coi như không tồn tại"
```

Khác biệt nằm ở **thông tin bạn tiết lộ**. 403 xác nhận bản ghi đó **tồn tại** — kẻ tấn công dò id lần lượt sẽ phân biệt được "id hợp lệ nhưng không thuộc về tôi" với "id không tồn tại", và từ đó suy ra quy mô dữ liệu, tốc độ tăng trưởng, hoặc tồn tại của một khách hàng cụ thể.

| Dùng | Khi |
|---|---|
| **403** | Người dùng biết tài nguyên tồn tại là bình thường — bản ghi dùng chung trong tổ chức |
| **404** | Tồn tại của bản ghi là thông tin nhạy cảm — dữ liệu giữa các khách hàng, hồ sơ y tế, tài chính |

Với hệ thống đa khách hàng (multi-tenant), **404 gần như luôn đúng**: khách hàng A không được biết khách hàng B tồn tại.

Nhất quán trong toàn API, và ghi rõ lựa chọn trong tài liệu để người tích hợp không nhầm.

### 10.7.5 — Danh sách: lọc trong truy vấn

Sai lầm hay gặp là áp cách làm của một bản ghi lên cả danh sách:

```csharp
// SAI — nạp TẤT CẢ rồi lọc trong bộ nhớ
var all = await _db.Customers.ToListAsync(ct);

var visible = new List<Customer>();
foreach (var c in all)
{
    var r = await authorization.AuthorizeAsync(User, c, new SameOwnerRequirement());
    if (r.Succeeded) visible.Add(c);
}
```

Ba vấn đề: nạp toàn bộ bảng về bộ nhớ, chạy phân quyền N lần, và **phân trang sai hoàn toàn** — bạn lấy 20 bản ghi rồi lọc còn 3, trang sau lại lấy 20 bản ghi khác. Người dùng thấy các trang có số lượng khác nhau và tổng số đếm sai.

Quyền phải nằm **trong truy vấn**:

```csharp
public static IQueryable<Customer> VisibleTo(
    this IQueryable<Customer> query, ICurrentUser user)
{
    if (user.IsInRole(CrmRoles.Admin))
        return query;                                  // thay tat ca

    if (user.IsInRole(CrmRoles.Manager))
        return query.Where(c => c.Territory == user.Territory);

    return query.Where(c => c.OwnerId == user.Id);     // chi cua minh
}
```

```csharp
var query = _db.Customers.AsNoTracking().VisibleTo(_currentUser);

var total = await query.CountAsync(ct);
var items = await query.Skip(skip).Take(pageSize).ToListAsync(ct);
```

Database chỉ trả về những gì người dùng được xem, nên phân trang đúng, `Count` đúng, và không có dữ liệu thừa nào rời khỏi database.

Đánh đổi: **quy tắc giờ tồn tại ở hai nơi** — trong handler (cho một bản ghi) và trong `VisibleTo` (cho danh sách). Chúng có thể lệch nhau theo thời gian.

Hai cách giảm rủi ro:

**1. Global query filter** của EF Core, áp tự động cho mọi truy vấn:

```csharp
modelBuilder.Entity<Customer>().HasQueryFilter(
    c => c.TenantId == _tenantContext.TenantId);
```

Rất mạnh cho **multi-tenant**: không thể quên, vì nó áp cho mọi truy vấn tới entity đó. Nhưng nhớ `IgnoreQueryFilters()` tồn tại — mọi lời gọi tới nó phải được review.

**2. Một bộ test chạy trên cả hai đường.** Với mỗi vai trò, kiểm tra rằng "bản ghi X hiện trong danh sách" **khi và chỉ khi** "truy cập trực tiếp bản ghi X được cho phép". Đó là bất biến bạn cần bảo vệ.

### 10.7.6 — Đừng quên các đường khác

Phân quyền theo tài nguyên hay bị bỏ sót ở những nơi không phải `GET` và `PUT` chính:

- **Endpoint lồng nhau**: `/customers/{id}/orders` — kiểm tra quyền trên `customer`, không chỉ trên `order`.
- **Xuất dữ liệu**: `/customers/export` thường được viết riêng và quên lọc.
- **Tìm kiếm**: kết quả tìm kiếm phải đi qua cùng một bộ lọc.
- **Tham chiếu trong body**: `PUT /orders/{id}` với `customerId` trỏ tới khách hàng của người khác.
- **Background job và webhook**: chạy ngoài ngữ cảnh người dùng, dễ bỏ qua mọi kiểm tra.

Trường hợp thứ tư đáng chú ý: bạn kiểm tra quyền trên `order` nhưng không kiểm tra rằng `customerId` trong body thuộc về người dùng — và họ gán đơn hàng của mình cho khách hàng của người khác.

### 10.7.7 — Rà lại code của bạn

**Danh sách rà soát phân quyền theo tài nguyên**

- [ ] Mọi endpoint nhận id đều kiểm tra quyền trên bản ghi, không chỉ [Authorize].
- [ ] Kiểm tra quyền xảy ra SAU khi nạp bản ghi.
- [ ] Lựa chọn giữa 403 và 404 là có chủ đích và nhất quán.
- [ ] Hệ thống multi-tenant trả 404, không trả 403.
- [ ] Danh sách lọc quyền trong truy vấn, không lọc sau khi nạp.
- [ ] Phân trang và Count chạy trên truy vấn đã lọc quyền.
- [ ] Endpoint lồng nhau kiểm tra quyền trên tài nguyên cha.
- [ ] Endpoint export và tìm kiếm dùng cùng bộ lọc quyền.
- [ ] Id tham chiếu trong body được kiểm tra thuộc về người dùng.
- [ ] Mọi lời gọi IgnoreQueryFilters đều được review.

## Bài tập áp dụng

#### Bài 1 — Khai thác IDOR bằng cách đổi một con số trên URL

Tạo hai người dùng, mỗi người một khách hàng. Đăng nhập bằng người thứ nhất và gọi endpoint bằng id của khách hàng người thứ hai. Ghi lại kết quả trước và sau khi thêm kiểm tra quyền.

**Tiêu chí hoàn thành:** bạn nêu được vì sao `[Authorize(Roles = "SalesRep")]` **trả lời đúng** câu hỏi nó được hỏi mà vẫn để lọt lỗ hổng.

Gợi ý và lời giải — Bài 1

**Gợi ý.** Attribute chạy **trước khi** action bắt đầu — tức là trước khi ai đó biết `id` trỏ tới bản ghi nào.

**Lời giải — endpoint dễ tổn thương:**

```csharp
[HttpGet("{id:guid}")]
[Authorize(Roles = "SalesRep")]
public async Task<IActionResult> GetById(Guid id, CancellationToken ct)
{
    var customer = await _db.Customers.FindAsync([id], ct);
    return customer is null ? NotFound() : Ok(customer);    // KHÔNG kiểm chủ sở hữu
}
```

```bash
# An đăng nhập, xem khách hàng của mình — đúng
curl -s -H "Authorization: Bearer $TOKEN_AN" .../customers/8f3a1b2c-... | jq .name
# "Công ty Minh Phát"

# An đổi id thành khách hàng của Bình
curl -s -H "Authorization: Bearer $TOKEN_AN" .../customers/7c1d9e4f-... | jq .name
# "Tập đoàn Bắc Nam"        <- KHÁCH HÀNG CỦA BÌNH
```

**Câu trả lời cho tiêu chí.** `[Authorize(Roles = "SalesRep")]` được hỏi: *"người này có vai trò SalesRep không?"* — và An **đúng là** SalesRep. Attribute trả lời chính xác.

Vấn đề là câu hỏi thật sự cần trả lời khác hẳn: *"người này có được xem **bản ghi này** không?"* Câu đó không trả lời được nếu chưa biết bản ghi là gì, mà attribute thì chạy **trước** khi action nạp dữ liệu. Nó không có tài nguyên trong tay, nên về nguyên tắc nó không thể trả lời.

```text
Phân quyền theo vai trò:    (người dùng)              -> có/không
Phân quyền theo tài nguyên: (người dùng, TÀI NGUYÊN)  -> có/không
```

Thiếu vế thứ hai là thiếu hẳn một chiều thông tin.

**Bản đã sửa:**

```csharp
[HttpGet("{id:guid}")]
[Authorize(Roles = "SalesRep")]
public async Task<IActionResult> GetById(Guid id, CancellationToken ct)
{
    var customer = await _db.Customers.FindAsync([id], ct);
    if (customer is null) return NotFound();

    var authorized = await _authz.AuthorizeAsync(User, customer, "CustomerOwner");
    if (!authorized.Succeeded) return Forbid();

    return Ok(customer);
}
```

```text
403
```

**Vì sao lớp lỗi này phổ biến đến mức nằm đầu bảng OWASP.** Ba lý do cộng lại:

1. **Nó không gây lỗi.** Ứng dụng chạy đúng, log sạch, test xanh — vì test thường chỉ kiểm "người dùng xem được dữ liệu của mình".
2. **Khai thác không cần kỹ năng.** Đổi một con số trên thanh địa chỉ. Không cần công cụ, không cần hiểu gì về hệ thống.
3. **Nó có ở mọi endpoint nhận id.** Chỉ cần quên một chỗ trong hàng trăm chỗ.

**Vì vậy đừng dựa vào việc nhớ.** Hai lớp phòng vệ hệ thống hơn:

- **Global query filter** ở tầng `DbContext` — mọi truy vấn tự động lọc theo tenant hoặc chủ sở hữu, kể cả khi ai đó quên kiểm tra. Xem [bài 13.11](../../stage-04-database-production/module-13-entity-framework-core/13.10-global-query-filters.mdx).
- **Id không đoán được** — `Guid` thay vì số tăng dần. Không chặn được tấn công có chủ đích, nhưng chặn được việc dò hàng loạt.

#### Bài 2 — Lọc quyền sau khi phân trang làm hỏng cả hai

Cài lọc quyền **sau** khi nạp, tạo 100 bản ghi trong đó 10 thuộc về bạn, và gọi `?page=1&pageSize=20`. Ghi lại số bản ghi trả về và giá trị `total`. Chuyển sang lọc trong truy vấn và so sánh.

**Tiêu chí hoàn thành:** bạn chỉ ra được **ba** thứ sai cùng lúc, không chỉ một.

Gợi ý và lời giải — Bài 2

**Gợi ý.** Đếm lại: số dòng trả về, con số tổng, và lượng dữ liệu đi qua mạng.

**Lời giải — bản sai:**

```csharp
var all = await _db.Customers
    .OrderBy(c => c.Name)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync(ct);                                  // nạp 20 dòng BẤT KỲ

var visible = all.Where(c => c.OwnerId == userId);     // rồi mới lọc

return Ok(new PagedResponse<CustomerDto>(
    visible.Select(ToDto), page, pageSize,
    total: await _db.Customers.CountAsync(ct)));       // đếm TẤT CẢ
```

```bash
curl -s '.../customers?page=1&pageSize=20' | jq '{count: (.items | length), total}'
```

```json
{ "count": 2, "total": 100 }
```

**Ba thứ sai cùng lúc:**

**1. Số dòng trả về không đúng kích thước trang.** Yêu cầu 20, nhận 2 — vì trong 20 dòng đầu theo tên, chỉ 2 dòng thuộc về bạn. Trang 2 có thể trả 0 dòng, trang 3 trả 5 dòng. Giao diện không dựng nổi phân trang với dữ liệu như vậy.

**2. `total` nói dối.** Nó báo 100 trong khi bạn chỉ được xem 10. Người dùng thấy "5 trang" rồi bấm sang trang 4 và nhận trang trống. Tệ hơn: **con số 100 tự nó đã là rò rỉ thông tin** — bạn vừa cho biết hệ thống có 100 khách hàng.

**3. Dữ liệu của người khác đã rời database.** 18 bản ghi không được phép xem đã đi qua mạng, vào bộ nhớ tiến trình, có thể vào log EF Core, có thể vào một bản dump khi sự cố. Lọc ở tầng ứng dụng là lọc **sau khi** dữ liệu đã đi ra.

**Bản đúng — lọc trong truy vấn:**

```csharp
var query = _db.Customers.Where(c => c.OwnerId == userId);    // lọc TRƯỚC

var total = await query.CountAsync(ct);

var items = await query
    .OrderBy(c => c.Name)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .Select(ToDto)                                            // chiếu ở SQL
    .ToListAsync(ct);

return Ok(new PagedResponse<CustomerDto>(items, page, pageSize, total));
```

```json
{ "count": 10, "total": 10 }
```

Đúng cả ba: đủ 10 dòng, tổng đúng 10, và SQL sinh ra có `WHERE OwnerId = @p0` nên 90 bản ghi kia không bao giờ rời database.

**Vì sao `IAuthorizationService` không dùng được cho danh sách.** Nó nhận **một** tài nguyên và trả về có/không. Với danh sách, bạn cần một **biểu thức lọc** dịch được sang SQL. Hai bài toán khác nhau, và cần hai công cụ:

| | Một bản ghi | Danh sách |
|---|---|---|
| Công cụ | `IAuthorizationService` | Điều kiện trong `IQueryable` |
| Kết quả | 403 hoặc 404 | Danh sách đã lọc |

**Cách gọn nhất để không quên:** đặt điều kiện vào một phương thức mở rộng dùng chung.

```csharp
public static IQueryable<Customer> VisibleTo(
    this IQueryable<Customer> q, ClaimsPrincipal user)
{
    if (user.IsInRole("Admin")) return q;

    var userId = user.FindFirstValue(ClaimTypes.NameIdentifier);
    var territory = user.FindFirstValue("territory");

    return user.IsInRole("Manager")
        ? q.Where(c => c.Territory == territory)
        : q.Where(c => c.OwnerId == userId);
}
```

```csharp
var query = _db.Customers.VisibleTo(User);
```

Một nơi định nghĩa quy tắc, và `grep` tìm được mọi truy vấn **thiếu** nó.

#### Bài 3 — Đường xuất dữ liệu bị bỏ quên

Cài kiểm tra quyền đầy đủ cho `GET /customers/{id}` nhưng quên `GET /customers/export`. Xác nhận export trả dữ liệu của mọi người.

**Tiêu chí hoàn thành:** bạn liệt kê được **mọi** đường dữ liệu ra khỏi hệ thống của mình, không chỉ các endpoint REST.

Gợi ý và lời giải — Bài 3

**Gợi ý.** Đừng đọc controller. Hãy tìm mọi chỗ chạm vào `DbSet` rồi trả kết quả ra ngoài — kể cả những chỗ không phải controller.

**Lời giải — endpoint bị bỏ quên:**

```csharp
[HttpGet("export")]
[Authorize(Roles = "SalesRep")]
public async Task Export(CancellationToken ct)
{
    Response.ContentType = "text/csv";
    await using var writer = new StreamWriter(Response.Body);

    await foreach (var c in _db.Customers.AsAsyncEnumerable().WithCancellation(ct))
        await writer.WriteLineAsync($"{c.Id},{c.Name},{c.Email},{c.Revenue}");
}
```

```bash
curl -s -H "Authorization: Bearer $TOKEN_AN" .../customers/export | wc -l
# 100
```

**An xuất được toàn bộ 100 khách hàng**, dù endpoint chi tiết đã chặn đúng.

**Vì sao chỗ này bị quên.** Ba lý do:

1. Nó **không nhận id**, nên không ai nghĩ tới chuyện "kiểm tra chủ sở hữu".
2. Nó thường được viết sau, cho một yêu cầu riêng ("cho tôi xuất Excel").
3. Nó có `[Authorize]`, nên nhìn qua thì trông đã được bảo vệ.

**Danh sách mọi đường dữ liệu ra, và đây mới là sản phẩm của bài tập:**

| Đường ra | Hay bị quên vì |
|---|---|
| `GET /{id}` | — (thường được kiểm) |
| `GET /` (danh sách) | Lọc ở tầng ứng dụng thay vì trong truy vấn |
| `GET /export`, `/report` | Không nhận id |
| `GET /search`, `/autocomplete` | Trả "ít trường" nên tưởng vô hại |
| `GET /{id}/related`, `/{id}/history` | Kiểm quyền cha nhưng không kiểm con |
| Endpoint GraphQL | Một endpoint, nhiều resolver, mỗi cái một đường ra |
| SignalR hub | Gửi theo nhóm; sai nhóm là sai người nhận |
| Job nền gửi email hoặc báo cáo | Chạy không có `HttpContext`, không ai kiểm |
| Webhook đẩy sang đối tác | Dữ liệu rời hệ thống, không qua controller nào |

**Ba đường cuối nguy hiểm nhất** vì chúng không có `ClaimsPrincipal` — không có "người dùng" để kiểm tra quyền. Ở đó, quy tắc cách ly phải nằm **trong truy vấn**, không nằm ở tầng phân quyền.

**Cách rà soát bằng công cụ thay vì bằng trí nhớ:**

```bash
# Mọi chỗ chạm DbSet mà không có tên phương thức lọc dùng chung
grep -rn '_db\.\(Customers\|Leads\|Orders\)' --include=*.cs src/ \
  | grep -v 'VisibleTo\|ForTenant'
```

Mỗi dòng trả về là một chỗ cần giải thích tại sao không cần lọc.

**Và lớp phòng vệ hệ thống hơn cả: global query filter.**

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Customer>()
        .HasQueryFilter(c => c.TenantId == _tenant.TenantId);
}
```

Giờ **mọi** truy vấn qua `DbContext` đều mang điều kiện tenant, kể cả endpoint export ai đó viết vội lúc 5 giờ chiều. Nó không thay thế được kiểm tra chủ sở hữu ở mức bản ghi, nhưng nó chặn được lớp rò rỉ nghiêm trọng nhất: dữ liệu đi **xuyên qua các công ty khác nhau**. Hai cái bẫy của filter này được trình bày ở [bài 13.11](../../stage-04-database-production/module-13-entity-framework-core/13.10-global-query-filters.mdx).

## Tự kiểm tra

### Vì sao attribute không kiểm tra được quyền trên một bản ghi cụ thể?

Vì attribute chạy ở tầng phân quyền, trước khi action bắt đầu, nên bản ghi chưa được nạp từ database. Thứ tự bắt buộc phải là nạp bản ghi, kiểm tra quyền trên bản ghi đó, rồi mới thực hiện thao tác.

### IDOR là gì?

Insecure Direct Object Reference, tức endpoint chỉ kiểm tra đã đăng nhập chưa mà không kiểm tra bản ghi có thuộc về người dùng không, nên đổi id trong URL là đọc được dữ liệu của người khác. Nó thuộc Broken Access Control, hạng mục số một trong OWASP Top 10, và phổ biến vì code trông hoàn toàn bình thường.

### Dùng GUID thay số tự tăng có ngăn được IDOR không?

Không. Nó làm việc dò id khó hơn nhưng id vẫn xuất hiện trong URL, trong log và trong response của các endpoint khác. Đó là che giấu chứ không phải kiểm soát truy cập.

### Nên trả 403 hay 404 khi từ chối?

403 xác nhận bản ghi tồn tại, nên kẻ tấn công dò id sẽ phân biệt được id hợp lệ với id không tồn tại và suy ra thông tin về dữ liệu. Dùng 403 khi việc biết tài nguyên tồn tại là bình thường, và 404 khi chính sự tồn tại là nhạy cảm. Với hệ thống đa khách hàng thì 404 gần như luôn đúng.

### Vì sao không lọc quyền sau khi nạp danh sách?

Ba vấn đề: nạp toàn bộ bảng về bộ nhớ, chạy phân quyền N lần, và phân trang sai hoàn toàn vì bạn lấy 20 bản ghi rồi lọc còn 3. Người dùng thấy các trang có số lượng khác nhau và tổng số đếm sai. Quyền phải nằm trong truy vấn.

### Lọc quyền ở hai nơi có rủi ro gì?

Quy tắc tồn tại trong handler cho một bản ghi và trong bộ lọc truy vấn cho danh sách, nên chúng có thể lệch nhau theo thời gian. Giảm rủi ro bằng global query filter của EF Core cho multi-tenant, và bằng một bộ test kiểm tra bất biến rằng bản ghi hiện trong danh sách khi và chỉ khi truy cập trực tiếp được cho phép.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Nạp bản ghi trước, kiểm tra quyền sau.** Attribute không làm được việc này.
2. **IDOR là lỗ hổng phổ biến nhất** vì code trông hoàn toàn bình thường.
3. **Danh sách lọc trong truy vấn.** Lọc sau khi nạp làm hỏng phân trang và tổng số đếm.
