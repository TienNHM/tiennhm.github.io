# 11.13 — Ví dụ thực tế nhanh

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-03-aspnet-core-backend/module-11-signalr/11.13-quick-real-world-example
> Hub nhận token qua query string vì WebSocket không gửi được header: cách xác thực đúng và lỗi lộ token trong log.

> Một hạn chế kỹ thuật dẫn tới một lỗ hổng bảo mật: **WebSocket API của trình duyệt không cho gửi header tuỳ chỉnh**, nên không đính được `Authorization: Bearer ...` như mọi lời gọi HTTP khác. Cách giải quyết chuẩn của SignalR là đưa token vào **query string** — và nó đúng, nhưng kéo theo một hậu quả ít ai nghĩ tới: **query string bị ghi vào access log** của reverse proxy, của CDN, và của mọi tầng hạ tầng ở giữa. Một file log bị chia sẻ để gỡ lỗi có thể chứa hàng nghìn token còn hạn. Bài này trình bày cách xác thực hub đúng, cách che token trong log, và cách phân quyền ở cấp phương thức hub.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Xác thực kết nối SignalR đúng cách.
- Che token khỏi access log.
- Phân quyền ở cấp phương thức hub.
- Xử lý token hết hạn trong kết nối dài.

## Nội dung bài học

### 11.14.1 — Vấn đề

```javascript
// HTTP thông thường — gửi header được
fetch('/api/leads', { headers: { Authorization: `Bearer ${token}` } });

// WebSocket — API trình duyệt KHÔNG cho gửi header tuỳ chỉnh
new WebSocket('wss://api.company.com/hubs/notifications');
//            ^^ không có chỗ để đặt header
```

Đây là hạn chế của **chuẩn WebSocket trong trình duyệt**, không phải của SignalR. Cách giải quyết chuẩn:

```javascript
const connection = new signalR.HubConnectionBuilder()
    .withUrl('/hubs/notifications', {
        accessTokenFactory: () => getAccessToken()     // SignalR dua vao query string
    })
    .withAutomaticReconnect()
    .build();
```

```
Request thực tế:
GET /hubs/notifications?access_token=eyJhbGciOiJIUzI1NiIs...
```

```csharp
// Phia server — doc token tu query string
builder.Services.AddAuthentication()
    .AddJwtBearer(options =>
    {
        options.Events = new JwtBearerEvents
        {
            OnMessageReceived = context =>
            {
                var accessToken = context.Request.Query["access_token"];
                var path = context.HttpContext.Request.Path;

                // CHỈ cho endpoint hub — không áp dụng cho API thường
                if (!string.IsNullOrEmpty(accessToken) &&
                    path.StartsWithSegments("/hubs"))
                {
                    context.Token = accessToken;
                }

                return Task.CompletedTask;
            }
        };
    });
```

Điều kiện `path.StartsWithSegments("/hubs")` quan trọng: không có nó, **mọi** API đều chấp nhận token qua query string — và khi đó mọi lời gọi API cũng lộ token vào log.

### 11.14.2 — Hậu quả: token trong log

```
# Access log cua Nginx
10.0.1.5 - - [24/Sep/2026:10:15:32] "GET /hubs/notifications?access_token=eyJhbGci... HTTP/1.1" 101
```

Query string bị ghi vào **mọi** tầng:

| Nơi | Rủi ro |
|---|---|
| Access log của reverse proxy | File log chia sẻ khi gỡ lỗi |
| Log của CDN | Thường xuất ra hệ thống phân tích của bên thứ ba |
| Log của load balancer | Lưu trữ dài hạn theo chính sách hạ tầng |
| Lịch sử trình duyệt | Nếu URL bị mở trực tiếp |

Token còn hạn trong log nghĩa là ai đọc được log thì đăng nhập được với tư cách người dùng đó.

**Sửa — che trong cấu hình proxy:**

```nginx
# Nginx — định nghĩa định dạng log có che access_token
map $request_uri $loggable_uri {
    ~^(?<prefix>[^?]*)\?.*access_token=[^&]*(?<suffix>.*)$  "$prefix?access_token=***$suffix";
    default $request_uri;
}

log_format masked '$remote_addr - [$time_local] "$request_method $loggable_uri" $status';
access_log /var/log/nginx/access.log masked;
```

**Và ở phía ứng dụng:**

```csharp
builder.Services.AddHttpLogging(o =>
{
    o.LoggingFields = HttpLoggingFields.RequestPath | HttpLoggingFields.ResponseStatusCode;
    // KHÔNG bao gồm RequestQuery
});
```

**Giảm nhẹ quan trọng nhất:** giữ access token **ngắn hạn** (5–15 phút). Token trong log cũ hết hạn nhanh, nên cửa sổ rủi ro nhỏ ([bài 10.13](../module-10-authentication-authorization/10.12-mini-case-study.mdx)).

### 11.14.3 — Phân quyền trong hub

```csharp
[Authorize]
public sealed class NotificationHub : Hub
{
    public override async Task OnConnectedAsync()
    {
        var tenantId = Context.User?.FindFirst("tenant_id")?.Value;
        if (tenantId is null)
        {
            Context.Abort();          // tu choi ket noi
            return;
        }

        // Nhóm theo tenant — để gửi thông báo đúng phạm vi
        await Groups.AddToGroupAsync(Context.ConnectionId, $"tenant-{tenantId}");
        await base.OnConnectedAsync();
    }

    [Authorize(Roles = "SalesManager")]
    public async Task BroadcastToTeam(string message)
    {
        var tenantId = Context.User!.FindFirst("tenant_id")!.Value;
        await Clients.Group($"tenant-{tenantId}").SendAsync("TeamMessage", message);
    }
}
```

Ba điểm quan trọng:

- **`[Authorize]` trên lớp** áp dụng cho mọi phương thức, kể cả `OnConnectedAsync`.
- **`[Authorize(Roles = ...)]` trên phương thức** cho phân quyền chi tiết hơn — client gọi phương thức không có quyền sẽ nhận lỗi.
- **Nhóm theo tenant** là cách gửi đúng phạm vi. `Clients.All` trong hệ multi-tenant gần như luôn sai — nó gửi cho **mọi công ty**.

Điểm cuối đáng nhấn mạnh: đây là lỗi rò rỉ dữ liệu giữa tenant, cùng lớp với [bài 7.12](../../stage-02-csharp-professional/module-07-dependency-injection/7.11-mini-case-study.mdx) nhưng qua một con đường khác.

### 11.14.4 — Gửi cho đúng người dùng

```csharp
// Gửi theo user id — SignalR tự tìm MỌI kết nối của người đó
await _hubContext.Clients.User(userId.ToString()).SendAsync("NewLead", lead, ct);
```

`Clients.User` gửi tới **mọi thiết bị** của người dùng đó — điện thoại, máy tính, nhiều tab. Đó thường là hành vi bạn muốn.

Nó dựa vào `IUserIdProvider` để biết claim nào là id người dùng:

```csharp
public sealed class CustomUserIdProvider : IUserIdProvider
{
    public string? GetUserId(HubConnectionContext connection)
        => connection.User?.FindFirst("sub")?.Value;      // hoac claim ban dung
}

builder.Services.AddSingleton<IUserIdProvider, CustomUserIdProvider>();
```

Mặc định SignalR dùng `ClaimTypes.NameIdentifier`. Nếu token của bạn dùng claim khác — `sub` theo chuẩn JWT chẳng hạn — `Clients.User` sẽ **không tìm thấy ai** và thông báo biến mất im lặng. Đây là lỗi hay gặp và khó chẩn đoán vì không có thông báo lỗi nào.

### 11.14.5 — Token hết hạn trong kết nối dài

```
Access token: 15 phut
Ket noi WebSocket: co the mo hang gio

-> Sau 15 phut, token trong ket noi da het han
```

SignalR **không** tự kiểm tra lại token trên kết nối đang mở, nên kết nối vẫn hoạt động. Điều đó có thể chấp nhận được hoặc không, tuỳ nghiệp vụ.

Nếu cần đảm bảo, buộc kết nối lại định kỳ:

```javascript
const connection = new signalR.HubConnectionBuilder()
    .withUrl('/hubs/notifications', {
        accessTokenFactory: async () => {
            // Tự động làm mới token nếu sắp hết hạn
            if (isTokenExpiringSoon()) await refreshToken();
            return getAccessToken();
        }
    })
    .withAutomaticReconnect([0, 2000, 10000, 30000])
    .build();
```

`accessTokenFactory` được gọi **lại** mỗi lần kết nối lại, nên token mới được dùng tự động.

Mảng truyền vào `withAutomaticReconnect` là các khoảng chờ trước mỗi lần thử: ngay lập tức, 2 giây, 10 giây, 30 giây. Mặc định chỉ thử 4 lần rồi bỏ cuộc — với ứng dụng cần kết nối bền, hãy cấu hình dài hơn hoặc tự xử lý sự kiện `onclose`.

### 11.14.6 — Rà lại code của bạn

**Danh sách rà soát bảo mật SignalR**

- [ ] Token qua query string chỉ chấp nhận cho đường dẫn hub.
- [ ] Access log của proxy che giá trị access_token.
- [ ] HTTP logging của ứng dụng không ghi query string.
- [ ] Access token ngắn hạn để giảm cửa sổ rủi ro.
- [ ] Hub có Authorize ở cấp lớp.
- [ ] Phương thức nhạy cảm có Authorize riêng theo vai trò.
- [ ] Hệ multi-tenant dùng group theo tenant, không dùng Clients.All.
- [ ] IUserIdProvider khớp với claim thật trong token.
- [ ] accessTokenFactory làm mới token khi sắp hết hạn.

## Bài tập áp dụng

1. **Kiểm tra log.** Kết nối tới hub và tìm `access_token` trong access log của proxy. Cấu hình che rồi kiểm tra lại.

2. **Thử phân quyền.** Gọi một phương thức hub có `[Authorize(Roles = ...)]` bằng tài khoản không có vai trò đó.

3. **Kiểm tra IUserIdProvider.** Gửi thông báo bằng `Clients.User` và xác nhận nó tới đúng người, kể cả khi mở nhiều tab.

## Tự kiểm tra

### Vì sao SignalR phải đưa token vào query string?

Vì WebSocket API của trình duyệt không cho gửi header tuỳ chỉnh, nên không đính được header Authorization như lời gọi HTTP thông thường. Đây là hạn chế của chuẩn WebSocket, không phải của SignalR.

### Vì sao điều kiện path StartsWithSegments quan trọng?

Không có nó, mọi API đều chấp nhận token qua query string, nên mọi lời gọi API cũng lộ token vào access log chứ không riêng kết nối hub.

### Token trong query string bị ghi ở những đâu?

Access log của reverse proxy, log của CDN thường xuất ra hệ thống phân tích bên thứ ba, log của load balancer lưu trữ dài hạn, và lịch sử trình duyệt nếu URL bị mở trực tiếp.

### Giảm nhẹ quan trọng nhất cho rủi ro này là gì?

Giữ access token ngắn hạn, khoảng 5 tới 15 phút, nên token trong log cũ hết hạn nhanh và cửa sổ rủi ro nhỏ. Che token trong log là lớp bổ sung.

### Vì sao Clients.All gần như luôn sai trong hệ multi-tenant?

Vì nó gửi cho mọi công ty đang kết nối, tức rò rỉ dữ liệu giữa các tenant. Phải dùng group theo tenant và gửi tới đúng group.

### Lỗi IUserIdProvider biểu hiện thế nào?

Clients.User không tìm thấy ai và thông báo biến mất im lặng, không có lỗi nào. Nguyên nhân thường là token dùng claim sub theo chuẩn JWT trong khi SignalR mặc định tìm ClaimTypes.NameIdentifier.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Token qua query string là cách chuẩn**, nhưng chỉ cho phép trên đường dẫn hub.
2. **Query string vào access log** — che nó, và giữ token ngắn hạn.
3. **`Clients.All` trong hệ multi-tenant là rò rỉ dữ liệu.** Dùng group theo tenant.
