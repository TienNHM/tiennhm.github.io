# 4.9 — Những lỗi thường gặp

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-02-csharp-professional/module-04-csharp-core/4.9-common-mistakes
> Tám lỗi thiết kế lớp hay gặp nhất trong code .NET thật, mỗi lỗi kèm triệu chứng nhận biết, hậu quả cụ thể và cách sửa — từ god class tới so sánh chuỗi sai cách.

> Tám lỗi dưới đây gặp trong gần như mọi codebase .NET đã chạy được vài năm. Điểm chung của chúng: **không lỗi nào gây ra exception ngay lúc viết** — chúng chỉ làm code khó đổi dần, cho tới lúc một yêu cầu nhỏ mất ba ngày. Đáng chú ý nhất là lỗi cuối: **`string.Equals` mặc định so sánh theo thứ tự byte**, nên `"i".ToUpper()` trong văn hoá Thổ Nhĩ Kỳ cho ra `"İ"` chứ không phải `"I"` — một lỗi từng làm hỏng phần đăng nhập của nhiều hệ thống thật, và chỉ xuất hiện trên máy của người dùng ở đúng khu vực đó.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra tám lỗi thiết kế lớp phổ biến qua triệu chứng của chúng.
- Giải thích hậu quả cụ thể của từng lỗi, không chỉ nói "không tốt".
- Áp dụng cách sửa tương ứng.
- Biết vì sao so sánh chuỗi phải nêu rõ `StringComparison`.

## Nội dung bài học

### 4.10.1 — Field công khai có thể thay đổi

```csharp
// SAI
public class Order { public decimal Total; }

// ĐÚNG
public class Order { public decimal Total { get; private set; } }
```

**Triệu chứng:** bất kỳ ai cũng đặt được giá trị bất kỳ, kể cả số âm.

**Hậu quả:** không có chỗ nào chèn kiểm tra, và đổi field thành property sau này là **thay đổi phá vỡ tương thích nhị phân** — mọi assembly tham chiếu tới phải build lại.

### 4.10.2 — God class

```csharp
// SAI — 1200 dòng, xử lý CRUD, email, báo cáo, chiết khấu, xuất Excel
public class CustomerManager { }
```

**Triệu chứng:** file dài hơn 500 dòng; constructor nhận bảy phụ thuộc trở lên; tên class chứa `Manager`, `Helper`, `Util`, `Processor`.

**Hậu quả:** không viết unit test nổi vì phải dựng cả bảy phụ thuộc; hai người sửa cùng file mỗi tuần nên xung đột liên tục; và đổi định dạng Excel lại làm vỡ test của phần chiết khấu.

**Cách sửa** — tách theo **lý do thay đổi**, không tách theo số dòng:

```csharp
public class CustomerService     { }  // quy tắc nghiệp vụ
public class CustomerRepository  { }  // truy cập dữ liệu
public class CustomerExporter    { }  // xuất file
public class CustomerNotifier    { }  // gửi thông báo
```

Phép thử: *"Ai là người yêu cầu thay đổi class này?"* Nếu có nhiều hơn một nhóm người, hãy tách.

### 4.10.3 — Kế thừa để dùng lại code

```csharp
// SAI — PremiumCustomer kế thừa Customer chỉ để thêm một mức chiết khấu
public class PremiumCustomer : Customer
{
    public decimal DiscountRate => 0.15m;
}
```

**Triệu chứng:** lớp con chỉ thêm một hai thuộc tính; hoặc tên lớp con là một **trạng thái** chứ không phải một **loại**.

**Hậu quả:** khách hàng thường nâng hạng lên premium thì làm sao? Bạn không đổi được kiểu của một object đang tồn tại. Phải tạo object mới và cập nhật mọi tham chiếu.

**Cách sửa** — trạng thái là dữ liệu, không phải kiểu:

```csharp
public class Customer
{
    public CustomerTier Tier { get; private set; }
    public void Upgrade(CustomerTier tier) => Tier = tier;
}

public class DiscountPolicy
{
    public decimal GetRate(Customer c) => c.Tier switch
    {
        CustomerTier.Premium => 0.15m,
        CustomerTier.Gold    => 0.10m,
        _                    => 0m
    };
}
```

Quy tắc: **nếu một object có thể chuyển từ loại này sang loại kia trong đời nó, thì đó là trạng thái chứ không phải kiểu.**

### 4.10.4 — Phụ thuộc thẳng vào lớp cài đặt

```csharp
// SAI
public class OrderService
{
    private readonly SqlCustomerRepository _repo = new();
}
```

**Triệu chứng:** `new` một lớp hạ tầng ngay trong class nghiệp vụ.

**Hậu quả:** không test được nếu không có database thật; đổi ORM phải sửa tầng nghiệp vụ; và class tự quyết vòng đời của phụ thuộc thay vì để DI container lo.

**Cách sửa:** nhận qua constructor, khai báo bằng interface — chi tiết ở [bài 4.5](4.4-interface.mdx) và Module 7.

### 4.10.5 — Anemic model

```csharp
// SAI — class chỉ là túi dữ liệu, quy tắc nằm rải rác ngoài kia
public class Order
{
    public decimal Total { get; set; }
    public OrderStatus Status { get; set; }
}

// Ở service A
if (order.Status == OrderStatus.Draft) order.Status = OrderStatus.Confirmed;
// Ở service B — quên kiểm tra
order.Status = OrderStatus.Confirmed;
```

**Triệu chứng:** entity nghiệp vụ không có phương thức nào ngoài property.

**Hậu quả:** cùng một quy tắc được cài đặt ở nhiều chỗ, và chỉ cần một chỗ quên là dữ liệu sai.

**Cách sửa:** đưa hành vi vào entity — xem [bài 4.3](4.2-encapsulation.mdx). Lưu ý DTO thì **nên** anemic; vấn đề chỉ nằm ở entity nghiệp vụ.

### 4.10.6 — Trả về `null` thay vì nói rõ

```csharp
// Mơ hồ — null nghĩa là "không tìm thấy" hay "lỗi" hay "chưa có dữ liệu"?
public Customer? Find(int id) => _db.Customers.Find(id);
```

**Triệu chứng:** chuỗi `if (x != null)` lan khắp nơi; `NullReferenceException` lúc chạy.

**Cách sửa**, chọn theo ngữ nghĩa:

```csharp
// 1. Không tìm thấy là BÌNH THƯỜNG -> mẫu TryXxx
public bool TryFind(int id, out Customer customer)

// 2. Không tìm thấy là BẤT THƯỜNG -> ném ngoại lệ
public Customer GetById(int id) =>
    _db.Customers.Find(id) ?? throw new NotFoundException($"Khách hàng {id}");

// 3. Danh sách rỗng -> trả collection rỗng, KHÔNG BAO GIỜ trả null
public IReadOnlyList<Order> GetOrders(int customerId) =>
    _db.Orders.Where(...).ToList();      // rỗng vẫn là một danh sách hợp lệ
```

Trường hợp 3 là quy tắc tuyệt đối: **phương thức trả về collection không bao giờ trả `null`**. Người gọi phải `foreach` được mà không cần kiểm tra trước.

### 4.10.7 — Ngoại lệ dùng cho luồng thông thường

```csharp
// SAI — người dùng gõ sai ngày là chuyện bình thường
try { date = DateTime.Parse(input); }
catch (FormatException) { date = DateTime.Today; }
```

**Triệu chứng:** `try/catch` bên trong vòng lặp; bắt `FormatException` hay `KeyNotFoundException` như một phần của logic.

**Hậu quả:** ném ngoại lệ tốn kém hơn trả về `bool` rất nhiều lần vì phải dựng stack trace. Trong vòng lặp hàng nghìn lần, đây là lỗi hiệu năng thật.

```csharp
// ĐÚNG
if (!DateTime.TryParse(input, out var date))
    date = DateTime.Today;
```

Tiêu chí: **thất bại này có bình thường không?** Bình thường thì dùng `TryXxx`; bất thường thì mới ném.

### 4.10.8 — So sánh chuỗi không nêu rõ cách so sánh

Đây là lỗi tinh vi nhất trong danh sách, và nó có lịch sử làm hỏng hệ thống thật.

```csharp
// RỦI RO — phụ thuộc văn hoá của máy đang chạy
if (role.ToUpper() == "ADMIN") { }
if (string.Compare(a, b) == 0) { }
```

Trong văn hoá Thổ Nhĩ Kỳ, `"i".ToUpper()` cho ra `"İ"` (chữ I có dấu chấm) chứ **không** phải `"I"`. Nên `"admin".ToUpper() == "ADMIN"` trả về `false` trên máy đặt `tr-TR`. Đây là lỗi kinh điển tới mức có tên riêng: **Turkish I problem**.

```csharp
// ĐÚNG — nêu rõ ý định
if (string.Equals(role, "admin", StringComparison.OrdinalIgnoreCase)) { }
```

Chọn kiểu so sánh:

| Kiểu | Dùng cho |
|---|---|
| `Ordinal` | Mã, định danh, khoá, đường dẫn, tên file |
| `OrdinalIgnoreCase` | Như trên, không phân biệt hoa thường |
| `CurrentCulture` | Chuỗi **hiển thị cho người dùng**, khi sắp xếp |
| `InvariantCulture` | Rất hiếm; hầu như luôn có lựa chọn tốt hơn |

Quy tắc: **mọi so sánh chuỗi mang tính kỹ thuật đều dùng `Ordinal`**. Chỉ dùng so sánh theo văn hoá khi thật sự đang sắp xếp danh sách cho người đọc.

Chuyện tương tự xảy ra với định dạng số và ngày: `decimal.Parse("1,5")` cho kết quả khác nhau giữa `vi-VN` và `en-US`. Với dữ liệu máy đọc, luôn dùng `CultureInfo.InvariantCulture`.

### 4.10.9 — Rà lại code của bạn

**Danh sách rà soát lỗi thường gặp**

- [ ] Không có field public nào; chỉ có property.
- [ ] Không có class nào tên Manager, Helper hay Util mà dài quá 300 dòng.
- [ ] Không có constructor nào nhận quá 5 phụ thuộc.
- [ ] Không kế thừa chỉ để dùng lại code; trạng thái được mô hình hoá bằng dữ liệu.
- [ ] Không new lớp hạ tầng bên trong class nghiệp vụ.
- [ ] Entity nghiệp vụ có phương thức mang nghĩa nghiệp vụ.
- [ ] Phương thức trả về collection không bao giờ trả null.
- [ ] Không dùng try/catch cho luồng chạy thông thường.
- [ ] Mọi so sánh chuỗi kỹ thuật đều nêu rõ StringComparison.Ordinal.
- [ ] Parse số và ngày từ dữ liệu máy đều dùng InvariantCulture.

## Bài tập áp dụng

#### Bài 1 — Tái hiện lỗi Turkish I

Viết một đoạn code so sánh `"admin".ToUpper() == "ADMIN"`, đặt văn hoá hiện tại là `tr-TR` trước đó. Ghi lại kết quả. Sửa bằng `StringComparison.OrdinalIgnoreCase` và chạy lại.

**Tiêu chí hoàn thành:** bạn hiểu vì sao đây là lỗ hổng **bảo mật**, không chỉ là lỗi hiển thị.

Gợi ý và lời giải — Bài 1

**Gợi ý.** Tiếng Thổ Nhĩ Kỳ có **bốn** chữ i, không phải hai: `i` và `İ` là một cặp có chấm, `ı` và `I` là một cặp không chấm. Vậy `"i".ToUpper()` trong văn hoá Thổ cho ra chữ gì?

**Lời giải.**

```csharp
CultureInfo.CurrentCulture = new CultureInfo("tr-TR");

Console.WriteLine($"\"admin\".ToUpper() = {"admin".ToUpper()}");
Console.WriteLine($"ToUpper() == ADMIN -> {"admin".ToUpper() == "ADMIN"}");
Console.WriteLine($"OrdinalIgnoreCase  -> {string.Equals("admin", "ADMIN", StringComparison.OrdinalIgnoreCase)}");
```

**Kết quả chạy thật trên .NET 9:**

```text
"admin".ToUpper() = ADMİN
ToUpper() == ADMIN -> False
OrdinalIgnoreCase  -> True
```

`"admin".ToUpper()` cho `ADMİN` — chữ I **có chấm**, ký tự Unicode U+0130, khác hoàn toàn với `I` thường U+0049.

**Vì sao đây là lỗ hổng bảo mật.** Xét đoạn kiểm tra quyền rất hay gặp:

```csharp
if (user.Role.ToUpper() == "ADMIN")
    AllowDeleteEverything();
```

Trên máy chủ cấu hình văn hoá Thổ Nhĩ Kỳ, người dùng có vai trò `admin` **không** được nhận là quản trị viên — hệ thống từ chối người đúng. Nguy hiểm hơn là chiều ngược lại:

```csharp
if (input.ToLower() != "admin")        // chặn đăng ký tên admin
    AllowRegistration(input);
```

Người dùng đăng ký tên `ADMIN`. Trong văn hoá Thổ, `"ADMIN".ToLower()` cho `admın` — chữ i **không chấm** — nên khác `"admin"` và **lọt qua** bộ lọc. Giờ hệ thống có hai tài khoản mà mắt người đọc đều thấy là "admin".

**Ba nguồn khiến văn hoá đổi mà bạn không biết:**

| Nguồn | Tình huống |
|---|---|
| Ngôn ngữ hệ điều hành của máy chủ | Máy chủ đặt ở vùng khác |
| Biến môi trường `LANG` trong container | Image cơ sở khác nhau có mặc định khác nhau |
| Header `Accept-Language` của người dùng | Khi bật middleware bản địa hoá, văn hoá đổi **theo từng request** |

Dòng cuối đáng sợ nhất: cùng một dòng code cho kết quả khác nhau tuỳ vào ai đang gọi.

**Quy tắc — chia làm hai nhóm rõ ràng:**

| Mục đích | Dùng | Ví dụ |
|---|---|---|
| **So sánh trong logic** | `StringComparison.Ordinal` hoặc `OrdinalIgnoreCase` | Vai trò, mã, khoá, tên file, giao thức |
| **Hiển thị cho người dùng** | `StringComparison.CurrentCulture` | Sắp xếp danh sách tên để hiển thị |

Mặc định nên là **Ordinal**. Chỉ dùng văn hoá khi bạn thật sự đang sắp xếp hoặc so sánh thứ tự để **người đọc** nhìn.

**Cách phòng có hệ thống.** Bật bộ phân tích để trình biên dịch cảnh báo mỗi khi so sánh chuỗi không nêu rõ cách so sánh:

```xml
<PropertyGroup>
  <EnableNETAnalyzers>true</EnableNETAnalyzers>
  <AnalysisMode>Recommended</AnalysisMode>
</PropertyGroup>
```

Quy tắc `CA1862` cảnh báo khi dùng `ToUpper()` hoặc `ToLower()` để so sánh; `CA1310` yêu cầu nêu rõ `StringComparison`. Đây là hai cảnh báo đáng biến thành lỗi.

**Ghi nhớ.** Lỗi này có tên riêng — *Turkish I problem* — vì nó đã gây sự cố đủ nhiều để được đặt tên. Nó cũng là ví dụ điển hình cho một loại lỗi khó chịu: code đúng trên máy bạn, đúng trên CI, và sai trên đúng một môi trường.

#### Bài 2 — Săn god class

Liệt kê năm file dài nhất trong dự án. Với mỗi file, trả lời câu hỏi *"ai yêu cầu thay đổi class này"*. Nếu có nhiều hơn một nhóm người, phác thảo cách tách.

**Tiêu chí hoàn thành:** bạn tách theo **người yêu cầu thay đổi**, không tách theo số dòng.

Gợi ý và lời giải — Bài 2

**Gợi ý.** Tìm file dài nhất:

```bash
find . -name "*.cs" -not -path "*/obj/*" -not -path "*/bin/*" \
  | xargs wc -l | sort -rn | head -10
```

Nhưng số dòng chỉ là **dấu hiệu**, không phải tiêu chí. Tiêu chí là số **lý do độc lập** khiến file phải sửa.

**Lời giải — ví dụ một god class 900 dòng:**

```csharp
public class OrderService
{
    public Task<Order> CreateOrderAsync(...) { }            // nghiệp vụ đặt hàng
    public Task CancelOrderAsync(...) { }                   // nghiệp vụ đặt hàng
    public Task<decimal> CalculateTaxAsync(...) { }        // quy định thuế
    public Task<decimal> CalculateShippingAsync(...) { }// hợp đồng vận chuyển
    public Task SendConfirmationEmailAsync(...) { }          // marketing
    public Task SendSmsAsync(...) { }                   // marketing
    public Task<byte[]> ExportPdfAsync(...) { }          // kế toán
    public Task SyncToErpAsync(...) { }                // hệ thống ERP bên ngoài
    public Task<Report> RevenueReportAsync(...) { }   // ban giám đốc
}
```

**Bảng "ai yêu cầu thay đổi":**

| Nhóm phương thức | Ai yêu cầu đổi | Tần suất đổi |
|---|---|---|
| Tạo, huỷ đơn | Phòng kinh doanh | Cao |
| Tính thuế | Thay đổi quy định pháp luật | Thấp, nhưng bắt buộc và gấp |
| Phí vận chuyển | Đàm phán lại hợp đồng | Trung bình |
| Email, SMS | Marketing | **Rất cao** |
| Xuất PDF | Kế toán | Thấp |
| Đồng bộ ERP | Đội hệ thống ERP | Trung bình |
| Báo cáo | Ban giám đốc | Cao |

**Bảy nhóm người khác nhau** cùng có lý do sửa một file. Hậu quả cụ thể:

- Marketing đổi mẫu email, và lần triển khai đó **kéo theo** mọi thay đổi chưa xong của các nhóm khác.
- Hai người sửa hai việc không liên quan luôn gặp xung đột trong cùng file.
- Bài kiểm thử cho việc tính thuế phải dựng cả `IEmailSender` và `IPdfGenerator`.
- Không ai dám đụng vào file, vì không ai hiểu hết nó.

**Phác thảo tách:**

```text
OrderService          -> chỉ còn tạo, huỷ, điều phối    (~120 dòng)
TaxCalculator         -> tính thuế                       (~80 dòng)
ShippingFeeCalculator -> tính phí vận chuyển             (~60 dòng)
OrderNotifier         -> email và SMS                    (~100 dòng)
OrderPdfExporter      -> xuất PDF                        (~150 dòng)
ErpSyncService        -> đồng bộ ERP                     (~120 dòng)
OrderReportQuery      -> báo cáo (chỉ đọc)               (~200 dòng)
```

`OrderService` còn lại chỉ điều phối:

```csharp
public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly ITaxCalculator _tax;
    private readonly IOrderNotifier _notifier;

    public async Task<Result<Order>> CreateOrderAsync(CreateOrderRequest req, CancellationToken ct)
    {
        var order = Order.Create(req.CustomerId, req.Lines);
        if (order.IsFailure) return order;

        order.Value.ApplyTax(await _tax.CalculateAsync(order.Value, ct));
        await _repo.AddAsync(order.Value, ct);
        await _notifier.NotifyNewOrderAsync(order.Value, ct);
        return order;
    }
}
```

**Vì sao tách theo người yêu cầu chứ không theo số dòng.** Một class 600 dòng chỉ phục vụ **một** nhóm người vẫn là class tốt — tách nó ra chỉ làm code khó theo dõi. Ngược lại, một class 80 dòng phục vụ **ba** nhóm người là class có vấn đề.

Số dòng là dấu hiệu, không phải bệnh. Bệnh là **nhiều lý do độc lập để thay đổi** — chính là nội dung của Single Responsibility Principle, và [bài 5.2](../module-05-advanced-csharp/5.1-solid-principles.mdx) sẽ bàn kỹ.

**Cách tách an toàn từng bước.** Đừng tách một lần. Mỗi lần lấy ra **một** nhóm phương thức, viết kiểm thử cho nó, merge, rồi mới làm nhóm tiếp theo — đúng tinh thần commit nguyên tử ở [bài 3.5](../../stage-01-foundation/module-03-git-developer-workflow/3.4-basic-git-workflow.mdx).

#### Bài 3 — Đo giá của ngoại lệ

Viết vòng lặp 100.000 lần phân tích chuỗi sai định dạng, một lần dùng `try/catch` với `Parse`, một lần dùng `TryParse`. Đo bằng `Stopwatch` và ghi lại tỉ lệ.

**Tiêu chí hoàn thành:** bạn có tỉ lệ cụ thể và nêu được khi nào **vẫn nên** dùng ngoại lệ.

Gợi ý và lời giải — Bài 3

**Gợi ý.** Chạy ở chế độ Release và làm nóng trước, như [bài 1.8](../../stage-01-foundation/module-01-programming-logic/1.7-data-structures-and-big-o.mdx) đã nêu.

**Lời giải.**

```csharp
const int N = 100_000;

var sw = Stopwatch.StartNew();
int loi1 = 0;
for (int i = 0; i < N; i++)
{
    try { int.Parse("không phải số"); }
    catch (FormatException) { loi1++; }
}
sw.Stop();
var tEx = sw.Elapsed.TotalMilliseconds;

sw.Restart();
int loi2 = 0;
for (int i = 0; i < N; i++)
    if (!int.TryParse("không phải số", out _)) loi2++;
sw.Stop();
var tTry = sw.Elapsed.TotalMilliseconds;
```

**Kết quả đo thật trên .NET 9, chế độ Release:**

```text
try/catch Parse : 858.2 ms  (8.58  micro-giây mỗi lần)
TryParse        :   1.1 ms  (0.011 micro-giây mỗi lần)
chậm gấp        : 778 lần
```

**Vì sao ngoại lệ đắt.** Ném một ngoại lệ không chỉ là trả về một giá trị. Runtime phải:

1. Cấp phát đối tượng ngoại lệ trên heap.
2. **Đi ngược ngăn xếp** để tìm khối `catch` phù hợp — chi phí tỉ lệ với độ sâu ngăn xếp.
3. Thu thập dấu vết ngăn xếp, gồm tên phương thức, tên file và số dòng.
4. Tháo dỡ các khung ngăn xếp và chạy mọi khối `finally` trên đường đi.

Bước 2 và 3 là phần đắt nhất, và chúng **đắt hơn** khi ngăn xếp sâu — nghĩa là trong ứng dụng thật, con số còn tệ hơn trong bài đo này.

**Khi nào dùng cái gì:**

| Tình huống | Dùng | Vì sao |
|---|---|---|
| Đầu vào người dùng có thể sai | `TryParse`, `Result` | Sai là chuyện **bình thường**, không phải ngoại lệ |
| Tìm bản ghi có thể không tồn tại | Trả `null` hoặc `Option` | Không tìm thấy là kết quả hợp lệ |
| Vi phạm quy tắc nghiệp vụ dự đoán được | `Result` | Xảy ra thường xuyên, cần thông điệp rõ |
| Tham số sai do lỗi lập trình | **Ngoại lệ** | Đây là lỗi thật, phải dừng ngay và ồn ào |
| Mất kết nối database | **Ngoại lệ** | Thật sự bất thường, không dự đoán được |
| Trạng thái không thể xảy ra | **Ngoại lệ** | Phát hiện sớm còn hơn chạy tiếp với dữ liệu sai |

**Nguyên tắc.** Ngoại lệ dành cho những gì **ngoại lệ** — đúng như tên gọi. Nếu một tình huống xảy ra trong luồng bình thường của hệ thống, nó không phải ngoại lệ, và biểu diễn nó bằng giá trị trả về sẽ vừa nhanh hơn vừa rõ ràng hơn.

**Một hiểu nhầm cần đính chính.** Nhiều người kết luận từ con số này rằng "đừng bao giờ dùng ngoại lệ". Đó là kết luận sai. Một ngoại lệ mất khoảng 8,6 micro-giây; nếu nó xảy ra **một lần mỗi vài nghìn request**, chi phí đó hoàn toàn không đáng kể so với một truy vấn database mất vài mili-giây. Vấn đề chỉ xuất hiện khi ngoại lệ nằm trong **luồng thường xuyên** hoặc trong **vòng lặp**.

**Mẫu `Result` thay thế:**

```csharp
public readonly record struct Result<T>
{
    public bool IsSuccess { get; }
    public T? Value { get; }
    public string? Error { get; }

    private Result(bool ok, T? value, string? error) => (IsSuccess, Value, Error) = (ok, value, error);

    public static Result<T> Ok(T value) => new(true, value, null);
    public static Result<T> Fail(string error) => new(false, default, error);
}
```

## Tự kiểm tra

### Vì sao đổi field public thành property lại là thay đổi phá vỡ?

Vì field và property được truy cập bằng chỉ thị IL khác nhau. Mọi assembly đã biên dịch dựa trên field sẽ không chạy được với phiên bản mới dùng property, mà phải build lại. Với mã nguồn trong cùng solution thì không thấy vấn đề, nhưng với thư viện phát hành ra ngoài thì đó là thay đổi phá vỡ tương thích nhị phân.

### Nhận biết god class bằng cách nào?

Ba triệu chứng: file dài hơn khoảng năm trăm dòng, constructor nhận từ bảy phụ thuộc trở lên, và tên class chứa Manager, Helper, Util hay Processor. Phép thử dứt khoát là hỏi ai yêu cầu thay đổi class này — nếu có nhiều hơn một nhóm người thì nên tách.

### Khi nào kế thừa là sai cách mô hình hoá?

Khi lớp con đại diện cho một trạng thái chứ không phải một loại. Nếu một object có thể chuyển từ loại này sang loại kia trong đời nó — khách thường nâng hạng lên premium — thì đó là trạng thái, vì bạn không đổi được kiểu của một object đang tồn tại. Hãy mô hình hoá bằng một thuộc tính dữ liệu.

### Phương thức trả về collection có được trả null không?

Không bao giờ. Danh sách rỗng vẫn là một danh sách hợp lệ, và người gọi phải foreach được mà không cần kiểm tra trước. Trả null buộc mọi chỗ gọi thêm một nhánh kiểm tra, và chỉ cần quên một chỗ là NullReferenceException.

### Vì sao không nên dùng ngoại lệ cho luồng thông thường?

Vì ném ngoại lệ tốn kém hơn trả về bool rất nhiều lần do phải dựng stack trace. Trong một vòng lặp chạy hàng nghìn lần, đó là lỗi hiệu năng thật. Tiêu chí quyết định là hỏi thất bại này có bình thường không: người dùng gõ sai định dạng là bình thường nên dùng TryParse.

### Turkish I problem là gì?

Trong văn hoá Thổ Nhĩ Kỳ, chữ i viết hoa thành I có dấu chấm chứ không phải I thường. Nên so sánh kiểu role.ToUpper() bằng ADMIN trả về false trên máy đặt tr-TR, làm hỏng phần phân quyền. Cách tránh là luôn nêu rõ StringComparison.Ordinal hoặc OrdinalIgnoreCase cho mọi so sánh chuỗi mang tính kỹ thuật.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Không lỗi nào ở trên gây exception lúc viết.** Chúng chỉ làm code khó đổi dần — đó là lý do chúng sống sót lâu.
2. **Trạng thái không phải kiểu.** Nếu object đổi loại được trong đời nó, hãy dùng dữ liệu chứ đừng dùng kế thừa.
3. **Mọi so sánh chuỗi kỹ thuật đều nêu rõ `Ordinal`.** Mặc định phụ thuộc văn hoá là một quả mìn theo khu vực người dùng.
