# 4.2 — 1. Class và Object

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-02-csharp-professional/module-04-csharp-core/4.2-class-and-object
> Class là khuôn, object là thứ đúc ra từ khuôn. Kèm constructor bảo đảm object luôn hợp lệ ngay từ lúc sinh ra, khác biệt class với struct, và vì sao đừng để object rơi vào trạng thái nửa vời.

> Class là khuôn, object là thứ đúc ra từ khuôn đó. Nhưng điều đáng học không nằm ở cú pháp mà ở một nguyên tắc: **object phải hợp lệ ngay từ khoảnh khắc nó được tạo ra**. Constructor tồn tại để bảo đảm điều đó — nó là cơ hội **duy nhất** bạn có để từ chối một object sai. Bỏ qua cơ hội này thì hệ thống phải mang theo một loại object luôn có thể đang ở trạng thái nửa vời, và mọi phương thức dùng nó đều phải kiểm tra lại. Bài này cũng làm rõ khác biệt giữa `class` và `struct`, một quyết định ảnh hưởng tới cách object được sao chép và so sánh.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Khai báo class với field, property và constructor cho đúng vai trò từng thứ.
- Viết constructor bảo đảm object không bao giờ tồn tại ở trạng thái không hợp lệ.
- Chọn giữa `class` và `struct` theo tiêu chí rõ ràng.
- Dùng `init` và `required` để bất biến hoá mà vẫn khởi tạo linh hoạt.
- Nhận ra và tránh mẫu "object nửa vời".

## Nội dung bài học

### 4.2.1 — Class là khuôn, object là sản phẩm

```csharp
// Khuôn — mô tả một khách hàng TRÔNG như thế nào và LÀM được gì
public class Customer
{
    public int Id { get; }
    public string Name { get; private set; }
    public decimal TotalSpent { get; private set; }

    public Customer(int id, string name)
    {
        Id = id;
        Name = name;
    }

    public void RecordPurchase(decimal amount) => TotalSpent += amount;
}

// Object — thứ đúc ra từ khuôn
var a = new Customer(1, "Nguyen Van A");
var b = new Customer(2, "Tran Thi B");
```

`a` và `b` dùng chung một khuôn nhưng là **hai vùng nhớ độc lập**. Sửa `a` không đụng tới `b` — vì đây là kiểu tham chiếu, và như [bài 1.2](https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-01-foundation/module-01-programming-logic/1.2-variables-and-data-types) đã nói, phép gán `var c = a;` mới là chỗ cần cẩn thận.

### 4.2.2 — Field hay property?

```csharp
public class Order
{
    private decimal _total;              // field: trạng thái nội bộ
    public decimal Total => _total;      // property: cách bên ngoài nhìn vào

    public string Code { get; init; }    // auto-property, chỉ gán lúc khởi tạo
    public int LineCount { get; private set; }   // đọc công khai, ghi nội bộ
}
```

Quy tắc dùng được ngay: **field luôn `private`, property là thứ công khai**.

Lý do không phải hình thức. Property là một **điểm chặn**: sau này bạn thêm được kiểm tra, ghi log, hoặc tính toán lười mà **không phá vỡ code đang gọi**. Field công khai thì không có chỗ nào để chèn những thứ đó, và đổi nó thành property là một thay đổi phá vỡ tương thích nhị phân.

```csharp
// Hôm nay
public decimal Total { get; private set; }

// Sáu tháng sau — thêm kiểm tra, code gọi KHÔNG phải sửa
private decimal _total;
public decimal Total
{
    get => _total;
    private set => _total = value >= 0 ? value : throw new ArgumentException();
}
```

### 4.2.3 — Constructor: cơ hội duy nhất để từ chối

Đây là ý quan trọng nhất của bài.

```csharp
// YẾU — object có thể tồn tại ở trạng thái vô nghĩa
public class Order
{
    public int CustomerId { get; set; }
    public decimal Total { get; set; }
}

var order = new Order();       // CustomerId = 0, Total = 0 — đơn hàng của ai?
```

Object trên **hợp lệ về mặt cú pháp nhưng vô nghĩa về mặt nghiệp vụ**. Và vì nó tồn tại được, mọi hàm nhận `Order` đều phải phòng thủ: kiểm tra `CustomerId > 0`, kiểm tra `Total`, kiểm tra lại ở tầng sau nữa.

```csharp
// MẠNH — không có cách nào tạo ra một Order vô nghĩa
public class Order
{
    public int CustomerId { get; }
    public decimal Total { get; private set; }
    public OrderStatus Status { get; private set; }

    public Order(int customerId, decimal total)
    {
        if (customerId <= 0)
            throw new ArgumentOutOfRangeException(nameof(customerId));
        if (total < 0)
            throw new ArgumentOutOfRangeException(nameof(total));

        CustomerId = customerId;
        Total = total;
        Status = OrderStatus.Draft;
    }
}
```

Lợi ích lan ra toàn hệ thống: **mọi hàm nhận `Order` giờ được bảo đảm nó hợp lệ**, nên chúng không cần kiểm tra lại. Đây là cách giảm số lượng `if` trong codebase nhiều nhất trên mỗi dòng bỏ ra.

Nguyên tắc chung: **làm cho trạng thái sai không biểu diễn được**, thay vì kiểm tra trạng thái sai ở khắp nơi.

### 4.2.4 — `init` và `required`

```csharp
public class Customer
{
    public required string Name { get; init; }   // C# 11: bắt buộc phải gán
    public required string Email { get; init; }
    public string? Phone { get; init; }          // tuỳ chọn
}

var c = new Customer { Name = "A", Email = "a@company.com" };
c.Name = "B";        // Lỗi biên dịch — init chỉ gán được lúc khởi tạo

var bad = new Customer { Name = "A" };   // Lỗi biên dịch — thiếu Email
```

Bộ đôi này cho bạn **cú pháp khởi tạo bằng object initializer** mà vẫn giữ được hai bảo đảm của constructor: không thiếu trường bắt buộc, và không sửa được sau khi tạo.

Khi nào dùng cái nào:

- **Constructor** khi việc tạo object cần kiểm tra chéo giữa nhiều trường, hoặc cần tính toán.
- **`required` + `init`** khi chỉ cần gán thẳng và số trường nhiều (constructor 8 tham số rất khó đọc ở chỗ gọi).

### 4.2.5 — `class` hay `struct`

| | `class` | `struct` |
|---|---|---|
| Loại kiểu | Tham chiếu | Giá trị |
| Phép gán | Chép địa chỉ | **Chép toàn bộ dữ liệu** |
| So sánh `==` mặc định | Theo tham chiếu | Theo từng trường |
| Có thể `null` | Có | Không (trừ `Nullable`) |
| Kế thừa | Có | Không |

Tiêu chí chọn `struct`, cần **đủ cả bốn**:

1. Kích thước nhỏ, thường dưới 16 byte.
2. Bất biến về mặt logic.
3. Sẽ được tạo ra rất nhiều.
4. Không cần kế thừa.

Trong code nghiệp vụ backend, câu trả lời gần như luôn là `class`. `struct` thuộc về những chỗ nhạy hiệu năng — toạ độ, khoảng thời gian, định danh nhỏ.

Cảnh báo về `struct` có thể thay đổi:

```csharp
struct Point { public int X; public int Y; }

var list = new List<Point> { new() { X = 1, Y = 2 } };
// list[0].X = 99;    // Lỗi biên dịch — list[0] trả về một BẢN SAO
```

Đây là nguồn nhầm lẫn kinh điển. Nếu bạn định làm `struct`, hãy làm nó bất biến — hoặc dùng `readonly record struct`.

### 4.2.6 — `static`: thuộc về class, không thuộc về object

```csharp
public class Order
{
    private static int _counter;                     // dùng chung mọi object
    public static Order CreateDraft(int customerId)  // gọi không cần object
        => new Order(customerId, 0m);

    public int SequenceNumber { get; }               // riêng từng object

    private Order(int customerId, decimal total) { /* ... */ }
}

var o = Order.CreateDraft(42);      // gọi trên CLASS
```

`static` hợp cho hàm tiện ích thuần tuý và factory method. Nhưng **trạng thái `static` có thể thay đổi là nguồn lỗi khó lần nhất trong ứng dụng web**: mọi request dùng chung nó, và nhiều request chạy song song.

```csharp
// SAI trong ứng dụng web — tranh chấp giữa các request
public static List<Order> Cache = new();
```

Nếu cần trạng thái dùng chung, hãy đi qua dependency injection với vòng đời được khai báo rõ — chủ đề của Module 7 và của bài [Singleton, Scoped hay Transient](https://tiennhm.io.vn/blog/singleton-scoped-transient-captive-dependency).

### 4.2.7 — Rà lại code của bạn

**Danh sách rà soát class và object**

- [ ] Mọi field đều private; bên ngoài chỉ thấy property.
- [ ] Constructor từ chối mọi tham số làm object rơi vào trạng thái vô nghĩa.
- [ ] Không có class nghiệp vụ nào có constructor rỗng cộng toàn bộ property set công khai.
- [ ] Trường bắt buộc dùng required hoặc nằm trong constructor, không để người gọi quên.
- [ ] Trường không đổi sau khi tạo dùng init hoặc chỉ có getter.
- [ ] Không có trạng thái static có thể thay đổi nào trong code chạy theo request.
- [ ] struct nếu có thì bất biến; không có struct nào có field public settable.

## Bài tập áp dụng

1. **Đếm phòng thủ thừa.** Chọn một class nghiệp vụ có constructor rỗng. Đếm số lần các hàm khác phải kiểm tra lại tính hợp lệ của nó. Viết lại constructor để chặn từ đầu, rồi đếm số `if` xoá được.

2. **Chứng minh bản sao của struct.** Tạo một `struct` có field public, đưa vào `List`, rồi thử sửa qua chỉ số. Ghi lại lỗi biên dịch. Đổi sang `class` và làm lại.

3. **Đua trên trạng thái static.** Viết một endpoint ghi vào một `static List`, gọi song song 50 request. Ghi lại ngoại lệ hoặc dữ liệu sai nhận được.

## Tự kiểm tra

### Vì sao field nên private còn property mới là thứ công khai?

Vì property là một điểm chặn: sau này bạn thêm được kiểm tra, ghi log hoặc tính toán lười mà không phá vỡ code đang gọi. Field công khai không có chỗ nào để chèn những thứ đó, và đổi nó thành property là một thay đổi phá vỡ tương thích nhị phân.

### Vì sao constructor quan trọng đến thế?

Vì nó là cơ hội duy nhất để từ chối một object sai. Nếu constructor không kiểm tra, hệ thống phải mang theo một loại object luôn có thể đang ở trạng thái nửa vời, và mọi hàm dùng nó đều phải kiểm tra lại. Chặn từ constructor là cách giảm số lượng if trong codebase nhiều nhất trên mỗi dòng bỏ ra.

### required và init giải quyết vấn đề gì?

Chúng cho bạn cú pháp object initializer dễ đọc mà vẫn giữ hai bảo đảm của constructor: required buộc phải gán trường bắt buộc nếu không thì lỗi biên dịch, init chỉ cho gán lúc khởi tạo nên object không sửa được sau đó. Hợp khi class có nhiều trường mà constructor tám tham số sẽ khó đọc.

### Khi nào nên dùng struct thay vì class?

Khi đủ cả bốn điều kiện: kích thước nhỏ thường dưới 16 byte, bất biến về mặt logic, sẽ được tạo rất nhiều, và không cần kế thừa. Trong code nghiệp vụ backend thì câu trả lời gần như luôn là class; struct thuộc về những chỗ nhạy hiệu năng như toạ độ hay khoảng thời gian.

### Vì sao không sửa được phần tử struct qua chỉ số của List?

Vì struct là kiểu giá trị, nên list[0] trả về một bản sao chứ không phải tham chiếu tới phần tử trong danh sách. Sửa bản sao đó không có ý nghĩa gì nên trình biên dịch chặn luôn. Đây là lý do struct nên bất biến, hoặc dùng readonly record struct.

### Vì sao trạng thái static có thể thay đổi lại nguy hiểm trong ứng dụng web?

Vì mọi request dùng chung nó và nhiều request chạy song song, nên xảy ra tranh chấp dữ liệu rất khó tái hiện. Nếu cần trạng thái dùng chung thì phải đi qua dependency injection với vòng đời khai báo rõ ràng, thay vì một biến static ẩn trong class.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Constructor là cơ hội duy nhất để từ chối.** Dùng nó, và mọi hàm phía sau bớt được một tầng phòng thủ.
2. **Làm cho trạng thái sai không biểu diễn được** thay vì kiểm tra nó ở khắp nơi.
3. **`static` có thể thay đổi là bom hẹn giờ trong ứng dụng web.** Mọi request dùng chung một biến.
