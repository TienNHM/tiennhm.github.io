# 4.3 — 2. Encapsulation

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-02-csharp-professional/module-04-csharp-core/4.3-encapsulation
> Đóng gói không phải là bọc field bằng getter/setter. Nó là giữ bất biến nghiệp vụ ở một chỗ duy nhất — và cái bẫy lớn nhất là trả về collection mà người ngoài sửa được.

> Đóng gói thường bị dạy thành "đừng để field `public`, hãy bọc bằng getter và setter". Cách hiểu đó bỏ sót toàn bộ giá trị: một property `{ get; set; }` bọc quanh field **không đóng gói được gì cả** — nó chỉ thêm hai dòng code cho cùng mức độ tự do. Đóng gói thật sự là **giữ bất biến nghiệp vụ ở một chỗ duy nhất**: thay vì cho bên ngoài đặt giá trị tuỳ ý, class phơi ra những **hành vi** hợp lệ và tự bảo vệ quy tắc của mình. Bài này cũng chỉ ra cái bẫy bị bỏ qua nhiều nhất: **trả về một `List` là trao cho người gọi quyền sửa trạng thái nội bộ của bạn**.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Phân biệt "bọc field" với đóng gói thật sự.
- Thiết kế API của class theo hành vi thay vì theo dữ liệu.
- Chỉ ra vì sao trả về `List` phá vỡ đóng gói, và trả gì thay thế.
- Đặt bất biến nghiệp vụ ở một chỗ duy nhất.
- Chọn đúng giữa `private set`, `init` và chỉ có getter.

## Nội dung bài học

### 4.3.1 — Bọc field không phải đóng gói

```csharp
// KHÔNG đóng gói gì cả — chỉ dài hơn
public class Order
{
    private decimal _total;
    public decimal Total { get => _total; set => _total = value; }
}

order.Total = -500_000m;      // vẫn đặt được giá trị vô lý
```

Property trên cho bên ngoài **đúng mức tự do** như một field công khai. Nó chỉ tốn thêm chỗ.

```csharp
// ĐÓNG GÓI — class tự giữ quy tắc của mình
public class Order
{
    private readonly List<OrderLine> _lines = new();

    public decimal Total => _lines.Sum(l => l.Amount);   // TÍNH ra, không lưu
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;

    public void AddLine(Product product, int quantity)
    {
        if (Status != OrderStatus.Draft)
            throw new InvalidOperationException("Đơn đã chốt, không thêm dòng được.");
        if (quantity <= 0)
            throw new ArgumentOutOfRangeException(nameof(quantity));

        _lines.Add(new OrderLine(product, quantity));
    }

    public void Confirm()
    {
        if (_lines.Count == 0)
            throw new InvalidOperationException("Đơn rỗng không chốt được.");
        Status = OrderStatus.Confirmed;
    }
}
```

Khác biệt cốt lõi: **không ai đặt được `Total`**, vì `Total` không phải thứ để đặt — nó là **hệ quả** của các dòng hàng. Và không ai chốt được một đơn rỗng, vì quy tắc đó nằm trong `Confirm()`.

### 4.3.2 — Thiết kế theo hành vi, không theo dữ liệu

```csharp
// Theo DỮ LIỆU — class chỉ là cái túi, quy tắc nằm rải rác bên ngoài
public class BankAccount
{
    public decimal Balance { get; set; }
}

// ... ở đâu đó trong service
if (account.Balance >= amount)          // quy tắc ở đây
    account.Balance -= amount;

// ... ở một service khác, ai đó quên kiểm tra
account.Balance -= amount;              // số dư âm
```

```csharp
// Theo HÀNH VI — quy tắc nằm cùng chỗ với dữ liệu
public class BankAccount
{
    public decimal Balance { get; private set; }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));
        if (amount > Balance)
            throw new InvalidOperationException("Số dư không đủ.");

        Balance -= amount;
    }

    public void Deposit(decimal amount) { /* ... */ }
}
```

Câu hỏi để tự kiểm tra thiết kế:

> Nếu tôi thêm một quy tắc nghiệp vụ mới, tôi phải sửa **bao nhiêu chỗ**?

Với phiên bản đầu: mọi nơi có `account.Balance -=`. Với phiên bản sau: đúng một chỗ.

Một class chỉ toàn `{ get; set; }` và không có phương thức nào thường được gọi là **anemic model** — mô hình thiếu máu. Nó không sai tuyệt đối (DTO thì đúng là nên như vậy), nhưng với thực thể nghiệp vụ thì nó đẩy toàn bộ quy tắc ra ngoài, nơi chúng dễ bị bỏ sót.

### 4.3.3 — Cái bẫy collection

Đây là chỗ bị bỏ qua nhiều nhất, kể cả trong code của người có kinh nghiệm.

```csharp
public class Order
{
    private readonly List<OrderLine> _lines = new();
    public List<OrderLine> Lines => _lines;      // TRAO QUYỀN SỬA
}

order.Lines.Clear();                 // xoá sạch, không qua kiểm tra nào
order.Lines.Add(new OrderLine(...)); // thêm thẳng, bỏ qua AddLine
```

Mọi quy tắc trong `AddLine` vừa bị vô hiệu hoá. `private readonly` trên field **không** bảo vệ được nội dung của list — nó chỉ ngăn việc gán một list khác vào.

Ba cách sửa, theo thứ tự nên dùng:

```csharp
// 1. Trả về giao diện chỉ đọc — không sao chép, phản ánh thay đổi
public IReadOnlyList<OrderLine> Lines => _lines;

// 2. Trả về bản sao — an toàn tuyệt đối nhưng tốn bộ nhớ
public IReadOnlyList<OrderLine> Lines => _lines.ToList();

// 3. Không phơi ra collection, chỉ phơi ra thứ người gọi thật sự cần
public int LineCount => _lines.Count;
public bool HasLine(int productId) => _lines.Any(l => l.ProductId == productId);
```

Lưu ý về cách 1: `IReadOnlyList` ngăn gọi `Add` và `Clear`, nhưng người gọi vẫn **ép kiểu ngược** về `List` được. Nó là hàng rào cho người trung thực, không phải cho kẻ cố tình. Cần bảo đảm tuyệt đối thì dùng cách 2 hoặc `_lines.AsReadOnly()`.

Và nếu các phần tử bên trong là kiểu có thể thay đổi, người gọi vẫn sửa được từng phần tử — nên `OrderLine` cũng nên bất biến.

### 4.3.4 — Bất biến nghiệp vụ ở một chỗ

**Bất biến** (invariant) là quy tắc luôn phải đúng với mọi object của class, ở mọi thời điểm.

Ví dụ cho `Order`:

- Tổng tiền luôn bằng tổng các dòng.
- Đơn đã chốt không sửa được dòng.
- Đơn rỗng không chốt được.
- Số lượng mỗi dòng luôn dương.

Mỗi bất biến phải được bảo vệ ở **đúng một chỗ** — bên trong class. Nếu một bất biến được kiểm tra ở ba service khác nhau, thì chắc chắn có ngày ai đó viết service thứ tư mà quên.

```csharp
public void AddLine(Product product, int quantity)
{
    // Bất biến 2 và 4 được bảo vệ ngay tại đây
    if (Status != OrderStatus.Draft) throw new InvalidOperationException();
    if (quantity <= 0) throw new ArgumentOutOfRangeException(nameof(quantity));

    _lines.Add(new OrderLine(product, quantity));
    // Bất biến 1 tự động đúng vì Total được TÍNH chứ không LƯU
}
```

Chú ý dòng cuối: khi `Total` là thuộc tính tính toán, bất biến "tổng tiền luôn bằng tổng các dòng" **không thể sai được** — bạn đã làm cho trạng thái sai không biểu diễn được, thay vì phải nhớ đồng bộ hai thứ.

### 4.3.5 — Chọn mức độ mở

| Cách khai báo | Ai đặt được | Dùng khi |
|---|---|---|
| `{ get; }` + gán trong constructor | Chỉ constructor | Giá trị cố định suốt đời object |
| `{ get; init; }` | Constructor và object initializer | Bất biến, nhiều trường |
| `{ get; private set; }` | Chỉ phương thức trong class | Thay đổi được, nhưng theo quy tắc |
| `{ get; protected set; }` | Class con | Hiếm dùng, cân nhắc kỹ |
| `{ get; set; }` | Bất kỳ ai | **DTO, view model** |

Dòng cuối không phải lỗi. DTO là túi dữ liệu để chuyển qua ranh giới, nó **nên** có `{ get; set; }`. Vấn đề chỉ xảy ra khi thực thể nghiệp vụ cũng được viết như DTO.

Nguyên tắc: **bắt đầu ở mức đóng nhất, chỉ mở ra khi có nhu cầu thật**. Mở thì dễ, đóng lại thì phá vỡ code đang gọi.

### 4.3.6 — Rà lại code của bạn

**Danh sách rà soát đóng gói**

- [ ] Không có property nào chỉ là { get; set; } bọc quanh field trong class nghiệp vụ.
- [ ] Không trả về List hay ICollection ra khỏi class; dùng IReadOnlyList hoặc bản sao.
- [ ] Giá trị suy ra được thì TÍNH chứ không LƯU rồi đồng bộ thủ công.
- [ ] Mỗi bất biến nghiệp vụ được bảo vệ ở đúng một chỗ, bên trong class.
- [ ] Class nghiệp vụ có phương thức mang nghĩa nghiệp vụ, không chỉ toàn property.
- [ ] Phần tử bên trong collection được phơi ra cũng bất biến.
- [ ] Mức truy cập bắt đầu ở mức đóng nhất và chỉ mở khi có nhu cầu thật.

## Bài tập áp dụng

1. **Phá vỡ đóng gói của chính mình.** Tìm một class trong dự án có property trả về `List`. Viết một dòng code từ bên ngoài phá vỡ một quy tắc nghiệp vụ của class đó. Sau đó sửa bằng `IReadOnlyList` và thử lại.

2. **Đếm chỗ phải sửa.** Chọn một quy tắc nghiệp vụ trong hệ thống. Đếm số file phải sửa nếu quy tắc đó thay đổi. Nếu nhiều hơn một, thử gom về trong entity và đếm lại.

3. **Biến LƯU thành TÍNH.** Tìm một trường được lưu và phải đồng bộ thủ công (ví dụ `TotalAmount` cập nhật mỗi khi thêm dòng). Đổi thành thuộc tính tính toán và xoá mọi chỗ đồng bộ.

## Tự kiểm tra

### Vì sao property { get; set; } bọc quanh field không phải là đóng gói?

Vì nó cho bên ngoài đúng mức tự do như một field công khai — ai cũng đặt được giá trị bất kỳ, kể cả giá trị vô lý. Đóng gói thật sự là class tự giữ quy tắc của mình: phơi ra hành vi hợp lệ thay vì phơi ra chỗ để ghi giá trị tuỳ ý.

### Vì sao trả về List phá vỡ đóng gói?

Vì người gọi gọi được Add và Clear thẳng lên danh sách nội bộ, bỏ qua mọi kiểm tra trong phương thức của class. Khai báo field là private readonly không giúp gì, vì nó chỉ ngăn gán một list khác chứ không ngăn sửa nội dung list hiện tại.

### IReadOnlyList có bảo vệ tuyệt đối không?

Không. Người gọi vẫn ép kiểu ngược về List được. Nó là hàng rào cho người trung thực chứ không phải cho kẻ cố tình. Cần bảo đảm tuyệt đối thì trả về bản sao bằng ToList hoặc dùng AsReadOnly. Ngoài ra nếu phần tử bên trong có thể thay đổi thì người gọi vẫn sửa được từng phần tử.

### Anemic model là gì và khi nào nó chấp nhận được?

Là class chỉ toàn property get set mà không có phương thức nào mang nghĩa nghiệp vụ, khiến quy tắc bị đẩy ra ngoài và rải rác khắp nơi. Với DTO và view model thì đó là đúng, vì chúng chỉ là túi dữ liệu chuyển qua ranh giới. Vấn đề chỉ xảy ra khi thực thể nghiệp vụ cũng được viết như DTO.

### Vì sao nên TÍNH thay vì LƯU giá trị suy ra được?

Vì khi Total là thuộc tính tính từ các dòng, bất biến tổng tiền luôn bằng tổng các dòng không thể sai được. Nếu lưu thành một trường riêng thì phải nhớ đồng bộ ở mọi chỗ thay đổi dòng hàng, và chỉ cần quên một chỗ là dữ liệu lệch.

### Nên bắt đầu ở mức truy cập nào?

Mức đóng nhất có thể, rồi chỉ mở ra khi có nhu cầu thật. Lý do thực dụng: mở rộng quyền truy cập là thay đổi tương thích ngược, còn siết lại thì phá vỡ mọi code đang gọi. Đi từ chặt sang lỏng dễ hơn nhiều so với chiều ngược lại.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Đóng gói là giữ quy tắc, không phải bọc field.** Câu hỏi đúng là "thêm một quy tắc thì phải sửa mấy chỗ".
2. **Trả về `List` là trao chìa khoá nhà.** Dùng `IReadOnlyList` hoặc đừng phơi collection ra.
3. **Tính thay vì lưu.** Giá trị suy ra được mà lưu riêng là một bất biến chờ bị phá vỡ.
