# 15.14 — Ví dụ thực tế nhanh

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-04-database-production/module-15-docker-deployment/15.14-quick-real-world-example
> Mỗi lần deploy mất 40 request đang xử lý: ENTRYPOINT shell form nuốt SIGTERM, và ba điều kiện để dừng mượt.

> Mỗi lần triển khai, khoảng **40 request đang xử lý bị cắt giữa chừng** — người dùng thấy lỗi mạng, và một số giao dịch dở dang. Đội cho rằng "deploy thì phải vậy", nhưng không phải: nguyên nhân là **một dấu ngoặc vuông trong Dockerfile**. Viết `ENTRYPOINT dotnet Crm.Api.dll` (shell form) khiến ứng dụng chạy như **tiến trình con của `/bin/sh`**, và `sh` **không chuyển tiếp** SIGTERM. Ứng dụng không bao giờ biết nó sắp bị dừng, nên nó không kịp làm gì — 30 giây sau, Kubernetes gửi SIGKILL và cắt ngang mọi thứ. Đổi sang exec form `ENTRYPOINT ["dotnet", "Crm.Api.dll"]` là sửa xong một nửa vấn đề; nửa còn lại là **ba điều kiện** để dừng mượt thật sự.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Phân biệt exec form và shell form trong Dockerfile.
- Cấu hình dừng mượt cho ASP.NET Core.
- Đặt `preStop` và `terminationGracePeriodSeconds` đúng.
- Kiểm chứng rằng không còn request bị cắt.

## Nội dung bài học

### 15.14.1 — Sự cố

```dockerfile
# Dockerfile — shell form
ENTRYPOINT dotnet Crm.Api.dll
```

```
Docker chay:  /bin/sh -c "dotnet Crm.Api.dll"

Tien trinh 1 (PID 1):  /bin/sh
Tien trinh con:        dotnet

Kubernetes gui SIGTERM -> PID 1 (tuc /bin/sh)
/bin/sh KHONG chuyen tiep tin hieu cho tien trinh con
-> dotnet KHONG BIET gi
-> sau 30 giay: SIGKILL -> cat ngang moi request
```

```dockerfile
# Sua — exec form
ENTRYPOINT ["dotnet", "Crm.Api.dll"]
```

```
Docker chay:  dotnet Crm.Api.dll  (truc tiep)

Tien trinh 1 (PID 1):  dotnet      <- nhan SIGTERM

Kubernetes gui SIGTERM -> dotnet nhan duoc
-> ASP.NET Core bat dau dung muot
```

Một cặp dấu ngoặc vuông. Đây là lỗi rất phổ biến vì shell form ngắn hơn và trông tự nhiên hơn.

**Cách kiểm tra nhanh:**

```bash
docker exec <container> ps aux
# Neu thay "/bin/sh -c dotnet ..." o PID 1 -> dang dung shell form
```

### 15.14.2 — Điều kiện 2: ứng dụng phải xử lý SIGTERM

Nhận được tín hiệu là chưa đủ — ứng dụng phải **làm gì đó** với nó.

ASP.NET Core xử lý sẵn: khi nhận SIGTERM, nó ngừng nhận request mới và chờ request đang chạy hoàn thành. Nhưng thời gian chờ mặc định chỉ **5 giây**:

```csharp
builder.Services.Configure<HostOptions>(options =>
{
    options.ShutdownTimeout = TimeSpan.FromSeconds(30);
});
```

Với `BackgroundService`, bạn phải **tự** xử lý:

```csharp
protected override async Task ExecuteAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)          // ct bi huy khi shutdown
    {
        try
        {
            await XuLyMotLoAsync(ct);
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            _logger.LogInformation("Đang dừng, hoàn tất lô hiện tại");
            break;                                // thoat vong lap TU TE
        }
    }
}
```

Nếu `BackgroundService` bỏ qua `CancellationToken`, nó chạy tới khi bị SIGKILL — và một lô đang xử lý dở có thể để lại dữ liệu nửa vời.

### 15.14.3 — Điều kiện 3: load balancer phải ngừng gửi request trước

Đây là phần tinh vi nhất, và thiếu nó thì hai điều kiện trên vẫn chưa đủ:

```
t=0   Kubernetes gui SIGTERM cho pod
t=0   Kubernetes BAT DAU go pod khoi Service endpoint
      -> nhung viec nay mat vai giay de lan toi moi node
t=1   Pod da ngung nhan request moi (do SIGTERM)
t=2   Mot node CHUA cap nhat van gui request toi pod nay
      -> Ket noi bi tu choi
```

Khoảng thời gian giữa "pod ngừng nhận" và "mọi node biết điều đó" là nơi request bị mất.

```yaml
lifecycle:
  preStop:
    exec:
      command: ["sleep", "15"]      # CHO truoc khi bat dau dung
```

`preStop` chạy **trước** khi Kubernetes gửi SIGTERM. Trong 15 giây đó, pod vẫn phục vụ bình thường, còn Kubernetes đã bắt đầu gỡ nó khỏi endpoint — nên khi SIGTERM tới, không còn request mới nào được gửi tới.

Nghe phản trực giác — cố tình chờ để dừng nhanh hơn — nhưng đó chính là điều làm cho việc dừng **không mất request nào**.

### 15.14.4 — Tổng hợp cấu hình

```yaml
spec:
  terminationGracePeriodSeconds: 60      # tong thoi gian cho phep

  containers:
    - name: crm-api
      lifecycle:
        preStop:
          exec:
            command: ["sleep", "15"]     # (1) cho load balancer cap nhat

      readinessProbe:
        httpGet:
          path: /health/ready
          port: 8080
        periodSeconds: 5
        failureThreshold: 2
```

```
Dong ho khi dung pod:

t=0    Kubernetes bat dau go pod khoi Service endpoint
t=0    preStop chay: sleep 15          <- pod VAN phuc vu
t=15   preStop xong -> gui SIGTERM
t=15   ASP.NET Core ngung nhan request moi, cho request dang chay
t=~20  Request cuoi cung hoan thanh -> tien trinh thoat
       (neu chua xong toi t=60 -> SIGKILL)
```

**Quan hệ giữa các con số phải đúng:**

```
terminationGracePeriodSeconds  >  preStop + ShutdownTimeout
               60              >     15   +       30
```

Sai quan hệ này là nguyên nhân phổ biến khiến cấu hình "trông đúng" nhưng vẫn mất request: nếu `terminationGracePeriodSeconds` là 30 và `preStop` là 15, ứng dụng chỉ còn 15 giây để hoàn thành mọi việc.

### 15.14.5 — Kiểm chứng

```bash
# Chay tai lien tuc
hey -z 60s -c 10 https://api.company.com/api/leads &

# Trien khai trong luc dang co tai
kubectl rollout restart deployment/crm-api

# Xem ket qua
wait
```

```
Status code distribution:
  [200]  14203 responses      <- TAT CA thanh cong
```

Nếu thấy `[502]`, `[503]` hoặc lỗi kết nối, một trong ba điều kiện chưa đúng.

Cách xác định điều kiện nào thiếu:

```bash
# Kiem tra exec form
kubectl exec <pod> -- ps aux | head -3

# Kiem tra pod nhan duoc SIGTERM
kubectl logs <pod> --previous | grep -i "shutting down\|application stopping"
```

Nếu log trước khi pod dừng **không có** dòng nào về việc dừng, ứng dụng không nhận được SIGTERM — tức vẫn đang dùng shell form hoặc có một lớp shell ở giữa.

### 15.14.6 — Hai cái bẫy khác

**Bẫy 1 — script khởi động bọc ngoài:**

```dockerfile
# VAN co van de — script la PID 1
ENTRYPOINT ["/app/start.sh"]
```

```bash
#!/bin/bash
# start.sh
dotnet Crm.Api.dll        # dotnet la tien trinh CON -> khong nhan SIGTERM
```

```bash
#!/bin/bash
# Sua — exec THAY THE tien trinh shell
exec dotnet Crm.Api.dll   # dotnet TRO THANH PID 1
```

Từ khoá `exec` thay thế tiến trình shell bằng tiến trình mới, giữ nguyên PID — nên `dotnet` trở thành PID 1 và nhận tín hiệu trực tiếp.

**Bẫy 2 — kết nối database chưa đóng:**

```csharp
// Dam bao DbContext va connection duoc dispose khi shutdown
builder.Services.AddDbContext<AppDbContext>(...);   // scoped -> tu dispose theo request

// Voi ket noi giu lau, dang ky IHostApplicationLifetime
lifetime.ApplicationStopping.Register(() =>
{
    _logger.LogInformation("Đang đóng kết nối");
    _connection.Close();
});
```

`ApplicationStopping` chạy **trước** khi host dừng hẳn — đúng chỗ để đóng kết nối broker, huỷ đăng ký khỏi service discovery, hoặc đẩy nốt dữ liệu đang đệm.

### 15.14.7 — Rà lại code của bạn

**Danh sách rà soát dừng mượt**

- [ ] ENTRYPOINT dùng exec form với dấu ngoặc vuông.
- [ ] Nếu có script khởi động, nó dùng exec để thay thế tiến trình.
- [ ] Đã xác nhận PID 1 là dotnet, không phải /bin/sh.
- [ ] ShutdownTimeout đặt đủ dài cho request chậm nhất.
- [ ] BackgroundService tôn trọng CancellationToken.
- [ ] Có preStop sleep để load balancer kịp cập nhật.
- [ ] terminationGracePeriodSeconds lớn hơn preStop cộng ShutdownTimeout.
- [ ] Đã kiểm chứng bằng cách deploy trong lúc có tải.
- [ ] Kết nối dài hạn được đóng trong ApplicationStopping.

## Bài tập áp dụng

1. **So sánh hai form.** Dựng container với shell form rồi exec form, gửi SIGTERM và xem log ứng dụng có phản ứng không.

2. **Kiểm tra PID 1.** Chạy `ps aux` trong container của bạn và xác nhận tiến trình nào là PID 1.

3. **Deploy dưới tải.** Chạy tải liên tục rồi `rollout restart`, đếm số request thất bại trước và sau khi thêm `preStop`.

## Tự kiểm tra

### Vì sao shell form trong ENTRYPOINT gây mất request?

Vì Docker chạy ứng dụng qua /bin/sh, nên sh là PID 1 và nhận SIGTERM, còn nó không chuyển tiếp tín hiệu cho tiến trình con. Ứng dụng không biết mình sắp bị dừng, và 30 giây sau SIGKILL cắt ngang mọi thứ.

### Làm sao kiểm tra container đang dùng form nào?

Chạy ps aux trong container và xem PID 1 là gì. Nếu thấy /bin/sh -c thì đang dùng shell form; nếu thấy dotnet thì đang dùng exec form.

### Vì sao cần preStop sleep dù ứng dụng đã xử lý SIGTERM đúng?

Vì việc gỡ pod khỏi Service endpoint mất vài giây để lan tới mọi node. Trong khoảng đó, node chưa cập nhật vẫn gửi request tới pod đã ngừng nhận. preStop cho load balancer thời gian cập nhật trong khi pod vẫn phục vụ bình thường.

### Quan hệ giữa các con số thời gian phải thế nào?

terminationGracePeriodSeconds phải lớn hơn tổng của preStop và ShutdownTimeout. Sai quan hệ này khiến cấu hình trông đúng nhưng ứng dụng không đủ thời gian hoàn thành request đang chạy.

### Vì sao script khởi động cần từ khoá exec?

Vì không có nó, dotnet là tiến trình con của script và không nhận được SIGTERM. Từ khoá exec thay thế tiến trình shell bằng tiến trình mới và giữ nguyên PID, nên dotnet trở thành PID 1.

### ApplicationStopping dùng để làm gì?

Nó chạy trước khi host dừng hẳn, đúng chỗ để đóng kết nối broker, huỷ đăng ký khỏi service discovery, hoặc đẩy nốt dữ liệu đang đệm trong bộ nhớ.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Exec form với dấu ngoặc vuông** — shell form nuốt SIGTERM.
2. **`preStop sleep` cho load balancer kịp cập nhật** — cố tình chờ để không mất request.
3. **`terminationGracePeriodSeconds` phải lớn hơn `preStop` cộng `ShutdownTimeout`.**
