# 13.11 — Mở rộng và đào sâu

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-04-database-production/module-13-entity-framework-core/13.11-advanced-notes
> Compiled query, interceptor, owned entity, bulk extension và compiled model — kỹ thuật EF Core nâng cao và điều kiện dùng.

> Những kỹ thuật EF Core nối tiếp Module 13, kèm điều kiện cụ thể. Kỹ thuật có tỷ lệ lợi ích cao nhất là **interceptor**: nó cho phép áp dụng hành vi chung — audit, soft delete, outbox, ghi log truy vấn chậm — cho **mọi** thao tác mà không sửa một dòng nào trong code nghiệp vụ. Kỹ thuật bị dùng sai nhiều nhất là **thư viện bulk**: chúng nhanh hơn thật, nhưng bỏ qua change tracker nên **không kích hoạt interceptor, không sinh domain event, và không áp global query filter** — dùng chúng cho dữ liệu có ý nghĩa nghiệp vụ là mất những thứ đó một cách im lặng.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Dùng interceptor cho hành vi áp dụng chung.
- Biết compiled query giúp bao nhiêu và khi nào.
- Chọn giữa owned entity và complex type.
- Biết thư viện bulk bỏ qua những gì.

## Nội dung bài học

### 13.12.1 — Interceptor: ưu tiên cao

**Điều kiện kích hoạt:** cần hành vi áp dụng cho mọi thao tác.

```csharp
public sealed class AuditInterceptor(ICurrentUser currentUser, TimeProvider clock)
    : SaveChangesInterceptor
{
    public override ValueTask<InterceptionResult<int>> SavingChangesAsync(
        DbContextEventData eventData, InterceptionResult<int> result, CancellationToken ct = default)
    {
        var context = eventData.Context;
        if (context is null) return base.SavingChangesAsync(eventData, result, ct);

        var now = clock.GetUtcNow().UtcDateTime;

        foreach (var entry in context.ChangeTracker.Entries<IAuditable>())
        {
            switch (entry.State)
            {
                case EntityState.Added:
                    entry.Entity.CreatedUtc = now;
                    entry.Entity.CreatedBy = currentUser.Id;
                    break;

                case EntityState.Modified:
                    entry.Entity.ModifiedUtc = now;
                    entry.Entity.ModifiedBy = currentUser.Id;
                    break;

                case EntityState.Deleted:
                    // Soft delete — doi thanh Modified thay vi xoa that
                    entry.State = EntityState.Modified;
                    entry.Entity.IsDeleted = true;
                    entry.Entity.DeletedUtc = now;
                    break;
            }
        }

        return base.SavingChangesAsync(eventData, result, ct);
    }
}
```

Một interceptor lo cả audit lẫn soft delete cho **mọi** entity, và không use case nào phải nhớ làm việc đó.

Loại interceptor thứ hai đáng có ngay: ghi log truy vấn chậm.

```csharp
public sealed class SlowQueryInterceptor(ILogger<SlowQueryInterceptor> logger)
    : DbCommandInterceptor
{
    public override ValueTask<DbDataReader> ReaderExecutedAsync(
        DbCommand command, CommandExecutedEventData eventData,
        DbDataReader result, CancellationToken ct = default)
    {
        if (eventData.Duration.TotalMilliseconds > 500)
        {
            logger.LogWarning("Truy vấn chậm {Ms}ms: {Sql}",
                eventData.Duration.TotalMilliseconds, command.CommandText);
        }

        return base.ReaderExecutedAsync(command, eventData, result, ct);
    }
}
```

Nó bắt được truy vấn chậm **trên production với dữ liệu thật** — nơi vấn đề thực sự xuất hiện ([bài 19.5](../../stage-05-senior-engineering/module-19-performance-engineering/19.4-database-first-bottleneck.mdx)).

Interceptor cũng là cách cài outbox pattern gọn nhất ([bài 17.4](../../stage-05-senior-engineering/module-17-distributed-systems/17.3-outbox-pattern-applied.mdx)).

### 13.12.2 — Compiled query

**Điều kiện kích hoạt:** truy vấn giống hệt nhau chạy hàng nghìn lần.

```csharp
private static readonly Func<AppDbContext, Guid, CancellationToken, Task<Lead?>> _layLead =
    EF.CompileAsyncQuery((AppDbContext db, Guid id, CancellationToken ct) =>
        db.Leads.FirstOrDefault(l => l.Id == id));

// Su dung
var lead = await _layLead(_db, id, ct);
```

EF Core cache kế hoạch truy vấn sẵn, nhưng vẫn phải **phân tích cây biểu thức** mỗi lần để tìm khoá cache. Compiled query bỏ qua bước đó.

Cải thiện thực tế: khoảng **10–30%** thời gian chuẩn bị truy vấn — đáng kể chỉ khi truy vấn rất nhanh và chạy rất nhiều lần. Với truy vấn tốn 50ms ở database, tiết kiệm vài trăm micro giây không đổi gì.

**Hạn chế:** không dùng được cho truy vấn có cấu trúc thay đổi theo điều kiện (lọc động, sắp xếp động) — vì cây biểu thức phải cố định.

### 13.12.3 — Compiled model

**Điều kiện kích hoạt:** model có hàng trăm entity và cold start quan trọng.

```bash
dotnet ef dbcontext optimize --output-dir Generated --namespace Crm.Infrastructure.Generated
```

```csharp
builder.Services.AddDbContext<AppDbContext>(o =>
    o.UseSqlServer(cs).UseModel(AppDbContextModel.Instance));
```

EF Core dựng model từ cấu hình khi khởi tạo `DbContext` lần đầu. Với model lớn, việc đó tốn **vài giây** — đáng kể cho serverless hoặc khi pod khởi động lại thường xuyên.

**Cái bẫy:** model đã sinh **không tự cập nhật** khi bạn đổi cấu hình entity. Phải chạy lại lệnh trên, và nếu quên thì ứng dụng dùng model cũ — gây lỗi khó hiểu vì code và model không khớp. Đưa lệnh này vào build script.

### 13.12.4 — Owned entity và complex type

**Điều kiện kích hoạt:** value object cần ánh xạ vào nhiều cột.

```csharp
// Owned entity — co tu EF Core 2
b.OwnsOne(l => l.DiaChi, a =>
{
    a.Property(x => x.SoNha).HasColumnName("DiaChi_SoNha");
    a.Property(x => x.Duong).HasColumnName("DiaChi_Duong");
});

// Complex type — EF Core 8+, tot hon
b.ComplexProperty(l => l.DiaChi, a =>
{
    a.Property(x => x.SoNha).HasColumnName("DiaChi_SoNha");
});
```

| | Owned entity | Complex type |
|---|---|---|
| Có định danh ngầm | **Có** | Không |
| Được theo dõi riêng | Có | **Không** |
| Chia sẻ instance được | Không | **Có** |
| Dùng trong truy vấn `Select` | Hạn chế | **Tự do** |

Khác biệt thực tế quan trọng: với owned entity, EF Core coi nó như một entity có định danh, nên **không** dùng chung một instance cho hai bản ghi được — gán cùng một object `DiaChi` cho hai `Lead` sẽ ném exception. Complex type không có vấn đề đó, vì nó thật sự là một **giá trị**.

Với value object, complex type là lựa chọn đúng ([bài 16.14](../../stage-05-senior-engineering/module-16-clean-architecture/16.13-advanced-notes.mdx)).

### 13.12.5 — Thư viện bulk: biết nó bỏ qua gì

**Điều kiện kích hoạt:** thao tác hàng chục nghìn bản ghi trở lên.

```csharp
// EFCore.BulkExtensions
await _db.BulkInsertAsync(danhSachLead, ct);
await _db.BulkUpdateAsync(danhSachLead, ct);
```

Nhanh hơn `SaveChanges` hàng chục lần vì nó dùng `SqlBulkCopy` thay vì sinh câu `INSERT` riêng cho từng hàng.

**Cái giá — nó bỏ qua toàn bộ tầng EF Core:**

| Bỏ qua | Hậu quả |
|---|---|
| Change tracker | Không biết entity nào đổi |
| **Interceptor** | **Không có audit, không có soft delete** |
| **Domain event** | **Không sinh event, outbox trống** |
| **Global query filter** | **Không lọc theo tenant** |
| Validation của EF Core | Dữ liệu sai vẫn ghi được |

Ba hàng in đậm là lý do phải cẩn thận. Hàng cuối cùng đặc biệt nguy hiểm trong hệ multi-tenant: bulk update không áp global query filter, nên một điều kiện sai có thể sửa dữ liệu của **mọi** tenant ([bài 13.11](13.10-global-query-filters.mdx)).

**Quy tắc:** dùng bulk cho **nhập dữ liệu kỹ thuật** — import ban đầu, đồng bộ từ hệ thống ngoài, dữ liệu tham chiếu. Dùng `SaveChanges` cho **thao tác có ý nghĩa nghiệp vụ**.

`ExecuteUpdate` và `ExecuteDelete` có sẵn trong EF Core cũng bỏ qua những thứ tương tự, nhưng chúng ít nguy hiểm hơn vì **vẫn áp** global query filter ([bài 13.8](13.7-performance.mdx)).

### 13.12.6 — Những chủ đề khác

| Chủ đề | Nội dung | Ưu tiên |
|---|---|---|
| **Interceptor** | Hành vi áp dụng chung | **Cao** |
| **`AsSplitQuery`** | Tránh cartesian explosion | **Cao** |
| Value converter | Ánh xạ kiểu tuỳ chỉnh | Trung bình |
| `IModelCacheKeyFactory` | Model khác nhau theo tenant | Trung bình |
| Shadow property | Thuộc tính không có trong lớp | Thấp |
| Compiled query | Bỏ bước phân tích biểu thức | Thấp |

`IModelCacheKeyFactory` đáng nói vì nó giải quyết một cái bẫy cụ thể: nếu global query filter dùng giá trị đọc tại thời điểm dựng model, mọi tenant sẽ dùng chung filter của tenant đầu tiên.

```csharp
public sealed class TenantModelCacheKeyFactory : IModelCacheKeyFactory
{
    public object Create(DbContext context, bool designTime)
        => (context.GetType(), ((AppDbContext)context).TenantId, designTime);
}
```

Giải pháp đơn giản hơn cho hầu hết trường hợp: viết filter tham chiếu tới **service** chứ không tới **giá trị** — khi đó EF Core đánh giá lại nó mỗi lần truy vấn.

### 13.12.7 — Thứ tự nên học

| Ưu tiên | Kỹ thuật | Vì sao |
|---|---|---|
| **Cao** | Interceptor cho audit và soft delete | Áp dụng chung, không sửa code nghiệp vụ |
| **Cao** | Interceptor ghi log truy vấn chậm | Bắt vấn đề trên dữ liệu thật |
| **Cao** | `AsSplitQuery` | Tránh cartesian explosion |
| Trung bình | Complex type cho value object | Đúng ngữ nghĩa hơn owned entity |
| Trung bình | Thư viện bulk | Khi nhập dữ liệu kỹ thuật lượng lớn |
| Thấp | Compiled query, compiled model | Chỉ khi đo được là vấn đề |

Sau Module 13, bước tiếp theo là [Module 14 — Caching và Background Jobs](../module-14-caching-background-jobs/).

### 13.12.8 — Rà lại code của bạn

**Danh sách rà soát EF Core nâng cao**

- [ ] Audit và soft delete cài bằng interceptor, không lặp ở mỗi use case.
- [ ] Có interceptor ghi log truy vấn vượt ngưỡng thời gian.
- [ ] Value object dùng complex type thay vì owned entity.
- [ ] Thư viện bulk chỉ dùng cho nhập dữ liệu kỹ thuật.
- [ ] Biết bulk không áp global query filter và không sinh domain event.
- [ ] Global query filter tham chiếu service, không chụp giá trị.
- [ ] Nếu dùng compiled model, lệnh sinh lại nằm trong build script.
- [ ] Truy vấn nhiều collection dùng AsSplitQuery.

## Bài tập áp dụng

1. **Viết interceptor.** Cài `AuditInterceptor` cho một entity và xác nhận `CreatedUtc` được điền tự động.

2. **Bắt truy vấn chậm.** Thêm `SlowQueryInterceptor` với ngưỡng thấp và xem log sinh ra khi chạy ứng dụng.

3. **Thử bulk.** Chạy `BulkInsert` trên entity có global query filter theo tenant và xác nhận filter không được áp.

## Tự kiểm tra

### Interceptor giải quyết vấn đề gì?

Nó cho phép áp dụng hành vi chung như audit, soft delete, outbox hay ghi log truy vấn chậm cho mọi thao tác mà không sửa dòng nào trong code nghiệp vụ, và không use case nào phải nhớ làm việc đó.

### Compiled query cải thiện được bao nhiêu?

Khoảng mười tới ba mươi phần trăm thời gian chuẩn bị truy vấn, vì nó bỏ bước phân tích cây biểu thức. Nó chỉ đáng kể khi truy vấn rất nhanh và chạy rất nhiều lần; với truy vấn tốn năm mươi mili giây ở database thì không đổi gì.

### Cái bẫy của compiled model là gì?

Model đã sinh không tự cập nhật khi bạn đổi cấu hình entity. Quên chạy lại lệnh sinh thì ứng dụng dùng model cũ, gây lỗi khó hiểu vì code và model không khớp. Nên đưa lệnh đó vào build script.

### Complex type hơn owned entity ở điểm nào?

Owned entity có định danh ngầm và được theo dõi riêng, nên không dùng chung một instance cho hai bản ghi được. Complex type thật sự là một giá trị nên không có hạn chế đó, và dùng tự do trong truy vấn Select.

### Thư viện bulk bỏ qua những gì?

Change tracker, interceptor nên không có audit và soft delete, domain event nên outbox trống, và global query filter nên không lọc theo tenant. Ba cái sau là lý do phải cẩn thận với dữ liệu có ý nghĩa nghiệp vụ.

### Vì sao ExecuteUpdate ít nguy hiểm hơn thư viện bulk?

Vì nó vẫn áp global query filter, nên không sửa nhầm dữ liệu của tenant khác. Nó vẫn bỏ qua interceptor và domain event, nhưng rủi ro rò rỉ dữ liệu giữa tenant thì không có.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Interceptor là kỹ thuật lợi ích cao nhất** — audit, soft delete, outbox, log truy vấn chậm ở một chỗ.
2. **Thư viện bulk bỏ qua interceptor, domain event và global query filter** — biết trước khi dùng.
3. **Complex type đúng hơn owned entity** cho value object.
