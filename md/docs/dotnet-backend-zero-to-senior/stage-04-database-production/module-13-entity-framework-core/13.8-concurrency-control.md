# 13.8 — 8. Concurrency Control

> Nguồn: https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-04-database-production/module-13-entity-framework-core/13.8-concurrency-control
> RowVersion và concurrency token, ba chiến lược xử lý xung đột, vì sao ExecuteUpdate bỏ qua kiểm tra, và cập nhật không cần đọc trước.

> Không có concurrency control, mặc định là **last write wins**: hai người cùng mở một bản ghi, người lưu sau **ghi đè** thay đổi của người trước và **không ai biết**. EF Core phát hiện điều đó bằng cách đưa **concurrency token** vào mệnh đề `WHERE` của lệnh `UPDATE` — nếu 0 dòng bị ảnh hưởng thì ai đó đã sửa trước, và EF ném `DbUpdateConcurrencyException`. Ba điểm quan trọng: **`ROWVERSION` của SQL Server tự đổi mỗi lần ghi**, nên nó bắt được cả thay đổi từ ngoài ứng dụng; **`ExecuteUpdateAsync` bỏ qua hoàn toàn cơ chế này**; và với bộ đếm, **cập nhật nguyên tử không cần đọc trước** giải quyết vấn đề tốt hơn mọi chiến lược xử lý xung đột.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Cấu hình concurrency token cho SQL Server và PostgreSQL.
- Chọn giữa ba chiến lược xử lý xung đột.
- Trả lỗi 409 hữu ích cho client.
- Biết khi nào nên tránh xung đột thay vì xử lý nó.
- Kiểm thử hành vi đồng thời.

## Nội dung bài học

### 13.9.1 — Vấn đề

```
t=0   An   doc Lead #42 (Value = 100)
t=1   Binh doc Lead #42 (Value = 100)
t=2   An   lưu Value = 150
t=3   Bình lưu Value = 200        <- ghi đè thay đổi của An
```

Đây là **lost update**, và nó xảy ra **im lặng**. Không có lỗi, không có log, và An chỉ phát hiện khi mở lại bản ghi.

Với dữ liệu tài chính hoặc tồn kho, đó là lỗi nghiêm trọng.

### 13.9.2 — Concurrency token

```csharp
// SQL Server — ROWVERSION tự động đổi mỗi lần ghi
public byte[] RowVersion { get; set; } = [];

builder.Property(c => c.RowVersion).IsRowVersion();
```

```csharp
// PostgreSQL — dùng cột hệ thống xmin
builder.UseXminAsConcurrencyToken();
```

```csharp
// Bất kỳ provider — token thủ công
public Guid Version { get; set; }

builder.Property(c => c.Version).IsConcurrencyToken();
// Phải TỰ cập nhật mỗi lần sửa
```

`IsRowVersion()` mạnh hơn hai cách kia ở một điểm: **database tự đổi giá trị**, nên nó bắt được cả thay đổi từ script thủ công hay một ứng dụng khác. Token thủ công chỉ đổi khi code của bạn nhớ đổi.

EF Core sinh:

```sql
UPDATE Leads SET Value = @p0, Status = @p1
WHERE Id = @p2 AND RowVersion = @p3;      -- token trong WHERE

-- 0 dòng bị ảnh hưởng => DbUpdateConcurrencyException
```

**Không nhất thiết dùng `ROWVERSION`.** Bất kỳ cột nào cũng làm concurrency token được:

```csharp
builder.Property(p => p.Stock).IsConcurrencyToken();
```

Khi đó `WHERE` chứa `Stock = @giá_trị_gốc`, nên chỉ xung đột **trên chính cột đó** mới bị phát hiện. Hai người sửa hai cột khác nhau vẫn thành công cả hai — thường là điều bạn muốn.

### 13.9.3 — Ba chiến lược

```csharp
try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var databaseValues = await entry.GetDatabaseValuesAsync(ct);

    if (databaseValues is null)
        return Result.Fail("Bản ghi đã bị xoá bởi người dùng khác");

    // ... xử lý theo một trong ba chiến lược
}
```

**1. Client wins** — ghi đè, chỉ cập nhật token:

```csharp
entry.OriginalValues.SetValues(databaseValues);
await db.SaveChangesAsync(ct);
```

Đơn giản nhưng **mất thay đổi của người kia**. Chỉ đúng khi người dùng có thẩm quyền cao hơn hoặc dữ liệu không quan trọng.

**2. Store wins** — bỏ thay đổi của mình:

```csharp
await entry.ReloadAsync(ct);
return Result.Fail("Bản ghi đã thay đổi, vui lòng thử lại");
```

An toàn nhưng người dùng **mất công nhập lại**.

**3. Merge có kiểm soát** — trả cả hai giá trị để người dùng quyết định:

```csharp
var conflicts = new List<FieldConflict>();

foreach (var property in entry.Metadata.GetProperties())
{
    var proposed = entry.Property(property.Name).CurrentValue;
    var current  = databaseValues[property];
    var original = entry.Property(property.Name).OriginalValue;

    // CHỈ báo xung đột khi CẢ HAI cùng sửa một trường
    if (!Equals(proposed, original) && !Equals(current, original))
        conflicts.Add(new FieldConflict(property.Name, original, proposed, current));
}

return Result.Conflict(conflicts);
```

Điều kiện trong `if` là phần tinh tế: nếu bạn sửa `Value` còn người kia sửa `Status`, **không có xung đột thật** — chỉ cần gộp cả hai. Chỉ khi cả hai cùng sửa **một trường** mới cần người dùng quyết định.

Trả về HTTP **409 Conflict** kèm chi tiết:

```csharp
return Conflict(new ProblemDetails
{
    Status = StatusCodes.Status409Conflict,
    Title = "Bản ghi đã được người khác cập nhật",
    Extensions = { ["conflicts"] = conflicts }
});
```

Đây là đúng mã trạng thái cho tình huống này ([bài 8.5](../../stage-03-aspnet-core-backend/module-08-aspnet-core-fundamentals/8.4-controllers-and-actions.mdx)).

### 13.9.4 — Truyền token qua API

Với ứng dụng web, client không giữ `DbContext` giữa hai request — nên token phải đi qua API:

```csharp
public sealed record UpdateLeadRequest
{
    public required string Title { get; init; }
    public required decimal Value { get; init; }
    public required string RowVersion { get; init; }    // Base64
}
```

```csharp
[HttpPut("{id:int}")]
public async Task<IActionResult> Update(int id, UpdateLeadRequest request, CancellationToken ct)
{
    var lead = await db.Leads.FirstOrDefaultAsync(l => l.Id == id, ct);
    if (lead is null) return NotFound();

    // Gán giá trị GỐC mà client đã thấy
    db.Entry(lead).Property(l => l.RowVersion).OriginalValue =
        Convert.FromBase64String(request.RowVersion);

    lead.Title = request.Title;
    lead.Value = request.Value;

    try
    {
        await db.SaveChangesAsync(ct);
        return NoContent();
    }
    catch (DbUpdateConcurrencyException)
    {
        return Conflict(...);
    }
}
```

Dòng `OriginalValue` là mấu chốt: không có nó, EF dùng giá trị **vừa đọc từ database** làm token — và kiểm tra luôn thành công, vì bạn vừa đọc xong. Xung đột không bao giờ được phát hiện.

Cách chuẩn hơn về mặt HTTP là dùng **ETag** và `If-Match` ([bài 9.8](../../stage-03-aspnet-core-backend/module-09-web-api-professional/9.7-response-caching-and-output-caching.mdx)):

```http
GET /api/v1/leads/42
ETag: "AAAAAAAAB9E="

PUT /api/v1/leads/42
If-Match: "AAAAAAAAB9E="
```

Thiếu `If-Match` thì trả **428 Precondition Required**; token không khớp thì trả **412 Precondition Failed**.

### 13.9.5 — `ExecuteUpdate` bỏ qua tất cả

```csharp
// KHÔNG kiểm tra concurrency token
await db.Leads.Where(l => l.Id == 42)
              .ExecuteUpdateAsync(s => s.SetProperty(l => l.Value, 200), ct);
```

`ExecuteUpdateAsync` sinh `UPDATE ... WHERE Id = 42` — **không** có token trong `WHERE` ([bài 13.8](13.7-performance.mdx)). Nó luôn thành công và luôn ghi đè.

Cần kiểm tra thì đưa token vào `Where` thủ công:

```csharp
var affected = await db.Leads
    .Where(l => l.Id == 42 && l.RowVersion == expectedVersion)
    .ExecuteUpdateAsync(s => s.SetProperty(l => l.Value, 200), ct);

if (affected == 0) return Result.Conflict();
```

### 13.9.6 — Tránh xung đột thay vì xử lý nó

Với **bộ đếm và số dư**, cách tốt nhất là **không đọc trước**:

```csharp
// KÉM — đọc, sửa, lưu. Có thể xung đột.
var product = await db.Products.FindAsync([id], ct);
product.Stock -= quantity;
await db.SaveChangesAsync(ct);

// TỐT — một câu lệnh nguyên tử, kiểm tra ngay trong WHERE
var affected = await db.Products
    .Where(p => p.Id == id && p.Stock >= quantity)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Stock, p => p.Stock - quantity), ct);

if (affected == 0) return Result.Fail("Không đủ hàng");
```

Không có khoảng trống giữa đọc và ghi, nên **không có xung đột nào để xử lý** — đúng mẫu ở [bài 12.7](../module-12-sql-deep-dive/12.6-transactions-and-locking.mdx).

Với thao tác quan trọng mà thử lại không chấp nhận được, dùng pessimistic lock:

```csharp
var product = await db.Products
    .FromSql($"SELECT * FROM Products WITH (UPDLOCK, ROWLOCK) WHERE Id = {id}")
    .FirstAsync(ct);
```

Nhưng nhớ nó mở ra rủi ro deadlock, và phải nằm trong transaction.

### 13.9.7 — Kiểm thử

```csharp
[Fact]
public async Task ConcurrentUpdate_ShouldThrowConcurrencyException()
{
    await using var ctx1 = _factory.CreateDbContext();
    await using var ctx2 = _factory.CreateDbContext();

    var lead1 = await ctx1.Leads.FirstAsync(l => l.Id == 42);
    var lead2 = await ctx2.Leads.FirstAsync(l => l.Id == 42);   // CÙNG bản ghi

    lead1.Value = 150;
    await ctx1.SaveChangesAsync();          // thành công

    lead2.Value = 200;
    await Assert.ThrowsAsync<DbUpdateConcurrencyException>(
        () => ctx2.SaveChangesAsync());     // xung dot
}
```

**Hai `DbContext` riêng** là điều kiện bắt buộc: cùng một context thì identity map trả về **cùng một instance**, và không có xung đột nào xảy ra ([bài 13.2](13.1-ef-core-overview.mdx)).

Bài test này phải chạy trên **database thật** — InMemory provider không có `ROWVERSION` ([bài 9.9](../../stage-03-aspnet-core-backend/module-09-web-api-professional/9.8-api-testing.mdx)).

### 13.9.8 — Rà lại code của bạn

**Danh sách rà soát concurrency**

- [ ] Mọi entity người dùng sửa đồng thời đều có concurrency token.
- [ ] SQL Server dùng IsRowVersion để database tự đổi giá trị.
- [ ] DbUpdateConcurrencyException được bắt và xử lý, không để thành lỗi 500.
- [ ] Chiến lược xử lý xung đột được chọn có chủ đích, không mặc định client wins.
- [ ] Chỉ báo xung đột khi cả hai bên cùng sửa một trường.
- [ ] API trả 409 kèm giá trị hiện tại để client quyết định.
- [ ] Token được truyền qua API và gán vào OriginalValue.
- [ ] ExecuteUpdate có token trong Where nếu cần kiểm tra concurrency.
- [ ] Bộ đếm và tồn kho dùng cập nhật nguyên tử, không đọc rồi ghi.
- [ ] Có test đồng thời dùng hai DbContext riêng trên database thật.

## Bài tập áp dụng

#### Bài 1 — Lost update

Với entity **không** có concurrency token, mô phỏng hai người cùng sửa và xác nhận thay đổi của người đầu biến mất **không có lỗi nào**. Thêm `IsRowVersion` và kiểm chứng.

**Tiêu chí hoàn thành:** bạn giải thích được vì sao database **không** coi đây là lỗi, và nêu được vì sao `RowVersion` phát hiện được trong khi transaction thì không.

Gợi ý và lời giải — Bài 1

**Gợi ý.** Nhìn từ phía database, hai lệnh `UPDATE` tuần tự trông như thế nào?

**Lời giải — không có token:**

```csharp
await using var db1 = await _factory.CreateDbContextAsync(ct);
await using var db2 = await _factory.CreateDbContextAsync(ct);

var lead1 = await db1.Leads.FirstAsync(l => l.Id == 1, ct);   // cả hai đọc cùng trạng thái
var lead2 = await db2.Leads.FirstAsync(l => l.Id == 1, ct);

lead1.Status = "Won";                    // người A đổi trạng thái
await db1.SaveChangesAsync(ct);

lead2.Value = 9_000_000;                 // người B đổi giá trị
await db2.SaveChangesAsync(ct);          // không exception nào
```

```sql
SELECT Id, Status, Value FROM Leads WHERE Id = 1;
```

```text
Id   Status   Value
1    New      9000000
```

`Status = "Won"` của người A biến mất. Cả hai lệnh `SaveChangesAsync` đều trả về 1 và không ném gì cả.

**Vì sao database không coi đây là lỗi.** Vì nhìn từ phía nó, đây là hai lệnh hoàn toàn hợp lệ, chạy tuần tự, không chồng lấn:

```sql
-- 08:00:01 — từ db1
UPDATE Leads SET Status = N'Won' WHERE Id = 1;              -- 1 dòng

-- 08:00:03 — từ db2
UPDATE Leads SET Status = N'New', Value = 9000000 WHERE Id = 1;   -- 1 dòng
```

Lệnh thứ hai chạy **sau khi** lệnh thứ nhất đã commit. Không có khoá nào bị tranh chấp, không có deadlock, không có vi phạm ràng buộc. Database làm đúng thứ nó được yêu cầu.

Thông tin bị thiếu là **ý định**: người B nghĩ mình đang sửa từ trạng thái đã đọc lúc 08:00:00, nhưng trạng thái đó không còn nữa. Database không biết người B đã đọc gì — nó chỉ thấy một lệnh `UPDATE` đến.

Chú ý cả `Status = N'New'` trong lệnh thứ hai: EF Core gửi **mọi cột** mà nó cho là đã thay đổi so với `OriginalValues` của context 2 — và `OriginalValues` đó chụp từ lúc 08:00:00, khi `Status` còn là `New`. Đó chính là cách thay đổi của A bị ghi đè.

**Bản sửa:**

```csharp
public class Lead
{
    public int Id { get; set; }
    public string Status { get; set; } = null!;
    public decimal Value { get; set; }

    [Timestamp]
    public byte[] RowVersion { get; set; } = null!;
}
```

```csharp
builder.Property(l => l.RowVersion).IsRowVersion();
```

```text
Microsoft.EntityFrameworkCore.DbUpdateConcurrencyException:
The database operation was expected to affect 1 row(s), but actually affected 0 row(s);
data may have been modified or deleted since entities were loaded.
```

**Vì sao `RowVersion` phát hiện được.** Nó thêm điều kiện "trạng thái phải còn như lúc tôi đọc" vào mệnh đề `WHERE`:

```sql
-- Người A
UPDATE Leads SET Status = N'Won', RowVersion = <mới>
WHERE Id = 1 AND RowVersion = 0x00000000000007D1;      -- 1 dòng, thành công

-- Người B — RowVersion đã đổi vì lệnh trên
UPDATE Leads SET Value = 9000000, RowVersion = <mới>
WHERE Id = 1 AND RowVersion = 0x00000000000007D1;      -- 0 DÒNG
```

`rowversion` của SQL Server là một bộ đếm **toàn database**, tự tăng mỗi khi dòng được ghi. Người B gửi giá trị cũ, không khớp, nên `UPDATE` không chạm dòng nào. EF Core biết mình mong đợi 1 dòng, nhận về 0, và ném `DbUpdateConcurrencyException`.

Điều cốt lõi: **ý định được mã hoá vào `WHERE`**. Giờ database biết người B đang giả định gì, nên nó kiểm tra được giả định đó.

**Vì sao transaction không phát hiện được** — đây là hiểu nhầm phổ biến nhất về chủ đề này:

```csharp
await using var tx = await db2.Database.BeginTransactionAsync(ct);
var lead = await db2.Leads.FirstAsync(l => l.Id == 1, ct);
lead.Value = 9_000_000;
await db2.SaveChangesAsync(ct);
await tx.CommitAsync(ct);       // vẫn ghi đè thay đổi của A
```

Transaction bảo đảm **tính nguyên tử và cô lập trong thời gian nó mở**. Nhưng ở đây, mỗi người đọc và ghi trong transaction **riêng** của mình, và hai transaction đó không chồng lấn về thời gian:

```text
A:  [đọc-ghi-commit]
B:               [đọc-ghi-commit]
                 ^ bắt đầu sau khi A đã commit — không có xung đột nào để cô lập
```

Và trong một ứng dụng web, khoảng cách còn lớn hơn nhiều: người dùng đọc ở request `GET` lúc 08:00, sửa form trong năm phút, rồi gửi `PUT` lúc 08:05. **Không transaction nào tồn tại qua hai request** — mỗi request có `DbContext` riêng, kết nối riêng, transaction riêng.

Đây là lý do vấn đề này có tên riêng: **optimistic concurrency qua nhiều request**. Transaction giải quyết tranh chấp trong **mili giây**; `RowVersion` giải quyết tranh chấp trong **phút hoặc giờ**.

| | Transaction | `RowVersion` |
|---|---|---|
| Phạm vi | Một đơn vị công việc | Từ lúc đọc tới lúc ghi, bao lâu cũng được |
| Qua được nhiều request HTTP | Không | Có |
| Giữ khoá | Có | Không |
| Chi phí khi không có xung đột | Có | Gần như không |

**Một cách duy nhất để transaction giải quyết được vấn đề này** là giữ nó mở suốt từ `GET` tới `PUT` — tức giữ khoá database trong năm phút, cho mỗi người dùng đang mở form. Với mười người dùng đồng thời, hệ thống dừng hoạt động. Đó là lý do mọi ứng dụng web đều chọn optimistic concurrency.

#### Bài 2 — Token không được truyền qua tầng HTTP

Cài endpoint `PUT` **không** gán `OriginalValue`, gửi token cũ, và xác nhận xung đột **không** được phát hiện. Thêm dòng gán và kiểm chứng.

**Tiêu chí hoàn thành:** bạn giải thích được vì sao chỉ khai báo `IsRowVersion` là **chưa đủ**, và nêu được cách đưa token qua HTTP an toàn.

Gợi ý và lời giải — Bài 2

**Gợi ý.** Khi endpoint đọc lại entity từ database, `OriginalValues` chứa giá trị của thời điểm nào?

**Lời giải — bản có lỗi:**

```csharp
app.MapPut("/leads/{id}", async (int id, CapNhatLeadRequest req, CrmDbContext db, CancellationToken ct) =>
{
    var lead = await db.Leads.FirstOrDefaultAsync(l => l.Id == id, ct);
    if (lead is null) return Results.NotFound();

    lead.Status = req.Status;
    lead.Value  = req.Value;

    await db.SaveChangesAsync(ct);      // KHÔNG BAO GIỜ ném DbUpdateConcurrencyException
    return Results.NoContent();
});
```

Client gửi `RowVersion` trong body, nhưng không ai dùng tới. Hai request đồng thời vẫn ghi đè nhau như khi chưa có token nào.

**Vì sao chỉ khai báo `IsRowVersion` là chưa đủ.** EF Core dựng mệnh đề `WHERE` từ **`OriginalValues` của entry**, không phải từ dữ liệu client gửi lên. Và `OriginalValues` được chụp **lúc entity được nạp**:

```text
08:00:00  Client A gọi GET    -> RowVersion = 0x...7D1, hiển thị lên form
08:02:00  Client B gọi PUT    -> ghi thành công, RowVersion thành 0x...7D2
08:05:00  Client A gọi PUT    -> endpoint nạp lại entity
                                 OriginalValues.RowVersion = 0x...7D2  <- MỚI NHẤT
                                 UPDATE ... WHERE RowVersion = 0x...7D2 -> 1 dòng, OK
```

Endpoint vừa đọc lại entity **sau khi** B đã ghi, nên `OriginalValues` chứa phiên bản mới nhất. Điều kiện `WHERE` luôn khớp, và xung đột không bao giờ bị phát hiện.

Nói gọn: `RowVersion` so sánh "phiên bản lúc tôi nạp trong request này" với "phiên bản hiện tại". Nhưng thứ bạn cần so sánh là **"phiên bản mà người dùng đã nhìn thấy"** với "phiên bản hiện tại". Hai thứ đó chỉ trùng nhau khi việc đọc và việc ghi nằm trong cùng một request — và với form của người dùng thì không bao giờ.

**Bản sửa — gán `OriginalValue` bằng token client gửi lên:**

```csharp
app.MapPut("/leads/{id}", async (int id, CapNhatLeadRequest req, CrmDbContext db, CancellationToken ct) =>
{
    var lead = await db.Leads.FirstOrDefaultAsync(l => l.Id == id, ct);
    if (lead is null) return Results.NotFound();

    // Dòng quyết định: nói cho EF Core biết người dùng đã nhìn thấy phiên bản nào
    db.Entry(lead).Property(l => l.RowVersion).OriginalValue = req.RowVersion;

    lead.Status = req.Status;
    lead.Value  = req.Value;

    try
    {
        await db.SaveChangesAsync(ct);
        return Results.NoContent();
    }
    catch (DbUpdateConcurrencyException)
    {
        return Results.Conflict(new { message = "Bản ghi đã được người khác sửa. Hãy tải lại." });
    }
});
```

```sql
UPDATE Leads SET Status = @p0, Value = @p1
WHERE Id = @p2 AND RowVersion = @p3;     -- @p3 là token CLIENT gửi lên
-- 0 dòng -> DbUpdateConcurrencyException -> HTTP 409
```

**Cách đưa token qua HTTP — hai lựa chọn:**

**1. Trong body của DTO** — đơn giản nhất, phù hợp với form nội bộ:

```csharp
public record CapNhatLeadRequest(string Status, decimal Value, byte[] RowVersion);
public record LeadDto(int Id, string Status, decimal Value, byte[] RowVersion);
```

`byte[]` được `System.Text.Json` tuần tự hoá thành Base64, nên nó đi qua JSON an toàn. Client chỉ cần gửi lại nguyên giá trị đã nhận.

**2. Qua HTTP header `ETag` và `If-Match`** — đúng chuẩn HTTP, và là lựa chọn nên dùng cho API công khai:

```csharp
app.MapGet("/leads/{id}", async (int id, CrmDbContext db, HttpContext http, CancellationToken ct) =>
{
    var lead = await db.Leads.AsNoTracking().FirstOrDefaultAsync(l => l.Id == id, ct);
    if (lead is null) return Results.NotFound();

    http.Response.Headers.ETag = $"\"{Convert.ToBase64String(lead.RowVersion)}\"";
    return Results.Ok(new LeadDto(lead.Id, lead.Status, lead.Value));
});

app.MapPut("/leads/{id}", async (int id, CapNhatLeadRequest req, CrmDbContext db,
                                 HttpContext http, CancellationToken ct) =>
{
    var ifMatch = http.Request.Headers.IfMatch.FirstOrDefault();
    if (string.IsNullOrEmpty(ifMatch))
        return Results.StatusCode(StatusCodes.Status428PreconditionRequired);

    var lead = await db.Leads.FirstOrDefaultAsync(l => l.Id == id, ct);
    if (lead is null) return Results.NotFound();

    db.Entry(lead).Property(l => l.RowVersion).OriginalValue =
        Convert.FromBase64String(ifMatch.Trim('"'));

    lead.Status = req.Status;
    lead.Value  = req.Value;

    try
    {
        await db.SaveChangesAsync(ct);
        return Results.NoContent();
    }
    catch (DbUpdateConcurrencyException)
    {
        return Results.StatusCode(StatusCodes.Status412PreconditionFailed);
    }
});
```

Cách này có ba ưu điểm: token không lẫn vào dữ liệu nghiệp vụ, mã trạng thái đúng ngữ nghĩa HTTP (`428` khi thiếu, `412` khi không khớp), và client HTTP chuẩn — kể cả proxy và cache — hiểu được.

**Bốn điều cần nhớ:**

1. **Token phải đi qua `GET` xuống client.** Nếu DTO trả về không chứa `RowVersion` hoặc `ETag`, client không có gì để gửi lại.
2. **Thiếu token phải là lỗi, không phải mặc định cho qua.** Trả `428 Precondition Required` thay vì lặng lẽ bỏ kiểm tra — nếu không, một client cũ sẽ vô hiệu hoá toàn bộ cơ chế mà không ai biết.
3. **Đừng nhận `RowVersion` qua model binding tự động vào entity.** Nó không tự thành `OriginalValue`; phải gán tường minh như ở trên.
4. **`ExecuteUpdate` bỏ qua kiểm tra này hoàn toàn** ([bài 13.7](13.7-performance.mdx)) — đừng dùng nó cho đường ghi cần phát hiện xung đột.

**Test bắt được lỗi ngay từ đầu:**

```csharp
[Fact]
public async Task PUT_voi_token_cu_phai_tra_ve_409()
{
    var truoc = await _client.GetFromJsonAsync<LeadDto>("/leads/1");

    await _client.PutAsJsonAsync("/leads/1",
        new CapNhatLeadRequest("Won", 5_000_000, truoc!.RowVersion));     // người B ghi trước

    var res = await _client.PutAsJsonAsync("/leads/1",
        new CapNhatLeadRequest("Lost", 1_000_000, truoc.RowVersion));     // người A, token cũ

    res.StatusCode.Should().Be(HttpStatusCode.Conflict);
}
```

Test này là thứ duy nhất bắt được dạng lỗi ở đầu bài, vì bản có lỗi **chạy đúng trong mọi kịch bản một người dùng** — và đó là tất cả những gì test thủ công bao phủ.

#### Bài 3 — Cập nhật nguyên tử

Cài trừ kho bằng đọc-sửa-lưu, bắn 100 request đồng thời trừ 1 đơn vị từ kho 50, và đếm số đơn thành công. So sánh với `ExecuteUpdateAsync` có điều kiện trong `Where`.

**Tiêu chí hoàn thành:** bạn giải thích được vì sao `ExecuteUpdate` có điều kiện **không cần** concurrency token, và nêu được giới hạn của cách này.

Gợi ý và lời giải — Bài 3

**Gợi ý.** Đếm xem có bao nhiêu lần đi về database giữa lúc đọc số tồn và lúc ghi số mới.

**Lời giải — bản đọc-sửa-lưu:**

```csharp
public async Task<bool> TruKhoAsync(int productId, int soLuong, CancellationToken ct)
{
    await using var db = await _factory.CreateDbContextAsync(ct);

    var product = await db.Products.FirstAsync(p => p.Id == productId, ct);
    if (product.Stock < soLuong) return false;         // kiểm tra

    product.Stock -= soLuong;                          // sửa
    await db.SaveChangesAsync(ct);                     // ghi
    return true;
}
```

```csharp
var tasks = Enumerable.Range(0, 100).Select(_ => TruKhoAsync(1, 1, ct));
var ketQua = await Task.WhenAll(tasks);
Console.WriteLine($"Thành công: {ketQua.Count(x => x)}");
```

```text
Thành công: 87
Stock trong database: -37
```

Kho 50 mà 87 đơn thành công, và số tồn âm. Con số chính xác đổi theo mỗi lần chạy — dấu hiệu kinh điển của race condition.

**Vì sao.** Có một **khe hở** giữa kiểm tra và ghi:

```text
Luồng A: đọc Stock = 50
Luồng B: đọc Stock = 50        <- cùng thấy 50
Luồng A: kiểm tra 50 >= 1  OK
Luồng B: kiểm tra 50 >= 1  OK  <- cả hai đều qua
Luồng A: UPDATE Stock = 49
Luồng B: UPDATE Stock = 49     <- ghi đè, chỉ trừ 1 thay vì 2
```

Đây là mẫu **kiểm-tra-rồi-hành-động** (check-then-act), và nó luôn sai khi có đồng thời: điều kiện được kiểm tra trên một ảnh chụp đã cũ tại thời điểm hành động.

**Bản `ExecuteUpdate` có điều kiện:**

```csharp
public async Task<bool> TruKhoAsync(int productId, int soLuong, CancellationToken ct)
{
    await using var db = await _factory.CreateDbContextAsync(ct);

    var soDong = await db.Products
        .Where(p => p.Id == productId && p.Stock >= soLuong)     // điều kiện Ở TRONG WHERE
        .ExecuteUpdateAsync(s => s.SetProperty(p => p.Stock, p => p.Stock - soLuong), ct);

    return soDong == 1;
}
```

```text
Thành công: 50
Stock trong database: 0
```

Đúng 50, mọi lần chạy.

```sql
UPDATE Products SET Stock = Stock - @soLuong
WHERE Id = @productId AND Stock >= @soLuong;
```

**Vì sao không cần concurrency token.** Vì khe hở đã biến mất — kiểm tra và ghi nằm trong **cùng một câu lệnh**:

```text
Đọc-sửa-lưu:     [SELECT] ... khe hở ... [UPDATE]
                            ^^^^^^^ luồng khác chen vào được

ExecuteUpdate:   [UPDATE ... WHERE Stock >= @n]
                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ một câu lệnh, một lần
```

Database giữ khoá ghi trên dòng đó suốt thời gian thực thi lệnh. Hai lệnh `UPDATE` trên cùng dòng **bắt buộc** phải tuần tự — đó là bảo đảm cơ bản của mọi database quan hệ, không cần cấu hình gì thêm.

Và điều kiện `Stock >= @soLuong` được đánh giá trên **giá trị hiện tại tại thời điểm ghi**, không phải trên giá trị đọc từ trước. Không có ảnh chụp cũ, nên không có gì để lỗi thời.

`RowVersion` giải quyết **cùng vấn đề đó bằng cách khác**: nó không đóng khe hở, mà phát hiện khi có người chen vào. Ở đây khe hở không tồn tại, nên không có gì để phát hiện.

**Ba giới hạn của cách này:**

**1. Không biết vì sao thất bại.** `soDong == 0` gộp chung hai nguyên nhân khác hẳn nhau:

```csharp
// Không đủ hàng?  Hay sản phẩm không tồn tại?
return soDong == 1;
```

Phải truy vấn thêm mới phân biệt được — và lúc đó lại có khe hở, nhưng khe hở này vô hại vì nó chỉ ảnh hưởng tới **thông điệp lỗi**, không ảnh hưởng tới dữ liệu:

```csharp
if (soDong == 1) return KetQua.ThanhCong();

var tonTai = await db.Products.AnyAsync(p => p.Id == productId, ct);
return tonTai ? KetQua.KhongDuHang() : KetQua.KhongTimThay();
```

**2. Chỉ làm được những gì SQL biểu diễn được.** Logic phức tạp — kiểm tra hạn mức tín dụng theo nhiều bảng, áp quy tắc giá theo hạng khách hàng — không nhét vừa một `WHERE`. Lúc đó phải quay về đọc-sửa-lưu kèm `RowVersion`, hoặc dùng pessimistic locking:

```csharp
var product = await db.Products
    .FromSql($"SELECT * FROM Products WITH (UPDLOCK, ROWLOCK) WHERE Id = {productId}")
    .FirstAsync(ct);
```

**3. Bỏ qua interceptor, domain event và audit** — như mọi `ExecuteUpdate` ([bài 13.7](13.7-performance.mdx)). Phải đặt tay:

```csharp
.ExecuteUpdateAsync(s => s
    .SetProperty(p => p.Stock,      p => p.Stock - soLuong)
    .SetProperty(p => p.UpdatedUtc, _clock.GetUtcNow().UtcDateTime), ct);
```

**Bảng chọn cho cập nhật có điều kiện:**

| Tình huống | Cách |
|---|---|
| Trừ kho, trừ số dư, tăng bộ đếm | **`ExecuteUpdate` có điều kiện** |
| Người dùng sửa form qua nhiều request | **`RowVersion`** |
| Logic nghiệp vụ phức tạp, nhiều bảng | Transaction + `UPDLOCK` |
| Nhiều bước phải nguyên tử cùng nhau | Transaction, hoặc gộp vào một `UPDATE` nếu được |

**Và một test cho mỗi thao tác kiểu này:**

```csharp
[Fact]
public async Task Tru_kho_dong_thoi_khong_duoc_vuot_qua_so_ton()
{
    await TaoSanPhamAsync(id: 1, stock: 50);

    var ketQua = await Task.WhenAll(
        Enumerable.Range(0, 100).Select(_ => _service.TruKhoAsync(1, 1, ct)));

    ketQua.Count(x => x).Should().Be(50);
    (await LayTonKhoAsync(1)).Should().Be(0);
}
```

Test này cần database thật (không dùng được in-memory provider, vì nó không có khoá dòng), và nó là một trong số ít test đáng chạy với đồng thời thật — vì đây là loại lỗi mà **chỉ** đồng thời thật mới phát hiện được.

## Tự kiểm tra

### Lost update xảy ra thế nào?

Hai người cùng đọc một bản ghi, người lưu sau ghi đè thay đổi của người trước. Nó xảy ra im lặng, không có lỗi và không có log, nên người bị ghi đè chỉ phát hiện khi mở lại bản ghi.

### EF Core phát hiện xung đột bằng cách nào?

Nó đưa concurrency token vào mệnh đề WHERE của lệnh UPDATE. Nếu không dòng nào bị ảnh hưởng thì ai đó đã sửa trước, và EF ném DbUpdateConcurrencyException.

### Vì sao IsRowVersion mạnh hơn token thủ công?

Vì database tự đổi giá trị mỗi lần ghi, nên nó bắt được cả thay đổi từ script thủ công hay từ một ứng dụng khác. Token thủ công chỉ đổi khi code của bạn nhớ đổi.

### Khi nào mới thật sự là xung đột cần người dùng quyết định?

Chỉ khi cả hai bên cùng sửa cùng một trường. Nếu bạn sửa một trường còn người kia sửa trường khác thì chỉ cần gộp cả hai, không có gì để hỏi. Điều kiện kiểm tra là giá trị đề xuất khác giá trị gốc và giá trị trong database cũng khác giá trị gốc.

### Vì sao phải gán OriginalValue khi nhận token từ API?

Vì không có nó, EF dùng giá trị vừa đọc từ database làm token, nên kiểm tra luôn thành công và xung đột không bao giờ được phát hiện. Phải gán giá trị gốc mà client đã thấy vào OriginalValue của thuộc tính token.

### Cách tốt nhất cho bộ đếm và tồn kho là gì?

Không đọc trước, mà dùng một câu lệnh cập nhật nguyên tử với điều kiện kiểm tra ngay trong WHERE, rồi xem số dòng bị ảnh hưởng. Không có khoảng trống giữa đọc và ghi nên không có xung đột nào để xử lý.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Không có token thì mặc định là ghi đè im lặng.**
2. **Gán `OriginalValue` khi token đến từ client** — nếu không, kiểm tra luôn thành công.
3. **Bộ đếm nên tránh xung đột bằng cập nhật nguyên tử**, không xử lý xung đột.
