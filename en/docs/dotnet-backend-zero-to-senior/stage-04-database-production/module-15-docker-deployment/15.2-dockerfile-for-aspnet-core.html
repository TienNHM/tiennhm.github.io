15.3 — 2. Dockerfile cho ASP.NET Core

Summary

Một Dockerfile .NET tốt phải đạt bốn điều: nhỏ (multi-stage, image chiseled), build nhanh (cache layer đúng thứ tự cộng cache mount cho NuGet), an toàn (non-root, không có SDK trong image cuối), và báo đúng trạng thái (health check). Hai thay đổi từ .NET 8 khiến nhiều Dockerfile cũ sai: cổng mặc định đổi từ 80 sang 8080, và image .NET 8+ chạy non-root sẵn với user app — nên tự tạo user như trước là thừa và có thể gây lỗi quyền. Còn một chi tiết về hành vi: ENTRYPOINT dạng shell làm dotnet không nhận được SIGTERM, nên container bị kill cứng sau 10 giây thay vì shutdown gọn gàng.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Viết multi-stage Dockerfile tối ưu cache.
  • Chọn giữa các image cơ sở của Microsoft.
  • Cấu hình non-root và cổng đúng cho .NET 8+.
  • Thêm health check phù hợp.
  • Đảm bảo container shutdown gọn gàng.

Nội dung bài học​

15.3.1 — Dockerfile đầy đủ​

# syntax=docker/dockerfile:1

# ===== Stage 1: Build =====
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
ARG BUILD_CONFIGURATION=Release
WORKDIR /src

# Copy CHỈ file dự án trước -> cache restore
COPY ["Directory.Packages.props", "Directory.Build.props", "./"]
COPY ["src/CrmApi/CrmApi.csproj", "src/CrmApi/"]
COPY ["src/CrmApi.Application/CrmApi.Application.csproj", "src/CrmApi.Application/"]
COPY ["src/CrmApi.Infrastructure/CrmApi.Infrastructure.csproj", "src/CrmApi.Infrastructure/"]
COPY ["src/CrmApi.Domain/CrmApi.Domain.csproj", "src/CrmApi.Domain/"]

# Cache mount — package NuGet được giữ giữa các lần build
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore "src/CrmApi/CrmApi.csproj"

COPY . .

RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet publish "src/CrmApi/CrmApi.csproj" \
        -c $BUILD_CONFIGURATION \
        -o /app/publish \
        --no-restore \
        /p:UseAppHost=false

# ===== Stage 2: Runtime =====
FROM mcr.microsoft.com/dotnet/aspnet:9.0-noble-chiseled AS final
WORKDIR /app

# .NET 8+ CHẠY NON-ROOT SẴN với user "app" — không cần tạo user
# USER app   <- đã là mặc định

COPY --from=build /app/publish .

EXPOSE 8080
ENTRYPOINT ["dotnet", "CrmApi.dll"]

Bốn chi tiết đáng giải thích:

# syntax=docker/dockerfile:1 bật các tính năng BuildKit như --mount=type=cache.

--mount=type=cache giữ package NuGet giữa các lần build mà không đưa chúng vào layer image. Khác với cache layer thông thường, nó vẫn hoạt động khi layer bị vô hiệu — tiết kiệm lớn trên CI.

/p:UseAppHost=false bỏ file thực thi gốc; bạn chạy bằng dotnet App.dll nên nó không cần thiết. Tiết kiệm vài MB.

ENTRYPOINT dạng exec (mảng JSON) thay vì dạng shell — mục 15.3.4.

15.3.2 — Chọn image cơ sở​

ImageKích thướcCó shellDùng khi
aspnet:9.0~220 MBCóMặc định, dễ chẩn đoán
aspnet:9.0-alpine~110 MBCó (sh)Nhỏ; musl libc khác glibc
aspnet:9.0-noble-chiseled~110 MBKhôngProduction — bề mặt tấn công nhỏ
aspnet:9.0-noble-chiseled-extra~130 MBKhôngNhư trên, thêm ICU và tzdata
runtime-deps + self-contained~90 MBTuỳAOT, tối giản tuyệt đối

Chiseled là lựa chọn được Microsoft khuyến nghị cho production: không shell, không package manager, không user root — nên CVE của những thành phần đó không áp dụng. Đổi lại, docker exec vào để chẩn đoán là không được.

Alpine dùng musl libc thay glibc. Phần lớn ứng dụng chạy tốt, nhưng thư viện native (SkiaSharp, driver database cũ) có thể lỗi. Kiểm tra kỹ trước khi dùng.

Hai vấn đề hay gặp với chiseled và alpine:

# ICU — cần cho so sánh chuỗi theo văn hoá
ENV DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=false
# => dung image "-extra" co ICU, hoac bat invariant mode

# Múi giờ — chiseled không có tzdata
# => dung "-extra", hoac cai tzdata

Bật DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=true làm image nhỏ hơn nhưng đổi hành vi so sánh chuỗi — ToUpper() với tiếng Thổ Nhĩ Kỳ, sắp xếp tiếng Việt. Chỉ bật khi chắc chắn ứng dụng không phụ thuộc văn hoá.

15.3.3 — Non-root và cổng​

Từ .NET 8, image chính thức chạy non-root sẵn với user app (UID 64198):

# THUA voi .NET 8+ — va co the gay loi quyen
RUN addgroup --system appgroup && adduser --system --ingroup appgroup appuser
USER appuser

Tự tạo user rồi COPY file vào có thể khiến file thuộc root mà user mới không đọc được — một lỗi khó chẩn đoán.

Cổng mặc định đổi từ 80 sang 8080 trong .NET 8. Lý do: cổng dưới 1024 cần quyền đặc biệt, và container non-root không có quyền đó.

EXPOSE 8080
# ASPNETCORE_HTTP_PORTS=8080 là mặc định từ .NET 8

Dockerfile cũ dùng EXPOSE 80 với image .NET 8+ sẽ khiến container chạy nhưng không ai kết nối được — ứng dụng nghe 8080, bạn map cổng 80.

Cần cổng khác:

ENV ASPNETCORE_HTTP_PORTS=5000
EXPOSE 5000

ASPNETCORE_URLS vẫn dùng được nhưng ASPNETCORE_HTTP_PORTS đơn giản hơn cho trường hợp thường gặp.

Đừng dùng HTTPS trong container khi đã có reverse proxy: TLS kết thúc ở proxy, container chỉ nghe HTTP (bài 8.2). Quản lý chứng chỉ trong image là phức tạp không cần thiết.

15.3.4 — ENTRYPOINT và shutdown gọn gàng​

# SAI — dang shell: /bin/sh -c "dotnet CrmApi.dll"
ENTRYPOINT dotnet CrmApi.dll

# DUNG — dang exec: dotnet la PID 1
ENTRYPOINT ["dotnet", "CrmApi.dll"]

Với dạng shell, sh là PID 1 và dotnet là tiến trình con. docker stop gửi SIGTERM tới PID 1 — tức tới sh, và sh không chuyển tiếp tín hiệu.

Kết quả: ứng dụng .NET không bao giờ nhận SIGTERM, không chạy IHostApplicationLifetime.ApplicationStopping, không shutdown gọn gàng. Sau 10 giây, Docker gửi SIGKILL và giết cứng.

Hậu quả thật: request đang xử lý bị cắt, BackgroundService bị cắt giữa chừng (bài 9.10), kết nối database không đóng sạch.

Triệu chứng dễ nhận: mỗi lần deploy đều có một loạt lỗi trong log, và docker stop luôn mất đúng 10 giây.

Cho thời gian shutdown đủ dài:

docker stop --time=30 crm-api
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(25));     // NHO hon docker stop timeout

ShutdownTimeout của ứng dụng phải nhỏ hơn timeout của Docker, nếu không Docker giết trước khi ứng dụng kịp dọn dẹp.

15.3.5 — Health check​

HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
    CMD curl -f http://localhost:8080/health/live || exit 1

Image chiseled không có curl. Ba cách xử lý:

# 1. Dung image -extra va cai curl (lam tang kich thuoc)

# 2. Viết một health check bằng chính .NET
HEALTHCHECK CMD ["dotnet", "CrmApi.dll", "--healthcheck"]

# 3. KHÔNG đặt HEALTHCHECK trong Dockerfile — để orchestrator lo

Cách 3 là đúng nhất cho Kubernetes: livenessProbe và readinessProbe mạnh hơn nhiều HEALTHCHECK của Docker, và chúng phân biệt hai loại (bài 8.10).

HEALTHCHECK của Docker chỉ hữu ích với Docker Compose và docker run đơn lẻ.

--start-period là tham số hay bị quên: trong khoảng đó, thất bại không tính. Ứng dụng .NET cần vài giây để JIT và khởi tạo; không có nó, container bị đánh dấu unhealthy trước khi kịp khởi động.

15.3.6 — Giảm kích thước thêm​

<!-- .csproj -->
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
Kỹ thuậtGiảmRủi ro
Chiseled220 → 110 MBKhông chẩn đoán được bên trong
UseAppHost=falseVài MBKhông
InvariantGlobalization~30 MBĐổi hành vi so sánh chuỗi
PublishTrimmedĐáng kểPhản chiếu có thể gãy lúc chạy

Hai hàng cuối có rủi ro thật. PublishTrimmed loại bỏ code "không dùng" theo phân tích tĩnh — nhưng phản chiếu, serialize động và DI dựa trên kiểu có thể gãy lúc chạy, không phải lúc build.

Nếu dùng, phải test kỹ trên bản đã trim, không chỉ bản Debug.

Với phần lớn ứng dụng, chiseled một mình đã đủ: 110 MB không phải vấn đề, và chi phí kéo image chỉ trả một lần vì layer được cache.

15.3.7 — Rà lại code của bạn​

Danh sách rà soát Dockerfile

  • •Multi-stage build; image cuối không chứa SDK.
  • •File .csproj được copy và restore trước khi copy mã nguồn.
  • •Dùng cache mount cho thư mục package NuGet.
  • •Image cơ sở là chiseled hoặc alpine cho production.
  • •Không tự tạo user với image .NET 8+; nó đã non-root sẵn.
  • •EXPOSE và cấu hình cổng khớp 8080, không phải 80.
  • •ENTRYPOINT dạng exec, không phải dạng shell.
  • •ShutdownTimeout của ứng dụng nhỏ hơn timeout của docker stop.
  • •HEALTHCHECK có start-period, hoặc để orchestrator lo probe.
  • •Đã kiểm tra ICU và tzdata nếu dùng image chiseled hoặc alpine.
  • •Nếu bật PublishTrimmed thì đã test kỹ bản đã trim.

Bài tập áp dụng​

Bài 1 — ENTRYPOINT dạng shell nuốt tín hiệu​

Build image với ENTRYPOINT dotnet App.dll, chạy, rồi docker stop và đo thời gian. Log ApplicationStopping và xác nhận nó không chạy. Đổi sang dạng exec và kiểm chứng.

Tiêu chí hoàn thành: bạn giải thích được chuỗi sự kiện từ docker stop tới lúc tiến trình chết, và chỉ ra chính xác chỗ tín hiệu bị mất.

Gợi ý và lời giải — Bài 1

Gợi ý. docker stop gửi tín hiệu cho tiến trình nào?

Lời giải — dạng shell:

ENTRYPOINT dotnet Crm.Api.dll
app.Lifetime.ApplicationStopping.Register(() =>
    logger.LogWarning("ApplicationStopping — bắt đầu dọn dẹp"));
app.Lifetime.ApplicationStopped.Register(() =>
    logger.LogWarning("ApplicationStopped — đã dừng"));
time docker stop crm-api
real    0m10.312s
docker logs crm-api | tail -3
info: Microsoft.Hosting.Lifetime[0]
      Application started. Press Ctrl+C to shut down.

Không có dòng ApplicationStopping nào. Container mất đúng 10 giây — thời gian chờ mặc định của docker stop — rồi bị SIGKILL.

Dạng exec:

ENTRYPOINT ["dotnet", "Crm.Api.dll"]
real    0m0.847s
warn: Crm.Api[0] ApplicationStopping — bắt đầu dọn dẹp
info: Microsoft.Hosting.Lifetime[0] Application is shutting down...
warn: Crm.Api[0] ApplicationStopped — đã dừng

Chuỗi sự kiện từ docker stop tới lúc tiến trình chết:

1. docker stop <container>
2. Docker gửi SIGTERM tới tiến trình PID 1 trong container
3. PID 1 nhận SIGTERM
4. .NET host bắt SIGTERM -> kích hoạt ApplicationStopping
5. Ngừng nhận request mới, chờ request đang chạy hoàn tất
6. Chạy IHostedService.StopAsync, dọn tài nguyên
7. ApplicationStopped -> tiến trình thoát với mã 0
8. Docker thấy container đã thoát, kết thúc

Nếu bước 7 không xảy ra trong thời gian chờ (mặc định 10 giây), Docker chuyển sang bước 9:

9. Docker gửi SIGKILL -> nhân xoá tiến trình ngay lập tức

Chỗ tín hiệu bị mất là ở bước 2 và 3. Với dạng shell, Docker không chạy dotnet trực tiếp mà bọc nó trong một shell:

/bin/sh -c "dotnet Crm.Api.dll"
PID 1: /bin/sh -c "dotnet Crm.Api.dll"     <- nhận SIGTERM
  └─ PID 7: dotnet Crm.Api.dll             <- KHÔNG nhận được gì

/bin/sh trở thành PID 1 và nhận SIGTERM. Nhưng sh ở chế độ không tương tác không chuyển tiếp tín hiệu cho tiến trình con — nó chỉ chờ con kết thúc. Nên dotnet không bao giờ biết có ai yêu cầu nó dừng.

Với dạng exec, dotnet chính là PID 1 và nhận tín hiệu trực tiếp:

PID 1: dotnet Crm.Api.dll     <- nhận SIGTERM, xử lý đúng

Hậu quả thực tế của 10 giây đó:

Mỗi lần deploy:
  - Request đang xử lý bị cắt giữa chừng -> người dùng thấy lỗi
  - Transaction database không được commit hay rollback rõ ràng
  - Message đang xử lý không được ack -> broker gửi lại
  - Kết nối không được đóng -> pool phía kia chờ timeout
  - Rolling update chậm 10 giây mỗi pod

Với 10 pod, một lần deploy mất thêm 100 giây, và mỗi pod làm hỏng vài chục request. Chi tiết ở bài 15.13.

Ba cách viết ENTRYPOINT, và điều cần biết về từng cách:

1. Dạng exec — mặc định đúng:

ENTRYPOINT ["dotnet", "Crm.Api.dll"]

2. Khi cần shell (biến môi trường, nhiều lệnh) — dùng exec tường minh:

ENTRYPOINT ["/bin/sh", "-c", "exec dotnet Crm.Api.dll --urls http://+:$PORT"]

Từ khoá exec khiến shell thay thế chính nó bằng tiến trình dotnet, nên dotnet trở thành PID 1. Thiếu exec là quay lại vấn đề ban đầu.

3. Khi cần script khởi động — script phải exec ở dòng cuối:

#!/bin/sh
set -e

echo "Chạy migration..."
dotnet Crm.Api.dll --migrate-only

echo "Khởi động ứng dụng..."
exec dotnet Crm.Api.dll          # exec — KHÔNG được thiếu
ENTRYPOINT ["/app/entrypoint.sh"]

Kiểm tra PID 1 — cách nhanh nhất để biết bạn có vấn đề này không:

docker exec crm-api ps -o pid,comm
  PID COMMAND
    1 dotnet          <- ĐÚNG

  PID COMMAND
    1 sh              <- SAI
    7 dotnet

Và một trường hợp đặc biệt: ứng dụng sinh tiến trình con. Nếu ứng dụng của bạn chạy ffmpeg, chromium hay một công cụ ngoài, tiến trình con mồ côi sẽ trở thành zombie vì PID 1 (là dotnet) không thu hoạch chúng. Lúc đó cần một init thật:

ENTRYPOINT ["/usr/bin/tini", "--", "dotnet", "Crm.Api.dll"]

Hoặc để Docker cung cấp:

docker run --init crm-api

Chỉ cần điều này khi ứng dụng thật sự sinh tiến trình con — với một API ASP.NET Core thông thường thì không.

Tăng thời gian chờ nếu ứng dụng cần lâu hơn 10 giây để dọn:

docker stop --time=30 crm-api
# Kubernetes
spec:
  terminationGracePeriodSeconds: 30

Và cho .NET biết nó có bao nhiêu thời gian:

builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(25));   // nhỏ hơn 30 ở trên

Đặt ShutdownTimeout nhỏ hơn thời gian chờ của nền tảng là quan trọng: nếu bằng hoặc lớn hơn, .NET vẫn đang dọn thì SIGKILL đã tới, và bạn mất phần cuối của quá trình dọn dẹp — thường là phần ghi log nói rằng mọi thứ đã xong.

Bài 2 — Cổng đã đổi từ .NET 8​

Dùng EXPOSE 80 với image .NET 9, map -p 8080:80, và xác nhận không kết nối được. Sửa thành 8080.

Tiêu chí hoàn thành: bạn nêu được vì sao Microsoft đổi cổng mặc định, và hiểu EXPOSE thật sự làm gì.

Gợi ý và lời giải — Bài 2

Gợi ý. Cổng dưới 1024 cần quyền gì trên Linux?

Lời giải:

FROM mcr.microsoft.com/dotnet/aspnet:9.0
EXPOSE 80
ENTRYPOINT ["dotnet", "Crm.Api.dll"]
docker run -d -p 8080:80 --name crm-api crm-api
curl http://localhost:8080/health
curl: (52) Empty reply from server
docker logs crm-api | grep "Now listening"
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://[::]:8080

Ứng dụng nghe cổng 8080, nhưng bạn đang map cổng 80. Không có gì nghe ở cổng 80, nên kết nối bị từ chối.

docker run -d -p 8080:8080 --name crm-api crm-api
curl http://localhost:8080/health      # OK

Vì sao Microsoft đổi cổng mặc định từ .NET 8. Vì cổng dưới 1024 là cổng đặc quyền trên Linux — chỉ tiến trình có CAP_NET_BIND_SERVICE hoặc chạy bằng root mới bind được.

.NET 7 trở về trước:  mặc định cổng 80  -> container PHẢI chạy bằng root
.NET 8 trở đi:        mặc định cổng 8080 -> chạy được bằng non-root

Đây là điều kiện tiên quyết để image .NET chạy được bằng user thường:

FROM mcr.microsoft.com/dotnet/aspnet:9.0
USER $APP_UID                                 # user 1654, không phải root
EXPOSE 8080
ENTRYPOINT ["dotnet", "Crm.Api.dll"]

Với cổng 80, dòng USER này làm ứng dụng không khởi động được:

System.Net.Sockets.SocketException (13): Permission denied
   at System.Net.Sockets.Socket.Bind(EndPoint localEP)

Và chạy container bằng root là một trong những vấn đề bảo mật container phổ biến nhất: nếu kẻ tấn công thoát được khỏi container, họ có quyền root trên máy chủ. Nhiều cụm Kubernetes có chính sách chặn hẳn:

securityContext:
  runAsNonRoot: true          # pod bị từ chối nếu image chạy bằng root
  runAsUser: 1654
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
  capabilities:
    drop: ["ALL"]

Nói cách khác: đổi cổng mặc định không phải một thay đổi tuỳ hứng mà là thứ mở khoá cho cả nhóm cấu hình bảo mật ở trên.

EXPOSE thật sự làm gì — đây là phần hay bị hiểu sai nhất:

EXPOSE không mở cổng, không map cổng, không ảnh hưởng tới mạng. Nó là tài liệu.

EXPOSE 8080

Ba tác dụng thật, và không cái nào là "mở cổng":

  1. Siêu dữ liệu cho người đọc — docker inspect và docker ps hiển thị nó.
  2. docker run -P (chữ P hoa) map mọi cổng đã EXPOSE tới cổng ngẫu nhiên trên máy chủ.
  3. Một số công cụ đọc nó — Docker Compose, một số PaaS dùng để đoán cổng mặc định.

Container vẫn kết nối được kể cả khi không có EXPOSE nào:

FROM mcr.microsoft.com/dotnet/aspnet:9.0
# không có EXPOSE
ENTRYPOINT ["dotnet", "Crm.Api.dll"]
docker run -d -p 8080:8080 crm-api
curl http://localhost:8080/health      # vẫn hoạt động

Thứ thật sự quyết định là cổng mà ứng dụng nghe, và -p ánh xạ nó ra ngoài.

Ba cách đặt cổng, theo thứ tự ưu tiên tăng dần:

# 1. Biến môi trường — cách nên dùng
ENV ASPNETCORE_HTTP_PORTS=8080
# 2. Biến URLs — ghi đè cách 1, cho phép chỉ định cả địa chỉ
ENV ASPNETCORE_URLS=http://+:8080
# 3. Tham số dòng lệnh — ghi đè tất cả
dotnet Crm.Api.dll --urls http://+:8080

ASPNETCORE_HTTP_PORTS là biến mới từ .NET 8, và nó sạch hơn ASPNETCORE_URLS cho trường hợp thông thường — bạn chỉ nói cổng, không phải nhớ cú pháp http://+:.

Lưu ý ASPNETCORE_URLS ghi đè ASPNETCORE_HTTP_PORTS. Đặt cả hai với giá trị khác nhau là nguồn của những ca chẩn đoán dài, vì Dockerfile nói một đằng còn ứng dụng làm một nẻo.

Danh sách kiểm tra khi container không kết nối được:

# 1. Ứng dụng nghe cổng nào?
docker logs crm-api | grep "Now listening"

# 2. Cổng được map thế nào?
docker port crm-api

# 3. Ứng dụng có nghe trên MỌI giao diện không?
docker exec crm-api sh -c 'cat /proc/net/tcp | head -5'

Bước 3 bắt được một lỗi khác cũng hay gặp: ứng dụng nghe localhost thay vì 0.0.0.0.

ASPNETCORE_URLS=http://localhost:8080   -> chỉ nghe TRONG container, không ra ngoài được
ASPNETCORE_URLS=http://+:8080           -> nghe mọi giao diện, ĐÚNG

Lỗi này đặc biệt dễ mắc khi sao chép cấu hình từ launchSettings.json — file đó dùng localhost vì nó dành cho chạy trên máy dev, nơi không có ranh giới container nào để vượt qua.

Bài 3 — Cache mount cho NuGet​

Build image có và không có --mount=type=cache cho NuGet, xoá cache Docker giữa hai lần, và so sánh thời gian restore.

Tiêu chí hoàn thành: bạn nêu được khác biệt giữa cache mount và layer cache, và biết khi nào cache mount không giúp được gì.

Gợi ý và lời giải — Bài 3

Gợi ý. Layer cache bị vô hiệu khi layer trước đổi. Cache mount có bị vậy không?

Lời giải:

# syntax=docker/dockerfile:1
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
WORKDIR /src
COPY ["src/Crm.Api/Crm.Api.csproj", "src/Crm.Api/"]

RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore "src/Crm.Api/Crm.Api.csproj"

COPY . .
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet publish "src/Crm.Api/Crm.Api.csproj" -c Release -o /app --no-restore

Dòng # syntax= ở đầu là bắt buộc để dùng cú pháp cache mount, và nó phải là dòng đầu tiên của file.

docker builder prune -af          # xoá layer cache, GIỮ cache mount
docker build -t crm-api .
Không cache mount:  restore 48 s   (tải 312 gói từ nuget.org)
Có cache mount:      restore  6 s   (đọc từ cache cục bộ)

Khác biệt giữa hai cơ chế:

Layer cacheCache mount
Đơn vịCả một layerMột thư mục
Bị vô hiệu khiLayer trước đổiKhông bao giờ tự động
Nằm trong image cuốiCó — làm image toKhông
Chia sẻ giữa các build khác nhauChỉ khi layer giống hệtLuôn luôn
Chia sẻ giữa các dự ánKhôngCó, nếu cùng target
Xoá bằngdocker builder prunedocker builder prune --filter type=exec.cachemount

Điểm mấu chốt: cache mount sống sót qua việc layer bị vô hiệu.

Kịch bản: thêm một gói NuGet mới

Layer cache:   layer restore bị vô hiệu (vì .csproj đổi)
               -> chạy lại restore từ đầu

Cache mount:   layer restore vẫn bị vô hiệu
               -> nhưng thư mục /root/.nuget/packages VẪN CÒN
               -> restore chỉ tải MỘT gói mới, 311 gói kia đọc từ cache

Đây chính là lý do cache mount có giá trị: nó giúp đúng trong trường hợp mà layer cache không giúp được — khi phụ thuộc thay đổi.

Cache mount cho các công cụ khác:

# npm
RUN --mount=type=cache,target=/root/.npm npm ci

# apt
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt/lists,sharing=locked \
    apt-get update && apt-get install -y curl

# Go
RUN --mount=type=cache,target=/go/pkg/mod go build ./...

sharing=locked cho apt là cần thiết vì apt không chịu được hai tiến trình cùng ghi — mặc định sharing=shared sẽ gây lỗi khi build song song.

Khi nào cache mount không giúp được gì — bốn trường hợp:

1. CI dùng runner sạch mỗi lần. Đây là trường hợp quan trọng nhất, và nó làm nhiều người thất vọng:

GitHub Actions cấp một máy ảo mới cho mỗi job
-> không có cache mount nào từ lần chạy trước
-> cache mount hoàn toàn vô tác dụng

Giải pháp là dùng cache backend của CI thay vì trông chờ vào máy:

- uses: docker/build-push-action@v6
  with:
    cache-from: type=gha
    cache-to: type=gha,mode=max

Hoặc, đơn giản hơn và thường hiệu quả hơn, dùng cache của chính setup-dotnet:

- uses: actions/setup-dotnet@v4
  with:
    dotnet-version: '9.0.x'
    cache: true
    cache-dependency-path: '**/packages.lock.json'

2. Lần build đầu tiên. Cache rỗng thì không có gì để đọc — cache mount chỉ giúp từ lần thứ hai.

3. Build trên máy khác. Cache mount là cục bộ theo BuildKit instance. Máy A và máy B không chia sẻ.

4. docker builder prune -af có xoá cả cache mount không? Có, nếu dùng -a (all). Để giữ cache mount:

docker builder prune -f --filter type=regular      # chỉ xoá layer cache

Và một cảnh báo quan trọng về tính tái lập. Cache mount là trạng thái ẩn không nằm trong Dockerfile:

Build trên máy A (cache có gói cũ):  dùng phiên bản 1.2.0
Build trên máy B (cache rỗng):        tải phiên bản 1.2.1 mới nhất
-> hai image khác nhau từ cùng một commit

Với dotnet restore và một phạm vi phiên bản lỏng (Version="1.2.*"), điều này xảy ra thật. Khoá phiên bản để loại bỏ hẳn:

dotnet restore --use-lock-file
<PropertyGroup>
  <RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
  <RestoreLockedMode Condition="'$(ContinuousIntegrationBuild)' == 'true'">true</RestoreLockedMode>
</PropertyGroup>

RestoreLockedMode trong CI khiến build thất bại nếu packages.lock.json không khớp với .csproj — nghĩa là không ai có thể vô tình đổi phiên bản gói mà không commit file khoá.

Tổng kết thứ tự ưu tiên khi tối ưu thời gian build:

1. .dockerignore                  -> lợi ích lớn nhất, công sức ít nhất
2. Thứ tự layer đúng              -> lợi ích lớn, công sức ít
3. Cache backend của CI           -> lợi ích lớn trên CI (nơi thực sự quan trọng)
4. Cache mount                    -> lợi ích vừa, chủ yếu cho build cục bộ
5. Multi-stage và image nhỏ hơn   -> giảm kích thước, không giảm thời gian build

Nhiều nhóm bắt đầu từ mục 4 hoặc 5 và ngạc nhiên vì không thấy cải thiện trên CI. Hãy làm theo thứ tự trên.

Tự kiểm tra​

Frequently asked questions

Vì sao multi-stage build quan trọng?

Nó tách môi trường build có SDK khỏi môi trường chạy chỉ có runtime, nên image cuối nhỏ hơn nhiều và không chứa compiler hay mã nguồn. SDK khoảng 780 MB còn runtime khoảng 220 MB, hoặc 110 MB với bản chiseled.

Image chiseled là gì và đánh đổi ra sao?

Nó không có shell, không có package manager và không có user root, nên bề mặt tấn công nhỏ và nhiều CVE không áp dụng. Đổi lại bạn không exec vào để chẩn đoán được, và phải dùng bản extra nếu cần ICU hoặc dữ liệu múi giờ.

Hai thay đổi nào của .NET 8 làm Dockerfile cũ sai?

Cổng mặc định đổi từ 80 sang 8080 vì container non-root không mở được cổng dưới 1024, và image chính thức đã chạy non-root sẵn với user app nên tự tạo user là thừa và có thể gây lỗi quyền truy cập file.

Vì sao ENTRYPOINT dạng shell gây vấn đề?

Với dạng shell, sh là PID 1 và dotnet là tiến trình con, mà docker stop gửi SIGTERM tới PID 1 và sh không chuyển tiếp tín hiệu. Ứng dụng không bao giờ nhận SIGTERM nên không shutdown gọn gàng, và sau 10 giây Docker giết cứng. Triệu chứng là mỗi lần deploy đều có một loạt lỗi và docker stop luôn mất đúng 10 giây.

ShutdownTimeout của ứng dụng nên đặt thế nào?

Nhỏ hơn timeout của docker stop hoặc terminationGracePeriodSeconds của Kubernetes. Nếu lớn hơn thì orchestrator giết tiến trình trước khi ứng dụng kịp dọn dẹp, và mọi cấu hình shutdown gọn gàng trở thành vô nghĩa.

PublishTrimmed có rủi ro gì?

Nó loại bỏ code không dùng theo phân tích tĩnh, nhưng phản chiếu, serialize động và DI dựa trên kiểu có thể gãy lúc chạy chứ không phải lúc build. Nếu dùng thì phải test kỹ trên chính bản đã trim.

Kết luận​

Ba điều đáng nhớ nhất:

  1. ENTRYPOINT dạng exec — dạng shell khiến SIGTERM không tới ứng dụng.
  2. .NET 8+ đã non-root và nghe cổng 8080. Dockerfile cũ cần sửa cả hai.
  3. Chiseled cho production, nhưng kiểm tra ICU và múi giờ trước.
