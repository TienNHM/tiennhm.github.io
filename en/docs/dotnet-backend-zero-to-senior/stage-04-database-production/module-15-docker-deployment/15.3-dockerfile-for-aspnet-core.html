15.3 — 2. Dockerfile cho ASP.NET Core

Summary

Một Dockerfile .NET tốt phải đạt bốn điều: nhỏ (multi-stage, image chiseled), build nhanh (cache layer đúng thứ tự cộng cache mount cho NuGet), an toàn (non-root, không có SDK trong image cuối), và báo đúng trạng thái (health check). Hai thay đổi từ .NET 8 khiến nhiều Dockerfile cũ sai: cổng mặc định đổi từ 80 sang 8080, và image .NET 8+ chạy non-root sẵn với user app — nên tự tạo user như trước là thừa và có thể gây lỗi quyền. Còn một chi tiết về hành vi: ENTRYPOINT dạng shell làm dotnet không nhận được SIGTERM, nên container bị kill cứng sau 10 giây thay vì shutdown gọn gàng.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Viết multi-stage Dockerfile tối ưu cache.
  • Chọn giữa các image cơ sở của Microsoft.
  • Cấu hình non-root và cổng đúng cho .NET 8+.
  • Thêm health check phù hợp.
  • Đảm bảo container shutdown gọn gàng.

Nội dung bài học​

15.3.1 — Dockerfile đầy đủ​

# syntax=docker/dockerfile:1

# ===== Stage 1: Build =====
FROM mcr.microsoft.com/dotnet/sdk:9.0 AS build
ARG BUILD_CONFIGURATION=Release
WORKDIR /src

# Copy CHI file du an truoc -> cache restore
COPY ["Directory.Packages.props", "Directory.Build.props", "./"]
COPY ["src/CrmApi/CrmApi.csproj", "src/CrmApi/"]
COPY ["src/CrmApi.Application/CrmApi.Application.csproj", "src/CrmApi.Application/"]
COPY ["src/CrmApi.Infrastructure/CrmApi.Infrastructure.csproj", "src/CrmApi.Infrastructure/"]
COPY ["src/CrmApi.Domain/CrmApi.Domain.csproj", "src/CrmApi.Domain/"]

# Cache mount — package NuGet duoc giu giua cac lan build
RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet restore "src/CrmApi/CrmApi.csproj"

COPY . .

RUN --mount=type=cache,target=/root/.nuget/packages \
    dotnet publish "src/CrmApi/CrmApi.csproj" \
        -c $BUILD_CONFIGURATION \
        -o /app/publish \
        --no-restore \
        /p:UseAppHost=false

# ===== Stage 2: Runtime =====
FROM mcr.microsoft.com/dotnet/aspnet:9.0-noble-chiseled AS final
WORKDIR /app

# .NET 8+ CHAY NON-ROOT SAN voi user "app" — khong can tao user
# USER app   <- da la mac dinh

COPY --from=build /app/publish .

EXPOSE 8080
ENTRYPOINT ["dotnet", "CrmApi.dll"]

Bốn chi tiết đáng giải thích:

# syntax=docker/dockerfile:1 bật các tính năng BuildKit như --mount=type=cache.

--mount=type=cache giữ package NuGet giữa các lần build mà không đưa chúng vào layer image. Khác với cache layer thông thường, nó vẫn hoạt động khi layer bị vô hiệu — tiết kiệm lớn trên CI.

/p:UseAppHost=false bỏ file thực thi gốc; bạn chạy bằng dotnet App.dll nên nó không cần thiết. Tiết kiệm vài MB.

ENTRYPOINT dạng exec (mảng JSON) thay vì dạng shell — mục 15.3.4.

15.3.2 — Chọn image cơ sở​

ImageKích thướcCó shellDùng khi
aspnet:9.0~220 MBCóMặc định, dễ chẩn đoán
aspnet:9.0-alpine~110 MBCó (sh)Nhỏ; musl libc khác glibc
aspnet:9.0-noble-chiseled~110 MBKhôngProduction — bề mặt tấn công nhỏ
aspnet:9.0-noble-chiseled-extra~130 MBKhôngNhư trên, thêm ICU và tzdata
runtime-deps + self-contained~90 MBTuỳAOT, tối giản tuyệt đối

Chiseled là lựa chọn được Microsoft khuyến nghị cho production: không shell, không package manager, không user root — nên CVE của những thành phần đó không áp dụng. Đổi lại, docker exec vào để chẩn đoán là không được.

Alpine dùng musl libc thay glibc. Phần lớn ứng dụng chạy tốt, nhưng thư viện native (SkiaSharp, driver database cũ) có thể lỗi. Kiểm tra kỹ trước khi dùng.

Hai vấn đề hay gặp với chiseled và alpine:

# ICU — can cho so sanh chuoi theo van hoa
ENV DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=false
# => dung image "-extra" co ICU, hoac bat invariant mode

# Mui gio — chiseled khong co tzdata
# => dung "-extra", hoac cai tzdata

Bật DOTNET_SYSTEM_GLOBALIZATION_INVARIANT=true làm image nhỏ hơn nhưng đổi hành vi so sánh chuỗi — ToUpper() với tiếng Thổ Nhĩ Kỳ, sắp xếp tiếng Việt. Chỉ bật khi chắc chắn ứng dụng không phụ thuộc văn hoá.

15.3.3 — Non-root và cổng​

Từ .NET 8, image chính thức chạy non-root sẵn với user app (UID 64198):

# THUA voi .NET 8+ — va co the gay loi quyen
RUN addgroup --system appgroup && adduser --system --ingroup appgroup appuser
USER appuser

Tự tạo user rồi COPY file vào có thể khiến file thuộc root mà user mới không đọc được — một lỗi khó chẩn đoán.

Cổng mặc định đổi từ 80 sang 8080 trong .NET 8. Lý do: cổng dưới 1024 cần quyền đặc biệt, và container non-root không có quyền đó.

EXPOSE 8080
# ASPNETCORE_HTTP_PORTS=8080 la mac dinh tu .NET 8

Dockerfile cũ dùng EXPOSE 80 với image .NET 8+ sẽ khiến container chạy nhưng không ai kết nối được — ứng dụng nghe 8080, bạn map cổng 80.

Cần cổng khác:

ENV ASPNETCORE_HTTP_PORTS=5000
EXPOSE 5000

ASPNETCORE_URLS vẫn dùng được nhưng ASPNETCORE_HTTP_PORTS đơn giản hơn cho trường hợp thường gặp.

Đừng dùng HTTPS trong container khi đã có reverse proxy: TLS kết thúc ở proxy, container chỉ nghe HTTP (bài 8.2). Quản lý chứng chỉ trong image là phức tạp không cần thiết.

15.3.4 — ENTRYPOINT và shutdown gọn gàng​

# SAI — dang shell: /bin/sh -c "dotnet CrmApi.dll"
ENTRYPOINT dotnet CrmApi.dll

# DUNG — dang exec: dotnet la PID 1
ENTRYPOINT ["dotnet", "CrmApi.dll"]

Với dạng shell, sh là PID 1 và dotnet là tiến trình con. docker stop gửi SIGTERM tới PID 1 — tức tới sh, và sh không chuyển tiếp tín hiệu.

Kết quả: ứng dụng .NET không bao giờ nhận SIGTERM, không chạy IHostApplicationLifetime.ApplicationStopping, không shutdown gọn gàng. Sau 10 giây, Docker gửi SIGKILL và giết cứng.

Hậu quả thật: request đang xử lý bị cắt, BackgroundService bị cắt giữa chừng (bài 9.10), kết nối database không đóng sạch.

Triệu chứng dễ nhận: mỗi lần deploy đều có một loạt lỗi trong log, và docker stop luôn mất đúng 10 giây.

Cho thời gian shutdown đủ dài:

docker stop --time=30 crm-api
builder.Services.Configure<HostOptions>(o =>
    o.ShutdownTimeout = TimeSpan.FromSeconds(25));     // NHO hon docker stop timeout

ShutdownTimeout của ứng dụng phải nhỏ hơn timeout của Docker, nếu không Docker giết trước khi ứng dụng kịp dọn dẹp.

15.3.5 — Health check​

HEALTHCHECK --interval=30s --timeout=5s --start-period=20s --retries=3 \
    CMD curl -f http://localhost:8080/health/live || exit 1

Image chiseled không có curl. Ba cách xử lý:

# 1. Dung image -extra va cai curl (lam tang kich thuoc)

# 2. Viet mot health check bang chinh .NET
HEALTHCHECK CMD ["dotnet", "CrmApi.dll", "--healthcheck"]

# 3. KHONG dat HEALTHCHECK trong Dockerfile — de orchestrator lo

Cách 3 là đúng nhất cho Kubernetes: livenessProbe và readinessProbe mạnh hơn nhiều HEALTHCHECK của Docker, và chúng phân biệt hai loại (bài 8.10).

HEALTHCHECK của Docker chỉ hữu ích với Docker Compose và docker run đơn lẻ.

--start-period là tham số hay bị quên: trong khoảng đó, thất bại không tính. Ứng dụng .NET cần vài giây để JIT và khởi tạo; không có nó, container bị đánh dấu unhealthy trước khi kịp khởi động.

15.3.6 — Giảm kích thước thêm​

<!-- .csproj -->
<PropertyGroup>
  <PublishTrimmed>true</PublishTrimmed>
  <InvariantGlobalization>true</InvariantGlobalization>
</PropertyGroup>
Kỹ thuậtGiảmRủi ro
Chiseled220 → 110 MBKhông chẩn đoán được bên trong
UseAppHost=falseVài MBKhông
InvariantGlobalization~30 MBĐổi hành vi so sánh chuỗi
PublishTrimmedĐáng kểPhản chiếu có thể gãy lúc chạy
Native AOTRất lớnNhiều hạn chế; ASP.NET Core hỗ trợ một phần

Hai hàng cuối có rủi ro thật. PublishTrimmed loại bỏ code "không dùng" theo phân tích tĩnh — nhưng phản chiếu, serialize động và DI dựa trên kiểu có thể gãy lúc chạy, không phải lúc build.

Nếu dùng, phải test kỹ trên bản đã trim, không chỉ bản Debug.

Với phần lớn ứng dụng, chiseled một mình đã đủ: 110 MB không phải vấn đề, và chi phí kéo image chỉ trả một lần vì layer được cache.

15.3.7 — Rà lại code của bạn​

Danh sách rà soát Dockerfile

  • •Multi-stage build; image cuối không chứa SDK.
  • •File .csproj được copy và restore trước khi copy mã nguồn.
  • •Dùng cache mount cho thư mục package NuGet.
  • •Image cơ sở là chiseled hoặc alpine cho production.
  • •Không tự tạo user với image .NET 8+; nó đã non-root sẵn.
  • •EXPOSE và cấu hình cổng khớp 8080, không phải 80.
  • •ENTRYPOINT dạng exec, không phải dạng shell.
  • •ShutdownTimeout của ứng dụng nhỏ hơn timeout của docker stop.
  • •HEALTHCHECK có start-period, hoặc để orchestrator lo probe.
  • •Đã kiểm tra ICU và tzdata nếu dùng image chiseled hoặc alpine.
  • •Nếu bật PublishTrimmed thì đã test kỹ bản đã trim.

Bài tập áp dụng​

  1. ENTRYPOINT dạng shell. Build image với ENTRYPOINT dotnet App.dll, chạy, rồi docker stop và đo thời gian. Log ApplicationStopping và xác nhận nó không chạy. Đổi sang dạng exec và kiểm chứng.

  2. Cổng sai. Dùng EXPOSE 80 với image .NET 9, map -p 8080:80, và xác nhận không kết nối được. Sửa thành 8080.

  3. Cache mount. Build image có và không có --mount=type=cache cho NuGet, xoá cache Docker giữa hai lần, và so sánh thời gian restore.

Tự kiểm tra​

Frequently asked questions

Vì sao multi-stage build quan trọng?

Nó tách môi trường build có SDK khỏi môi trường chạy chỉ có runtime, nên image cuối nhỏ hơn nhiều và không chứa compiler hay mã nguồn. SDK khoảng 780 MB còn runtime khoảng 220 MB, hoặc 110 MB với bản chiseled.

Image chiseled là gì và đánh đổi ra sao?

Nó không có shell, không có package manager và không có user root, nên bề mặt tấn công nhỏ và nhiều CVE không áp dụng. Đổi lại bạn không exec vào để chẩn đoán được, và phải dùng bản extra nếu cần ICU hoặc dữ liệu múi giờ.

Hai thay đổi nào của .NET 8 làm Dockerfile cũ sai?

Cổng mặc định đổi từ 80 sang 8080 vì container non-root không mở được cổng dưới 1024, và image chính thức đã chạy non-root sẵn với user app nên tự tạo user là thừa và có thể gây lỗi quyền truy cập file.

Vì sao ENTRYPOINT dạng shell gây vấn đề?

Với dạng shell, sh là PID 1 và dotnet là tiến trình con, mà docker stop gửi SIGTERM tới PID 1 và sh không chuyển tiếp tín hiệu. Ứng dụng không bao giờ nhận SIGTERM nên không shutdown gọn gàng, và sau 10 giây Docker giết cứng. Triệu chứng là mỗi lần deploy đều có một loạt lỗi và docker stop luôn mất đúng 10 giây.

ShutdownTimeout của ứng dụng nên đặt thế nào?

Nhỏ hơn timeout của docker stop hoặc terminationGracePeriodSeconds của Kubernetes. Nếu lớn hơn thì orchestrator giết tiến trình trước khi ứng dụng kịp dọn dẹp, và mọi cấu hình shutdown gọn gàng trở thành vô nghĩa.

PublishTrimmed có rủi ro gì?

Nó loại bỏ code không dùng theo phân tích tĩnh, nhưng phản chiếu, serialize động và DI dựa trên kiểu có thể gãy lúc chạy chứ không phải lúc build. Nếu dùng thì phải test kỹ trên chính bản đã trim.

Kết luận​

Ba điều đáng nhớ nhất:

  1. ENTRYPOINT dạng exec — dạng shell khiến SIGTERM không tới ứng dụng.
  2. .NET 8+ đã non-root và nghe cổng 8080. Dockerfile cũ cần sửa cả hai.
  3. Chiseled cho production, nhưng kiểm tra ICU và múi giờ trước.
