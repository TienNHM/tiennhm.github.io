13.4 — 3. Relationships

Summary

Cái bẫy nguy hiểm nhất trong bài này là DeleteBehavior không chỉ nói về database. Cascade khiến EF Core tự xoá các entity con đã được nạp vào change tracker, kể cả khi database không có ON DELETE CASCADE — nghĩa là xoá một Customer có thể sinh ra hàng trăm lệnh DELETE mà bạn không hề viết. Điểm thứ hai: có khoá ngoại tường minh trong entity (public int CustomerId) thay đổi hẳn cách làm việc — bạn gán quan hệ mà không cần nạp entity cha, và biết được khoá ngoại mà không cần Include. Thứ ba: required hay optional được suy ra từ tính nullable của khoá ngoại, nên int và int? cho hai hành vi xoá mặc định khác nhau.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Khai báo quan hệ với khoá ngoại tường minh và hiểu lợi ích.
  • Chọn đúng DeleteBehavior và biết nó ảnh hưởng gì ở cả hai tầng.
  • Cấu hình many-to-many có và không có bảng nối chứa dữ liệu.
  • Xử lý self-reference và quan hệ tuỳ chọn.
  • Tránh chu trình cascade mà SQL Server từ chối.

Nội dung bài học​

13.4.1 — Khoá ngoại tường minh​

// KHÔNG có khoá ngoại tường minh — EF dùng shadow property
public class Contact
{
    public int Id { get; set; }
    public Customer Customer { get; set; } = null!;
}

// CÓ khoá ngoại tường minh — khuyến nghị
public class Contact
{
    public int Id { get; set; }
    public int CustomerId { get; set; }                  // tường minh
    public Customer Customer { get; set; } = null!;
}

Bốn lợi ích của cách thứ hai:

// 1. Gán quan hệ mà KHÔNG cần nạp entity cha
var contact = new Contact { CustomerId = 42, FullName = "Nguyen Van A" };
db.Contacts.Add(contact);                 // không cần SELECT Customer

// 2. Biết khoá ngoại mà không cần Include
var customerId = contact.CustomerId;      // không sinh truy vấn

// 3. Loc theo khoa ngoai truc tiep
await db.Contacts.Where(c => c.CustomerId == 42).ToListAsync(ct);

// 4. DTO map thẳng được

Không có nó, EF Core dùng shadow property — cột tồn tại trong database nhưng không có trong lớp C#. Truy cập phải qua db.Entry(contact).Property("CustomerId"), và mọi thao tác gán quan hệ đều cần nạp entity cha.

Quy ước đặt tên để EF tự nhận: {TênNavigation}Id (CustomerId cho navigation Customer) hoặc {TênKiểu}Id. Khác quy ước thì khai rõ:

builder.HasOne(c => c.Customer)
       .WithMany(cu => cu.Contacts)
       .HasForeignKey(c => c.OwnerCustomerId);

13.4.2 — Required so với optional​

public int CustomerId { get; set; }       // REQUIRED — contact phai thuoc customer
public int? AssignedUserId { get; set; }  // OPTIONAL — lead co the chua gan ai

EF Core suy ra từ tính nullable của khoá ngoại, và điều đó quyết định hành vi xoá mặc định:

Khoá ngoạiQuan hệDeleteBehavior mặc định
intRequiredCascade
int?OptionalClientSetNull

Đây là chi tiết rất đáng biết: đổi int thành int? âm thầm đổi hành vi xoá từ xoá con sang gán NULL.

Khai rõ ràng để không phụ thuộc vào suy luận:

builder.HasOne(c => c.Customer)
       .WithMany(cu => cu.Contacts)
       .HasForeignKey(c => c.CustomerId)
       .IsRequired()
       .OnDelete(DeleteBehavior.Cascade);

13.4.3 — DeleteBehavior ảnh hưởng hai tầng​

DeleteBehaviorEF Core làm gì (entity đã nạp)Database
CascadeXoá entity conON DELETE CASCADE
ClientCascadeXoá entity conNO ACTION
SetNullGán NULL cho khoá ngoạiON DELETE SET NULL
ClientSetNullGán NULL (chỉ entity đã nạp)NO ACTION
RestrictKhông làm gìNO ACTION
NoActionKhông làm gìNO ACTION

Cột giữa là phần bị bỏ qua nhiều nhất. Ví dụ cụ thể:

var customer = await db.Customers
    .Include(c => c.Contacts)          // nap 200 contact vao change tracker
    .FirstAsync(c => c.Id == 42, ct);

db.Customers.Remove(customer);
await db.SaveChangesAsync(ct);

Với Cascade, EF Core sinh:

DELETE FROM Contacts WHERE Id = 1;     -- 200 lệnh riêng biệt
DELETE FROM Contacts WHERE Id = 2;
...
DELETE FROM Customers WHERE Id = 42;

EF Core không dựa vào cascade của database cho những entity nó đã theo dõi — nó tự sinh lệnh xoá cho từng cái. Với 200 contact, đó là 201 lệnh trong một transaction.

Không Include thì EF chỉ xoá Customer và để database lo phần còn lại — nhanh hơn nhiều. Nghịch lý: Include trước khi xoá làm mọi thứ chậm hơn.

Với xoá hàng loạt, dùng ExecuteDeleteAsync để bỏ qua change tracker hoàn toàn:

await db.Customers.Where(c => c.Status == CustomerStatus.Inactive)
                  .ExecuteDeleteAsync(ct);     // một lệnh DELETE

Restrict khác NoAction ở chỗ Restrict khiến EF Core không tự động sửa gì cả và ném lỗi nếu bạn cố xoá cha còn con — hữu ích khi bạn muốn lỗi rõ ràng thay vì xoá ngầm.

13.4.4 — Chu trình cascade​

Customers --cascade--> Leads
Users     --cascade--> Leads

SQL Server từ chối tạo cấu hình này: nhiều đường cascade cùng tới một bảng. Lỗi xuất hiện lúc dotnet ef database update, không phải lúc biên dịch.

Cách xử lý: chọn một đường cascade, những đường còn lại dùng NoAction hoặc SetNull:

// Contacts theo Customer — cascade
builder.HasMany(c => c.Contacts).WithOne(ct => ct.Customer)
       .OnDelete(DeleteBehavior.Cascade);

// Leads không biến mất khi nhân viên nghỉ — SetNull
builder.HasMany(u => u.AssignedLeads).WithOne(l => l.AssignedUser)
       .HasForeignKey(l => l.AssignedUserId)
       .OnDelete(DeleteBehavior.SetNull);

Lựa chọn này thường phản ánh đúng nghiệp vụ: lead vẫn tồn tại khi nhân viên nghỉ việc, chỉ mất người phụ trách.

Tắt cascade cho toàn bộ mô hình khi bạn muốn kiểm soát thủ công:

foreach (var fk in modelBuilder.Model.GetEntityTypes()
                               .SelectMany(e => e.GetForeignKeys())
                               .Where(fk => !fk.IsOwnership && fk.DeleteBehavior == DeleteBehavior.Cascade))
{
    fk.DeleteBehavior = DeleteBehavior.Restrict;
}

Nhiều team làm vậy với lý do: xoá dây chuyền ngoài ý muốn nguy hiểm hơn một lỗi rõ ràng bắt bạn xử lý tường minh.

13.4.5 — Many-to-many​

// EF Core 5+: không cần lớp bảng nối
public class Lead  { public ICollection<Tag> Tags { get; set; } = []; }
public class Tag   { public ICollection<Lead> Leads { get; set; } = []; }

builder.HasMany(l => l.Tags)
       .WithMany(t => t.Leads)
       .UsingEntity(j => j.ToTable("LeadTags"));

EF Core tự tạo bảng nối. Đơn giản, nhưng chỉ đúng khi quan hệ không mang dữ liệu.

Ngay khi bạn cần biết "ai gắn tag này, lúc nào", quan hệ trở thành một thực thể:

public class LeadTag
{
    public int LeadId { get; set; }
    public Lead Lead { get; set; } = null!;

    public int TagId { get; set; }
    public Tag Tag { get; set; } = null!;

    public DateTime TaggedAt { get; set; }
    public string TaggedBy { get; set; } = string.Empty;   // dữ liệu riêng
}

builder.HasMany(l => l.Tags)
       .WithMany(t => t.Leads)
       .UsingEntity<LeadTag>(
           r => r.HasOne(lt => lt.Tag).WithMany().HasForeignKey(lt => lt.TagId),
           l => l.HasOne(lt => lt.Lead).WithMany().HasForeignKey(lt => lt.LeadId),
           j =>
           {
               j.HasKey(lt => new { lt.LeadId, lt.TagId });
               j.Property(lt => lt.TaggedAt).HasDefaultValueSql("SYSUTCDATETIME()");
           });

Bạn giữ được cả hai: navigation trực tiếp lead.Tags, và truy cập bảng nối khi cần TaggedAt.

Lời khuyên thực dụng: nếu có khả năng quan hệ sẽ mang dữ liệu, khai bảng nối tường minh ngay từ đầu — chuyển đổi về sau cần migration và sửa code ở nhiều nơi.

13.4.6 — Self-reference​

public class User
{
    public int Id { get; set; }
    public int? ManagerId { get; set; }                    // NULL cho cấp cao nhất
    public User? Manager { get; set; }
    public ICollection<User> DirectReports { get; set; } = [];
}

builder.HasOne(u => u.Manager)
       .WithMany(u => u.DirectReports)
       .HasForeignKey(u => u.ManagerId)
       .OnDelete(DeleteBehavior.Restrict);     // KHÔNG cascade

Restrict ở đây gần như bắt buộc: Cascade trên self-reference có thể xoá cả cây tổ chức khi bạn xoá một người quản lý.

Truy vấn cây có độ sâu tuỳ ý là giới hạn thật của EF Core — LINQ không diễn đạt được đệ quy. Dùng recursive CTE (bài 12.4):

var subordinates = await db.Users.FromSql($"""
    WITH OrgChart AS (
        SELECT Id, DisplayName, ManagerId, 0 AS Level
        FROM   Users WHERE Id = {managerId}
        UNION ALL
        SELECT u.Id, u.DisplayName, u.ManagerId, oc.Level + 1
        FROM   Users u JOIN OrgChart oc ON u.ManagerId = oc.Id
    )
    SELECT * FROM OrgChart
    """).ToListAsync(ct);

13.4.7 — Rà lại code của bạn​

Danh sách rà soát quan hệ

  • •Mọi quan hệ đều có khoá ngoại tường minh trong entity.
  • •DeleteBehavior được khai rõ, không dựa vào suy luận từ nullable.
  • •Hiểu rằng Cascade khiến EF tự sinh lệnh xoá cho entity đã nạp.
  • •Không Include các collection lớn ngay trước khi xoá entity cha.
  • •Xoá hàng loạt dùng ExecuteDeleteAsync.
  • •Không có chu trình cascade nhiều đường tới cùng một bảng.
  • •Self-reference dùng Restrict, không dùng Cascade.
  • •Many-to-many có khả năng mang dữ liệu thì khai bảng nối tường minh.
  • •Truy vấn cây độ sâu tuỳ ý dùng recursive CTE, không dùng Include lồng nhau.
  • •Hành vi xoá phản ánh đúng nghiệp vụ, không chỉ chọn cho tiện.

Bài tập áp dụng​

Bài 1 — Include làm chậm xoá​

Xoá một Customer có 200 contact, một lần có Include(c => c.Contacts) và một lần không. Bật log SQL, đếm số lệnh sinh ra và so sánh thời gian.

Tiêu chí hoàn thành: bạn giải thích được vì sao Include thêm lệnh SQL thay vì bớt, và nói được khi nào bắt buộc phải Include khi xoá.

Gợi ý và lời giải — Bài 1

Gợi ý. EF Core chỉ xử lý được những entity nó đang theo dõi. Hãy hỏi: nếu nó theo dõi 200 contact thì nó sẽ làm gì với chúng?

Lời giải — không Include:

var customer = await _db.Customers.FirstAsync(c => c.Id == id, ct);
_db.Customers.Remove(customer);
await _db.SaveChangesAsync(ct);
SELECT TOP(1) [c].[Id], [c].[Name] FROM [Customers] AS [c] WHERE [c].[Id] = @__id_0
DELETE FROM [Customers] WHERE [Id] = @p0
-- 2 câu lệnh

Database tự xoá 200 contact bằng ON DELETE CASCADE, trong cùng lệnh DELETE đó.

Có Include:

var customer = await _db.Customers
    .Include(c => c.Contacts)
    .FirstAsync(c => c.Id == id, ct);
_db.Customers.Remove(customer);
await _db.SaveChangesAsync(ct);
SELECT [c].[Id], [c].[Name], [t].[Id], [t].[Name], [t].[CustomerId]
FROM [Customers] AS [c] LEFT JOIN [Contacts] AS [t] ON [c].[Id] = [t].[CustomerId]
WHERE [c].[Id] = @__id_0

DELETE FROM [Contacts] WHERE [Id] = @p0
DELETE FROM [Contacts] WHERE [Id] = @p1
...                                        (198 lệnh nữa)
DELETE FROM [Customers] WHERE [Id] = @p200
-- 202 câu lệnh
Số câu lệnhThời gian điển hình
Không Include2~4 ms
Có Include202~180 ms

Vì sao Include thêm lệnh thay vì bớt. Đây là chỗ trực giác đánh lừa: người ta hay nghĩ Include là để "gộp mọi thứ vào một truy vấn". Nó đúng khi đọc, và sai ngược lại khi xoá.

Nguyên nhân nằm ở quy tắc: EF Core chỉ tác động lên entity nó đang theo dõi.

Không Include:
   Tracker chứa:  [Customer #7]
   SaveChanges:   1 lệnh DELETE cho Customer
   200 contact:   database tự lo bằng ON DELETE CASCADE

Có Include:
   Tracker chứa:  [Customer #7] + [Contact #1 .. #200]
   Remove(customer) -> cascade CỦA EF CORE đánh dấu cả 200 contact là Deleted
   SaveChanges:   201 lệnh DELETE

Có hai cơ chế cascade cùng tên, ở hai tầng khác nhau:

Cascade của EF CoreCascade của database
Chạy ở đâuTrong tiến trình .NETTrong database engine
Áp choEntity đang được theo dõiMọi dòng liên quan
Sinh raMột DELETE cho mỗi entityKhông sinh lệnh nào thêm
Cần nạp dữ liệuCóKhông

Không Include nghĩa là không có contact nào trong tracker, nên cascade của EF Core không có gì để làm, và cascade của database làm hết — trong một lệnh.

Khi nào bắt buộc phải Include khi xoá. Ba trường hợp:

1. Khi DeleteBehavior là ClientCascade hoặc ClientSetNull. Tên đã nói rõ: cascade xảy ra ở phía client, tức trong tiến trình .NET. Nếu entity con không được nạp, EF Core không biết chúng tồn tại và DELETE cha sẽ thất bại vì vi phạm khoá ngoại:

builder.HasOne(c => c.Customer).WithMany(c => c.Contacts)
       .OnDelete(DeleteBehavior.ClientCascade);   // buộc phải Include khi xoá

2. Khi database không có ràng buộc cascade. Với quan hệ tuỳ chọn (CustomerId nullable), EF Core mặc định dùng ClientSetNull, và database không có gì để tự làm.

3. Khi bạn cần chạy logic trên từng entity con — ghi audit, phát domain event, xoá file đính kèm. Những việc đó cần entity thật trong bộ nhớ.

Cách tốt nhất cho xoá hàng loạt — ExecuteDeleteAsync:

await _db.Contacts.Where(c => c.CustomerId == id).ExecuteDeleteAsync(ct);
await _db.Customers.Where(c => c.Id == id).ExecuteDeleteAsync(ct);
// 2 câu lệnh, 0 entity được nạp, kể cả khi có 200.000 contact

Đổi lại, nó bỏ qua interceptor và domain event — cùng đánh đổi đã nói ở bài 13.2.

Một chi tiết dễ bỏ sót: cả 201 lệnh DELETE của bản Include chạy trong một transaction do SaveChanges mở. Với 200 contact thì không sao; với 200.000 thì transaction giữ khoá trong nhiều phút và transaction log phình to — đúng vấn đề đã mổ xẻ ở bài 12.8.

Bài 2 — Chu trình cascade​

Tạo hai đường cascade cùng tới bảng Leads, chạy dotnet ef database update, và ghi lại lỗi. Sửa bằng SetNull cho một đường.

Tiêu chí hoàn thành: bạn giải thích được vì sao SQL Server từ chối, và nêu được vì sao PostgreSQL không từ chối cùng cấu hình đó.

Gợi ý và lời giải — Bài 2

Gợi ý. Hãy nghĩ xem database phải quyết định gì khi một dòng bị xoá theo hai đường cascade cùng lúc.

Lời giải — mô hình gây lỗi:

public class Lead
{
    public int Id { get; set; }
    public int CustomerId { get; set; }          // đường 1
    public Customer Customer { get; set; } = null!;
    public int AssignedUserId { get; set; }      // đường 2
    public User AssignedUser { get; set; } = null!;
}
Customer ──cascade──> Lead
   │                    ↑
   └──cascade──> User ──┘

Cả hai khoá ngoại đều NOT NULL, nên EF Core mặc định đặt DeleteBehavior.Cascade cho cả hai. Xoá một Customer sẽ cascade tới Lead theo đường trực tiếp, và tới User rồi từ User cascade tiếp tới Lead.

dotnet ef database update
Microsoft.Data.SqlClient.SqlException (0x80131904):
Introducing FOREIGN KEY constraint 'FK_Leads_Users_AssignedUserId' on table
'Leads' may cause cycles or multiple cascade paths. Specify ON DELETE NO ACTION
or ON UPDATE NO ACTION, or modify other FOREIGN KEY constraints.

Vì sao SQL Server từ chối. SQL Server thực thi cascade bằng một cơ chế không có thứ tự xác định và không cho phép một dòng bị tác động hai lần trong cùng một thao tác cascade. Khi có hai đường tới cùng bảng, nó không đảm bảo được:

  • Một Lead sẽ bị xoá bao nhiêu lần, và theo đường nào trước.
  • Nếu hai đường có hành vi khác nhau — một CASCADE, một SET NULL — thì dòng đó kết thúc ở trạng thái nào.

Thay vì chọn một thứ tự tuỳ tiện rồi cho ra kết quả không xác định, SQL Server từ chối ngay lúc tạo ràng buộc. Quan trọng: nó từ chối dựa trên cấu trúc schema, không phải dựa trên dữ liệu — kể cả khi không có dòng nào thực sự nằm trên cả hai đường, lỗi vẫn xuất hiện.

Đây là lựa chọn thiết kế bảo thủ: thà báo lỗi lúc migration còn hơn xoá sai dữ liệu lúc chạy.

Bản sửa — chọn một đường và hạ xuống:

builder.Entity<Lead>()
    .HasOne(l => l.Customer).WithMany(c => c.Leads)
    .HasForeignKey(l => l.CustomerId)
    .OnDelete(DeleteBehavior.Cascade);      // xoá khách hàng thì xoá lead — hợp lý

builder.Entity<Lead>()
    .HasOne(l => l.AssignedUser).WithMany(u => u.AssignedLeads)
    .HasForeignKey(l => l.AssignedUserId)
    .OnDelete(DeleteBehavior.Restrict);     // xoá nhân viên thì KHÔNG xoá lead

Muốn dùng SetNull thì khoá ngoại phải cho phép null:

public int? AssignedUserId { get; set; }
public User? AssignedUser { get; set; }
.OnDelete(DeleteBehavior.SetNull);   // nhân viên nghỉ việc -> lead thành chưa gán

Và việc chọn giữa hai cách này là một quyết định nghiệp vụ, không phải kỹ thuật:

Hành viNghĩa nghiệp vụ
CascadeLead thuộc về khách hàng, không có ý nghĩa nếu khách hàng biến mất
RestrictKhông cho xoá nhân viên khi còn lead được gán — buộc bàn giao trước
SetNullLead sống độc lập, chỉ mất thông tin ai phụ trách

Câu hỏi để chọn: "Nếu bản ghi cha biến mất, bản ghi con còn ý nghĩa không?" Lead của một khách hàng đã xoá thì không; lead của một nhân viên đã nghỉ thì có — nó vẫn là cơ hội kinh doanh thật.

Vì sao PostgreSQL không từ chối cùng cấu hình đó — đây là phần chính của bài:

-- PostgreSQL chấp nhận không phàn nàn
ALTER TABLE leads ADD CONSTRAINT fk_leads_customer
    FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE CASCADE;
ALTER TABLE leads ADD CONSTRAINT fk_leads_user
    FOREIGN KEY (assigned_user_id) REFERENCES users(id) ON DELETE CASCADE;

PostgreSQL thực thi ràng buộc khoá ngoại bằng trigger nội bộ, chạy tuần tự và đệ quy. Một dòng bị xoá hai lần theo hai đường không phải vấn đề: lần thứ hai đơn giản là không tìm thấy dòng nào để xoá. Không có gì không xác định, nên không cần cấm.

SQL Server:  cascade dạng tập hợp, không thứ tự -> nhiều đường = không xác định -> CẤM
PostgreSQL:  cascade dạng trigger, tuần tự      -> nhiều đường = an toàn        -> CHO PHÉP

Hệ quả thực tế — và đây là lý do bài này quan trọng với dự án đa database:

Một mô hình EF Core chạy tốt trên PostgreSQL có thể không migrate được trên SQL Server, dù code C# không đổi một dòng. Nếu dự án hỗ trợ cả hai, hãy thiết kế theo ràng buộc của SQL Server — nó là mẫu số chung.

Và đừng để EF Core chọn hộ. Khai báo OnDelete tường minh cho mọi quan hệ:

// Đặt trong OnModelCreating, sau khi mọi cấu hình đã chạy
foreach (var fk in modelBuilder.Model.GetEntityTypes().SelectMany(e => e.GetForeignKeys()))
{
    if (fk.DeleteBehavior == DeleteBehavior.Cascade && !fk.IsOwnership)
        Console.WriteLine($"Cascade: {fk.DeclaringEntityType.ShortName()} -> {fk.PrincipalEntityType.ShortName()}");
}

Chạy một lần và đọc danh sách — bạn sẽ thấy vài đường cascade mà bạn không hề chủ ý tạo ra. Mỗi đường trong đó là một cách để DELETE xoá nhiều hơn bạn tưởng.

Bài 3 — Bảng nối có dữ liệu​

Bắt đầu với many-to-many không bảng nối tường minh, rồi chuyển sang có TaggedAt và TaggedBy. Ghi lại migration sinh ra và số chỗ phải sửa trong code.

Tiêu chí hoàn thành: bạn nêu được vì sao nên khai báo bảng nối tường minh ngay từ đầu, ngay cả khi chưa có cột phụ nào.

Gợi ý và lời giải — Bài 3

Gợi ý. So sánh chi phí của hai việc: viết thêm một class lúc đầu, và đổi mọi chỗ gọi sáu tháng sau.

Lời giải — điểm xuất phát, many-to-many ngầm:

public class Lead   { public List<Tag>  Tags  { get; set; } = new(); }
public class Tag    { public List<Lead> Leads { get; set; } = new(); }
builder.Entity<Lead>()
    .HasMany(l => l.Tags).WithMany(t => t.Leads)
    .UsingEntity(j => j.ToTable("LeadTags"));

EF Core tự sinh bảng nối, và code dùng nó rất gọn:

lead.Tags.Add(tag);
lead.Tags.Remove(tag);
var soLead = await _db.Tags.Where(t => t.Id == id).SelectMany(t => t.Leads).CountAsync(ct);

Sau khi thêm hai cột — bảng nối tường minh:

public class LeadTag
{
    public int      LeadId   { get; set; }
    public Lead     Lead     { get; set; } = null!;
    public int      TagId    { get; set; }
    public Tag      Tag      { get; set; } = null!;
    public DateTime TaggedAt { get; set; }
    public string   TaggedBy { get; set; } = null!;
}

public class Lead { public List<LeadTag> LeadTags { get; set; } = new(); }
public class Tag  { public List<LeadTag> LeadTags { get; set; } = new(); }
builder.Entity<LeadTag>(b =>
{
    b.HasKey(lt => new { lt.LeadId, lt.TagId });
    b.HasOne(lt => lt.Lead).WithMany(l => l.LeadTags).HasForeignKey(lt => lt.LeadId);
    b.HasOne(lt => lt.Tag ).WithMany(t => t.LeadTags).HasForeignKey(lt => lt.TagId);
});

Migration sinh ra — và đây là chỗ đáng chú ý nhất:

migrationBuilder.AddColumn<DateTime>(
    name: "TaggedAt", table: "LeadTags", nullable: false,
    defaultValue: new DateTime(1, 1, 1, 0, 0, 0, 0, DateTimeKind.Unspecified));

migrationBuilder.AddColumn<string>(
    name: "TaggedBy", table: "LeadTags", nullable: false, defaultValue: "");

Bảng không bị tạo lại — EF Core nhận ra đây vẫn là bảng LeadTags và chỉ thêm cột. Dữ liệu cũ còn nguyên, nhưng mang giá trị mặc định vô nghĩa: TaggedAt bằng năm 0001 và TaggedBy bằng chuỗi rỗng.

Nếu bản ghi cũ phải mang giá trị hợp lý, bạn phải tự viết:

migrationBuilder.Sql(@"
    UPDATE LeadTags
    SET TaggedAt = (SELECT CreatedAt FROM Leads WHERE Leads.Id = LeadTags.LeadId),
        TaggedBy = 'he-thong'
    WHERE TaggedAt = '0001-01-01'");

Số chỗ phải sửa trong code — phần đắt nhất. Mọi chỗ chạm tới Tags đều đổi:

// Trước                          | Sau
lead.Tags.Add(tag);               // lead.LeadTags.Add(new LeadTag {
                                  //     TagId = tag.Id, TaggedAt = now, TaggedBy = userId });

lead.Tags.Remove(tag);            // var lt = lead.LeadTags.First(x => x.TagId == tag.Id);
                                  // lead.LeadTags.Remove(lt);

lead.Tags.Any(t => t.Name == "x") // lead.LeadTags.Any(lt => lt.Tag.Name == "x")

.Include(l => l.Tags)             // .Include(l => l.LeadTags).ThenInclude(lt => lt.Tag)

.SelectMany(t => t.Leads)         // .SelectMany(t => t.LeadTags).Select(lt => lt.Lead)

Trên một dự án CRM cỡ vừa, con số điển hình là 20–40 chỗ: service, query handler, mapping profile, seeder, và test. Không chỗ nào khó, nhưng mỗi chỗ phải đọc và hiểu lại, và không có công cụ nào tự làm được vì phép biến đổi không thuần tuý cơ học — Add cần giá trị cho hai cột mới, lấy từ đâu là quyết định của bạn.

Vì sao nên khai báo tường minh ngay từ đầu. Vì câu hỏi thật không phải "bảng nối này có cần cột phụ không?" mà là "sau này nó có bao giờ cần không?". Và với quan hệ many-to-many trong hệ thống nghiệp vụ, câu trả lời gần như luôn là có:

LeadTag        -> ai gắn, lúc nào
UserRole       -> gán từ bao giờ, hết hạn khi nào, ai duyệt
ProductCategory-> thứ tự hiển thị, có phải danh mục chính không
OrderPromotion -> áp dụng lúc nào, giảm bao nhiêu

Trường hợp thật sự không bao giờ cần cột phụ rất hiếm, vì bản thân việc hai thực thể được liên kết đã là một sự kiện nghiệp vụ — và sự kiện thì có thời điểm và có người thực hiện.

Cái giá của việc khai báo tường minh ngay từ đầu:

  • Thêm một class khoảng 10 dòng.
  • Code gọi dài hơn một chút: lead.LeadTags.Add(new LeadTag { TagId = id }) thay vì lead.Tags.Add(tag).

Cái giá của việc đổi sau: 20–40 chỗ sửa, một migration thêm cột với dữ liệu cũ mang giá trị vô nghĩa, và một script UPDATE phải nghĩ ra giá trị hợp lý cho quá khứ.

Một cách dung hoà — giữ cả hai, để code đọc vẫn gọn:

public class Lead
{
    public List<LeadTag> LeadTags { get; set; } = new();

    // Không ánh xạ xuống database, chỉ để đọc cho tiện
    [NotMapped]
    public IEnumerable<Tag> Tags => LeadTags.Select(lt => lt.Tag);
}

Nhưng cẩn thận: Tags ở đây không dùng được trong LINQ to Entities vì EF Core không dịch được thuộc tính [NotMapped]. Nó chỉ hoạt động sau khi dữ liệu đã ở trong bộ nhớ. Dùng nó trong Where sẽ ném exception lúc chạy — nên nếu chọn cách này, hãy đặt tên cho rõ, chẳng hạn TagsDaNap, để không ai nhầm.

Tự kiểm tra​

Frequently asked questions

Vì sao nên khai khoá ngoại tường minh trong entity?

Nó cho phép gán quan hệ mà không cần nạp entity cha, đọc được khoá ngoại mà không cần Include, lọc trực tiếp theo khoá ngoại, và map thẳng sang DTO. Không có nó thì EF dùng shadow property, chỉ truy cập được qua API của change tracker.

EF Core suy ra quan hệ required hay optional từ đâu?

Từ tính nullable của khoá ngoại: kiểu không nullable là required với DeleteBehavior mặc định Cascade, kiểu nullable là optional với mặc định ClientSetNull. Nghĩa là đổi int thành int nullable sẽ âm thầm đổi hành vi xoá.

DeleteBehavior ảnh hưởng ở những tầng nào?

Cả EF Core lẫn database. Phần hay bị bỏ qua là EF Core tự sinh lệnh xoá cho các entity con đã nạp vào change tracker, kể cả khi database không có cascade. Nên xoá một cha có 200 con đã Include sẽ sinh 201 lệnh thay vì một.

Vì sao Include trước khi xoá lại làm chậm?

Vì nó nạp các entity con vào change tracker, và EF Core sẽ sinh một lệnh DELETE riêng cho từng cái thay vì để database xử lý cascade. Không Include thì EF chỉ xoá entity cha và database lo phần còn lại; với xoá hàng loạt thì dùng ExecuteDeleteAsync.

Chu trình cascade gây vấn đề gì?

SQL Server từ chối tạo cấu hình có nhiều đường cascade cùng tới một bảng, và lỗi chỉ xuất hiện lúc chạy migration chứ không phải lúc biên dịch. Cách xử lý là chọn một đường cascade, những đường còn lại dùng NoAction hoặc SetNull, và lựa chọn đó thường phản ánh đúng nghiệp vụ.

Khi nào cần bảng nối tường minh cho many-to-many?

Ngay khi quan hệ mang dữ liệu riêng, ví dụ ai gắn tag và lúc nào. Dùng UsingEntity với kiểu bảng nối thì bạn giữ được cả navigation trực tiếp lẫn truy cập dữ liệu của bảng nối. Nếu có khả năng quan hệ sẽ mang dữ liệu thì nên khai tường minh ngay từ đầu.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Cascade khiến EF tự xoá entity đã nạp — Include trước khi xoá là phản tác dụng.
  2. Nullable của khoá ngoại quyết định hành vi xoá mặc định. Khai rõ để không bất ngờ.
  3. Self-reference phải dùng Restrict, nếu không một lệnh xoá có thể quét cả cây.
