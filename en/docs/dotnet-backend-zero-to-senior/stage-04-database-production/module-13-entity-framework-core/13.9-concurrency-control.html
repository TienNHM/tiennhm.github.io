13.9 — 8. Concurrency Control

Summary

Không có concurrency control, mặc định là last write wins: hai người cùng mở một bản ghi, người lưu sau ghi đè thay đổi của người trước và không ai biết. EF Core phát hiện điều đó bằng cách đưa concurrency token vào mệnh đề WHERE của lệnh UPDATE — nếu 0 dòng bị ảnh hưởng thì ai đó đã sửa trước, và EF ném DbUpdateConcurrencyException. Ba điểm quan trọng: ROWVERSION của SQL Server tự đổi mỗi lần ghi, nên nó bắt được cả thay đổi từ ngoài ứng dụng; ExecuteUpdateAsync bỏ qua hoàn toàn cơ chế này; và với bộ đếm, cập nhật nguyên tử không cần đọc trước giải quyết vấn đề tốt hơn mọi chiến lược xử lý xung đột.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Cấu hình concurrency token cho SQL Server và PostgreSQL.
  • Chọn giữa ba chiến lược xử lý xung đột.
  • Trả lỗi 409 hữu ích cho client.
  • Biết khi nào nên tránh xung đột thay vì xử lý nó.
  • Kiểm thử hành vi đồng thời.

Nội dung bài học​

13.9.1 — Vấn đề​

t=0   An   doc Lead #42 (Value = 100)
t=1   Binh doc Lead #42 (Value = 100)
t=2   An   luu Value = 150
t=3   Binh luu Value = 200        <- ghi de thay doi cua An

Đây là lost update, và nó xảy ra im lặng. Không có lỗi, không có log, và An chỉ phát hiện khi mở lại bản ghi.

Với dữ liệu tài chính hoặc tồn kho, đó là lỗi nghiêm trọng.

13.9.2 — Concurrency token​

// SQL Server — ROWVERSION tu dong doi moi lan ghi
public byte[] RowVersion { get; set; } = [];

builder.Property(c => c.RowVersion).IsRowVersion();
// PostgreSQL — dung cot he thong xmin
builder.UseXminAsConcurrencyToken();
// Bat ky provider — token thu cong
public Guid Version { get; set; }

builder.Property(c => c.Version).IsConcurrencyToken();
// Phai TU cap nhat moi lan sua

IsRowVersion() mạnh hơn hai cách kia ở một điểm: database tự đổi giá trị, nên nó bắt được cả thay đổi từ script thủ công hay một ứng dụng khác. Token thủ công chỉ đổi khi code của bạn nhớ đổi.

EF Core sinh:

UPDATE Leads SET Value = @p0, Status = @p1
WHERE Id = @p2 AND RowVersion = @p3;      -- token trong WHERE

-- 0 dong bi anh huong => DbUpdateConcurrencyException

Không nhất thiết dùng ROWVERSION. Bất kỳ cột nào cũng làm concurrency token được:

builder.Property(p => p.Stock).IsConcurrencyToken();

Khi đó WHERE chứa Stock = @giá_trị_gốc, nên chỉ xung đột trên chính cột đó mới bị phát hiện. Hai người sửa hai cột khác nhau vẫn thành công cả hai — thường là điều bạn muốn.

13.9.3 — Ba chiến lược​

try
{
    await db.SaveChangesAsync(ct);
}
catch (DbUpdateConcurrencyException ex)
{
    var entry = ex.Entries.Single();
    var databaseValues = await entry.GetDatabaseValuesAsync(ct);

    if (databaseValues is null)
        return Result.Fail("Bản ghi đã bị xoá bởi người dùng khác");

    // ... xu ly theo mot trong ba chien luoc
}

1. Client wins — ghi đè, chỉ cập nhật token:

entry.OriginalValues.SetValues(databaseValues);
await db.SaveChangesAsync(ct);

Đơn giản nhưng mất thay đổi của người kia. Chỉ đúng khi người dùng có thẩm quyền cao hơn hoặc dữ liệu không quan trọng.

2. Store wins — bỏ thay đổi của mình:

await entry.ReloadAsync(ct);
return Result.Fail("Bản ghi đã thay đổi, vui lòng thử lại");

An toàn nhưng người dùng mất công nhập lại.

3. Merge có kiểm soát — trả cả hai giá trị để người dùng quyết định:

var conflicts = new List<FieldConflict>();

foreach (var property in entry.Metadata.GetProperties())
{
    var proposed = entry.Property(property.Name).CurrentValue;
    var current  = databaseValues[property];
    var original = entry.Property(property.Name).OriginalValue;

    // CHI bao xung dot khi CA HAI cung sua mot truong
    if (!Equals(proposed, original) && !Equals(current, original))
        conflicts.Add(new FieldConflict(property.Name, original, proposed, current));
}

return Result.Conflict(conflicts);

Điều kiện trong if là phần tinh tế: nếu bạn sửa Value còn người kia sửa Status, không có xung đột thật — chỉ cần gộp cả hai. Chỉ khi cả hai cùng sửa một trường mới cần người dùng quyết định.

Trả về HTTP 409 Conflict kèm chi tiết:

return Conflict(new ProblemDetails
{
    Status = StatusCodes.Status409Conflict,
    Title = "Bản ghi đã được người khác cập nhật",
    Extensions = { ["conflicts"] = conflicts }
});

Đây là đúng mã trạng thái cho tình huống này (bài 8.5).

13.9.4 — Truyền token qua API​

Với ứng dụng web, client không giữ DbContext giữa hai request — nên token phải đi qua API:

public sealed record UpdateLeadRequest
{
    public required string Title { get; init; }
    public required decimal Value { get; init; }
    public required string RowVersion { get; init; }    // Base64
}
[HttpPut("{id:int}")]
public async Task<IActionResult> Update(int id, UpdateLeadRequest request, CancellationToken ct)
{
    var lead = await db.Leads.FirstOrDefaultAsync(l => l.Id == id, ct);
    if (lead is null) return NotFound();

    // Gan gia tri GOC ma client da thay
    db.Entry(lead).Property(l => l.RowVersion).OriginalValue =
        Convert.FromBase64String(request.RowVersion);

    lead.Title = request.Title;
    lead.Value = request.Value;

    try
    {
        await db.SaveChangesAsync(ct);
        return NoContent();
    }
    catch (DbUpdateConcurrencyException)
    {
        return Conflict(...);
    }
}

Dòng OriginalValue là mấu chốt: không có nó, EF dùng giá trị vừa đọc từ database làm token — và kiểm tra luôn thành công, vì bạn vừa đọc xong. Xung đột không bao giờ được phát hiện.

Cách chuẩn hơn về mặt HTTP là dùng ETag và If-Match (bài 9.8):

GET /api/v1/leads/42
ETag: "AAAAAAAAB9E="

PUT /api/v1/leads/42
If-Match: "AAAAAAAAB9E="

Thiếu If-Match thì trả 428 Precondition Required; token không khớp thì trả 412 Precondition Failed.

13.9.5 — ExecuteUpdate bỏ qua tất cả​

// KHONG kiem tra concurrency token
await db.Leads.Where(l => l.Id == 42)
              .ExecuteUpdateAsync(s => s.SetProperty(l => l.Value, 200), ct);

ExecuteUpdateAsync sinh UPDATE ... WHERE Id = 42 — không có token trong WHERE (bài 13.8). Nó luôn thành công và luôn ghi đè.

Cần kiểm tra thì đưa token vào Where thủ công:

var affected = await db.Leads
    .Where(l => l.Id == 42 && l.RowVersion == expectedVersion)
    .ExecuteUpdateAsync(s => s.SetProperty(l => l.Value, 200), ct);

if (affected == 0) return Result.Conflict();

13.9.6 — Tránh xung đột thay vì xử lý nó​

Với bộ đếm và số dư, cách tốt nhất là không đọc trước:

// KEM — doc, sua, luu. Co the xung dot.
var product = await db.Products.FindAsync([id], ct);
product.Stock -= quantity;
await db.SaveChangesAsync(ct);

// TOT — mot cau lenh nguyen tu, kiem tra ngay trong WHERE
var affected = await db.Products
    .Where(p => p.Id == id && p.Stock >= quantity)
    .ExecuteUpdateAsync(s => s.SetProperty(p => p.Stock, p => p.Stock - quantity), ct);

if (affected == 0) return Result.Fail("Không đủ hàng");

Không có khoảng trống giữa đọc và ghi, nên không có xung đột nào để xử lý — đúng mẫu ở bài 12.7.

Với thao tác quan trọng mà thử lại không chấp nhận được, dùng pessimistic lock:

var product = await db.Products
    .FromSql($"SELECT * FROM Products WITH (UPDLOCK, ROWLOCK) WHERE Id = {id}")
    .FirstAsync(ct);

Nhưng nhớ nó mở ra rủi ro deadlock, và phải nằm trong transaction.

13.9.7 — Kiểm thử​

[Fact]
public async Task ConcurrentUpdate_ShouldThrowConcurrencyException()
{
    await using var ctx1 = _factory.CreateDbContext();
    await using var ctx2 = _factory.CreateDbContext();

    var lead1 = await ctx1.Leads.FirstAsync(l => l.Id == 42);
    var lead2 = await ctx2.Leads.FirstAsync(l => l.Id == 42);   // CUNG ban ghi

    lead1.Value = 150;
    await ctx1.SaveChangesAsync();          // thanh cong

    lead2.Value = 200;
    await Assert.ThrowsAsync<DbUpdateConcurrencyException>(
        () => ctx2.SaveChangesAsync());     // xung dot
}

Hai DbContext riêng là điều kiện bắt buộc: cùng một context thì identity map trả về cùng một instance, và không có xung đột nào xảy ra (bài 13.2).

Bài test này phải chạy trên database thật — InMemory provider không có ROWVERSION (bài 9.9).

13.9.8 — Rà lại code của bạn​

Danh sách rà soát concurrency

  • •Mọi entity người dùng sửa đồng thời đều có concurrency token.
  • •SQL Server dùng IsRowVersion để database tự đổi giá trị.
  • •DbUpdateConcurrencyException được bắt và xử lý, không để thành lỗi 500.
  • •Chiến lược xử lý xung đột được chọn có chủ đích, không mặc định client wins.
  • •Chỉ báo xung đột khi cả hai bên cùng sửa một trường.
  • •API trả 409 kèm giá trị hiện tại để client quyết định.
  • •Token được truyền qua API và gán vào OriginalValue.
  • •ExecuteUpdate có token trong Where nếu cần kiểm tra concurrency.
  • •Bộ đếm và tồn kho dùng cập nhật nguyên tử, không đọc rồi ghi.
  • •Có test đồng thời dùng hai DbContext riêng trên database thật.

Bài tập áp dụng​

  1. Lost update. Với entity không có concurrency token, mô phỏng hai người cùng sửa và xác nhận thay đổi của người đầu biến mất không có lỗi nào. Thêm IsRowVersion và kiểm chứng.

  2. Token không được truyền. Cài endpoint PUT không gán OriginalValue, gửi token cũ, và xác nhận xung đột không được phát hiện. Thêm dòng gán và kiểm chứng.

  3. Cập nhật nguyên tử. Cài trừ kho bằng đọc-sửa-lưu, bắn 100 request đồng thời trừ 1 đơn vị từ kho 50, và đếm số đơn thành công. So sánh với ExecuteUpdateAsync có điều kiện trong Where.

Tự kiểm tra​

Frequently asked questions

Lost update xảy ra thế nào?

Hai người cùng đọc một bản ghi, người lưu sau ghi đè thay đổi của người trước. Nó xảy ra im lặng, không có lỗi và không có log, nên người bị ghi đè chỉ phát hiện khi mở lại bản ghi.

EF Core phát hiện xung đột bằng cách nào?

Nó đưa concurrency token vào mệnh đề WHERE của lệnh UPDATE. Nếu không dòng nào bị ảnh hưởng thì ai đó đã sửa trước, và EF ném DbUpdateConcurrencyException.

Vì sao IsRowVersion mạnh hơn token thủ công?

Vì database tự đổi giá trị mỗi lần ghi, nên nó bắt được cả thay đổi từ script thủ công hay từ một ứng dụng khác. Token thủ công chỉ đổi khi code của bạn nhớ đổi.

Khi nào mới thật sự là xung đột cần người dùng quyết định?

Chỉ khi cả hai bên cùng sửa cùng một trường. Nếu bạn sửa một trường còn người kia sửa trường khác thì chỉ cần gộp cả hai, không có gì để hỏi. Điều kiện kiểm tra là giá trị đề xuất khác giá trị gốc và giá trị trong database cũng khác giá trị gốc.

Vì sao phải gán OriginalValue khi nhận token từ API?

Vì không có nó, EF dùng giá trị vừa đọc từ database làm token, nên kiểm tra luôn thành công và xung đột không bao giờ được phát hiện. Phải gán giá trị gốc mà client đã thấy vào OriginalValue của thuộc tính token.

Cách tốt nhất cho bộ đếm và tồn kho là gì?

Không đọc trước, mà dùng một câu lệnh cập nhật nguyên tử với điều kiện kiểm tra ngay trong WHERE, rồi xem số dòng bị ảnh hưởng. Không có khoảng trống giữa đọc và ghi nên không có xung đột nào để xử lý.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Không có token thì mặc định là ghi đè im lặng.
  2. Gán OriginalValue khi token đến từ client — nếu không, kiểm tra luôn thành công.
  3. Bộ đếm nên tránh xung đột bằng cập nhật nguyên tử, không xử lý xung đột.
