3.4 — Checklist an toàn khi làm Git

Summary

Vì commit là bất biến, gần như mọi sai lầm trong Git đều hoàn tác được — git reflog ghi lại mọi lần HEAD di chuyển và giữ trong 90 ngày, kể cả những commit không còn nhánh nào trỏ tới. Điều đáng học không phải là "cẩn thận", mà là biết chính xác ba thứ không cứu được: thay đổi chưa commit bị reset --hard xoá, file chưa theo dõi bị clean -fd xoá, và lịch sử chung bị push --force ghi đè trên máy người khác. Mọi thứ khác đều có công thức khôi phục, và bài này liệt kê chúng.

Mục tiêu bài học​

Sau bài này bạn có thể:

  • Dùng git reflog để tìm lại commit sau một thao tác sai.
  • Nêu ba trường hợp thực sự mất dữ liệu và cách phòng.
  • Chọn --force-with-lease thay cho --force và giải thích khác biệt.
  • Khôi phục đúng cho bốn tình huống hay gặp nhất.
  • Dùng stash và worktree để chuyển việc mà không mất thao tác dở.

Nội dung bài học​

3.4.1 — Lưới an toàn: git reflog​

git reflog
# a1b2c3d HEAD@{0}: reset: moving to HEAD~3
# 9f8e7d6 HEAD@{1}: commit: feat: them bao cao doanh thu   ← tưởng đã mất
# 5c4b3a2 HEAD@{2}: commit: fix: sua loi lam tron

reflog ghi lại mọi lần HEAD di chuyển trên máy bạn: commit, checkout, reset, rebase, merge. Mặc định giữ 90 ngày.

Quay về bất kỳ điểm nào trong đó:

git reset --hard 9f8e7d6        # về đúng trạng thái commit đó
# hoặc an toàn hơn:
git branch cuu-ho 9f8e7d6       # tạo nhánh mới trỏ vào, không đụng nhánh hiện tại

Cách thứ hai nên là phản xạ: tạo nhánh trước, xem xét sau. Nó không phá gì cả.

Lưu ý quan trọng: reflog là cục bộ. Nó không được đẩy lên, và không cứu được thứ bạn chưa bao giờ commit.

3.4.2 — Ba thứ thật sự không cứu được​

1. Thay đổi chưa commit bị git reset --hard xoá.

git reset --hard HEAD     # mọi sửa đổi chưa commit biến mất, không hỏi lại

Không có bản sao nào. reflog không giúp được vì chưa từng có commit nào.

2. File chưa theo dõi bị git clean -fd xoá.

git clean -fd             # xoá mọi file và thư mục Git chưa theo dõi

Git chưa bao giờ biết những file đó tồn tại. Luôn chạy thử trước:

git clean -nd             # -n = chỉ LIỆT KÊ, không xoá

3. Lịch sử chung bị push --force ghi đè.

Commit của bạn vẫn còn trong reflog của bạn. Nhưng nếu đồng nghiệp đã pull phiên bản cũ và đang làm việc trên đó, một cú force push đặt họ vào trạng thái phân kỳ rất khó gỡ.

3.4.3 — --force-with-lease thay cho --force​

git push --force              # NGUY HIỂM: đè lên mọi thứ trên remote
git push --force-with-lease   # AN TOÀN: từ chối nếu remote đã có commit mới

--force-with-lease kiểm tra rằng remote vẫn đang ở đúng chỗ mà bạn nghĩ. Nếu ai đó vừa push thêm gì đó, lệnh thất bại thay vì xoá công sức của họ.

Không có lý do nào để dùng --force khi đã có --force-with-lease. Hãy đặt nó thành thói quen — hoặc thành alias:

git config --global alias.pushf "push --force-with-lease"

3.4.4 — Bốn công thức khôi phục​

Lỡ commit vào sai nhánh

# Đang ở main, lẽ ra phải ở feature/abc
git branch feature/abc        # tạo nhánh giữ commit lại
git reset --hard HEAD~1       # đưa main về trạng thái trước commit
git checkout feature/abc      # sang nhánh đúng, commit vẫn còn

Lỡ reset --hard và mất commit

git reflog                    # tìm mã commit trước khi reset
git reset --hard <mã đó>

Lỡ xoá nhánh chưa merge

git reflog                    # tìm commit cuối của nhánh đã xoá
git branch <tên-nhánh> <mã>

Rebase hỏng giữa chừng

git rebase --abort            # quay về trạng thái trước khi rebase
# hoặc, nếu đã xong mà kết quả sai:
git reflog                    # tìm ORIG_HEAD hoặc commit trước rebase
git reset --hard <mã đó>

3.4.5 — Cất việc dở: stash và worktree​

Tình huống quen thuộc: đang làm dở một tính năng thì có lỗi khẩn cấp cần sửa ngay.

# Cách 1 — stash: cất tạm thay đổi
git stash push -m "dang lam bao cao"
git checkout -b hotfix/loi-khan-cap
# ... sửa, commit, push ...
git checkout feature/bao-cao
git stash pop                 # lấy lại thay đổi

Ba điều cần biết về stash:

  • git stash list xem những gì đang cất.
  • pop lấy ra và xoá khỏi danh sách; apply lấy ra mà giữ lại.
  • Mặc định stash không cất file chưa theo dõi. Thêm -u để cất cả chúng — đây là chỗ hay làm người ta mất file.
# Cách 2 — worktree: hai thư mục, hai nhánh, cùng một kho
git worktree add ../hotfix hotfix/loi-khan-cap
cd ../hotfix                  # thư mục riêng, nhánh riêng
# ... sửa xong ...
cd -
git worktree remove ../hotfix

worktree tốt hơn stash khi việc khẩn cấp mất nhiều thời gian: bạn không phải đụng gì tới thư mục đang làm dở, và cả hai vẫn dùng chung một kho nên không tốn thêm dung lượng đáng kể.

3.4.6 — Lệnh nguy hiểm, xếp theo mức độ​

LệnhRủi roTrước khi chạy
git clean -fdMất vĩnh viễn file chưa theo dõiChạy git clean -nd xem trước
git reset --hardMất vĩnh viễn thay đổi chưa commitgit stash trước
git checkout -- <file>Mất vĩnh viễn sửa đổi trong file đóXem git diff trước
git push --forceĐè lịch sử người khácDùng --force-with-lease
git rebase trên nhánh chungMọi người phân kỳChỉ rebase nhánh riêng của bạn
git filter-repoViết lại toàn bộ lịch sửSao lưu kho trước

Quy tắc bao trùm: ba lệnh đầu là ba lệnh duy nhất phá được dữ liệu chưa commit. Nhớ ba cái tên đó là đủ để cẩn thận đúng chỗ.

3.4.7 — Danh sách an toàn​

Thói quen an toàn với Git

  • •Commit sớm và thường xuyên — commit là thứ duy nhất reflog cứu được.
  • •Chạy git status trước mọi lệnh có chữ reset, clean hay checkout.
  • •Luôn dùng git clean -nd trước khi dùng git clean -fd.
  • •Luôn dùng --force-with-lease thay cho --force.
  • •Chỉ rebase nhánh chưa ai khác dùng.
  • •Khi hoảng, tạo nhánh cứu hộ trước rồi mới xử lý tiếp.
  • •Dùng git stash -u khi cần cất cả file chưa theo dõi.
  • •Trước thao tác lớn, tạo một nhánh đánh dấu điểm quay về.

Bài tập áp dụng​

Bài 1 — Tự làm mất rồi tự cứu​

Trên một kho thử: tạo ba commit, chạy git reset --hard HEAD~3, rồi dùng reflog khôi phục đủ cả ba. Ghi lại từng lệnh đã dùng.

Tiêu chí hoàn thành: khôi phục xong, git log hiện lại đủ ba commit với đúng mã băm cũ.

Gợi ý và lời giải — Bài 1

Gợi ý. reset --hard chỉ dời con trỏ nhánh. Ba commit vẫn nằm trong kho, chỉ là không còn tên nào trỏ tới chúng nữa. reflog ghi lại mọi lần HEAD di chuyển, nên nó vẫn nhớ vị trí cũ.

Lời giải.

mkdir thu && cd thu && git init -q
echo 1 > f.txt && git add . && git commit -q -m "commit 1"
echo 2 >> f.txt && git commit -q -am "commit 2"
echo 3 >> f.txt && git commit -q -am "commit 3"

git log --oneline
# c3c3c3c commit 3
# b2b2b2b commit 2
# a1a1a1a commit 1

git reset --hard HEAD~3
git log --oneline
# (trống — nhánh đã lùi về trước commit đầu tiên)

Khôi phục:

git reflog
# a1a1a1a HEAD@{0}: reset: moving to HEAD~3
# c3c3c3c HEAD@{1}: commit: commit 3
# b2b2b2b HEAD@{2}: commit: commit 2
# a1a1a1a HEAD@{3}: commit (initial): commit 1

git reset --hard c3c3c3c        # hoặc: git reset --hard HEAD@{1}
git log --oneline               # đủ ba commit, đúng mã băm cũ

Vì sao mã băm không đổi. Đây là điểm đáng chú ý. Bạn không "tạo lại" ba commit — chúng chưa bao giờ biến mất. Bạn chỉ trỏ nhánh main về lại commit c3c3c3c, và vì commit là bất biến (xem bài 3.2) nên toàn bộ chuỗi cha con phía sau nó còn nguyên.

Hai cách viết, và khi nào dùng cái nào:

CáchƯuNhược
git reset --hard c3c3c3cChỉ đích danh, không đổi theo thời gianPhải sao chép mã băm
git reset --hard HEAD@{1}Gõ nhanhChỉ số dịch chuyển mỗi khi HEAD di chuyển thêm

Sau khi chạy vài lệnh nữa, HEAD@{1} đã trỏ vào chỗ khác. Vì vậy khi đang xử lý sự cố thật, hãy dùng mã băm.

Commit "mồ côi" sống được bao lâu. Commit không còn tham chiếu nào sẽ bị trình dọn rác của Git xoá, nhưng không phải ngay. Mặc định:

git config gc.reflogExpire          # 90 ngày — mục reflog còn tham chiếu
git config gc.reflogExpireUnreachable  # 30 ngày — mục reflog đã mất tham chiếu

Nghĩa là bạn có khoảng 30 ngày để cứu một commit bị mất theo cách này. Quá đủ cho mọi tình huống thực tế — miễn là bạn biết reflog tồn tại, và đó là toàn bộ mục đích của bài tập này.

Một lệnh nữa đáng biết. Khi reflog không đủ — ví dụ commit nằm ở một nhánh đã xoá mà bạn không nhớ tên — dùng:

git fsck --lost-found

Nó liệt kê mọi đối tượng không còn tham chiếu trong kho.

Bài 2 — Chứng minh giới hạn của reflog​

Sửa một file nhưng không commit, chạy git reset --hard. Thử tìm lại thay đổi đó bằng reflog. Giải thích vì sao không tìm được.

Tiêu chí hoàn thành: bạn nêu đúng điều kiện để reflog cứu được một thứ gì đó.

Gợi ý và lời giải — Bài 2

Gợi ý. reflog ghi lại lịch sử di chuyển của các tham chiếu — tức là của HEAD và các nhánh. Một thay đổi chưa commit thì chưa có tham chiếu nào trỏ tới nó. Vậy reflog có gì để ghi không?

Lời giải.

echo "dòng mới chưa commit" >> file.txt
git reset --hard -q
cat file.txt
# dòng 1              <- dòng vừa thêm đã mất

reflog sau đó không có mục nào cho thay đổi này. Nó chỉ có các mục ứng với lần commit gần nhất — và số mục không tăng lên sau thao tác reset --hard.

Vì sao. Git chỉ theo dõi những gì đã được đưa vào cơ sở dữ liệu đối tượng. Một thay đổi chỉ tồn tại trong thư mục làm việc thì chưa phải đối tượng Git nào cả — nó chỉ là byte trên đĩa. reset --hard ghi đè thư mục làm việc bằng nội dung của commit, và những byte đó mất vĩnh viễn.

Điều kiện để reflog cứu được. Chỉ một điều kiện, nhưng phải thoả: nội dung đó đã từng được đưa vào kho Git, dù chỉ là qua git add.

Đây là chi tiết đáng giá nhất của bài: git add đã đủ, không cần commit. Khi bạn git add, Git tạo một đối tượng blob trong kho. Blob đó không có tên trỏ tới, nhưng git fsck tìm được:

git fsck --lost-found
# dangling blob 1bd073f92aa619bab70244cf38d9c5c169357670

git cat-file -p 1bd073f   # đọc lại nội dung

Ba thứ reflog không cứu được:

Mất gìVì sao
Thay đổi chưa add bao giờChưa từng có đối tượng Git nào
File chưa được theo dõi, bị git clean -fd xoáGit chưa từng biết tới chúng
Nội dung trong stash đã stash drop quá lâuCũng là đối tượng mồ côi, bị dọn rác

Thói quen rút ra. Commit sớm và thường xuyên, kể cả commit dang dở với message tạm bợ. Lịch sử luôn dọn lại được bằng rebase -i hoặc --amend; công việc chưa commit thì không cứu lại được. Một commit wip xấu xí vẫn tốt hơn nhiều so với nửa ngày làm việc bốc hơi.

Cách khác để cất việc dở an toàn:

git stash push -m "dang lam bao cao"   # cất tạm, có tạo đối tượng Git
git stash list
git stash pop

stash tạo commit thật trong kho, nên nội dung được bảo vệ — khác hẳn với việc để thay đổi nằm trơ trong thư mục làm việc.

Bài 3 — So sánh hai kiểu force​

Trên một kho thử có hai bản clone: từ clone A push một commit, rồi từ clone B thử push --force và push --force-with-lease. Ghi lại thông báo khác nhau.

Tiêu chí hoàn thành: bạn xác nhận được rằng --force-with-lease bảo vệ commit của A, còn --force thì xoá nó.

Gợi ý và lời giải — Bài 3

Gợi ý. --force-with-lease so sánh trạng thái thật trên máy chủ với trạng thái mà máy bạn tưởng là đang có trên máy chủ (nhánh theo dõi origin/main). Hai thứ đó khác nhau khi ai đó vừa push mà bạn chưa fetch.

Lời giải — dựng kịch bản:

git init -q --bare central
git init -q A && cd A
echo base > f.txt && git add . && git commit -q -m "base"
git branch -M main && git remote add origin ../central && git push -q origin main

cd .. && git clone -q -b main central B      # B chụp lại trạng thái lúc này

cd A && echo a >> f.txt && git commit -q -am "commit tu A" && git push -q origin main
cd ../B && echo b >> f.txt && git commit -q -am "commit tu B"

Giờ B có một commit dựa trên trạng thái cũ, và chưa biết A đã push.

Kết quả thật của ba lệnh:

=========== B: git push (thường) ===========
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '.../central'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally.

=========== B: git push --force-with-lease ===========
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '.../central'

=========== B: git push --force ===========
 + 901b4ce...6ea9ab3 main -> main (forced update)

Trạng thái máy chủ sau mỗi lệnh:

Sau lệnhLịch sử trên central
push bị từ chốicommit tu A, base — nguyên vẹn
push --force-with-lease bị từ chốicommit tu A, base — vẫn nguyên vẹn
push --force thành côngcommit tu B, base — commit của A đã biến mất

Công việc của A bị xoá khỏi máy chủ, và A không nhận được cảnh báo nào.

Hai thông báo từ chối khác nhau ở đâu:

  • (fetch first) — máy chủ có commit mà bạn không có. Đây là cơ chế bảo vệ mặc định.
  • (stale info) — bạn cố ý ghi đè, nhưng Git phát hiện origin/main trên máy bạn đã lỗi thời so với máy chủ, nên từ chối.

Khác biệt tinh tế nhưng quan trọng: --force-with-lease không từ chối mọi lần ghi đè. Nó chỉ từ chối khi có người khác đã push kể từ lần fetch cuối của bạn. Nếu bạn rebase nhánh cá nhân của mình và không ai đụng vào, nó cho phép bình thường.

Vì sao đây là lựa chọn mặc định đúng. Sau khi rebase, bạn bắt buộc phải force push vì mã băm đã đổi. --force-with-lease cho bạn làm việc đó, đồng thời chặn đúng tình huống nguy hiểm là ghi đè lên công việc của người khác.

Đặt nó thành mặc định:

git config --global alias.pushf 'push --force-with-lease'

Một cái bẫy của --force-with-lease. Nếu bạn chạy git fetch ngay trước khi force push, nhánh theo dõi được cập nhật và --force-with-lease sẽ không còn thấy gì bất thường — nó cho qua, và commit của người khác vẫn bị xoá. Vì vậy đừng fetch rồi force push ngay; hãy nhìn git log origin/main trước xem có gì mới không.

Tự kiểm tra​

Frequently asked questions

git reflog cứu được những gì?

Nó ghi lại mọi lần HEAD di chuyển trên máy bạn — commit, checkout, reset, rebase, merge — và giữ trong 90 ngày. Nhờ đó tìm lại được commit sau khi reset nhầm, khôi phục nhánh đã xoá, hoặc quay về trước một lần rebase hỏng. Nhưng nó là dữ liệu cục bộ, không được đẩy lên, và chỉ cứu được thứ đã từng là commit.

Ba thứ nào thật sự không cứu được trong Git?

Thay đổi chưa commit bị git reset --hard xoá; file chưa được theo dõi bị git clean -fd xoá; và lịch sử chung bị push --force ghi đè trên máy người khác. Hai cái đầu mất vĩnh viễn vì Git chưa bao giờ lưu chúng. Cái thứ ba thì commit của bạn vẫn còn trong reflog, nhưng đồng nghiệp đã pull bản cũ sẽ rơi vào trạng thái phân kỳ khó gỡ.

--force-with-lease khác --force ở đâu?

--force đè lên remote bất kể có gì ở đó. --force-with-lease kiểm tra remote vẫn đang ở đúng vị trí bạn nghĩ; nếu ai đó vừa push thêm commit thì lệnh thất bại thay vì xoá công sức của họ. Không có lý do nào để dùng --force khi đã có --force-with-lease.

Lỡ commit vào sai nhánh thì xử lý thế nào?

Tạo nhánh đúng ngay tại vị trí hiện tại để giữ commit lại, rồi đưa nhánh sai về trạng thái trước commit bằng reset, sau đó chuyển sang nhánh đúng. Ba lệnh: git branch tên-đúng, git reset --hard HEAD~1, git checkout tên-đúng.

stash và worktree nên dùng cái nào?

Dùng stash khi việc xen ngang ngắn, vài phút là xong. Dùng worktree khi việc khẩn cấp mất nhiều thời gian, vì nó cho bạn một thư mục riêng với nhánh riêng mà không phải đụng gì tới thư mục đang làm dở. Cả hai dùng chung một kho nên worktree không tốn thêm dung lượng đáng kể.

Vì sao git stash hay làm người ta mất file?

Vì mặc định stash không cất file chưa được Git theo dõi. Người dùng tưởng đã cất hết rồi chuyển nhánh, và những file mới tạo vẫn nằm nguyên ở thư mục làm việc, dễ bị ghi đè hoặc bị clean xoá. Phải thêm tuỳ chọn -u để cất cả file chưa theo dõi.

Kết luận​

Ba điều đáng nhớ nhất:

  1. Commit sớm là hình thức bảo hiểm rẻ nhất. reflog chỉ cứu được thứ đã từng là commit.
  2. Chỉ ba lệnh phá được dữ liệu chưa commit: reset --hard, clean -fd, checkout -- <file>.
  3. Khi hoảng, tạo nhánh trước. git branch cuu-ho <mã> không phá gì và cho bạn thời gian suy nghĩ.
