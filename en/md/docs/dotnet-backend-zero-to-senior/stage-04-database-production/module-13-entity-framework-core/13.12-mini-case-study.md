# 13.12 — Mini case study

> Nguồn: https://tiennhm.io.vn/en/docs/dotnet-backend-zero-to-senior/stage-04-database-production/module-13-entity-framework-core/13.12-mini-case-study
> Migration xoá cột chứa dữ liệu thật trên production: vì sao EF Core sinh lệnh đó, và quy trình migration an toàn ba bước.

> Sự cố mất dữ liệu kinh điển với EF Core: đổi tên một thuộc tính từ `PhoneNumber` thành `Phone`, EF Core sinh migration **`DropColumn` + `AddColumn`** — và khi chạy trên production, **18.000 số điện thoại biến mất**. EF Core không làm sai: nó so sánh model mới với snapshot và thấy một cột biến mất, một cột xuất hiện. Nó **không có cách nào biết** đó là cùng một cột được đổi tên. Bài này trình bày **quy trình ba bước** để mọi migration đều an toàn, cách khôi phục khi đã lỡ chạy, và một luật cứng: **luôn đọc file migration trước khi commit** — vì lỗi này lộ ra rất rõ khi đọc, và hoàn toàn vô hình nếu không đọc.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Nhận ra migration nguy hiểm trước khi chạy.
- Đổi tên cột mà không mất dữ liệu.
- Áp dụng quy trình migration ba bước.
- Triển khai thay đổi schema không downtime.

## Nội dung bài học

### 13.13.1 — Sự cố

```csharp
// Đổi tên thuộc tính cho nhất quán
public class Customer
{
    public string PhoneNumber { get; set; }    // trước
    public string Phone { get; set; }          // sau
}
```

```bash
dotnet ef migrations add RenamePhoneNumber
```

```csharp
// File migration sinh ra
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropColumn(name: "PhoneNumber", table: "Customers");

    migrationBuilder.AddColumn<string>(
        name: "Phone", table: "Customers", nullable: true);
}
```

```
Chay tren production:
  DROP COLUMN PhoneNumber   -> 18.000 số điện thoại BIẾN MẤT
  ADD COLUMN Phone          -> cột mới, toàn NULL
```

Không có exception nào. Migration chạy **thành công**.

**EF Core không làm sai.** Nó so sánh model hiện tại với `ModelSnapshot` và thấy: một cột không còn, một cột mới xuất hiện. Nó không có cách nào biết đó là cùng một cột được đổi tên — thông tin đó chỉ nằm trong đầu bạn.

### 13.13.2 — Cách đúng: RenameColumn

```csharp
// Sửa thủ công file migration
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "PhoneNumber",
        table: "Customers",
        newName: "Phone");
}

protected override void Down(MigrationBuilder migrationBuilder)
{
    migrationBuilder.RenameColumn(
        name: "Phone",
        table: "Customers",
        newName: "PhoneNumber");
}
```

`RenameColumn` sinh `sp_rename` trên SQL Server hoặc `ALTER TABLE ... RENAME COLUMN` trên PostgreSQL — **giữ nguyên dữ liệu**.

**Đây là lý do phải đọc mọi file migration trước khi commit.** Lỗi này hiển hiện rõ ràng khi đọc `Up()`, và hoàn toàn vô hình nếu bạn chỉ chạy `dotnet ef migrations add` rồi commit.

### 13.13.3 — Bốn loại lệnh cần cảnh giác

| Lệnh | Rủi ro |
|---|---|
| `DropColumn` | **Mất dữ liệu cột đó** |
| `DropTable` | **Mất cả bảng** |
| `AlterColumn` thu hẹp kiểu | **Cắt cụt dữ liệu** — `nvarchar(200)` xuống `nvarchar(50)` |
| `AlterColumn` sang `NOT NULL` | **Thất bại** nếu có hàng `NULL` |

Hai loại cuối tinh vi hơn:

```csharp
// Thu hẹp kiểu — SQL Server CẮT dữ liệu dài hơn, không báo lỗi
migrationBuilder.AlterColumn<string>(
    name: "Note", table: "Leads", maxLength: 50, oldMaxLength: 2000);
```

```csharp
// Sang NOT NULL — thất bại nếu có hàng NULL, nên phải xử lý TRƯỚC
migrationBuilder.Sql("UPDATE Leads SET Status = 'New' WHERE Status IS NULL");
migrationBuilder.AlterColumn<string>(
    name: "Status", table: "Leads", nullable: false, oldNullable: true);
```

Thứ tự trong ví dụ thứ hai quan trọng: điền giá trị mặc định **trước**, rồi mới đổi ràng buộc.

### 13.13.4 — Quy trình ba bước

**Bước 1 — đọc và sửa file migration:**

```bash
dotnet ef migrations add TenMigration
cat Migrations/*_TenMigration.cs      # DOC KY, moi lan
```

Tìm bốn loại lệnh ở mục trên. Nếu thấy, dừng lại và hỏi: đây có đúng là điều mình muốn không?

**Bước 2 — sinh script SQL và xem lại:**

```bash
# Script tu migration hien tai len migration moi
dotnet ef migrations script MigrationTruoc MigrationMoi --output review.sql
```

Đây là **SQL thật** sẽ chạy trên database. Đọc nó là cách chắc chắn nhất để biết điều gì sắp xảy ra — đôi khi lệnh trông vô hại trong C# lại sinh ra SQL không như mong đợi.

**Bước 3 — thử trên bản sao production:**

```bash
# Khôi phục backup production vào môi trường staging
# Chạy script, đo thời gian, kiểm tra dữ liệu
sqlcmd -S staging -d CrmStaging -i review.sql
```

Bước này bắt được hai thứ mà môi trường phát triển không bao giờ bắt được: **thời gian chạy thật** (thêm index trên 10 triệu hàng có thể mất 20 phút và khoá bảng) và **dữ liệu thật vi phạm ràng buộc mới**.

### 13.13.5 — Thay đổi không downtime

Với bảng lớn đang phục vụ, đổi tên cột trong một bước vẫn gây gián đoạn: code cũ và code mới không cùng chạy được. Dùng **expand-contract**:

```
Giai đoạn 1 — MỞ RỘNG (tương thích ngược):
  1. Thêm cột Phone (nullable)
  2. Trien khai code GHI vao CA HAI cot, DOC tu PhoneNumber
  3. Chạy script chép dữ liệu: UPDATE Customers SET Phone = PhoneNumber

Giai đoạn 2 — CHUYỂN:
  4. Trien khai code DOC tu Phone, van ghi ca hai
  5. Theo dõi vài ngày, xác nhận không có vấn đề

Giai doan 3 — THU HEP:
  6. Trien khai code chi dung Phone
  7. Xoá cột PhoneNumber
```

Mỗi bước **tương thích ngược**, nên có thể triển khai dần và quay lại bất cứ lúc nào.

```csharp
// Giai doan 1-2: ghi ca hai cot
public string Phone
{
    get => _phone;
    set { _phone = value; PhoneNumber = value; }
}
```

Dài hơn nhiều so với một migration, nhưng đây là cách **duy nhất** thay đổi schema của bảng lớn mà không dừng hệ thống ([bài 12.9](../module-12-sql-deep-dive/12.8-database-migration-strategy.mdx)).

Cùng nguyên tắc áp dụng cho việc đổi kiểu cột, tách bảng, hoặc gộp bảng.

### 13.13.6 — Khi đã lỡ chạy

**Nếu phát hiện trong vài phút:**

```sql
-- SQL Server: khôi phục tới thời điểm TRƯỚC migration
RESTORE DATABASE CrmProduction_Temp
FROM DISABK = 'backup.bak'
WITH MOVE ..., NORECOVERY;

RESTORE LOG CrmProduction_Temp
FROM DISK = 'log.trn'
WITH STOPAT = '2026-09-24 14:29:00', RECOVERY;   -- ngay TRƯỚC migration

-- Rồi chép dữ liệu cột bị mất sang database thật
```

Khôi phục vào database **tạm** rồi chép dữ liệu sang — không khôi phục đè lên production, vì bạn sẽ mất mọi giao dịch từ sau thời điểm đó.

**Nếu phát hiện muộn** và không có point-in-time recovery, dữ liệu mất vĩnh viễn.

**Điều kiện tiên quyết:** database phải ở `FULL` recovery model và có sao lưu transaction log định kỳ. Không có nó, point-in-time recovery không khả thi — và đó là điều cần kiểm tra **trước** khi cần tới nó.

### 13.13.7 — Rà lại code của bạn

**Danh sách rà soát migration**

- [ ] Luôn đọc file migration trước khi commit.
- [ ] Đổi tên cột dùng RenameColumn, không để DropColumn và AddColumn.
- [ ] Tìm DropColumn, DropTable, AlterColumn thu hẹp trong mọi migration.
- [ ] Sinh script SQL và đọc trước khi chạy trên production.
- [ ] Thử migration trên bản sao dữ liệu production.
- [ ] Đã đo thời gian chạy migration trên dữ liệu cỡ thật.
- [ ] Thay đổi bảng lớn dùng expand-contract nhiều giai đoạn.
- [ ] Database ở FULL recovery model và có sao lưu log định kỳ.
- [ ] Đã kiểm tra khôi phục từ backup thật sự hoạt động.

## Bài tập áp dụng

#### Bài 1 — Tái hiện sự cố

Đổi tên một thuộc tính, sinh migration, và đọc file sinh ra để thấy `DropColumn`.

**Tiêu chí hoàn thành:** bạn nêu được **ba** dấu hiệu trong một file migration cho biết nó sẽ phá dữ liệu.

Gợi ý và lời giải — Bài 1

**Gợi ý.** Đọc tên phương thức trong `Up()`. Cái nào **lấy đi** thứ gì đó?

**Lời giải:**

```csharp
public class Lead
{
    public string Phone { get; set; } = null!;        // đổi thành PhoneNumber
}
```

```bash
dotnet ef migrations add DoiTenPhone
cat Migrations/*_DoiTenPhone.cs
```

```csharp
protected override void Up(MigrationBuilder migrationBuilder)
{
    migrationBuilder.DropColumn(name: "Phone", table: "Leads");

    migrationBuilder.AddColumn<string>(
        name: "PhoneNumber", table: "Leads", type: "nvarchar(max)",
        nullable: false, defaultValue: "");
}
```

EF Core có in một cảnh báo khi sinh migration này:

```text
An operation was scaffolded that may result in the loss of data.
Please review the migration for accuracy.
```

Dòng đó trôi qua trong hàng chục dòng output khác, và không dừng bất cứ thứ gì lại. Nó không làm CI đỏ, không cần ai xác nhận.

**Ba dấu hiệu một migration sẽ phá dữ liệu:**

**Dấu hiệu 1 — có `Drop` gì đó trong `Up()`:**

```csharp
migrationBuilder.DropColumn(...)
migrationBuilder.DropTable(...)
migrationBuilder.DropPrimaryKey(...)
```

Đơn giản nhất và nghiêm trọng nhất. Mọi `Drop` trong `Up()` phải được một người thứ hai đọc.

Ngoại lệ hợp lệ duy nhất: xoá một cột mà bạn **chắc chắn** không còn dữ liệu cần giữ — và cách để chắc chắn là chạy `SELECT COUNT(*) WHERE <cột> IS NOT NULL` trên production trước, không phải là tin vào trí nhớ.

**Dấu hiệu 2 — cặp `DropColumn` và `AddColumn` trên cùng một bảng.** Đây là chữ ký của một lần đổi tên bị hiểu nhầm:

```csharp
migrationBuilder.DropColumn(name: "Phone", table: "Leads");
migrationBuilder.AddColumn<string>(name: "PhoneNumber", table: "Leads", ...);
//                                       ^^^^^^^^^^^ tên khác, cùng bảng, cùng kiểu
```

Ba tín hiệu cùng lúc — cùng bảng, kiểu tương thích, tên gần giống — gần như luôn nghĩa là "đổi tên", và phép sửa là `RenameColumn`. Xem [bài 13.4](13.4-migrations.mdx).

**Dấu hiệu 3 — `AlterColumn` thu hẹp hoặc đổi kiểu:**

```csharp
// Thu hẹp: mọi giá trị dài hơn 50 ký tự bị CẮT, không báo lỗi
migrationBuilder.AlterColumn<string>(
    name: "Notes", table: "Leads", maxLength: 50,
    oldClrType: typeof(string), oldType: "nvarchar(max)");

// Thành NOT NULL: mọi NULL thành chuỗi rỗng, mất thông tin "chưa biết"
migrationBuilder.AlterColumn<string>(
    name: "Source", table: "Leads", nullable: false, defaultValue: "",
    oldClrType: typeof(string), oldNullable: true);

// Đổi kiểu: giá trị không parse được thì migration THẤT BẠI giữa chừng
migrationBuilder.AlterColumn<int>(
    name: "Code", table: "Leads", oldClrType: typeof(string));
```

Ba biến thể này nguy hiểm hơn `DropColumn` ở một điểm: chúng **không trông giống thao tác phá huỷ**. `AlterColumn` nghe như "điều chỉnh", và người đọc lướt qua sẽ không dừng lại.

Cách kiểm tra trước khi chạy:

```sql
SELECT COUNT(*) FROM Leads WHERE LEN(Notes) > 50;        -- sẽ bị cắt bao nhiêu dòng?
SELECT COUNT(*) FROM Leads WHERE Source IS NULL;         -- bao nhiêu NULL sẽ mất nghĩa?
SELECT COUNT(*) FROM Leads WHERE TRY_CAST(Code AS INT) IS NULL AND Code IS NOT NULL;
```

Nếu kết quả khác 0, migration sẽ phá dữ liệu và bạn cần một bước chuyển đổi tường minh trước.

**Quy tắc tối thiểu cho nhóm:**

```text
1. Mọi migration phải được ĐỌC trước khi commit — không chỉ được sinh ra.
2. Migration có Drop hoặc AlterColumn cần một người thứ hai duyệt.
3. Trước khi chạy trên production, chạy các câu đếm ở trên trên bản sao dữ liệu thật.
4. Backup ngay trước khi chạy, tự động trong pipeline.
```

**Và một kiểm tra tự động cho bước 2:**

```bash
#!/usr/bin/env bash
NGUY_HIEM='DropColumn|DropTable|DropPrimaryKey|AlterColumn'
FILES=$(git diff --name-only origin/main...HEAD -- '*/Migrations/*.cs')
if [ -n "$FILES" ] && echo "$FILES" | xargs grep -lE "$NGUY_HIEM" 2>/dev/null; then
  echo "Migration có thao tác phá dữ liệu — gắn nhãn 'cần duyệt schema' cho PR này"
  exit 1
fi
```

#### Bài 2 — Sinh script và đọc SQL thật

Chạy `dotnet ef migrations script` cho migration gần nhất và đọc SQL thật.

**Tiêu chí hoàn thành:** bạn nêu được vì sao đọc SQL sinh ra cho biết nhiều hơn đọc file `.cs`, và biết dùng `--idempotent` đúng chỗ.

Gợi ý và lời giải — Bài 2

**Gợi ý.** Một phương thức `MigrationBuilder` có thể sinh ra bao nhiêu câu lệnh SQL?

**Lời giải:**

```bash
dotnet ef migrations script <migration-trước> <migration-này> \
    --output migration.sql --project src/Crm.Infrastructure
```

```sql
BEGIN TRANSACTION;
GO

DECLARE @var0 sysname;
SELECT @var0 = [d].[name]
FROM [sys].[default_constraints] [d]
INNER JOIN [sys].[columns] [c]
    ON [d].[parent_column_id] = [c].[column_id]
WHERE [d].[parent_object_id] = OBJECT_ID(N'[Leads]')
  AND [c].[name] = N'Phone';
IF @var0 IS NOT NULL EXEC(N'ALTER TABLE [Leads] DROP CONSTRAINT [' + @var0 + '];');
GO

ALTER TABLE [Leads] DROP COLUMN [Phone];
GO

ALTER TABLE [Leads] ADD [PhoneNumber] nvarchar(max) NOT NULL DEFAULT N'';
GO

INSERT INTO [__EFMigrationsHistory] ([MigrationId], [ProductVersion])
VALUES (N'20260925081422_DoiTenPhone', N'9.0.0');
GO

COMMIT;
GO
```

**Vì sao đọc SQL cho biết nhiều hơn đọc file `.cs` — bốn lý do:**

**1. Một dòng C# có thể sinh nhiều câu lệnh.** `DropColumn("Phone")` ở trên sinh **hai** thao tác: gỡ ràng buộc mặc định trước, rồi mới xoá cột. Chi tiết đó hoàn toàn vô hình trong file `.cs`, và nó là chỗ migration hay thất bại nhất khi cột có ràng buộc mà bạn không biết.

**2. Bạn thấy thao tác nào cần khoá bảng và trong bao lâu.** SQL thật cho biết đây là thao tác metadata hay là thao tác phải viết lại cả bảng:

```sql
-- Metadata, nhanh kể cả trên bảng lớn
ALTER TABLE [Leads] ADD [Source] nvarchar(100) NULL;

-- Viết lại TOÀN BỘ bảng, khoá suốt thời gian đó
ALTER TABLE [Leads] ALTER COLUMN [Notes] nvarchar(100) NOT NULL;
```

Với bảng 50 triệu dòng, câu thứ hai có thể khoá bảng nhiều phút — và bạn chỉ biết điều đó khi nhìn vào SQL.

**3. Bạn thấy phạm vi transaction.** Mặc định EF Core bọc cả migration trong một transaction. Với một migration lớn chạy nhiều phút, đó là một transaction giữ khoá suốt thời gian ấy, và transaction log phình theo ([bài 12.8](../module-12-sql-deep-dive/12.8-database-migration-strategy.mdx)).

Một số thao tác **không chạy được** trong transaction và cần tách riêng:

```csharp
migrationBuilder.Sql("CREATE INDEX IX_Leads_Name ON Leads(Name) WITH (ONLINE = ON);",
                     suppressTransaction: true);
```

**4. Đó là thứ DBA cần.** Ở nhiều tổ chức, ứng dụng không có quyền `ALTER` trên production. Quy trình là gửi file `.sql` cho DBA duyệt và chạy. File `.cs` không dùng được cho việc đó.

**`--idempotent` — dùng khi nào:**

```bash
dotnet ef migrations script --idempotent --output migration.sql
```

```sql
IF NOT EXISTS(SELECT * FROM [__EFMigrationsHistory]
              WHERE [MigrationId] = N'20260925081422_DoiTenPhone')
BEGIN
    ALTER TABLE [Leads] DROP COLUMN [Phone];
    ALTER TABLE [Leads] ADD [PhoneNumber] nvarchar(max) NOT NULL DEFAULT N'';
    INSERT INTO [__EFMigrationsHistory] ...
END;
GO
```

Mỗi migration được bọc trong `IF NOT EXISTS`, nên script **chạy lại được nhiều lần** mà không gây hại và không cần biết database đang ở phiên bản nào.

| Tình huống | Dùng |
|---|---|
| Triển khai tự động qua CI/CD | **`--idempotent`** — không cần biết môi trường đang ở đâu |
| Nhiều môi trường ở phiên bản khác nhau | **`--idempotent`** — một script cho tất cả |
| Script có thể bị chạy lại do retry của pipeline | **`--idempotent`** |
| Gửi DBA đọc và duyệt | Script thường — ngắn hơn, dễ đọc hơn |
| Chỉ cần xem SQL để học | Script thường |

**Giới hạn của `--idempotent`:** nó chỉ kiểm tra **migration đã chạy chưa**, chứ không kiểm tra **schema có đúng không**. Nếu ai đó sửa schema bằng tay, script vẫn chạy và vẫn có thể thất bại giữa chừng. Nó bảo vệ khỏi việc chạy lại, không bảo vệ khỏi trạng thái lệch.

**Quy trình triển khai nên dùng:**

```yaml
# Tách sinh script khỏi thực thi — đây là điểm quan trọng nhất
- name: Sinh script migration
  run: |
    dotnet ef migrations script --idempotent \
      --project src/Crm.Infrastructure \
      --output artifacts/migration.sql

- name: Lưu script làm artifact
  uses: actions/upload-artifact@v4
  with:
    name: migration-sql
    path: artifacts/migration.sql

- name: Chạy migration
  run: sqlcmd -S $SERVER -d $DB -i artifacts/migration.sql
```

Ba lợi ích so với gọi `dotnet ef database update` thẳng trên production:

1. **Script được lưu lại**, nên biết chính xác cái gì đã chạy khi cần điều tra.
2. **Có thể chèn một bước duyệt** giữa sinh và chạy, cho những migration nhạy cảm.
3. **Production không cần cài .NET SDK** và không cần chuỗi kết nối có quyền `ALTER` nằm trong ứng dụng.

Điểm thứ ba đáng nhấn mạnh: `dotnet ef database update` cần SDK và cần quyền đổi schema. Chạy nó từ ứng dụng nghĩa là ứng dụng — thứ tiếp xúc với internet — mang theo quyền `ALTER TABLE` suốt vòng đời của nó.

#### Bài 3 — Lập kế hoạch expand–contract

Lập kế hoạch ba giai đoạn cho một lần đổi tên cột trong dự án của bạn.

**Tiêu chí hoàn thành:** kế hoạch của bạn nói rõ **thời điểm không quay lại được** nằm ở đâu, và vì sao không gộp được các giai đoạn.

Gợi ý và lời giải — Bài 3

**Gợi ý.** Trong lúc triển khai, phiên bản cũ và phiên bản mới của ứng dụng cùng chạy. Cả hai nói chuyện với **một** database.

**Lời giải — đổi `Phone` thành `PhoneNumber`, bốn giai đoạn:**

**Giai đoạn 1 — Expand: thêm cột mới, ghi cả hai.**

```csharp
migrationBuilder.AddColumn<string>(
    name: "PhoneNumber", table: "Leads", nullable: true);

migrationBuilder.Sql("UPDATE Leads SET PhoneNumber = Phone WHERE PhoneNumber IS NULL;");
```

```csharp
public class Lead
{
    public string Phone { get; set; } = null!;          // vẫn còn
    public string? PhoneNumber { get; set; }            // mới

    public void DatSoDienThoai(string soDienThoai)
    {
        Phone = soDienThoai;                            // ghi cả hai
        PhoneNumber = soDienThoai;
    }
}
```

Đọc vẫn từ `Phone`. Cột mới có dữ liệu nhưng chưa ai dùng.

**Giai đoạn 2 — chuyển đọc sang cột mới.**

```csharp
public string SoDienThoaiHienThi => PhoneNumber ?? Phone;   // dự phòng về cột cũ
```

Vẫn ghi cả hai. Nếu cột mới có vấn đề, `??` tự lùi về cột cũ.

**Giai đoạn 3 — ngừng ghi cột cũ.**

```csharp
public void DatSoDienThoai(string soDienThoai) => PhoneNumber = soDienThoai;
```

Cột `Phone` vẫn tồn tại với dữ liệu cũ, nhưng không được ghi thêm.

**Giai đoạn 4 — Contract: xoá cột cũ.**

```csharp
migrationBuilder.DropColumn(name: "Phone", table: "Leads");
```

**Thời điểm không quay lại được nằm ở giai đoạn 4, và chỉ ở đó.**

```text
Giai đoạn 1:  rollback = triển khai lại code cũ. Cột mới thừa, vô hại.
Giai đoạn 2:  rollback = triển khai lại code cũ. Cột cũ vẫn đủ dữ liệu.
Giai đoạn 3:  rollback = triển khai lại code cũ. Dữ liệu ghi trong giai đoạn 3
              chỉ có ở cột mới -> mất phần chênh lệch, nhưng cột cũ vẫn dùng được.
Giai đoạn 4:  KHÔNG quay lại được. Dữ liệu đã bị xoá vĩnh viễn.
```

Giai đoạn 3 có một sắc thái đáng nói: rollback từ đây **mất những gì được ghi trong khoảng đó**. Nếu giai đoạn 3 chạy hai tuần rồi mới phát hiện vấn đề, hai tuần dữ liệu số điện thoại mới chỉ có ở `PhoneNumber`. Đó là lý do nên rút ngắn giai đoạn 3, hoặc giữ ghi cả hai cho tới sát giai đoạn 4.

Nên đặt khoảng chờ trước giai đoạn 4 đủ dài — **ít nhất một chu kỳ phát hành** — và chỉ chạy nó khi đã chắc không cần quay lại.

**Vì sao không gộp được các giai đoạn** — đây là phần chính của bài.

Trong một lần triển khai rolling, pod cũ và pod mới **cùng chạy** trong vài phút:

```text
t=0    10 pod chạy code CŨ (đọc/ghi cột Phone)
t=1    migration chạy
t=2     8 pod CŨ  +  2 pod MỚI
t=3     5 pod CŨ  +  5 pod MỚI      <- cả hai cùng phục vụ request thật
t=5     0 pod CŨ  + 10 pod MỚI
```

**Nếu gộp giai đoạn 1 và 4 thành một bước** — xoá `Phone`, thêm `PhoneNumber`, đổi code cùng lúc:

```text
t=1  migration xoá cột Phone
t=2  8 pod CŨ vẫn đang chạy, vẫn sinh SQL có cột Phone
     -> Invalid column name 'Phone'
     -> 80% request lỗi trong suốt thời gian triển khai
```

**Nếu gộp giai đoạn 1 và 3** — thêm cột mới và ngừng ghi cột cũ cùng lúc:

```text
Pod MỚI ghi  -> PhoneNumber = "0901234567", Phone = NULL
Pod CŨ đọc   -> Phone = NULL
             -> số điện thoại biến mất với 50% request
```

Lỗi này tệ hơn lỗi trước: nó **không ném exception**, chỉ trả về dữ liệu sai cho một nửa người dùng, và biến mất khi triển khai xong — khiến việc tái hiện gần như không thể.

**Nguyên tắc chung rút ra từ hai kịch bản trên:**

> **Mỗi bước triển khai chỉ được thay đổi schema theo cách mà phiên bản code trước đó vẫn chạy đúng.**

Thêm cột nullable thoả điều kiện — code cũ không biết cột đó và không bị ảnh hưởng. Xoá cột thì không, vì code cũ vẫn tham chiếu tới nó.

Và số giai đoạn tối thiểu là **ba lần triển khai riêng biệt**, vì có ba chuyển đổi trạng thái mà mỗi cái cần code cũ và code mới cùng đúng:

```text
ghi-cũ, đọc-cũ  ->  ghi-cả-hai, đọc-cũ  ->  ghi-cả-hai, đọc-mới  ->  ghi-mới, đọc-mới
                 │                       │                        │
                 triển khai 1            triển khai 2             triển khai 3
```

Không có cách nào rút ngắn nếu vẫn muốn triển khai không downtime.

**Ngoại lệ duy nhất:** nếu bạn **chấp nhận downtime** — dừng hẳn ứng dụng, chạy migration, khởi động lại bản mới — thì làm một bước được. Với hệ thống nội bộ có cửa sổ bảo trì, đây thường là lựa chọn đúng: đơn giản hơn nhiều, và cái giá là mười phút ngừng dịch vụ lúc 2 giờ sáng.

Quyết định giữa bốn giai đoạn và một cửa sổ bảo trì là quyết định về **chi phí vận hành**, không phải về kỹ thuật. Đừng làm expand–contract chỉ vì nó nghe chuyên nghiệp hơn.

**Mẫu kế hoạch viết ra cho nhóm:**

```markdown
## Đổi tên Leads.Phone -> Leads.PhoneNumber

| GĐ | Nội dung | Phát hành | Rollback | Rủi ro |
|----|----------|-----------|----------|--------|
| 1 | Thêm cột nullable + sao chép dữ liệu; code ghi cả hai | v2.4.0 | Được | Thấp |
| 2 | Đọc từ cột mới, dự phòng `?? Phone` | v2.5.0 | Được | Thấp |
| 3 | Ngừng ghi cột cũ | v2.6.0 | Được, mất dữ liệu từ GĐ3 | Trung bình |
| 4 | DropColumn Phone | v2.8.0 | **KHÔNG** | Cao |

- Khoảng chờ trước GĐ4: 2 chu kỳ phát hành (khoảng 4 tuần).
- Trước GĐ4: backup, và kiểm tra `SELECT COUNT(*) FROM Leads WHERE PhoneNumber IS NULL`.
- Người duyệt GĐ4: <tên>.
```

Bảng này đáng viết ra ngay cả cho một dự án nhỏ — vì bốn giai đoạn kéo dài nhiều tuần, và người chạy giai đoạn 4 có thể không phải người đã lập kế hoạch.

## Tự kiểm tra

### Vì sao EF Core sinh DropColumn khi đổi tên thuộc tính?

Vì nó so sánh model hiện tại với snapshot và thấy một cột không còn, một cột mới xuất hiện. Nó không có cách nào biết đó là cùng một cột được đổi tên, vì thông tin đó chỉ nằm trong đầu người viết code.

### Vì sao phải đọc file migration trước khi commit?

Vì lỗi kiểu này hiển hiện rất rõ khi đọc phương thức Up, và hoàn toàn vô hình nếu chỉ chạy lệnh sinh migration rồi commit. Migration chạy thành công và không có exception nào.

### Bốn loại lệnh cần cảnh giác là gì?

DropColumn làm mất dữ liệu cột, DropTable làm mất cả bảng, AlterColumn thu hẹp kiểu làm cắt cụt dữ liệu mà không báo lỗi, và AlterColumn sang NOT NULL thất bại nếu còn hàng null.

### Vì sao phải thử migration trên bản sao dữ liệu production?

Vì nó bắt được hai thứ mà môi trường phát triển không bao giờ bắt được: thời gian chạy thật, ví dụ thêm index trên mười triệu hàng có thể mất hàng chục phút và khoá bảng, và dữ liệu thật vi phạm ràng buộc mới.

### Expand-contract hoạt động thế nào?

Ba giai đoạn: thêm cột mới và ghi vào cả hai cột trong khi vẫn đọc cột cũ, chuyển sang đọc cột mới và theo dõi vài ngày, rồi mới xoá cột cũ. Mỗi bước tương thích ngược nên triển khai dần và quay lại được bất cứ lúc nào.

### Điều kiện để khôi phục dữ liệu bị migration xoá là gì?

Database phải ở FULL recovery model và có sao lưu transaction log định kỳ. Và nên khôi phục vào một database tạm rồi chép dữ liệu sang, chứ không khôi phục đè lên production vì sẽ mất mọi giao dịch sau thời điểm đó.

## Kết luận

Ba điều đáng nhớ nhất:

1. **EF Core không biết bạn đang đổi tên** — nó chỉ thấy một cột mất, một cột mới.
2. **Đọc file migration mỗi lần.** Lỗi này rất rõ khi đọc và vô hình khi không đọc.
3. **Bảng lớn cần expand-contract**, không thay đổi trong một bước.
