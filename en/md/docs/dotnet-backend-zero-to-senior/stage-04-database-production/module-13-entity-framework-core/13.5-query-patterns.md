# 13.5 — 5. Query Patterns

> Nguồn: https://tiennhm.io.vn/en/docs/dotnet-backend-zero-to-senior/stage-04-database-production/module-13-entity-framework-core/13.5-query-patterns
> Projection thay vì Include, split query và cartesian explosion, explicit loading, FindAsync, và compiled query cho đường chạy nóng.

> Mẫu truy vấn quan trọng nhất trong EF Core là **projection**: `Select` vào một DTO thay vì nạp entity đầy đủ rồi map. Nó cho ba lợi ích cùng lúc — SQL chỉ lấy **đúng cột cần**, không có change tracking, và không cần `Include`. Cái bẫy đi kèm là **cartesian explosion**: `Include` hai collection cùng lúc sinh ra `JOIN` chéo, nên một khách hàng có 10 contact và 20 lead trả về **200 dòng** cho một bản ghi — và với ba collection thì con số nhân tiếp. `AsSplitQuery()` giải quyết bằng cách tách thành nhiều truy vấn, nhưng nó có cái giá riêng: không còn **nhất quán** giữa các truy vấn nếu không có transaction.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Dùng projection và biết khi nào cần entity đầy đủ.
- Nhận ra cartesian explosion và chọn giữa single và split query.
- Dùng explicit loading và filtered include.
- Biết `FindAsync` khác `FirstOrDefaultAsync` ở đâu.
- Dùng compiled query cho đường chạy nóng.

## Nội dung bài học

### 13.6.1 — Projection là mặc định

```csharp
// KEM — nap toan bo entity roi map
var customers = await db.Customers
    .Include(c => c.Contacts)
    .ToListAsync(ct);

var dtos = customers.Select(c => new CustomerDto(c.Id, c.Name, c.Contacts.Count));
```

```csharp
// TỐT — SQL chỉ lấy đúng những gì cần
var dtos = await db.Customers
    .Select(c => new CustomerDto(c.Id, c.Name, c.Contacts.Count()))
    .ToListAsync(ct);
```

Phiên bản đầu nạp **mọi cột** của `Customers` và **mọi cột** của tất cả `Contacts` — kể cả một cột `Notes` dài 10KB mà DTO không dùng. Phiên bản sau sinh:

```sql
SELECT c.Id, c.Name, (SELECT COUNT(*) FROM Contacts WHERE CustomerId = c.Id)
FROM Customers c;
```

Ba lợi ích của projection:

1. **Ít dữ liệu hơn** qua mạng và trong bộ nhớ.
2. **Không có tracking** — EF không theo dõi kiểu ẩn danh hay DTO, nên `AsNoTracking` là thừa.
3. **Không cần `Include`** — projection tự sinh JOIN hoặc subquery.

Điểm 3 hay bị bỏ qua: `Include` **vô tác dụng** khi có `Select`. EF Core bỏ qua nó, và điều này gây bối rối vì code trông như đang eager load.

```csharp
// Include bị BỎ QUA hoàn toàn
var dtos = await db.Customers
    .Include(c => c.Contacts)          // vo nghia
    .Select(c => new CustomerDto(c.Id, c.Name))
    .ToListAsync(ct);
```

**Khi nào vẫn cần entity đầy đủ:** khi bạn sẽ **sửa** nó. Projection cho đối tượng không được tracking, nên `SaveChanges` không làm gì.

Lồng collection trong projection cũng được:

```csharp
var dto = await db.Customers
    .Where(c => c.Id == id)
    .Select(c => new CustomerDetailDto(
        c.Id, c.Name,
        c.Contacts.Select(ct2 => new ContactDto(ct2.Id, ct2.FullName)).ToList()))
    .FirstOrDefaultAsync(ct);
```

### 13.6.2 — Cartesian explosion

```csharp
var customer = await db.Customers
    .Include(c => c.Contacts)          // 10 contact
    .Include(c => c.Leads)             // 20 lead
    .FirstOrDefaultAsync(c => c.Id == 42, ct);
```

EF Core sinh **một** truy vấn với hai `LEFT JOIN`:

```
10 contact x 20 lead = 200 DÒNG cho MỘT khách hàng
Mỗi dòng lặp lại toàn bộ cột của Customers
```

EF Core khử trùng lặp khi vật chất hoá, nên **kết quả đúng** — nhưng 200 dòng đã đi qua mạng, và cột `Customer.Notes` được lặp lại 200 lần.

Với ba collection (10 × 20 × 15), đó là **3.000 dòng**.

```csharp
// Split query — MOI collection mot truy van
var customer = await db.Customers
    .Include(c => c.Contacts)
    .Include(c => c.Leads)
    .AsSplitQuery()
    .FirstOrDefaultAsync(c => c.Id == 42, ct);
```

```sql
SELECT * FROM Customers WHERE Id = 42;                    -- 1 dong
SELECT * FROM Contacts WHERE CustomerId = 42;             -- 10 dong
SELECT * FROM Leads WHERE CustomerId = 42;                -- 20 dong
-- Tổng: 31 dòng thay vì 200
```

| | Single query | Split query |
|---|---|---|
| Số lần đi về database | 1 | **N + 1** |
| Dữ liệu truyền | **Nhân lên** | Tuyến tính |
| Nhất quán | **Đảm bảo** | Không, trừ khi có transaction |
| Tốt khi | Một collection, hoặc collection nhỏ | **Nhiều collection, dữ liệu lớn** |

Hàng "nhất quán" là cái giá thật của split query: giữa truy vấn 1 và truy vấn 2, ai đó có thể thêm một contact — và bạn nhận một ảnh chụp không nhất quán. Với báo cáo thì không sao; với dữ liệu tài chính thì cần transaction.

Bật mặc định khi phần lớn truy vấn có nhiều collection:

```csharp
options.UseSqlServer(conn, sql => sql.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));
```

**Nhưng cách tốt nhất thường là projection** — nó tránh được cả hai vấn đề vì chỉ lấy đúng cột cần.

### 13.6.3 — Filtered include

```csharp
// EF Core 5+: loc ngay trong Include
var customers = await db.Customers
    .Include(c => c.Contacts.Where(ct2 => ct2.IsPrimary))
    .Include(c => c.Leads.Where(l => l.Status != LeadStatus.Lost)
                          .OrderByDescending(l => l.CreatedAt)
                          .Take(5))
    .ToListAsync(ct);
```

Trước EF Core 5, việc này phải làm bằng projection hoặc lọc trong bộ nhớ sau khi nạp hết.

Ba ràng buộc: chỉ dùng được `Where`, `OrderBy`, `Skip`, `Take`; **cùng một navigation phải lọc giống nhau** ở mọi nơi trong truy vấn; và nó **không** áp dụng khi entity đã nằm trong change tracker — khi đó bạn thấy cả những bản đã nạp trước đó.

Ràng buộc cuối gây ra hành vi khó hiểu: cùng một đoạn code cho kết quả khác nhau tuỳ vào context đã nạp gì. Với `AsNoTracking` thì không có vấn đề này.

### 13.6.4 — Explicit loading

```csharp
var customer = await db.Customers.FindAsync([id], ct);

// Chỉ nạp contact khi thực sự cần
if (needContacts)
    await db.Entry(customer!).Collection(c => c.Contacts).LoadAsync(ct);

// Nap co dieu kien
await db.Entry(customer!).Collection(c => c.Leads)
        .Query().Where(l => l.Status == LeadStatus.New)
        .LoadAsync(ct);

// Chỉ ĐẾM, không nạp
var leadCount = await db.Entry(customer!).Collection(c => c.Leads)
                        .Query().CountAsync(ct);
```

Hữu ích khi bạn **không biết trước** có cần dữ liệu liên quan hay không. Nhưng cẩn thận: gọi nó trong vòng lặp là tạo ra N+1 ([bài 13.7](13.6-n-plus-1-problem.mdx)).

`.Query()` đặc biệt hữu ích cho việc đếm — nó sinh `COUNT(*)` thay vì nạp toàn bộ collection để gọi `.Count`.

**Lazy loading** thì ngược lại — đừng bật:

```csharp
// TRANH
options.UseLazyLoadingProxies();
```

Nó khiến mọi truy cập navigation property **âm thầm** sinh truy vấn. Một `foreach` vô hại trong tầng trình bày biến thành 500 lần đi về database, và không có gì trong code báo hiệu điều đó.

### 13.6.5 — `FindAsync` so với `FirstOrDefaultAsync`

```csharp
var a = await db.Customers.FindAsync([id], ct);
var b = await db.Customers.FirstOrDefaultAsync(c => c.Id == id, ct);
```

| | `FindAsync` | `FirstOrDefaultAsync` |
|---|---|---|
| Kiểm tra change tracker trước | **Có** | Không |
| Luôn đi database | Không | **Có** |
| Chỉ tìm theo khoá chính | **Có** | Bất kỳ điều kiện |
| Dùng được `Include` | **Không** | Có |
| Áp global query filter | **Không** | **Có** |

Hai hàng cuối quan trọng. `FindAsync` **bỏ qua global query filter** — nghĩa là nó **tìm thấy cả bản ghi đã xoá mềm** ([bài 13.11](13.10-global-query-filters.mdx)). Đây là nguồn của lỗi "tại sao tôi lấy được khách hàng đã xoá".

`FindAsync` nhanh hơn khi entity đã nằm trong change tracker (không sinh truy vấn nào), nên nó tốt cho luồng cập nhật. Với truy vấn đọc có filter, dùng `FirstOrDefaultAsync`.

### 13.6.6 — Compiled query

```csharp
private static readonly Func<CrmDbContext, int, CancellationToken, Task<CustomerDto?>>
    GetCustomerDto = EF.CompileAsyncQuery(
        (CrmDbContext db, int id, CancellationToken ct) =>
            db.Customers
              .Where(c => c.Id == id)
              .Select(c => new CustomerDto(c.Id, c.Name, c.Email))
              .FirstOrDefault());

// Goi
var dto = await GetCustomerDto(db, id, ct);
```

EF Core cache plan biên dịch LINQ, nhưng vẫn phải **băm cây biểu thức** mỗi lần để tra cache. Compiled query bỏ qua bước đó.

Lợi ích thật: khoảng **10–30%** cho truy vấn đơn giản chạy **rất nhiều lần**. Với truy vấn phức tạp hoặc chạy ít, chênh lệch không đáng kể.

Ba ràng buộc: phải là `static readonly`; **không** thay đổi cấu trúc truy vấn theo điều kiện (mất hết ý nghĩa); và `CancellationToken` phải là tham số của lambda, không bắt từ bên ngoài.

Chỉ dùng sau khi **đã đo** và thấy chi phí biên dịch truy vấn là đáng kể — với hầu hết ứng dụng, nó không phải nút thắt.

### 13.6.7 — Rà lại code của bạn

**Danh sách rà soát mẫu truy vấn**

- [ ] Truy vấn đọc dùng projection vào DTO, không nạp entity đầy đủ.
- [ ] Không có Include nào đi kèm Select — nó bị bỏ qua.
- [ ] Truy vấn có nhiều Include collection dùng AsSplitQuery hoặc projection.
- [ ] Hiểu rằng split query không đảm bảo nhất quán nếu không có transaction.
- [ ] Filtered include không dùng trên truy vấn có tracking nếu kết quả phải chính xác.
- [ ] Không bật lazy loading proxies.
- [ ] Explicit loading không nằm trong vòng lặp.
- [ ] Đếm collection dùng .Query().CountAsync(), không nạp rồi .Count.
- [ ] Biết FindAsync bỏ qua global query filter.
- [ ] Compiled query chỉ dùng sau khi đã đo, cho truy vấn chạy rất nhiều lần.

## Bài tập áp dụng

#### Bài 1 — Cartesian explosion

Với một khách hàng có 20 contact và 30 lead, chạy truy vấn hai `Include`. Bật log SQL, đếm số dòng trả về. Thêm `AsSplitQuery()` và so sánh cả số dòng lẫn số lần đi về database.

**Tiêu chí hoàn thành:** bạn tính được số dòng trước khi chạy, và nêu được cái giá mà `AsSplitQuery` bắt bạn trả.

Gợi ý và lời giải — Bài 1

**Gợi ý.** `JOIN` hai collection độc lập cho ra **tích** của chúng, không phải tổng.

**Lời giải — tính trước khi chạy:**

```text
1 khách hàng × 20 contact × 30 lead = 600 dòng
```

Không phải 51 dòng (1 + 20 + 30) như trực giác gợi ý.

```csharp
var customer = await _db.Customers
    .Include(c => c.Contacts)
    .Include(c => c.Leads)
    .FirstAsync(c => c.Id == id, ct);
```

```sql
SELECT [c].[Id], [c].[Name],
       [t].[Id], [t].[Name], [t].[Email], [t].[CustomerId],
       [t0].[Id], [t0].[Name], [t0].[Value], [t0].[Status], [t0].[CustomerId]
FROM [Customers] AS [c]
LEFT JOIN [Contacts] AS [t]  ON [c].[Id] = [t].[CustomerId]
LEFT JOIN [Leads]    AS [t0] ON [c].[Id] = [t0].[CustomerId]
WHERE [c].[Id] = @__id_0
-- 600 dòng
```

Mỗi contact xuất hiện **30 lần**, mỗi lead xuất hiện **20 lần**, và tên khách hàng lặp lại 600 lần. EF Core gỡ trùng đúng bằng identity map và trả về một `Customer` với 20 contact và 30 lead — nhưng 600 dòng đã đi qua mạng rồi.

**Với `AsSplitQuery`:**

```csharp
var customer = await _db.Customers
    .Include(c => c.Contacts)
    .Include(c => c.Leads)
    .AsSplitQuery()
    .FirstAsync(c => c.Id == id, ct);
```

```sql
SELECT TOP(1) [c].[Id], [c].[Name] FROM [Customers] AS [c] WHERE [c].[Id] = @__id_0
SELECT [t].[Id], [t].[Name], [t].[Email], [t].[CustomerId] FROM [Contacts] AS [t] WHERE ...
SELECT [t0].[Id], [t0].[Name], [t0].[Value], ... FROM [Leads] AS [t0] WHERE ...
-- 1 + 20 + 30 = 51 dòng, 3 lần đi về database
```

| | Số dòng | Lần đi về DB | Byte truyền (ước lượng) |
|---|---:|---:|---:|
| Single query | 600 | 1 | ~72 KB |
| Split query | 51 | 3 | ~6 KB |

**Vì sao nó bùng nổ nhanh đến vậy.** Số dòng là **tích**, nên nó nhân lên theo mỗi `Include` collection thêm vào:

```text
1 Include:   20 dòng
2 Include:   20 × 30 = 600 dòng
3 Include:   20 × 30 × 15 = 9.000 dòng
4 Include:   20 × 30 × 15 × 10 = 90.000 dòng
```

Và điều nguy hiểm là nó **không tuyến tính theo dữ liệu**. Một khách hàng có gấp đôi contact và gấp đôi lead làm số dòng tăng **gấp bốn**. Truy vấn chạy ngon trên dev với khách hàng nhỏ có thể làm hết bộ nhớ trên production với một khách hàng lớn.

Còn với một danh sách nhiều khách hàng, nó nhân tiếp với số khách hàng — đây là lúc truy vấn chuyển từ chậm sang không dùng được.

**Cái giá của `AsSplitQuery` — hai thứ:**

**1. Nhiều lần đi về database, nên nhạy với độ trễ mạng.** Ba truy vấn tuần tự với độ trễ 5 ms mất 15 ms chỉ riêng cho đi về, trước khi tính thời gian thực thi. Trên cùng máy thì không đáng kể; qua mạng giữa các vùng địa lý thì đáng kể.

**2. Mất tính nhất quán — và đây là cái giá thật sự.** Ba truy vấn chạy tại **ba thời điểm khác nhau**:

```text
t=0 ms   SELECT khách hàng        -> nhận về "Công ty ABC"
t=5 ms                            -> một giao dịch khác THÊM một contact
t=6 ms   SELECT contact           -> nhận về 21 contact (không phải 20)
t=12 ms  SELECT lead              -> 30 lead
```

Với single query, `JOIN` chạy trong **một** ảnh chụp nhất quán và không có khe hở này.

Sửa được nếu cần, bằng cách bọc trong một transaction có mức cô lập đủ mạnh:

```csharp
await using var tx = await _db.Database.BeginTransactionAsync(
    IsolationLevel.Snapshot, ct);
```

Nhưng như vậy là đổi một vấn đề lấy một vấn đề khác: transaction giữ lâu hơn và giữ tài nguyên `tempdb` ([bài 12.6](../module-12-sql-deep-dive/12.6-transactions-and-locking.mdx)).

**Khi nào chọn gì:**

| Tình huống | Chọn |
|---|---|
| Một collection `Include` | Single query — không có tích nào để bùng nổ |
| Nhiều collection, mỗi cái vài phần tử | Single query — 600 dòng vẫn ổn |
| Nhiều collection, ít nhất một cái lớn | **Split query** |
| Cần nhất quán tuyệt đối giữa các collection | Single query, hoặc split trong transaction snapshot |
| **Chỉ cần vài trường** | **Projection** — không cần `Include` nào |

**Và dòng cuối thường là câu trả lời đúng nhất:**

```csharp
var dto = await _db.Customers
    .Where(c => c.Id == id)
    .Select(c => new CustomerDto(
        c.Id, c.Name,
        c.Contacts.Select(ct => new ContactDto(ct.Id, ct.Name)).ToList(),
        c.Leads.Where(l => l.Status == "New")
               .Select(l => new LeadDto(l.Id, l.Value)).ToList()))
    .FirstAsync(ct);
```

EF Core sinh SQL split query cho projection này một cách tự động, chỉ đọc các cột được nêu, và cho phép **lọc từng collection riêng** — thứ mà `Include` không làm được trước EF Core 5 và vẫn vụng về sau đó.

**Bật split query mặc định toàn ứng dụng, rồi chọn lại từng chỗ khi cần:**

```csharp
options.UseSqlServer(conn, o => o.UseQuerySplittingBehavior(QuerySplittingBehavior.SplitQuery));
```

```csharp
.AsSingleQuery()   // ở những truy vấn cần nhất quán
```

Mặc định này an toàn hơn theo nghĩa: hậu quả xấu nhất của split query là vài mili giây độ trễ thêm, còn hậu quả xấu nhất của single query là một truy vấn trả 90.000 dòng làm chết tiến trình.

#### Bài 2 — `Include` bị bỏ qua

Viết truy vấn có cả `Include` và `Select`, in SQL bằng `ToQueryString()`, và xác nhận không có JOIN nào cho navigation đó.

**Tiêu chí hoàn thành:** bạn giải thích được vì sao EF Core bỏ qua `Include` **trong im lặng**, và nêu được trường hợp `Include` vẫn có tác dụng khi đi cùng `Select`.

Gợi ý và lời giải — Bài 2

**Gợi ý.** `Include` nói "nạp thêm navigation này vào entity". Hãy hỏi: sau `Select`, còn entity nào không?

**Lời giải:**

```csharp
var query = _db.Leads
    .Include(l => l.Customer)                       // bị bỏ qua
    .Select(l => new { l.Id, l.Name, l.Value });

Console.WriteLine(query.ToQueryString());
```

```sql
SELECT [l].[Id], [l].[Name], [l].[Value]
FROM [Leads] AS [l]
-- không có JOIN tới Customers
```

Không exception, không cảnh báo. Trên EF Core 6 trở đi có một cảnh báo ở mức `Debug` mà hầu như không ai bật:

```text
warn: Microsoft.EntityFrameworkCore.Query[10112]
      The Include operation was ignored because the query has a final projection
      that does not include the navigation.
```

**Vì sao EF Core bỏ qua nó — và vì sao im lặng là đúng.** `Include` có nghĩa chính xác là: *"khi trả về entity, hãy nạp sẵn navigation này vào entity đó."* Nó thao tác trên **entity**.

`Select` chiếu kết quả sang một hình dạng khác. Sau nó, kết quả là object ẩn danh với ba trường `Id`, `Name`, `Value` — **không còn entity `Lead` nào** để gắn `Customer` vào.

```text
Không Select:   Lead { Id, Name, Value, Customer = <đã nạp> }
                                        ^^^^^^^^ Include có chỗ để gắn

Có Select:      { Id, Name, Value }
                                     không có chỗ nào cho Customer
```

Yêu cầu trở thành vô nghĩa, nên EF Core bỏ qua. Nó **không** thể ném exception, vì có một trường hợp hoàn toàn hợp lệ trông y hệt: `Select` dùng dữ liệu từ navigation đó. Ném lỗi sẽ phá vỡ code đúng.

**Trường hợp `Include` vẫn có tác dụng khi đi cùng `Select`** — khi projection **giữ lại entity**:

```csharp
var ketQua = await _db.Leads
    .Include(l => l.Customer)
    .Select(l => new { Lead = l, SoContact = l.Customer.Contacts.Count() })
    .ToListAsync(ct);

// ketQua[0].Lead.Customer  -> ĐÃ được nạp, không null
```

```sql
SELECT [l].[Id], [l].[Name], [l].[Value], [l].[CustomerId],
       [c].[Id], [c].[Name],
       (SELECT COUNT(*) FROM [Contacts] AS [c0] WHERE [c].[Id] = [c0].[CustomerId])
FROM [Leads] AS [l]
INNER JOIN [Customers] AS [c] ON [l].[CustomerId] = [c].[Id]
```

Ở đây `Lead = l` giữ nguyên entity trong kết quả, nên `Include` lại có chỗ để gắn `Customer` và `JOIN` xuất hiện trở lại.

**Điểm dễ hiểu nhầm nhất của cả bài:** truy vấn dưới đây hoạt động hoàn hảo **mà không cần `Include`**:

```csharp
var dto = await _db.Leads
    .Select(l => new LeadDto(l.Id, l.Name, l.Customer.Name))   // không Include
    .ToListAsync(ct);
```

```sql
SELECT [l].[Id], [l].[Name], [c].[Name]
FROM [Leads] AS [l]
INNER JOIN [Customers] AS [c] ON [l].[CustomerId] = [c].[Id]
```

`JOIN` vẫn có. Lý do: EF Core dịch **cả biểu thức projection** sang SQL, và `l.Customer.Name` trong projection tự sinh ra `JOIN` cần thiết.

Đây là điều khiến `Include` trở nên không cần thiết trong phần lớn truy vấn chỉ đọc:

```text
Include:  "nạp navigation vào entity"          -> cần khi bạn trả về ENTITY
Select:   "tôi cần đúng những trường này"      -> tự sinh JOIN, không cần Include
```

**Quy tắc thực dụng:**

| Bạn đang làm gì | Dùng |
|---|---|
| Đọc để trả về API hoặc hiển thị | `Select` — bỏ hẳn `Include` |
| Đọc entity rồi sửa và lưu | `Include` |
| Đọc entity để chạy logic nghiệp vụ trên nó | `Include` |

**Bật cảnh báo thành lỗi để không bao giờ gặp lại tình huống này:**

```csharp
options.UseSqlServer(conn)
       .ConfigureWarnings(w => w.Throw(CoreEventId.NavigationBaseIncludeIgnored));
```

Từ lúc này, một `Include` bị bỏ qua sẽ ném exception khi truy vấn chạy. Mỗi exception là một dòng code chết — hoặc, đáng lo hơn, một dòng mà tác giả **tưởng** là đang nạp dữ liệu nhưng không phải.

Nên bật nó ở mọi môi trường, không chỉ dev: `Include` bị bỏ qua không bao giờ là ý định của ai cả.

#### Bài 3 — `FindAsync` và soft delete

Bật global query filter loại bản ghi đã xoá mềm. Dùng `FindAsync` với id của một bản ghi đã xoá và xác nhận nó **vẫn trả về**. So sánh với `FirstOrDefaultAsync`.

**Tiêu chí hoàn thành:** bạn nêu được **hai** điều kiện để `FindAsync` bỏ qua filter, và giải thích vì sao điều này gây lỗi không ổn định.

Gợi ý và lời giải — Bài 3

**Gợi ý.** `FindAsync` có một tối ưu mà `FirstOrDefaultAsync` không có. Tối ưu đó chạm tới database khi nào?

**Lời giải:**

```csharp
builder.Entity<Lead>().HasQueryFilter(l => !l.IsDeleted);
```

```csharp
var lead = await _db.Leads.FirstAsync(l => l.Id == 1, ct);
lead.IsDeleted = true;
await _db.SaveChangesAsync(ct);

// Cùng một DbContext, lead vẫn đang được theo dõi
var byFind  = await _db.Leads.FindAsync(new object[] { 1 }, ct);
var byFirst = await _db.Leads.FirstOrDefaultAsync(l => l.Id == 1, ct);

Console.WriteLine($"FindAsync:            {(byFind  is null ? "null" : "TRẢ VỀ BẢN GHI")}");
Console.WriteLine($"FirstOrDefaultAsync:  {(byFirst is null ? "null" : "TRẢ VỀ BẢN GHI")}");
```

```text
FindAsync:            TRẢ VỀ BẢN GHI
FirstOrDefaultAsync:  null
```

**Hai điều kiện để `FindAsync` bỏ qua filter:**

**Điều kiện 1 — entity đang nằm trong change tracker.** `FindAsync` được thiết kế với một tối ưu: **tra identity map trước**. Nếu tìm thấy entity với khoá chính đó, nó trả về ngay **mà không chạm tới database**.

```text
FindAsync(1):
    ├─ Có trong identity map?  ──CÓ──> trả về ngay, KHÔNG có SQL
    │                                  -> không có WHERE, nên không có filter
    └─ KHÔNG ──> sinh truy vấn SQL, CÓ áp filter
```

Global query filter là một mệnh đề `WHERE` **được thêm vào SQL**. Không có SQL thì không có `WHERE`, và không có gì để lọc.

**Điều kiện 2 — entity vào tracker theo một đường không bị filter chặn.** Có ba đường như vậy:

```csharp
// a. Nạp trước khi bị đánh dấu xoá (ví dụ ở trên)
var lead = await _db.Leads.FirstAsync(l => l.Id == 1, ct);
lead.IsDeleted = true;

// b. Nạp qua IgnoreQueryFilters
var lead = await _db.Leads.IgnoreQueryFilters().FirstAsync(l => l.Id == 1, ct);

// c. Nạp gián tiếp qua navigation của một entity khác
var contact = await _db.Contacts.Include(c => c.Lead).FirstAsync(ct);
// Lead bị xoá mềm vẫn vào tracker — filter KHÔNG áp cho navigation
```

Đường (c) đáng chú ý nhất vì nó xảy ra mà không ai chủ ý: global query filter **không** được áp cho navigation property trong `Include`. Một `Lead` đã xoá mềm vào tracker qua cửa sau, và từ đó `FindAsync(1)` trả về nó.

**Vì sao điều này gây lỗi không ổn định** — đây là phần quan trọng nhất:

Kết quả của `FindAsync` phụ thuộc vào **trạng thái của change tracker**, tức vào **những gì đã chạy trước đó trong cùng request**:

```csharp
// Request A
public async Task<Lead?> LayLeadAsync(int id) => await _db.Leads.FindAsync(id);
// -> tracker rỗng -> có SQL -> filter áp -> trả null. ĐÚNG.

// Request B — cùng endpoint, nhưng có một bước xác thực chạy trước
public async Task<Lead?> LayLeadAsync(int id)
{
    await KiemTraQuyenAsync(id);        // hàm này nạp Lead bằng IgnoreQueryFilters
    return await _db.Leads.FindAsync(id);
    // -> tracker CÓ entity -> không SQL -> không filter -> TRẢ VỀ bản ghi đã xoá. SAI.
}
```

Cùng một dòng code, hai kết quả khác nhau, khác biệt duy nhất là **thứ tự các lời gọi trước đó**. Hệ quả:

- **Test đơn lẻ xanh, test chạy cả bộ đỏ** — hoặc ngược lại, tuỳ thứ tự chạy.
- **Chạy được trên dev, hỏng trên production** vì production có thêm một middleware nạp entity.
- **Lỗi biến mất khi bạn thêm log để tìm nó**, nếu dòng log đó cũng chạm vào tracker.
- Một thay đổi ở hàm **khác** làm hỏng hàm này, và code review không thấy gì bất thường ở cả hai phía.

Đây là dạng lỗi tốn nhiều giờ nhất để truy, vì triệu chứng không nằm ở chỗ có nguyên nhân.

**Ba cách xử lý, theo thứ tự nên chọn:**

**1. Đừng dùng `FindAsync` khi có global query filter.** Đây là lựa chọn mặc định đúng:

```csharp
var lead = await _db.Leads.FirstOrDefaultAsync(l => l.Id == id, ct);
```

`FirstOrDefaultAsync` **luôn** sinh SQL, nên filter **luôn** được áp. Mất đi tối ưu identity map, nhưng đổi lại hành vi xác định — và một truy vấn theo khoá chính vốn đã rất rẻ.

**2. Viết extension method thay thế**, nếu vẫn muốn giữ tối ưu ở nơi không có filter:

```csharp
public static Task<T?> TimTheoIdAsync<T>(this DbSet<T> set, int id, CancellationToken ct)
    where T : class, IHasId
    => set.FirstOrDefaultAsync(e => e.Id == id, ct);
```

Kèm một quy tắc analyzer cấm gọi `FindAsync` trực tiếp trên entity có filter.

**3. Gọi `ChangeTracker.Clear()` trước** — chỉ dùng khi bạn hiểu rõ hệ quả:

```csharp
_db.ChangeTracker.Clear();
var lead = await _db.Leads.FindAsync(new object[] { id }, ct);
```

Cách này **rất dễ gây hại**: nó vứt bỏ mọi thay đổi chưa lưu của mọi entity trong context. Gần như không bao giờ đáng dùng trong code nghiệp vụ — nhưng nó là công cụ đúng trong **test**, để mỗi khẳng định bắt đầu từ trạng thái sạch (như ở [bài 13.2](13.2-dbcontext-and-entity-configuration.mdx)).

**Một điểm cần nói cho đủ:** hành vi này **không phải bug** của EF Core. Nó là hệ quả trực tiếp và logic của hai tính năng đúng đắn — identity map và query filter dạng `WHERE` — gặp nhau. Tài liệu EF Core nói rõ `FindAsync` có thể trả về entity từ tracker mà không truy vấn. Cái bẫy nằm ở chỗ hai tính năng ấy được đọc riêng rẽ, và hậu quả của việc kết hợp chúng chỉ lộ ra khi đã ở production.

## Tự kiểm tra

### Vì sao projection nên là mặc định cho truy vấn đọc?

Nó cho ba lợi ích cùng lúc: SQL chỉ lấy đúng cột cần nên ít dữ liệu hơn, kết quả không được tracking nên không tốn bộ nhớ change tracker, và không cần Include vì projection tự sinh JOIN hoặc subquery. Chỉ cần entity đầy đủ khi bạn sẽ sửa nó.

### Include đi kèm Select thì sao?

Nó bị bỏ qua hoàn toàn. Điều này gây bối rối vì code trông như đang eager load, nhưng EF Core chỉ nhìn vào projection để quyết định lấy gì. Kiểm tra bằng ToQueryString sẽ thấy không có JOIN nào cho navigation đó.

### Cartesian explosion xảy ra thế nào?

Include hai collection cùng lúc sinh ra JOIN chéo, nên một bản ghi cha có 10 con loại A và 20 con loại B sẽ trả về 200 dòng, mỗi dòng lặp lại toàn bộ cột của bản ghi cha. Kết quả vẫn đúng vì EF khử trùng lặp, nhưng dữ liệu đã đi qua mạng, và với ba collection thì con số nhân tiếp.

### Split query có nhược điểm gì?

Nó tách thành nhiều lần đi về database, và quan trọng hơn là không đảm bảo nhất quán: giữa truy vấn thứ nhất và thứ hai, dữ liệu có thể thay đổi, nên bạn nhận một ảnh chụp không nhất quán trừ khi bọc trong transaction.

### FindAsync khác FirstOrDefaultAsync ở đâu?

FindAsync kiểm tra change tracker trước nên có thể không sinh truy vấn nào, nhưng nó chỉ tìm theo khoá chính, không dùng được Include, và quan trọng nhất là nó bỏ qua global query filter nên vẫn trả về bản ghi đã xoá mềm.

### Vì sao không nên bật lazy loading?

Vì mọi truy cập navigation property âm thầm sinh truy vấn, nên một vòng lặp vô hại trong tầng trình bày có thể biến thành hàng trăm lần đi về database mà không có gì trong code báo hiệu.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Projection là mặc định cho đọc.** `Include` kèm `Select` bị bỏ qua.
2. **Nhiều `Include` collection gây nhân dòng.** Dùng `AsSplitQuery` hoặc projection.
3. **`FindAsync` bỏ qua global query filter** — nó thấy cả bản ghi đã xoá mềm.
