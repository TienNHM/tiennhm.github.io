# 8.4 — 3. Routing

> Nguồn: https://tiennhm.io.vn/en/docs/dotnet-backend-zero-to-senior/stage-03-aspnet-core-backend/module-08-aspnet-core-fundamentals/8.4-routing
> Attribute routing, route constraint, thứ tự ưu tiên khi nhiều route cùng khớp, versioning, và khi nào chọn Minimal API thay vì controller.

> Routing quyết định **request nào chạy code nào**, và nó xảy ra ở hai bước tách biệt: `UseRouting()` **chọn** endpoint, `MapControllers()` **chạy** endpoint — mọi middleware nằm giữa hai bước đó đều biết endpoint nào sắp chạy. Thứ đáng học kỹ nhất là **route constraint**: `{id:int}` không chỉ để đẹp, nó khiến `/customers/abc` trả **404** thay vì đi vào action rồi nổ khi ép kiểu. Và khi nhiều route cùng khớp, ASP.NET Core **không chọn cái đăng ký trước** — nó chấm điểm theo độ cụ thể, nên `/customers/active` thắng `/customers/{id}` bất kể thứ tự.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Thiết kế route REST với attribute routing.
- Dùng constraint để chặn dữ liệu sai ngay ở tầng định tuyến.
- Giải thích cách ASP.NET Core chọn khi nhiều route cùng khớp.
- Triển khai versioning cho API.
- Chọn giữa controller và Minimal API có lý do.

## Nội dung bài học

### 8.4.1 — Hai bước của routing

```csharp
app.UseRouting();        // buoc 1: CHON endpoint, chua chay
app.UseAuthorization();  // biet endpoint roi -> doc duoc [Authorize] tren no
app.MapControllers();    // buoc 2: CHAY endpoint
```

Tách làm hai bước là có chủ đích: middleware nằm giữa có thể đọc metadata của endpoint sắp chạy. Đó là cách `UseAuthorization()` biết action nào cần quyền gì mà không phải tự phân tích URL.

```csharp
app.UseRouting();
app.Use(async (ctx, next) =>
{
    var name = ctx.GetEndpoint()?.DisplayName;   // null neu dat truoc UseRouting
    ...
    await next(ctx);
});
```

### 8.4.2 — Attribute routing

```csharp
[ApiController]
[Route("api/v1/[controller]")]              // => api/v1/customers
public class CustomersController : ControllerBase
{
    [HttpGet]                                // GET    api/v1/customers
    public Task<IActionResult> GetAll([FromQuery] PagedRequest request, CancellationToken ct);

    [HttpGet("{id:guid}", Name = "GetCustomer")]  // GET  api/v1/customers/{guid}
    public Task<IActionResult> GetById(Guid id, CancellationToken ct);

    [HttpGet("{id:guid}/orders")]            // GET    api/v1/customers/{guid}/orders
    public Task<IActionResult> GetOrders(Guid id, CancellationToken ct);

    [HttpPost]                               // POST   api/v1/customers
    public Task<IActionResult> Create(CreateCustomerRequest request, CancellationToken ct);

    [HttpPut("{id:guid}")]                   // PUT    api/v1/customers/{guid}
    public Task<IActionResult> Update(Guid id, UpdateCustomerRequest request, CancellationToken ct);

    [HttpDelete("{id:guid}")]                // DELETE api/v1/customers/{guid}
    public Task<IActionResult> Delete(Guid id, CancellationToken ct);
}
```

Ba điểm đáng chú ý:

- **`[controller]`** là token thay bằng tên lớp bỏ hậu tố `Controller`. Tiện, nhưng nghĩa là **đổi tên lớp là đổi URL** — một thay đổi phá vỡ hợp đồng API mà refactor tool sẽ vui vẻ làm hộ bạn. Với API công khai, viết thẳng `[Route("api/v1/customers")]`.
- **`Name = "GetCustomer"`** cho phép `CreatedAtRoute("GetCustomer", ...)` sinh URL mà không nối chuỗi.
- **Route lồng nhau phản ánh quan hệ sở hữu**: `/customers/{id}/orders` nói rằng order thuộc về customer. Đừng lồng quá hai tầng — `/customers/{a}/orders/{b}/lines/{c}` khó đọc và khó phân quyền.

Route tuyệt đối (bắt đầu bằng `/`) bỏ qua `[Route]` ở lớp:

```csharp
[HttpGet("/health/customers")]    // KHONG co tien to api/v1
```

### 8.4.3 — Constraint chặn lỗi sớm

| Constraint | Ví dụ | Khớp |
|---|---|---|
| `int` | `{id:int}` | Số nguyên |
| `guid` | `{id:guid}` | GUID |
| `long`, `decimal`, `bool`, `datetime` | `{d:datetime}` | Theo kiểu |
| `min(n)`, `max(n)`, `range(a,b)` | `{page:min(1)}` | Giá trị số |
| `minlength(n)`, `maxlength(n)`, `length(n)` | `{code:length(3)}` | Độ dài chuỗi |
| `alpha` | `{name:alpha}` | Chỉ chữ cái |
| `regex(...)` | `{code:regex(^[A-Z]{{3}}$)}` | Biểu thức chính quy |
| `required` | `{id:required}` | Không rỗng |

```csharp
[HttpGet("{id:guid}")]           // /customers/abc -> 404, khong vao action
[HttpGet("page/{n:int:min(1)}")] // ghep nhieu constraint bang dau hai cham
```

Điểm quan trọng: **constraint sai thì trả 404, không phải 400**. Về REST điều đó hợp lý — không có tài nguyên nào ở URL đó. Nhưng nó có nghĩa là client nhận 404 mà không biết mình gõ sai định dạng. Với những chỗ cần thông báo rõ, nhận `string` rồi validate trong action để trả 400 kèm lý do.

Trong `regex`, dấu `{` và `}` phải nhân đôi vì route template đã dùng chúng.

Constraint **không phải** cơ chế bảo mật hay validation nghiệp vụ — nó chỉ lọc định dạng. Validation thật ở [bài 8.6](8.6-model-validation.mdx).

### 8.4.4 — Khi nhiều route cùng khớp

```csharp
[HttpGet("{id:guid}")]     // /customers/{guid}
[HttpGet("active")]        // /customers/active
```

ASP.NET Core **không** chọn theo thứ tự đăng ký. Nó chấm điểm theo độ cụ thể, ưu tiên giảm dần:

1. Đoạn **chữ cố định** (`active`) thắng tham số.
2. Tham số **có constraint** (`{id:guid}`) thắng tham số trần.
3. Tham số trần (`{id}`) thắng catch-all.
4. Catch-all (`{**rest}`) thua tất cả.

Nên `/customers/active` luôn vào đúng action dù nó đăng ký sau.

Khi hai route **cùng điểm**, bạn nhận `AmbiguousMatchException` **lúc chạy** — không phải lúc biên dịch:

```csharp
[HttpGet("{id:int}")]      public IActionResult A(int id);
[HttpGet("{code:int}")]    public IActionResult B(int code);   // cung diem -> nem
```

Gỡ bằng `[HttpGet("...", Order = -1)]` (số nhỏ chạy trước), nhưng tốt hơn là sửa thiết kế route cho không mơ hồ.

### 8.4.5 — Versioning

```bash
dotnet add package Asp.Versioning.Mvc
```

```csharp
builder.Services.AddApiVersioning(options =>
{
    options.DefaultApiVersion = new ApiVersion(1, 0);
    options.AssumeDefaultVersionWhenUnspecified = true;
    options.ReportApiVersions = true;          // tra header api-supported-versions
}).AddMvc();
```

```csharp
[ApiVersion("1.0")]
[ApiVersion("2.0")]
[Route("api/v{version:apiVersion}/customers")]
public class CustomersController : ControllerBase
{
    [HttpGet, MapToApiVersion("1.0")]
    public Task<IActionResult> GetAllV1(CancellationToken ct);

    [HttpGet, MapToApiVersion("2.0")]
    public Task<IActionResult> GetAllV2(CancellationToken ct);
}
```

Ba cách đặt version, và mỗi cách có cái giá của nó:

| Cách | Ví dụ | Đánh đổi |
|---|---|---|
| **URL** | `/api/v2/customers` | Dễ thấy, dễ test bằng trình duyệt; nhưng URL của cùng một tài nguyên thay đổi theo version |
| **Header** | `api-version: 2.0` | URL ổn định, đúng tinh thần REST; nhưng không test được bằng thanh địa chỉ |
| **Query** | `?api-version=2.0` | Dễ dùng; nhưng lẫn với tham số nghiệp vụ |

URL versioning phổ biến nhất trong thực tế vì nó **hiển nhiên** — người đọc log, người viết tài liệu và người debug đều thấy ngay.

### 8.4.6 — Minimal API hay controller

```csharp
var customers = app.MapGroup("/api/v1/customers")
                   .WithTags("Customers")
                   .RequireAuthorization();

customers.MapGet("/", async (ICustomerService svc, CancellationToken ct)
    => Results.Ok(await svc.GetAllAsync(ct)));

customers.MapGet("/{id:guid}", async (Guid id, ICustomerService svc, CancellationToken ct)
    => await svc.GetByIdAsync(id, ct) is { } c ? Results.Ok(c) : Results.NotFound())
    .WithName("GetCustomer");

customers.MapPost("/", async (CreateCustomerRequest req, ICustomerService svc, CancellationToken ct) =>
{
    var c = await svc.CreateAsync(req, ct);
    return Results.CreatedAtRoute("GetCustomer", new { id = c.Id }, c);
});
```

`MapGroup` (.NET 7+) xoá phần lớn lý do cũ để chọn controller: nó cho bạn tiền tố chung, `RequireAuthorization()` chung, filter chung.

| Chọn Minimal API khi | Chọn controller khi |
|---|---|
| Service nhỏ, ít endpoint | API lớn, nhiều action cùng nhóm |
| Ưu tiên thời gian khởi động và thông lượng | Cần action filter, model binder tuỳ biến |
| Endpoint chủ yếu là chuyển tiếp | Cần `[ApiController]` với validation tự động |
| Team quen lập trình hàm | Team quen MVC, có sẵn quy ước |

Đừng **trộn hai kiểu cho cùng một tài nguyên**. Hai nơi định nghĩa `/customers` với hai quy ước phản hồi khác nhau là nợ kỹ thuật ngay từ ngày đầu.

### 8.4.7 — Rà lại code của bạn

**Danh sách rà soát routing**

- [ ] Mọi tham số route đều có constraint phù hợp kiểu dữ liệu.
- [ ] API công khai không dùng token [controller] trong route.
- [ ] Route có tên khi cần sinh URL bằng CreatedAtRoute.
- [ ] Không lồng tài nguyên quá hai tầng.
- [ ] Đã kiểm tra không có route nào mơ hồ gây AmbiguousMatchException.
- [ ] API có chiến lược version rõ ràng và nhất quán.
- [ ] Một tài nguyên chỉ được định nghĩa bằng một kiểu: controller hoặc Minimal API.
- [ ] Middleware cần biết endpoint được đặt sau UseRouting().

## Bài tập áp dụng

1. **Constraint chặn sớm.** Viết hai action, một dùng `{id:guid}` và một dùng `{id}`. Gọi cả hai với `abc` và ghi lại status code cùng nơi lỗi xảy ra trong mỗi trường hợp.

2. **Thứ tự ưu tiên.** Đăng ký `[HttpGet("{id:guid}")]` **trước** `[HttpGet("active")]`, gọi `/customers/active` và xác nhận nó vào đúng action thứ hai. Giải thích vì sao thứ tự không quan trọng.

3. **Route mơ hồ.** Tạo hai action có route cùng điểm số, chạy ứng dụng và ghi lại `AmbiguousMatchException` — chú ý nó xảy ra **lúc chạy**, không phải lúc build. Gỡ bằng `Order` rồi bằng cách sửa thiết kế, so sánh hai cách.

## Tự kiểm tra

### Vì sao routing tách thành UseRouting và MapControllers?

Để mọi middleware nằm giữa hai bước đó biết endpoint nào sắp chạy và đọc được metadata của nó. Đó là cách UseAuthorization biết action nào cần quyền gì mà không phải tự phân tích URL. Middleware đặt trước UseRouting thì GetEndpoint trả về null.

### Route constraint sai thì trả mã lỗi nào?

404 chứ không phải 400, vì về mặt REST thì không có tài nguyên nào ở URL đó. Nghĩa là client nhận 404 mà không biết mình gõ sai định dạng. Với những chỗ cần thông báo rõ thì nhận string rồi validate trong action để trả 400 kèm lý do.

### Khi nhiều route cùng khớp thì ASP.NET Core chọn thế nào?

Không theo thứ tự đăng ký mà theo độ cụ thể: đoạn chữ cố định thắng tham số, tham số có constraint thắng tham số trần, tham số trần thắng catch-all. Nên /customers/active luôn vào đúng action dù đăng ký sau /customers/{id}.

### AmbiguousMatchException xảy ra khi nào?

Khi hai route có cùng điểm số cụ thể, và nó xảy ra lúc chạy chứ không phải lúc biên dịch. Có thể gỡ bằng thuộc tính Order với số nhỏ chạy trước, nhưng tốt hơn là sửa thiết kế route cho không mơ hồ.

### Dùng token [controller] trong route có vấn đề gì?

Nó lấy tên lớp bỏ hậu tố Controller, nên đổi tên lớp là đổi URL. Đó là một thay đổi phá vỡ hợp đồng API mà công cụ refactor sẽ vui vẻ làm hộ bạn mà không cảnh báo. Với API công khai thì nên viết thẳng đường dẫn.

### Chọn Minimal API hay controller?

Minimal API hợp với service nhỏ, ít endpoint, ưu tiên thời gian khởi động và thông lượng; MapGroup từ .NET 7 đã xoá phần lớn lý do cũ để chọn controller. Controller hợp với API lớn cần action filter, model binder tuỳ biến hoặc validation tự động của ApiController. Quan trọng nhất là đừng trộn hai kiểu cho cùng một tài nguyên.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Constraint chặn dữ liệu sai ở tầng định tuyến** — nhưng nó trả 404, không phải 400.
2. **Độ cụ thể quyết định, không phải thứ tự đăng ký.**
3. **Chọn một kiểu cho mỗi tài nguyên** — controller hoặc Minimal API, đừng trộn.
