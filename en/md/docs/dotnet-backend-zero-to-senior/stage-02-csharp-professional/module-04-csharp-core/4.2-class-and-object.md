# 4.2 — 1. Class và Object

> Nguồn: https://tiennhm.io.vn/en/docs/dotnet-backend-zero-to-senior/stage-02-csharp-professional/module-04-csharp-core/4.2-class-and-object
> Class là khuôn, object là thứ đúc ra từ khuôn. Kèm constructor bảo đảm object luôn hợp lệ ngay từ lúc sinh ra, khác biệt class với struct, và vì sao đừng để object rơi vào trạng thái nửa vời.

> Class là khuôn, object là thứ đúc ra từ khuôn đó. Nhưng điều đáng học không nằm ở cú pháp mà ở một nguyên tắc: **object phải hợp lệ ngay từ khoảnh khắc nó được tạo ra**. Constructor tồn tại để bảo đảm điều đó — nó là cơ hội **duy nhất** bạn có để từ chối một object sai. Bỏ qua cơ hội này thì hệ thống phải mang theo một loại object luôn có thể đang ở trạng thái nửa vời, và mọi phương thức dùng nó đều phải kiểm tra lại. Bài này cũng làm rõ khác biệt giữa `class` và `struct`, một quyết định ảnh hưởng tới cách object được sao chép và so sánh.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Khai báo class với field, property và constructor cho đúng vai trò từng thứ.
- Viết constructor bảo đảm object không bao giờ tồn tại ở trạng thái không hợp lệ.
- Chọn giữa `class` và `struct` theo tiêu chí rõ ràng.
- Dùng `init` và `required` để bất biến hoá mà vẫn khởi tạo linh hoạt.
- Nhận ra và tránh mẫu "object nửa vời".

## Nội dung bài học

### 4.2.1 — Class là khuôn, object là sản phẩm

```csharp
// Khuôn — mô tả một khách hàng TRÔNG như thế nào và LÀM được gì
public class Customer
{
    public int Id { get; }
    public string Name { get; private set; }
    public decimal TotalSpent { get; private set; }

    public Customer(int id, string name)
    {
        Id = id;
        Name = name;
    }

    public void RecordPurchase(decimal amount) => TotalSpent += amount;
}

// Object — thứ đúc ra từ khuôn
var a = new Customer(1, "Nguyen Van A");
var b = new Customer(2, "Tran Thi B");
```

`a` và `b` dùng chung một khuôn nhưng là **hai vùng nhớ độc lập**. Sửa `a` không đụng tới `b` — vì đây là kiểu tham chiếu, và như [bài 1.2](https://tiennhm.io.vn/docs/dotnet-backend-zero-to-senior/stage-01-foundation/module-01-programming-logic/1.2-variables-and-data-types) đã nói, phép gán `var c = a;` mới là chỗ cần cẩn thận.

### 4.2.2 — Field hay property?

```csharp
public class Order
{
    private decimal _total;              // field: trạng thái nội bộ
    public decimal Total => _total;      // property: cách bên ngoài nhìn vào

    public string Code { get; init; }    // auto-property, chỉ gán lúc khởi tạo
    public int LineCount { get; private set; }   // đọc công khai, ghi nội bộ
}
```

Quy tắc dùng được ngay: **field luôn `private`, property là thứ công khai**.

Lý do không phải hình thức. Property là một **điểm chặn**: sau này bạn thêm được kiểm tra, ghi log, hoặc tính toán lười mà **không phá vỡ code đang gọi**. Field công khai thì không có chỗ nào để chèn những thứ đó, và đổi nó thành property là một thay đổi phá vỡ tương thích nhị phân.

```csharp
// Hôm nay
public decimal Total { get; private set; }

// Sáu tháng sau — thêm kiểm tra, code gọi KHÔNG phải sửa
private decimal _total;
public decimal Total
{
    get => _total;
    private set => _total = value >= 0 ? value : throw new ArgumentException();
}
```

### 4.2.3 — Constructor: cơ hội duy nhất để từ chối

Đây là ý quan trọng nhất của bài.

```csharp
// YẾU — object có thể tồn tại ở trạng thái vô nghĩa
public class Order
{
    public int CustomerId { get; set; }
    public decimal Total { get; set; }
}

var order = new Order();       // CustomerId = 0, Total = 0 — đơn hàng của ai?
```

Object trên **hợp lệ về mặt cú pháp nhưng vô nghĩa về mặt nghiệp vụ**. Và vì nó tồn tại được, mọi hàm nhận `Order` đều phải phòng thủ: kiểm tra `CustomerId > 0`, kiểm tra `Total`, kiểm tra lại ở tầng sau nữa.

```csharp
// MẠNH — không có cách nào tạo ra một Order vô nghĩa
public class Order
{
    public int CustomerId { get; }
    public decimal Total { get; private set; }
    public OrderStatus Status { get; private set; }

    public Order(int customerId, decimal total)
    {
        if (customerId <= 0)
            throw new ArgumentOutOfRangeException(nameof(customerId));
        if (total < 0)
            throw new ArgumentOutOfRangeException(nameof(total));

        CustomerId = customerId;
        Total = total;
        Status = OrderStatus.Draft;
    }
}
```

Lợi ích lan ra toàn hệ thống: **mọi hàm nhận `Order` giờ được bảo đảm nó hợp lệ**, nên chúng không cần kiểm tra lại. Đây là cách giảm số lượng `if` trong codebase nhiều nhất trên mỗi dòng bỏ ra.

Nguyên tắc chung: **làm cho trạng thái sai không biểu diễn được**, thay vì kiểm tra trạng thái sai ở khắp nơi.

### 4.2.4 — `init` và `required`

```csharp
public class Customer
{
    public required string Name { get; init; }   // C# 11: bắt buộc phải gán
    public required string Email { get; init; }
    public string? Phone { get; init; }          // tuỳ chọn
}

var c = new Customer { Name = "A", Email = "a@company.com" };
c.Name = "B";        // Lỗi biên dịch — init chỉ gán được lúc khởi tạo

var bad = new Customer { Name = "A" };   // Lỗi biên dịch — thiếu Email
```

Bộ đôi này cho bạn **cú pháp khởi tạo bằng object initializer** mà vẫn giữ được hai bảo đảm của constructor: không thiếu trường bắt buộc, và không sửa được sau khi tạo.

Khi nào dùng cái nào:

- **Constructor** khi việc tạo object cần kiểm tra chéo giữa nhiều trường, hoặc cần tính toán.
- **`required` + `init`** khi chỉ cần gán thẳng và số trường nhiều (constructor 8 tham số rất khó đọc ở chỗ gọi).

### 4.2.5 — `class` hay `struct`

| | `class` | `struct` |
|---|---|---|
| Loại kiểu | Tham chiếu | Giá trị |
| Phép gán | Chép địa chỉ | **Chép toàn bộ dữ liệu** |
| So sánh `==` mặc định | Theo tham chiếu | Theo từng trường |
| Có thể `null` | Có | Không (trừ `Nullable`) |
| Kế thừa | Có | Không |

Tiêu chí chọn `struct`, cần **đủ cả bốn**:

1. Kích thước nhỏ, thường dưới 16 byte.
2. Bất biến về mặt logic.
3. Sẽ được tạo ra rất nhiều.
4. Không cần kế thừa.

Trong code nghiệp vụ backend, câu trả lời gần như luôn là `class`. `struct` thuộc về những chỗ nhạy hiệu năng — toạ độ, khoảng thời gian, định danh nhỏ.

Cảnh báo về `struct` có thể thay đổi:

```csharp
struct Point { public int X; public int Y; }

var list = new List<Point> { new() { X = 1, Y = 2 } };
// list[0].X = 99;    // Lỗi biên dịch — list[0] trả về một BẢN SAO
```

Đây là nguồn nhầm lẫn kinh điển. Nếu bạn định làm `struct`, hãy làm nó bất biến — hoặc dùng `readonly record struct`.

### 4.2.6 — `static`: thuộc về class, không thuộc về object

```csharp
public class Order
{
    private static int _counter;                     // dùng chung mọi object
    public static Order CreateDraft(int customerId)  // gọi không cần object
        => new Order(customerId, 0m);

    public int SequenceNumber { get; }               // riêng từng object

    private Order(int customerId, decimal total) { /* ... */ }
}

var o = Order.CreateDraft(42);      // gọi trên CLASS
```

`static` hợp cho hàm tiện ích thuần tuý và factory method. Nhưng **trạng thái `static` có thể thay đổi là nguồn lỗi khó lần nhất trong ứng dụng web**: mọi request dùng chung nó, và nhiều request chạy song song.

```csharp
// SAI trong ứng dụng web — tranh chấp giữa các request
public static List<Order> Cache = new();
```

Nếu cần trạng thái dùng chung, hãy đi qua dependency injection với vòng đời được khai báo rõ — chủ đề của Module 7 và của bài [Singleton, Scoped hay Transient](https://tiennhm.io.vn/blog/singleton-scoped-transient-captive-dependency).

### 4.2.7 — Rà lại code của bạn

**Danh sách rà soát class và object**

- [ ] Mọi field đều private; bên ngoài chỉ thấy property.
- [ ] Constructor từ chối mọi tham số làm object rơi vào trạng thái vô nghĩa.
- [ ] Không có class nghiệp vụ nào có constructor rỗng cộng toàn bộ property set công khai.
- [ ] Trường bắt buộc dùng required hoặc nằm trong constructor, không để người gọi quên.
- [ ] Trường không đổi sau khi tạo dùng init hoặc chỉ có getter.
- [ ] Không có trạng thái static có thể thay đổi nào trong code chạy theo request.
- [ ] struct nếu có thì bất biến; không có struct nào có field public settable.

## Bài tập áp dụng

#### Bài 1 — Đếm phòng thủ thừa

Chọn một class nghiệp vụ có constructor rỗng. Đếm số lần các hàm khác phải kiểm tra lại tính hợp lệ của nó. Viết lại constructor để chặn từ đầu, rồi đếm số `if` xoá được.

**Tiêu chí hoàn thành:** bạn có hai con số — trước và sau — và nêu được vì sao cách mới **không thể** bị bỏ sót.

Gợi ý và lời giải — Bài 1

**Gợi ý.** Tìm các câu kiểm tra lặp lại nhiều nơi trên cùng một đối tượng:

```bash
grep -rn "string.IsNullOrEmpty(customer\|customer.Name == null\|customer.Email == null" --include=*.cs .
```

**Lời giải — trước:**

```csharp
public class Customer
{
    public string Name { get; set; }
    public string Email { get; set; }
    public decimal Revenue { get; set; }
}
```

Vì constructor không đòi hỏi gì, mọi hàm dùng `Customer` phải tự phòng thủ:

```csharp
public void GuiEmailChaoMung(Customer c)
{
    if (string.IsNullOrWhiteSpace(c.Email)) return;      // kiểm tra 1
    if (!c.Email.Contains('@')) return;                  // kiểm tra 2
    _smtp.Send(c.Email, $"Chào {c.Name ?? "bạn"}");      // kiểm tra 3 (ngầm)
}

public string HienThi(Customer c)
{
    if (string.IsNullOrWhiteSpace(c.Name)) return "(chưa có tên)";   // kiểm tra 4
    return c.Name;
}

public decimal TinhHoaHong(Customer c)
{
    if (c.Revenue < 0) return 0;                         // kiểm tra 5
    return c.Revenue * 0.05m;
}
```

**Sau — chặn tại constructor:**

```csharp
public class Customer
{
    public string Name { get; private set; }
    public Email Email { get; private set; }
    public decimal Revenue { get; private set; }

    public Customer(string name, Email email)
    {
        if (string.IsNullOrWhiteSpace(name))
            throw new ArgumentException("Tên khách hàng không được rỗng", nameof(name));

        Name = name;
        Email = email;      // Email tự xác thực trong constructor của nó
        Revenue = 0m;
    }

    public void GhiNhanDoanhThu(decimal soTien)
    {
        if (soTien <= 0)
            throw new ArgumentOutOfRangeException(nameof(soTien), "Doanh thu phải dương");
        Revenue += soTien;
    }
}
```

Các hàm dùng nó rút gọn lại:

```csharp
public void GuiEmailChaoMung(Customer c) => _smtp.Send(c.Email.Value, $"Chào {c.Name}");
public string HienThi(Customer c) => c.Name;
public decimal TinhHoaHong(Customer c) => c.Revenue * 0.05m;
```

**Kết quả: 5 kiểm tra xuống 0.**

**Vì sao cách mới không thể bị bỏ sót — và đây mới là điểm chính.** Chuyển kiểm tra vào constructor không chỉ giảm số dòng. Nó đổi **bản chất** của bảo đảm:

| | Kiểm tra rải rác | Kiểm tra trong constructor |
|---|---|---|
| Ai chịu trách nhiệm | Mọi người dùng lớp | Chính lớp đó |
| Quên một chỗ | Rất dễ, và không ai biết | **Không có chỗ nào để quên** |
| Thêm hàm mới | Phải nhớ kiểm tra lại | Không cần nghĩ tới |
| Bằng chứng | Không có | Tồn tại một `Customer` là bằng chứng nó hợp lệ |

Dòng cuối là điều đáng giá nhất. Khi constructor là **lối vào duy nhất** và nó từ chối dữ liệu sai, thì **sự tồn tại của đối tượng chính là bằng chứng nó hợp lệ**. Người đọc code không cần tự hỏi "chỗ này `Name` có thể null không" nữa.

**Ba điều cần có để bảo đảm này không bị thủng:**

1. **Không có constructor rỗng công khai.** Có một cái là mọi bảo đảm mất hiệu lực.
2. **Không có setter công khai.** Nếu không, người ta tạo hợp lệ rồi gán sai sau.
3. **Thay đổi trạng thái qua phương thức có tên nghiệp vụ**, và mỗi phương thức tự kiểm tra phần của nó.

**Một lưu ý về EF Core.** EF Core cần một constructor để dựng lại đối tượng từ database. Giải pháp là để nó `private`:

```csharp
private Customer() { }    // chỉ EF Core dùng, qua reflection
```

Trình biên dịch vẫn chặn code thường gọi nó, còn EF Core vẫn hoạt động. [Bài 13.3](../../stage-04-database-production/module-13-entity-framework-core/13.3-dbcontext-and-entity-configuration.mdx) trình bày chi tiết.

#### Bài 2 — Chứng minh bản sao của `struct`

Tạo một `struct` có field công khai, đưa vào `List`, rồi thử sửa qua chỉ số. Ghi lại lỗi biên dịch. Đổi sang `class` và làm lại.

**Tiêu chí hoàn thành:** bạn ghi lại được **mã lỗi** và giải thích vì sao mảng thì sửa được còn `List` thì không.

Gợi ý và lời giải — Bài 2

**Gợi ý.** Bộ chỉ mục của `List` là một **phương thức** trả về giá trị. Với kiểu giá trị, thứ trả về là một **bản sao**. Sửa một bản sao vừa được trả về thì có ý nghĩa gì?

**Lời giải.**

```csharp
public struct Diem { public int X; public int Y; }

var ds = new List<Diem> { new Diem { X = 1 } };
ds[0].X = 99;        // LỖI BIÊN DỊCH
```

**Lỗi thật trên .NET 9:**

```text
error CS1612: Cannot modify the return value of 'List<Diem>.this[int]'
              because it is not a variable
```

**Nhưng mảng thì được:**

```csharp
var mang = new Diem[] { new Diem { X = 1 } };
mang[0].X = 99;
Console.WriteLine(mang[0].X);   // 99
```

**Vì sao khác nhau.** Đây là chi tiết mà rất ít người biết:

- `List` có bộ chỉ mục là một **phương thức**. Với `struct`, nó trả về một **bản sao** trên ngăn xếp. Nếu C# cho phép sửa bản sao đó, thay đổi sẽ biến mất ngay lập tức mà không báo gì — nên trình biên dịch chặn thẳng.
- Mảng thì khác: `mang[0]` được trình biên dịch dịch thành **truy cập trực tiếp vào ô nhớ** của phần tử, không qua bản sao. Vì vậy sửa được, và sửa có tác dụng thật.

**Cách sửa phần tử `struct` trong `List`:**

```csharp
// Cách 1 — lấy ra, sửa, gán lại
var tam = ds[0];
tam.X = 99;
ds[0] = tam;

// Cách 2 — dùng CollectionsMarshal (nhanh, nhưng phải hiểu rủi ro)
ref var r = ref CollectionsMarshal.AsSpan(ds)[0];
r.X = 99;
```

Cách 2 lấy tham chiếu thẳng tới bộ nhớ nội bộ của `List`. Nó nhanh nhưng **tham chiếu đó trở nên không hợp lệ** nếu `List` thay đổi kích thước, nên chỉ dùng trong vòng lặp nóng và khi bạn chắc chắn không thêm bớt phần tử.

**Bài học lớn hơn cả lỗi biên dịch này.** `struct` là kiểu giá trị, nên **mọi** phép gán, mọi lần truyền tham số, mọi lần trả về đều tạo bản sao. Điều đó dẫn tới một quy tắc:

> **`struct` nên là bất biến.** Khai báo `readonly struct` và chỉ dùng thuộc tính `init`.

`struct` có thể thay đổi là nguồn của một lớp lỗi rất khó tìm, vì bạn sửa một bản sao mà tưởng đang sửa bản gốc. Trình biên dịch bắt được trường hợp `List` ở trên, nhưng không bắt được mọi trường hợp — ví dụ truyền `struct` vào một hàm rồi hàm đó sửa nó.

**Khi nào dùng `struct`.** Khi đối tượng nhỏ (dưới 16 byte), bất biến, và được tạo với số lượng rất lớn — ví dụ toạ độ, khoảng thời gian, số tiền. Ngoài ra thì `class` là mặc định đúng. [Bài 4.8](4.8-records-and-value-objects.mdx) bàn về `record struct`, kết hợp tính bất biến với so sánh theo giá trị.

#### Bài 3 — Đua trên trạng thái `static`

Viết một endpoint ghi vào một `static List`, gọi song song 50 request. Ghi lại ngoại lệ hoặc dữ liệu sai nhận được.

**Tiêu chí hoàn thành:** bạn tái hiện được lỗi, và nêu được vì sao nó **không xuất hiện** khi thử một mình.

Gợi ý và lời giải — Bài 3

**Gợi ý.** `List` **không an toàn khi truy cập đồng thời**. Khi hai luồng cùng `Add` một lúc, chúng có thể cùng đọc một giá trị `_size`, cùng ghi vào một ô, hoặc gặp nhau giữa lúc mảng nội bộ đang được cấp phát lại.

**Lời giải.**

```csharp
public static class KhoTam
{
    public static readonly List<string> DanhSach = new();
}

app.MapPost("/them", (string ten) =>
{
    KhoTam.DanhSach.Add(ten);
    return Results.Ok(KhoTam.DanhSach.Count);
});
```

Gọi song song:

```bash
for i in $(seq 1 50); do curl -s -X POST "localhost:5000/them?ten=$i" & done; wait
curl -s localhost:5000/dem
```

**Ba kết quả có thể xảy ra, tất cả đều sai:**

| Triệu chứng | Nguyên nhân |
|---|---|
| `Count` nhỏ hơn 50 | Hai luồng ghi đè cùng một ô |
| `IndexOutOfRangeException` | Ghi trong lúc mảng nội bộ đang được cấp phát lại |
| `NullReferenceException` khi duyệt | Đọc một ô chưa kịp được gán |

Điều đáng sợ là **kết quả không ổn định**: chạy mười lần có thể được chín lần đúng.

**Vì sao không xuất hiện khi thử một mình.** Thử thủ công nghĩa là gửi từng request một, nên không bao giờ có hai luồng cùng ở trong `Add` tại một thời điểm. Lỗi đua chỉ xuất hiện khi các thao tác **chồng lấn nhau về thời gian**, và xác suất đó tăng theo tải. Đây là lý do một lớp lỗi cả nhóm gọi là "lỗi chỉ có trên production".

**Ba cách sửa, theo thứ tự nên cân nhắc:**

```csharp
// Cách 1 — ĐỪNG dùng trạng thái static. Gần như luôn là câu trả lời đúng.
//   Dữ liệu cần chia sẻ -> database hoặc Redis.

// Cách 2 — nếu buộc phải giữ trong bộ nhớ, dùng kiểu an toàn đồng thời
public static readonly ConcurrentBag<string> DanhSach = new();

// Cách 3 — khoá tường minh, khi cần thao tác phức hợp
private static readonly Lock _khoa = new();
public static void Them(string ten)
{
    lock (_khoa) { DanhSach.Add(ten); }
}
```

**Vì sao cách 1 gần như luôn đúng.** Ngay cả khi bạn làm cho `static List` an toàn về mặt đồng thời, nó vẫn còn ba vấn đề chưa được giải quyết:

1. **Mất khi khởi động lại.** Mỗi lần triển khai là dữ liệu bay hết.
2. **Không dùng chung giữa các thể hiện.** Chạy hai bản ứng dụng là có hai danh sách khác nhau — đúng vấn đề đã chứng minh ở [bài 2.9](../../stage-01-foundation/module-02-computer-science-basics/2.9-hosting-and-cloud-co-ban.mdx).
3. **Tăng vô hạn.** Không có gì dọn nó, nên bộ nhớ chỉ có tăng.

**Trạng thái `static` chấp nhận được khi nào.** Khi nó **bất biến** và chỉ đọc: bảng tra hằng số, cấu hình nạp một lần lúc khởi động, biểu thức chính quy đã biên dịch. Đặc điểm chung là **không ai ghi vào nó sau khi khởi tạo**.

```csharp
// An toàn — bất biến, chỉ đọc
private static readonly IReadOnlyDictionary<string, decimal> PhiTheoKhuVuc =
    new Dictionary<string, decimal> { ["HN"] = 25_000m, ["HCM"] = 30_000m };

private static readonly Regex EmailPattern =
    new(@"^[^@\s]+@[^@\s]+$", RegexOptions.Compiled);
```

[Module 7](../module-07-dependency-injection/) trình bày cách thay trạng thái `static` bằng service có vòng đời rõ ràng, và vì sao `Singleton` giữ trạng thái người dùng lại là cùng một lỗi này dưới dạng khác.

## Tự kiểm tra

### Vì sao field nên private còn property mới là thứ công khai?

Vì property là một điểm chặn: sau này bạn thêm được kiểm tra, ghi log hoặc tính toán lười mà không phá vỡ code đang gọi. Field công khai không có chỗ nào để chèn những thứ đó, và đổi nó thành property là một thay đổi phá vỡ tương thích nhị phân.

### Vì sao constructor quan trọng đến thế?

Vì nó là cơ hội duy nhất để từ chối một object sai. Nếu constructor không kiểm tra, hệ thống phải mang theo một loại object luôn có thể đang ở trạng thái nửa vời, và mọi hàm dùng nó đều phải kiểm tra lại. Chặn từ constructor là cách giảm số lượng if trong codebase nhiều nhất trên mỗi dòng bỏ ra.

### required và init giải quyết vấn đề gì?

Chúng cho bạn cú pháp object initializer dễ đọc mà vẫn giữ hai bảo đảm của constructor: required buộc phải gán trường bắt buộc nếu không thì lỗi biên dịch, init chỉ cho gán lúc khởi tạo nên object không sửa được sau đó. Hợp khi class có nhiều trường mà constructor tám tham số sẽ khó đọc.

### Khi nào nên dùng struct thay vì class?

Khi đủ cả bốn điều kiện: kích thước nhỏ thường dưới 16 byte, bất biến về mặt logic, sẽ được tạo rất nhiều, và không cần kế thừa. Trong code nghiệp vụ backend thì câu trả lời gần như luôn là class; struct thuộc về những chỗ nhạy hiệu năng như toạ độ hay khoảng thời gian.

### Vì sao không sửa được phần tử struct qua chỉ số của List?

Vì struct là kiểu giá trị, nên list[0] trả về một bản sao chứ không phải tham chiếu tới phần tử trong danh sách. Sửa bản sao đó không có ý nghĩa gì nên trình biên dịch chặn luôn. Đây là lý do struct nên bất biến, hoặc dùng readonly record struct.

### Vì sao trạng thái static có thể thay đổi lại nguy hiểm trong ứng dụng web?

Vì mọi request dùng chung nó và nhiều request chạy song song, nên xảy ra tranh chấp dữ liệu rất khó tái hiện. Nếu cần trạng thái dùng chung thì phải đi qua dependency injection với vòng đời khai báo rõ ràng, thay vì một biến static ẩn trong class.

## Kết luận

Ba điều đáng nhớ nhất:

1. **Constructor là cơ hội duy nhất để từ chối.** Dùng nó, và mọi hàm phía sau bớt được một tầng phòng thủ.
2. **Làm cho trạng thái sai không biểu diễn được** thay vì kiểm tra nó ở khắp nơi.
3. **`static` có thể thay đổi là bom hẹn giờ trong ứng dụng web.** Mọi request dùng chung một biến.
