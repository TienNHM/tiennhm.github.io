# 4.10 — Mở rộng và đào sâu

> Nguồn: https://tiennhm.io.vn/en/docs/dotnet-backend-zero-to-senior/stage-02-csharp-professional/module-04-csharp-core/4.10-advanced-notes
> Required members, primary constructor, static abstract interface, IDisposable và collection expression — tính năng C# hiện đại đáng dùng.

> Những tính năng C# nối tiếp Module 4, xếp theo mức độ nên dùng. Ba thứ đáng áp dụng **ngay**: `required` (trình biên dịch buộc gán thuộc tính bắt buộc — loại bỏ cả một nhóm lỗi `null` khi tạo đối tượng), **primary constructor** (bỏ được đoạn gán tham số lặp đi lặp lại), và **collection expression** (`[]` thay cho `new List()`). Một thứ cần cẩn thận: **`IDisposable`** — không phải vì nó khó, mà vì **quên `using` là rò rỉ tài nguyên không có thông báo lỗi nào**, và trong một ứng dụng web nó biểu hiện thành cạn connection pool sau vài giờ chạy.

## Mục tiêu bài học

Sau bài này bạn có thể:

- Dùng `required` và primary constructor để viết gọn hơn.
- Cài đặt `IDisposable` đúng cách và biết khi nào cần.
- Biết static abstract member giải quyết vấn đề gì.
- Chọn cú pháp hiện đại phù hợp với dự án.

## Nội dung bài học

### 4.11.1 — required members: dùng ngay

```csharp
// Trước — không có gì buộc phải gán Name
public class Lead
{
    public string Name { get; set; }        // cảnh báo: có thể null
    public string Email { get; set; }
}

var lead = new Lead();                       // biên dịch được, Name là null
```

```csharp
// Sau — trình biên dịch BUỘC phải gán
public class Lead
{
    public required string Name { get; init; }
    public required string Email { get; init; }
    public string? Phone { get; init; }      // tuy chon, ro rang
}

var lead = new Lead();                       // LOI BIEN DICH
var lead = new Lead { Name = "An", Email = "an@x.com" };   // OK
```

Lợi ích cụ thể: nó loại bỏ cả một nhóm lỗi `NullReferenceException` ở tầng **biên dịch**, thay vì chờ tới lúc chạy. Và nó làm rõ ý định: đọc lớp là biết ngay trường nào bắt buộc.

Kết hợp với `init` cho đối tượng chỉ đọc sau khi tạo — đúng với hầu hết DTO và tham số cấu hình.

### 4.11.2 — Primary constructor: dùng ngay

```csharp
// Trước — ba lần lặp lại mỗi tên
public class LeadService
{
    private readonly ILeadRepository _repository;
    private readonly ILogger<LeadService> _logger;

    public LeadService(ILeadRepository repository, ILogger<LeadService> logger)
    {
        _repository = repository;
        _logger = logger;
    }
}

// Sau — mot dong
public class LeadService(ILeadRepository repository, ILogger<LeadService> logger)
{
    public async Task<Lead?> GetAsync(LeadId id, CancellationToken ct)
        => await repository.GetByIdAsync(id, ct);
}
```

Tham số dùng được trực tiếp trong mọi phương thức. Rất hợp với DI, nơi lớp nào cũng có vài dependency ([Module 7](../module-07-dependency-injection/)).

**Lưu ý:** tham số primary constructor **không tự động là `readonly`** như trường được gán trong constructor thường. Nếu cần chắc chắn không đổi, vẫn gán vào trường `readonly`:

```csharp
public class LeadService(ILeadRepository repository)
{
    private readonly ILeadRepository _repository = repository;
}
```

Với `record`, primary constructor sinh luôn thuộc tính public — khác với `class`, nơi tham số chỉ nằm trong phạm vi lớp.

### 4.11.3 — Collection expression: dùng ngay

```csharp
// Trước
List<string> names = new List<string> { "An", "Bình" };
int[] numbers = new int[] { 1, 2, 3 };
private readonly List<Activity> _activities = new();

// Sau — cú pháp thống nhất cho mọi kiểu collection
List<string> names = ["An", "Bình"];
int[] numbers = [1, 2, 3];
private readonly List<Activity> _activities = [];

// Ghép bằng spread
int[] all = [..numbers, 4, 5];
```

Ngắn hơn và — quan trọng hơn — **thống nhất** cho `List`, mảng, `Span` và `ImmutableArray`. Trước đây mỗi kiểu có cú pháp khởi tạo riêng.

### 4.11.4 — IDisposable: cẩn thận

**Cần khi** lớp giữ tài nguyên mà garbage collector không tự dọn: file handle, kết nối mạng, kết nối database, `HttpClient` tạo thủ công.

```csharp
public sealed class ExcelExporter : IDisposable
{
    private readonly FileStream _stream;
    private bool _disposed;

    public ExcelExporter(string path) => _stream = File.Create(path);

    public void Dispose()
    {
        if (_disposed) return;               // an toàn khi gọi nhiều lần
        _stream.Dispose();
        _disposed = true;
    }
}

// Sử dụng — using đảm bảo Dispose được gọi KỂ CẢ khi có exception
using var exporter = new ExcelExporter("revenue-report.xlsx");
exporter.Export(data);
// Dispose tự động gọi ở cuối phạm vi
```

**Vì sao quên `using` nguy hiểm:** không có lỗi nào được báo. Chương trình chạy bình thường, chỉ là tài nguyên không được trả lại. Trong ứng dụng web, biểu hiện là sau vài giờ chạy, mọi request bắt đầu timeout vì connection pool đã cạn — và nguyên nhân rất khó lần ra từ triệu chứng đó.

**Bản bất đồng bộ** cho tài nguyên có thao tác đóng tốn thời gian:

```csharp
public sealed class Repository : IAsyncDisposable
{
    public async ValueTask DisposeAsync() => await _connection.DisposeAsync();
}

await using var repo = new Repository();
```

**Khi nào KHÔNG cần:** lớp chỉ chứa dữ liệu và object thường. Garbage collector lo được. Cài `IDisposable` cho lớp không giữ tài nguyên gì là thêm việc vô ích cho người dùng lớp đó.

Và trong ASP.NET Core, **đừng tự `new HttpClient`** — dùng `IHttpClientFactory`, nó quản lý vòng đời kết nối đúng cách ([bài 7.6](../module-07-dependency-injection/7.5-registering-services.mdx)).

### 4.11.5 — Static abstract interface member

**Ưu tiên thấp** — hữu ích cho thư viện, ít dùng trong code nghiệp vụ.

```csharp
public interface IParsable<TSelf> where TSelf : IParsable<TSelf>
{
    static abstract TSelf Parse(string s);
}

public readonly record struct LeadId(Guid Value) : IParsable<LeadId>
{
    public static LeadId Parse(string s) => new(Guid.Parse(s));
}

// Giờ gọi được phương thức tĩnh qua generic
T ParseFrom<T>(string s) where T : IParsable<T> => T.Parse(s);
```

Trước .NET 7, không có cách nào ràng buộc "kiểu này phải có phương thức tĩnh tên `Parse`". Tính năng này làm được, và nó là nền tảng cho generic math trong .NET.

Trong code CRM thông thường bạn hiếm khi cần — nhưng biết nó tồn tại giúp đọc hiểu code thư viện hiện đại.

### 4.11.6 — Những tính năng khác

| Tính năng | Việc làm | Ưu tiên |
|---|---|---|
| `file` modifier | Giới hạn kiểu trong một file | Thấp |
| Raw string literal `"""` | Chuỗi nhiều dòng không cần escape | **Trung bình** |
| `nameof` | Lấy tên biến thành chuỗi | **Cao** |
| Interpolated string handler | Nội suy chuỗi hiệu năng cao | Thấp |
| `sealed` | Cấm kế thừa, cho phép JIT tối ưu | **Trung bình** |

```csharp
// Raw string — rất tiện cho SQL và JSON
var sql = """
    SELECT Id, Name, Email
    FROM Leads
    WHERE TenantId = @tenantId
      AND Status <> 'Lost'
    """;

// nameof — đổi tên thuộc tính thì chuỗi tự đổi theo
throw new ArgumentNullException(nameof(request));
```

`nameof` đáng dùng ở mọi nơi cần tên thành viên dưới dạng chuỗi: nếu ai đó đổi tên bằng refactor của IDE, chuỗi tự đổi theo — còn chuỗi viết tay thì lặng lẽ sai.

`sealed` nên là mặc định cho lớp không thiết kế để kế thừa: nó thể hiện ý định rõ ràng và cho JIT tối ưu lời gọi phương thức ảo.

### 4.11.7 — Thứ tự nên dùng

| Ưu tiên | Tính năng | Vì sao |
|---|---|---|
| **Cao** | `required`, primary constructor, `nameof` | Rẻ, lợi ích rõ ngay |
| **Cao** | Collection expression | Ngắn và thống nhất |
| Trung bình | Raw string, `sealed` | Cải thiện rõ ở đúng chỗ |
| Trung bình | `IDisposable` | Cần khi giữ tài nguyên, cẩn thận với `using` |
| Thấp | Static abstract, `file` modifier | Cho thư viện, hiếm dùng trong nghiệp vụ |

Sau Module 4, bước tiếp theo là [Module 5 — Advanced C#](../module-05-advanced-csharp/).

## Bài tập áp dụng

#### Bài 1 — Áp dụng `required`

Chọn một DTO trong dự án, thêm `required` cho trường bắt buộc và xem trình biên dịch bắt được bao nhiêu chỗ tạo thiếu.

**Tiêu chí hoàn thành:** bạn có **số lỗi biên dịch**, và phân biệt được `required` với kiểm chứng lúc chạy — hai thứ giải quyết hai vấn đề khác nhau.

Gợi ý và lời giải — Bài 1

**Gợi ý.** `required` là ràng buộc lúc **biên dịch**. Nó không thay thế `FluentValidation`, và cũng không được thay thế bởi nó.

**Lời giải — trước:**

```csharp
public class TaoLeadRequest
{
    public string HoTen { get; set; } = "";
    public string Email { get; set; } = "";
    public string? DienThoai { get; set; }
    public decimal GiaTri { get; set; }
    public int NhanVienId { get; set; }
}
```

```text
Vấn đề: new TaoLeadRequest() biên dịch được, và mọi trường đều rỗng.
Giá trị "" là cách che giấu việc thiếu dữ liệu, không phải cách xử lý nó.
```

**Sau:**

```csharp
public class TaoLeadRequest
{
    public required string HoTen { get; init; }
    public required string Email { get; init; }
    public string? DienThoai { get; init; }
    public required decimal GiaTri { get; init; }
    public required int NhanVienId { get; init; }
}
```

**`required` khác kiểm chứng lúc chạy thế nào:**

| | `required` | FluentValidation |
|---|---|---|
| Khi nào kiểm tra | **Lúc biên dịch** | Lúc chạy |
| Kiểm tra cái gì | Trường có **được gán** không | Giá trị có **hợp lệ** không |
| Bắt được | Code của bạn quên gán | Dữ liệu người dùng gửi sai |
| Thông báo lỗi | Lỗi biên dịch | Phản hồi 400 cho client |

```csharp
// required KHÔNG bắt được cái này — nó đã được gán
new TaoLeadRequest { HoTen = "", Email = "khong-phai-email", GiaTri = -5, ... };

// FluentValidation bắt được
RuleFor(x => x.HoTen).NotEmpty().MaximumLength(200);
RuleFor(x => x.Email).EmailAddress();
RuleFor(x => x.GiaTri).GreaterThan(0);
```

```text
required : "anh quên gán trường này"      -> lỗi của LẬP TRÌNH VIÊN
Validator: "giá trị này không hợp lệ"     -> lỗi của DỮ LIỆU
```

Cần cả hai, và chúng không chồng lên nhau.

**Ba điều cần biết khi dùng `required`:**

**1. Kết hợp với `init` để có bất biến.**

```csharp
public required string HoTen { get; init; }    // gán lúc khởi tạo, cấm đổi sau
public required string HoTen { get; set; }     // bắt buộc gán, nhưng vẫn đổi được sau
```

**2. Constructor có thể "hứa" đã gán đủ.**

```csharp
[SetsRequiredMembers]
public TaoLeadRequest(string hoTen, string email, decimal giaTri, int nhanVienId)
{
    HoTen = hoTen; Email = email; GiaTri = giaTri; NhanVienId = nhanVienId;
}
```

```text
Không có thuộc tính này, dùng constructor vẫn bị báo lỗi thiếu required.
Nhưng dùng nó là một lời hứa — trình biên dịch KHÔNG kiểm tra lại.
Gán thiếu trong constructor đó thì không ai nhắc.
```

**3. Tuần tự hoá JSON vẫn có thể tạo ra đối tượng thiếu trường.**

```csharp
var r = JsonSerializer.Deserialize<TaoLeadRequest>("""{"HoTen":"An"}""");
```

```text
System.Text.Json trên .NET 9 TÔN TRỌNG required và ném lỗi:
    JsonException: JSON deserialization for type 'TaoLeadRequest' was missing
                   required properties including: 'Email', 'GiaTri', 'NhanVienId'.

Nhưng các thư viện khác, hoặc reflection thủ công, có thể bỏ qua.
-> vẫn cần validator ở biên hệ thống.
```

**Bắt đầu từ đâu trong một dự án đang chạy:**

```text
Đừng thêm required cho mọi DTO cùng lúc — 14 lỗi ở một lớp là vừa sức,
200 lỗi ở 30 lớp thì sẽ bị lùi lại và không bao giờ làm.

Thứ tự nên làm:
    1. DTO đầu vào của API — nơi thiếu dữ liệu gây hại nhất
    2. Entity và value object trong domain
    3. DTO đầu ra — ít quan trọng hơn, vì dữ liệu do chính bạn dựng
```

#### Bài 2 — Rút gọn constructor

Chuyển ba lớp service sang primary constructor và đếm số dòng giảm được.

**Tiêu chí hoàn thành:** bạn có số dòng trước và sau, và biết một trường hợp **không nên** chuyển.

Gợi ý và lời giải — Bài 2

**Gợi ý.** Primary constructor tạo ra **tham số**, không phải trường. Khác biệt đó có hệ quả thật.

**Lời giải — trước:**

```csharp
public class LeadService
{
    private readonly CrmDbContext _db;
    private readonly ILogger<LeadService> _log;
    private readonly IEmailSender _email;
    private readonly IDateTimeProvider _thoiGian;

    public LeadService(
        CrmDbContext db,
        ILogger<LeadService> log,
        IEmailSender email,
        IDateTimeProvider thoiGian)
    {
        _db = db;
        _log = log;
        _email = email;
        _thoiGian = thoiGian;
    }

    public async Task<Lead> TaoAsync(TaoLeadRequest yc, CancellationToken ct)
    {
        var lead = new Lead(yc.HoTen, yc.Email, _thoiGian.Now);
        _db.Leads.Add(lead);
        await _db.SaveChangesAsync(ct);
        _log.LogInformation("Đã tạo lead {Id}", lead.Id);
        return lead;
    }
}
```

**Sau:**

```csharp
public class LeadService(
    CrmDbContext db,
    ILogger<LeadService> log,
    IEmailSender email,
    IDateTimeProvider thoiGian)
{
    public async Task<Lead> TaoAsync(TaoLeadRequest yc, CancellationToken ct)
    {
        var lead = new Lead(yc.HoTen, yc.Email, thoiGian.Now);
        db.Leads.Add(lead);
        await db.SaveChangesAsync(ct);
        log.LogInformation("Đã tạo lead {Id}", lead.Id);
        return lead;
    }
}
```

```text
Trước: 18 dòng cho phần khai báo và constructor
Sau  :  5 dòng
Giảm : 13 dòng mỗi lớp
```

```text
Ba lớp service -> giảm khoảng 39 dòng.
Và phần giảm là phần KHÔNG mang thông tin nào — chỉ là lặp lại tên bốn lần.
```

**Vì sao tiết kiệm nhiều như vậy: mỗi phụ thuộc xuất hiện 3 lần ở bản cũ.**

```text
1. Khai báo trường:     private readonly CrmDbContext _db;
2. Tham số constructor: CrmDbContext db,
3. Gán:                 _db = db;

Primary constructor: 1 lần.
```

**Và đây là trường hợp KHÔNG nên chuyển:**

```csharp
public class BaoCaoService
{
    private readonly CrmDbContext _db;
    private readonly IReadOnlyList<string> _cotMacDinh;      // tính từ cấu hình

    public BaoCaoService(CrmDbContext db, IOptions<BaoCaoOptions> tuyChon)
    {
        _db = db ?? throw new ArgumentNullException(nameof(db));

        _cotMacDinh = tuyChon.Value.Cot
            .Where(c => c.HienThi)
            .Select(c => c.Ten)
            .ToArray();                                       // XỬ LÝ trong constructor
    }
}
```

```text
Primary constructor không có CHỖ để viết logic khởi tạo.
Có thể lách bằng khởi tạo trường:
    private readonly IReadOnlyList<string> _cot = tuyChon.Value.Cot.Where(...)...;
nhưng khi logic dài hơn một biểu thức, nó khó đọc hơn hẳn.
```

**Ba điều cần biết về primary constructor:**

**1. Tham số KHÔNG phải trường — nhưng trình biên dịch tạo trường ẩn khi cần.**

```csharp
public class LeadService(CrmDbContext db)
{
    public void A() => db.Leads.Count();      // tạo trường ẩn để giữ db
}
```

```text
Hệ quả: không viết được `_db` theo quy ước đặt tên có gạch dưới
-> nếu đội có quy ước đó, đây là một thay đổi về phong cách cần thống nhất
```

**2. Tham số **thay đổi được** — khác với `readonly`.**

```csharp
public class Dem(int batDau)
{
    public void Tang() => batDau++;           // biên dịch được!
}
```

```text
Trường readonly thì không gán lại được.
Tham số primary constructor thì được -> mất một lớp bảo vệ.

Với phụ thuộc tiêm vào, điều này hiếm khi thành vấn đề thật,
nhưng đáng biết.
```

**3. Với `record`, tham số tự thành thuộc tính công khai. Với `class` thì không.**

```csharp
record DiaChi(string Tinh);      // DiaChi.Tinh là thuộc tính public
class DiaChi2(string tinh);      // tinh KHÔNG lộ ra ngoài
```

#### Bài 3 — Tìm `IDisposable` bị quên

Rà dự án tìm mọi chỗ tạo đối tượng `IDisposable` mà không có `using`.

**Tiêu chí hoàn thành:** bạn có danh sách kèm phân loại, và biết hai trường hợp **cố tình không dùng `using`** là đúng.

Gợi ý và lời giải — Bài 3

**Gợi ý.** Trình phân tích của .NET có sẵn quy tắc cho việc này. Bật nó lên nhanh hơn viết grep.

**Lời giải — bật phân tích tĩnh:**

```xml
<PropertyGroup>
  <EnableNETAnalyzers>true</EnableNETAnalyzers>
  <AnalysisMode>Recommended</AnalysisMode>
  <WarningsAsErrors>$(WarningsAsErrors);CA2000;CA1063;CA2213</WarningsAsErrors>
</PropertyGroup>
```

```bash
dotnet build 2>&1 | grep -E "CA2000|CA2213" | sort | uniq -c
```

```text
      7 warning CA2000: Call System.IDisposable.Dispose on object created by ...
      3 warning CA2213: 'X' contains field 'Y' that is of IDisposable type ...
```

Và lượt quét thủ công cho những gì phân tích tĩnh bỏ sót:

```bash
grep -rnE "new (SqlConnection|FileStream|StreamReader|StreamWriter|HttpClient|MemoryStream|CancellationTokenSource|SemaphoreSlim|Timer)\(" \
  --include="*.cs" src/ | grep -v "using " | grep -v "/Tests/"
```

```text
src/Crm.Api/Features/Import/DocFileHandler.cs:34:  var reader = new StreamReader(duongDan);
src/Crm.Api/Services/BaoCaoService.cs:88:          var stream = new MemoryStream();
src/Crm.Api/Infrastructure/EmailSender.cs:19:      private readonly SmtpClient _smtp = new();
src/Crm.Api/Services/KetNoiService.cs:22:          var cts = new CancellationTokenSource();
src/Crm.Api/Jobs/DongBoJob.cs:15:                  private readonly Timer _timer;
```

**Phân loại:**

| Chỗ | Đánh giá | Xử lý |
|---|---|---|
| `StreamReader` trong handler | **Rò rỉ** | Thêm `using` |
| `MemoryStream` trả về cho caller | Đúng, nhưng thiếu tài liệu | Ghi rõ ai chịu trách nhiệm huỷ |
| `SmtpClient` là trường | Rò rỉ | Lớp chứa phải cài `IDisposable` |
| `CancellationTokenSource` cục bộ | **Rò rỉ** | Thêm `using` |
| `Timer` là trường của `BackgroundService` | Đúng | Huỷ trong `Dispose` của lớp |

```csharp
// Rò rỉ
var reader = new StreamReader(duongDan);
var dong = await reader.ReadToEndAsync(ct);

// Sửa
using var reader = new StreamReader(duongDan);
var dong = await reader.ReadToEndAsync(ct);
```

**Và đây là hai trường hợp CỐ TÌNH không dùng `using` — cả hai đều đúng:**

**1. `HttpClient` lấy từ `IHttpClientFactory`.**

```csharp
// SAI — using làm đóng handler đang được dùng chung
using var client = _factory.CreateClient("billing");

// ĐÚNG — không using
var client = _factory.CreateClient("billing");
```

```text
Factory quản lý vòng đời của handler bên dưới, và tái dùng nó.
Dispose client không đóng handler ngay, nhưng nó tạo ra một mẫu sai
mà người đọc code sau sẽ bắt chước ở chỗ khác — nơi nó thật sự gây hại.

Và HttpClient tự tạo bằng new thì NGƯỢC LẠI: mỗi lần new là một
connection pool mới, dùng using vẫn để lại socket ở trạng thái TIME_WAIT.
-> đó chính là lý do IHttpClientFactory tồn tại.
```

**2. Đối tượng được trả về cho người gọi.**

```csharp
// ĐÚNG — người gọi chịu trách nhiệm huỷ
public Stream TaoBaoCaoAsync(int id)
{
    var stream = new MemoryStream();
    GhiVaoStream(stream, id);
    stream.Position = 0;
    return stream;                     // KHÔNG using ở đây
}

// Người gọi:
await using var bc = TaoBaoCaoAsync(id);
```

```text
Phân tích tĩnh có thể cảnh báo CA2000 ở đây — và đó là báo động giả.
Cách xử lý: tắt cảnh báo tại chỗ, kèm lý do.
```

```csharp
#pragma warning disable CA2000 // người gọi chịu trách nhiệm huỷ stream trả về
var stream = new MemoryStream();
#pragma warning restore CA2000
```

**Ba lỗi phổ biến nhất về `IDisposable` trong ASP.NET Core:**

**1. Lớp giữ trường `IDisposable` nhưng không tự cài `IDisposable`.**

```csharp
public sealed class EmailSender : IDisposable
{
    private readonly SmtpClient _smtp = new();
    public void Dispose() => _smtp.Dispose();
}
```

**2. Huỷ thứ do DI quản lý.**

```csharp
// SAI — DbContext do DI tạo và huỷ theo scope
public async Task XuLy(CrmDbContext db)
{
    using var _ = db;                  // huỷ sớm -> request hỏng
}
```

```text
Quy tắc: thứ bạn NHẬN qua tiêm phụ thuộc thì KHÔNG huỷ.
         thứ bạn TỰ tạo bằng new thì phải huỷ.
```

**3. Quên `await using` với `IAsyncDisposable`.**

```csharp
// Dùng using thường với một kiểu có cả hai giao diện
using var conn = new SqlConnection(cs);        // gọi Dispose đồng bộ

// Đúng hơn
await using var conn = new SqlConnection(cs);  // gọi DisposeAsync
```

```text
Dispose đồng bộ trên tài nguyên mạng có thể CHẶN luồng
-> với ứng dụng nhiều request, đây là một nguồn thread pool starvation
```

**Cách chắc chắn nhất để việc này không quay lại:**

```xml
<WarningsAsErrors>$(WarningsAsErrors);CA2000;CA2213;CA1816</WarningsAsErrors>
```

## Tự kiểm tra

### required giải quyết vấn đề gì?

Nó buộc người tạo đối tượng phải gán thuộc tính bắt buộc, và lỗi được bắt ở tầng biên dịch thay vì chờ tới lúc chạy. Nó cũng làm rõ ý định: đọc lớp là biết ngay trường nào bắt buộc.

### Tham số primary constructor có phải readonly không?

Không tự động. Khác với trường được gán trong constructor thường, nó có thể bị gán lại trong lớp. Nếu cần chắc chắn không đổi thì vẫn gán vào một trường readonly.

### Vì sao quên using với IDisposable lại nguy hiểm?

Vì không có lỗi nào được báo. Chương trình chạy bình thường, chỉ là tài nguyên không được trả lại. Trong ứng dụng web, sau vài giờ mọi request bắt đầu timeout vì connection pool cạn, và rất khó lần ra nguyên nhân từ triệu chứng đó.

### Khi nào không cần cài IDisposable?

Khi lớp chỉ chứa dữ liệu và object thường, vì garbage collector lo được. Cài nó cho lớp không giữ tài nguyên là thêm việc vô ích cho mọi người dùng lớp đó.

### Vì sao nên dùng nameof thay vì chuỗi viết tay?

Vì khi ai đó đổi tên thành viên bằng refactor của IDE, nameof tự đổi theo, còn chuỗi viết tay thì lặng lẽ sai và không có gì cảnh báo.

### Static abstract interface member giải quyết vấn đề gì?

Trước .NET 7 không có cách ràng buộc rằng một kiểu phải có phương thức tĩnh nhất định. Tính năng này cho phép gọi phương thức tĩnh qua generic, và là nền tảng cho generic math trong .NET.

## Kết luận

Ba điều đáng nhớ nhất:

1. **`required` và primary constructor rẻ và lợi ích rõ ngay** — dùng từ hôm nay.
2. **Quên `using` là rò rỉ tài nguyên không có thông báo lỗi nào.**
3. **`nameof` ở mọi nơi cần tên thành viên** — chuỗi viết tay sẽ lặng lẽ sai khi refactor.
